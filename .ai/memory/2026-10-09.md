### 真根因：libfmq read/write 返回 bool，被当 size_t 用（坑了两天）
- 本项目 vendored libfmq（include/fmq/MessageQueueBase.h:153/208）：
  `bool read(T* data, size_t count)` / `bool write(const T* data, size_t count)`。
- AidlEffectBase.cpp 旧代码 `const size_t n = mInputMQ->read(buf, chunk)` ——
  **成功(true) 隐式转成 1** → engine 处理 `n/ch = 1/2 = 0 帧` →
  Status 上报 `{fmqConsumed:1, fmqProduced:1}` → framework 校验
  `consumed(1) != floatsToWrite(3840)` → "read status failed" 风暴 + 1-float 假象。
- 之前"output MQ 容量恰好 1 buffer 导致 trickle"的根因诊断是**错的**（已更正）。
- 修复：drain loop 按 bool 语义重写（`if (!read(...)) break;`），
  chunk 向下取整到 safeCh 的整数倍（整帧处理）。
- 教训：**接入任何第三方 API 前先确认返回值语义**；`size_t n = f(...)` 吞 bool 是
  合法编译但语义全错的静默 bug，编译器只给 narrowing 警告（甚至没有）。

## 真机首验 bug：CoCreateInstance 漏参（16:20）
- 用户双击 exe 真机验证：DLL 正常找到加载，崩在 `WASAPI CoCreateInstance failed hr=0x80070057`。
- **根因**：CoCreateInstance 是 5 参数自由函数（rclsid, **pUnkOuter**, dwClsContext, riid, ppv），
  绑定误写成 4 参数 → x64 下 23(CLSCTX_ALL) 落到 pUnkOuter 位（野指针）→ E_INVALIDARG。
  修复：补 `Pointer<Void>` pUnkOuter 参数，调用传 nullptr。全表复查其余 COM 调用参数个数无误。
- 同步改 fatal 页文案（原来固定说"未找到 DLL"，初始化失败时误导）→ "引擎初始化失败"+通用指引。
- 教训：自由函数（非 COM 方法）签名没有 `this` 做锚点，漏参不报编译错——FFI 绑定时每个签名
  先查 MSDN 数清参数个数。

## 真机第二次反馈：点测试音卡住+闪退（16:24）
- **根因**：pump 渲染循环 `min(avail, 4096)` 超过 auradsp_create 的 max_block_frames=2048
  契约 → 引擎内部缓冲越界写 → 堆损坏 → 闪退；且 pump 的 catch 每 5ms 发一条 error 事件
  灌爆 UI 事件队列（卡住感）。
- 修复：块上限改 2048 与 create 契约对齐（const maxBlock 与缓冲同步）；catch 加 3s 同消息节流。
- 教训：**max_block_frames 是 process() 的硬上限**，音频循环的帧数 cap 必须与 create 参数
  同源；isolate 渲染循环的 catch 必须节流，否则异常会变成事件洪泛。

## 真机第三次反馈：日志定位到 renderClient this 指针 bug（16:39）
- 加了跨 isolate 文件日志（lib/engine/debug_log.dart → %TEMP%\auradsp_debug.log，
  main.dart 三级全局异常捕获同写一份）后一次复现即定位。
- **根因**：WasapiOut 里 getBuffer/releaseBuffer 是 IAudioRenderClient 的 vtable 方法，

  `first process done` 是最后一条（process 成功），崩溃点即其后首轮 getBuffer。

- 附带修：EXTENSIBLE SubFormat GUID 字节序（Data1/2/3 小端，原按字符串顺序比较导致
  float 格式误判 isFloat=false）；新增 writeToDevice() 设备格式适配（float32/int32/int16

- 教训：**COM 手写 vtable 绑定时，this 指针必须与接口严格对应**；同一 COM 对象族的

## 真机第四次反馈：可视化静止 / 参数不实时（16:45–17:00）
用户原话：「可视化根本不动弹，就只是第一帧然后静止，所有的音效从点击到生效都很慢，
托滑块似乎不是实时的」。三个问题分别定性修复：

### ① 可视化第一帧后静止 —— 引擎 `emit_viz` 硬门槛（确凿 bug）
- 旧代码：`if (frames < kVizFftSize) return;`（1024）。pump 首轮 `avail=1056 ≥ 1024`
  产出**唯一一帧**；此后每 5ms 轮询 `avail≈240`，**永久早退** → 表现为"第一帧然后静止"。
- 修复：create 时预分配 `viz_hist`（kVizFftSize×2 环形历史窗），emit_viz 改为把本块追加
  进环、再对"最近 1024 帧"做 FFT（RT 内无分配）。**任何块长都能持续出帧**。
- 同时把频谱归一化改成标准 dBFS：`amp = m*4/N`（汉宁相干增益 0.5 × 单边 2），
  `v = (20log10(amp)+60)/60` 裁到 [0,1]，取代旧的 `0.4*log10(1+9v)` 饱和式映射。
- UI 侧：viz 拉取一次读 8 帧只取最新（引擎 ~10ms 一帧、UI 33ms 拉一次，避免积压滞后）。

### ② 任意参数变更都全量重建 5 条效果链（架构 bug，但不是"慢"的主因）
- 旧 `apply_params_locked` 在**每个** set_param 里都重放 Bass/Reverb/Stereo/EQ/PostGain
  全链，其中 `Reverb_SetParam = sf_presetreverb()` 会重建混响状态。
- 改为 `apply_bass/apply_reverb/apply_stereo/apply_eq/apply_post` 精准应用，只碰被改那条链；
  全量重放只在 create 做一次。reverb 分支同时修了"关闭混响后 latency_ms 不回落"。
- **实测**：ctypes 烟囱测试显示 set_param 全部 ≤0.04ms（含品质档开混响后改其它参数 0.00ms）。
  → 结论：引擎侧本来就不慢，**"生效慢"的观感主要来自①可视化冻结（唯一实时反馈源死掉）**
  与③滑块只在松手时提交。诚实记录，不把架构修正包装成性能修复。

### ③ 滑块不实时
