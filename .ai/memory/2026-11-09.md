## feature/linux 与远端同步（受限网络下）

- **先纠一个误判**：用户判断「本地和远端都改了很多」，实测不成立。
  本地 27 个提交与远端**短 SHA 完全相同**、tree 逐一相等，远端在其上
  多 31 个 → 本地 behind 31 / ahead 0。误判源头是 remote-tracking ref
  停在 `331ee22` 未更新，`git status` 因此不显示 ahead/behind。
  判定手段：`gh api` 取远端提交的 tree SHA，与本地逐一比对——
  tree 相同即内容相同，比比对 commit 说明可靠得多。
- **网络实况**：`github.com:443` 超时（12s 无响应），`git fetch` /
  `git ls-remote` 均 21000ms 后 `Could not connect`；`api.github.com` 200。
  故一切同步走 `gh api`。
- **新增 `tools/bin/fetch_via_api.py`**（与 `push_via_api.py` 对偶）：
  Git Data API 逐字重建对象。三条硬约束——重建后**断言**对象哈希等于
  远端 SHA，对不上立即中止；tree 逐层比对本地已有则整枝跳过；时区未知
  时按候选表试算并校验 SHA。本次实测 31 提交只拉 109 blob / 186 tree
  （跳过已存在 655），296 次 API 调用，31/31 SHA 一致。
- **快进合并** `331ee22..a23c007`：78 文件 +3513/−524，无冲突。
  上轮安装器改造全部留存（`planUpdate`@app.dart:109、
  `classifyUninstallPath`@install_engine.dart:508、29 个向导测试）。
- **补掉 `push_via_api.py` 的既存缺陷**：自愈步硬调 `git fetch`，
  而该脚本存在的理由正是 fetch 不通 → ref 已更新却以异常退出，
  仓库停在「已推送但本地未对齐」。改为原生 fetch 失败即回落 API 拉取。
- **GitHub commit API 会归一化消息尾随换行**，于是经 API 推送的提交在
  远端比本地少一字节、SHA 必然不同（`e5dface` vs `f34e133`，tree 同为
  `c27c69b`，零内容损失）。`fetch_via_api.py` 因此增加「无尾换行」候选，
  但仍以哈希命中为准。**运维口径**：经 API 推送后必须 fetch + reset 对齐，
  否则 SHA 长期分叉，下次推送要人工收拾。
- 合并后门禁：ABI 仍 56 符号（mc-liveprog 是参数面扩展，未动 ABI）、
  补丁编号 185 处全过。
- **遗留**：Windows 发行包与 Linux 四件套均为 `331ee22` 时代产物，
  引擎已新增 `dsp_mc_liveprog`、参数面新增 `liveprogmc.*`，需重跑构建。
