## feature/linux 与远端同步（受限网络下）

- **先纠一个误判**：用户判断「本地和远端都改了很多」，实测不成立。
  本地 27 个提交与远端**短 SHA 完全相同**、tree 逐一相等，远端在其上
  多 31 个 → 本地 behind 31 / ahead 0。误判源头是 remote-tracking ref
  停在 `331ee22` 未更新，`git status` 因此不显示 ahead/behind。
  判定手段：`gh api` 取远端提交的 tree SHA，与本地逐一比对——
  tree 相同即内容相同，比比对 commit 说明可靠得多。
- **网络实况**：`github.com:443` 超时（12s 无响应），`git fetch` /
  `git ls-remote` 均 21000ms 后 `Could not connect`；`api.github.com` 200。
  故一切同步走 `gh api`。
- **新增 `tools/bin/fetch_via_api.py`**（与 `push_via_api.py` 对偶）：
  Git Data API 逐字重建对象。三条硬约束——重建后**断言**对象哈希等于
  远端 SHA，对不上立即中止；tree 逐层比对本地已有则整枝跳过；时区未知
  时按候选表试算并校验 SHA。本次实测 31 提交只拉 109 blob / 186 tree
  （跳过已存在 655），296 次 API 调用，31/31 SHA 一致。
- **快进合并** `331ee22..a23c007`：78 文件 +3513/−524，无冲突。
  上轮安装器改造全部留存（`planUpdate`@app.dart:109、
  `classifyUninstallPath`@install_engine.dart:508、29 个向导测试）。
- **补掉 `push_via_api.py` 的既存缺陷**：自愈步硬调 `git fetch`，
  而该脚本存在的理由正是 fetch 不通 → ref 已更新却以异常退出，
  仓库停在「已推送但本地未对齐」。改为原生 fetch 失败即回落 API 拉取。
- **GitHub commit API 会归一化消息尾随换行**，于是经 API 推送的提交在
  远端比本地少一字节、SHA 必然不同（`e5dface` vs `f34e133`，tree 同为
  `c27c69b`，零内容损失）。`fetch_via_api.py` 因此增加「无尾换行」候选，
  但仍以哈希命中为准。**运维口径**：经 API 推送后必须 fetch + reset 对齐，
  否则 SHA 长期分叉，下次推送要人工收拾。
- 合并后门禁：ABI 仍 56 符号（mc-liveprog 是参数面扩展，未动 ABI）、
  补丁编号 185 处全过。
- **遗留**：Windows 发行包与 Linux 四件套均为 `331ee22` 时代产物，
  引擎已新增 `dsp_mc_liveprog`、参数面新增 `liveprogmc.*`，需重跑构建。

## 发包：全量测试 + 重建发行包（2026-11-09 上午）

### 一、构建链路的四个坑（都在 Windows 侧，非产品缺陷）

1. **环境变量大小写重复键**。宿主（沙箱/CI 包装器）会让原生环境块里
   `PATH`/`path`/`Path` 并存、每个变量还各存两份（实测 404 项 vs 干净 224 项）。
   .NET Framework 的 `ProcessStartInfo.EnvironmentVariables` 是大小写敏感的
   Hashtable，第二个 "path" 撞键抛 `ArgumentException('path')`，
   发生在 MSBuild 的 `ToolTask.GetProcessStartInfo` 里 → **CL.exe 根本没被
   拉起**，编译目标既不产出也不让上层脚本失败。新增
   `tools/bin/win_env_sanitize.py`：读原生块（ctypes GetEnvironmentStringsW）
   按大小写合并（PATH 取并集、其余留首次值），再用干净环境启动子进程；
   顺带支持 PATHEXT 解析与 `.bat` 垫片转发（`flutter` 是 .bat，
   subprocess 直接 spawn 会 FileNotFoundError）。
2. **MSBuild 节点复用**。脏环境下启动的 worker 节点存活约 15 分钟，
   之后即使环境已修好也会复用这些节点 → cmake **立即 exit=1 且无任何输出**，
   表现为"构建无报错地中断、日志为空"。归一化器顺带设
   `MSBUILDDISABLENODEREUSE=1`。
3. **构建脚本只查文件存在就报"就绪"**。这是最坏的一层：cmake exit=1 被
   忽略，旧产物（两天前的 DLL）被当成本次产物发出去。
   `build_windows.ps1` 改为 `Invoke-Clean` 统一检查退出码，非零即中止；
   另在每条外部命令前清理**本仓库构建树相关**的残留 MSBuild/cmake 进程
   （按命令行含仓库路径判定，不误伤 VS）。
4. **并行度与超时**。VS 生成器默认 /m:32（32 核），C++ 大 TU 同时编译
   内存峰值可超 8GB → 进程被直接杀掉。限到 8 并发（用 `-m:8` 而非
   `/m:8`：后者从 Git-Bash 调用会被 MSYS 路径转换吃掉斜杠，MSBuild 报 MSB1008）。
   另注意工具后台任务超时上限是 600000ms，传更大值会被静默截断。

### 二、门禁缺失的前置产物（13 项 FAIL 的真因）

`test/runner.py --smoke` 有 13 个用例依赖一批**独立的小型测试程序**
（test_plugin_chain / test_host_quarantine / test_dll_dirs / rt_drain_test /
vaio_pump_wait_test / vm_detect / vm_pump_test / vm_parallel_test /
apo_inspect / silence_gate_test / AuraApo）。这些目标不在发行目标集里，
标准构建不产出 → **干净构建后跑门禁必然 FAIL 13 项**，与代码质量无关。
已把 11 个测试目标并入 `build_windows.ps1` 的 [3b/6] 步并校验产物存在。

### 三、三处 smoke 语义漂移（非回归，已用同步前引擎 A/B 排除）

用**同步前的发行引擎**（c7b5e813）复跑，失败项完全一致 → 排除回归。
真因都是「产品语义变了、用例没跟上」：
- `g_pluginGroupMask` 出厂默认是 `0x03`（255e61f「默认只开 A1/A2」），
  用例仍断言 `0xFF`。
- `vb_set_param_str` 返回**在用路数**（源码注释明说"nEng 是版型槽数，
  拿它比较会让镜像永远记不进去"），用例却拿槽位数（handles=8）比较。
- 插件组补挂只对**有引擎实例的组**生效（`BackfillGroupsForMask` 要求
  `PluginEngineAt(g)`）；本机只开通 2 条路由（routeState=[2,2,0,…]），
  用例却要求 8 个组全部就绪。已改为按在线路由组断言。
- `smoke_vm_protect` 需要**真实音频流动**：保护观测值由 RT 回调消费，
  桥整体空闲（hotGrp=-1）时注入永远不被读取 → 守卫无从触发。
  已加前置判定记 SKIP 而非 FAIL。

### 四、UI 自动化：前台锁 + 卡片改版

- **首次点击被 IDE 吃掉**。后台进程调 `SetForegroundWindow` 会被「前台锁」
  拒绝（函数返回 FALSE 而不报错），于是应用的第一次点击落到 IDE 上——
  UI 用例表现为"点空也不报错、断言拿到 0 像素差异"，最难查的一类假失败。
  `ui_test_kit.ensure_foreground` 改用 AttachThreadInput 借前台线程输入队列
  完成置前，并用 GetForegroundWindow 复核。**修完这一条，两个原本失败的
  UI 用例直接转绿**——它们的失败根因根本不是坐标。
- 卡片改版后锚点漂移（实测 1400x900）：动态压限器开关仍在 (1279,350)✓，
  但「高级」折叠头挪到卡片底部 → 需向下滚 3 格进视口，此时稳定在 (460,538)；
  主滑块「响应时常数」在 y 780..791（旧值 415..465 落在空白区）；
  高级区**不再有「输出增益门」滑块**，改为「分频中心频率」(y≈805)。
  另：卡片内曲线图与延迟读数是**实时动画**，全窗像素差分恒为几千像素
  （会掩盖抽屉没开），必须只比静态带。
