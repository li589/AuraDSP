  - **根因**：原 `listDirAsync` 使用 `d.list(...)` 真实 Stream 异步流，与 `CircularProgressIndicator` 持续请求帧动画冲突，导致微任务队列永不清空；
  - **修法**：改用 `Future(() { return d.listSync(); })` 在单次微任务队列中完成异步非阻塞扫描，并仅在自定义目录非空时启动目录异步检测，测试平稳 settle。

## 阶段6 VB 桥「加载期音频卡顿」根治（Z17 fan-in 预算感知）+ 静态门禁修复
- **根因链闭合**：用户实测「加载插件的一段时间内音频卡、之后不卡」。本机 VM 缓冲 2048 帧
  （预算 42.7ms），单组 Ozone process ≈ 27ms（8ch 并行下回调 ≈ max(单组)），回调远未超预算，
  但旧 Z17 fan-in 固定 2ms 截止会在加载/CPU 争用令组间耗时不均时把稍慢的 worker 组**误冻成
  straggler**——该组输出停在上块（陈旧/跳变 = 可听卡顿）。证据：探针 maxCbUs ≈ maxGrp0 + 2ms
  （恰为撞截止）、smoke 补挂期间 fanTimeouts>0。
- **修法（VmPumpCore.h）**：fan-in 截止改为预算感知——从回调起点钳总时长 ≤ budget − margin
  （margin = max(200µs, 7.5%预算)）。128 帧小缓冲 ≈ 旧 2ms 行为（且总时长真正进预算）；2048 大缓冲
  给足 ~12.5ms 余量，慢组得以完成而不再被误冻；总时长仍恒有上界 = 预算。qpf 不可用时回落旧
  自旋兜底。新增 PumpCtx.fanTimeouts（超时累计）诊断；vb_status 暴露 stuckG/fanTimeouts。
- **验证（2048 真实桥 + tone + Ozone ×8 组补挂）**：fanTimeouts=0、stuckG=0（此前每次加载必冻），
  maxCbUs≈maxGrp0≈31.8ms < 预算；`vm_parallel_test`（128 帧语义逐位 + straggler <100ms 有界）
  与 `smoke_vm_plugin_load_fast.py`（含测试音、loadSuspend、processCalls 断言）全绿。
- **加载期旁路（前一会话实现，本轮收尾）**：`g_loadSuspending`/`ApplyPluginGroupMask` eff=0；
  预算 <8ms 才启用（本机 2048 常态不启用——旁路会白丢几秒插件音色，不值得）。恢复走掩码重放，
  不覆盖用户掩码/Z12 保护态。
- **「拧旋钮/切模块不流畅」改善（module_pump.h）**：共享泵线程即 JUCE MessageManager 所在线程
  （全部编辑器消息/绘制/定时器），原 NORMAL 优先级在系统繁忙时被同层线程抢调度；抬到
  THREAD_PRIORITY_ABOVE_NORMAL(1)，远低于音频 RT 线程（15），音频保护不受影响。
- **预存静态门禁修复（与本会话无关的历史欠款）**：

  - D6：`cards_common.dart` 裸 `[PATCHED-AuraDSP]` 标记 → 登记 P-040（PATCHES.md，含动机/内容）。
