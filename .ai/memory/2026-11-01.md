## 实测结论（gcc 13.3 / CMake 3.28 / Ninja，Ubuntu 24.04 VM）

- legacy C 85 文件 + C++ 核心 19 TU 全量编译通过；产出
  `core/desktop/linux/out/Release/libauradsp_engine.so`。
- `nm -D --defined-only` 动态导出集 **恰为 .def 的 56 符号**（diff 全等）。
- ctypes 冒烟：`auradsp_version`=1.1.0、`auradsp_abi`=2、create(48k,512) →
  process 静音块 rc=0 → destroy 全通过。
- `test/runner.py --smoke`（Linux）：PASS 3（PLATFORM_ANY 三门禁，含新增
  Linux 源表门禁）/ SKIP 125（Windows 专属，未动其口径——默认拒绝式翻转
  仍属 S1）/ FAIL 0。

## 本期踩坑（后续智能体避雷）

1. **core 必须是 OBJECT 不能 STATIC**：MSVC 靠 `.def` 导出清单强制抽取
   静态库成员，ELF version script 无此作用——STATIC 时 `.so` 只有 20K、
   导出 0 个。与 Windows 侧 `auradsp_wincompat` 用 OBJECT 的理由相同。
2. **core 必须 `POSITION_INDEPENDENT_CODE ON`**：缺 `-fPIC` 时
   `engine_viz.cpp` 的 thread_local 静态量以非 PIC 重定位链入共享库被 ld 拒绝。
3. **不要叠加 `-fvisibility=hidden`**（修正方案 §3.2 表格口径）：本仓 ABI 头
   没有 visibility 宏，hidden 会把 56 个 ABI 符号一并隐藏、导出归零。
   导出集收口只靠 version script 的 `local: *`，效果等价且实测全等。
4. 无 shim 时 3 个 TU 在 GCC 下失败，两类根因：`auradsp_engine.cpp` 在
   `extern "C"` 块内 include 含模板的头（GCC 报 template with C linkage）；
   legacy `ns-eel.h` 的 `min`/`max` 宏撞 libstdc++ 头。均由 shim 预包含
   标准头化解，**未改 legacy 与核心源码一字**。
5. `-O0` 下 legacy 的 C99 `inline` 会产生未定义符号（如 `task_start*`）；
   Linux 目标单配置生成器缺省强制 Release，与成品口径一致。
