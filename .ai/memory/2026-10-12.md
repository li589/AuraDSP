
# 2026-10-12 工作日志

## CLAP 编辑器线程死锁 → 卸载永久挂死（已修复）

延续 2026-10-11 的插件宿主收尾。目标：`test_plugin_direct.exe` 退出码归 0。

### 第一轮定位得到的**假根因**

现象是"日志停在 `closeEditorSlot`"，据此判断"closeEditor 卡住"。
**错。** `std::cout` 重定向到文件时是全缓冲，进程被 `timeout` 杀掉后缓冲区整段丢失，
日志恰好停在最后一个 flush 点，把**更后面**的挂死伪装成"上一步之后就没输出"。

> **教训（可复用）**：诊断挂死类问题时，先确认日志通道本身是实时的。
> 给测试加 `std::cout << std::unitbuf` + 阶段耗时打点后，真实卡点立刻现形。
> 这一步不做，后面所有推理都建立在假地基上。

### 真根因

```
[DBG CLAP closeEditor] WaitForSingleObject -> 258 (TIMEOUT)   ← 800ms 内线程没退出
[DBG CLAP closeEditor] WM_QUIT -> tid 15420
[DBG CLAP closeEditor] DETACHED (thread still alive!)         ← detach，线程仍在跑
[DBG CLAP unload] step 3: plugin->destroy                     ← ★ 永久挂死
```

编辑器线程的消息泵退出路径上调用了插件 `gui->hide()` / `gui->destroy()`。
这两个同样受 JUCE `MessageManagerLock` 约束，**必须在 CLAP 认可的 main thread 上执行**；
在编辑器线程里调用 → 永久阻塞 → 宿主 800ms 超时后 detach →
随后 `plugin->destroy()` 等待该 GUI 资源释放 → 整条卸载链挂死。

**这与前一天 `set_parent` 死锁是同一根因的第二次发作**：凡是插件的 GUI 调用，
位置比顺序更重要——必须落在 CLAP 认可的 main thread 上。

### 修复四件套（`core/desktop/engine_api/auradsp_plugin_host.cpp`）

1. **GUI 调用归位**：`gui->hide` / `gui->destroy` 移出编辑器线程，改由调用线程在 `closeEditor()` 执行。
   编辑器线程职责收敛为「建窗口 → 泵消息 → 销毁自己的窗口」，全程不碰插件对象。
2. **退出握手**：`WM_CLOSE`（走窗口过程）+ `PostThreadMessage(WM_QUIT)`（兜底线程队列）双信号，
   等待 800ms → 3000ms。线程此时只做纯 Win32 清理，必然及时退出。
3. **只关一次**：`closeEditor` 会被调用两次（`unloadPluginSlotLocked` 一次 + `unload()` 内部一次），
   新增 `m_guiCreated` 原子标志守卫 `hide`/`destroy` 对一次 `create` 只执行一次。
4. **超时不泄漏**：新增 `m_editorAbort` 标志，编辑器线程在拿到 HWND 后立即检查并退出，
   不再进入永远等不到 `WM_CLOSE` 的消息泵；跨线程 `std::promise` 由「栈上对象引用捕获」
   改为 `std::shared_ptr`——超时返回后线程仍可能 `set_value`，引用栈帧即 UAF。

VST3 侧同构的「栈引用 promise + 超时泄漏线程」一并消除；
**VST3 的 `IPlugView` 调用位置未改**（实测无死锁证据，不做无依据的重构）。
