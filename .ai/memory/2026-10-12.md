
# 2026-10-12 工作日志

## CLAP 编辑器线程死锁 → 卸载永久挂死（已修复）

延续 2026-10-11 的插件宿主收尾。目标：`test_plugin_direct.exe` 退出码归 0。

### 第一轮定位得到的**假根因**

现象是"日志停在 `closeEditorSlot`"，据此判断"closeEditor 卡住"。
**错。** `std::cout` 重定向到文件时是全缓冲，进程被 `timeout` 杀掉后缓冲区整段丢失，
日志恰好停在最后一个 flush 点，把**更后面**的挂死伪装成"上一步之后就没输出"。

> **教训（可复用）**：诊断挂死类问题时，先确认日志通道本身是实时的。
> 给测试加 `std::cout << std::unitbuf` + 阶段耗时打点后，真实卡点立刻现形。
> 这一步不做，后面所有推理都建立在假地基上。

### 真根因

```
[DBG CLAP closeEditor] WaitForSingleObject -> 258 (TIMEOUT)   ← 800ms 内线程没退出
[DBG CLAP closeEditor] WM_QUIT -> tid 15420
[DBG CLAP closeEditor] DETACHED (thread still alive!)         ← detach，线程仍在跑
[DBG CLAP unload] step 3: plugin->destroy                     ← ★ 永久挂死
```

编辑器线程的消息泵退出路径上调用了插件 `gui->hide()` / `gui->destroy()`。
这两个同样受 JUCE `MessageManagerLock` 约束，**必须在 CLAP 认可的 main thread 上执行**；
在编辑器线程里调用 → 永久阻塞 → 宿主 800ms 超时后 detach →
随后 `plugin->destroy()` 等待该 GUI 资源释放 → 整条卸载链挂死。

**这与前一天 `set_parent` 死锁是同一根因的第二次发作**：凡是插件的 GUI 调用，
位置比顺序更重要——必须落在 CLAP 认可的 main thread 上。

### 修复四件套（`core/desktop/engine_api/auradsp_plugin_host.cpp`）

1. **GUI 调用归位**：`gui->hide` / `gui->destroy` 移出编辑器线程，改由调用线程在 `closeEditor()` 执行。
   编辑器线程职责收敛为「建窗口 → 泵消息 → 销毁自己的窗口」，全程不碰插件对象。
2. **退出握手**：`WM_CLOSE`（走窗口过程）+ `PostThreadMessage(WM_QUIT)`（兜底线程队列）双信号，
   等待 800ms → 3000ms。线程此时只做纯 Win32 清理，必然及时退出。
3. **只关一次**：`closeEditor` 会被调用两次（`unloadPluginSlotLocked` 一次 + `unload()` 内部一次），
   新增 `m_guiCreated` 原子标志守卫 `hide`/`destroy` 对一次 `create` 只执行一次。
4. **超时不泄漏**：新增 `m_editorAbort` 标志，编辑器线程在拿到 HWND 后立即检查并退出，
   不再进入永远等不到 `WM_CLOSE` 的消息泵；跨线程 `std::promise` 由「栈上对象引用捕获」
   改为 `std::shared_ptr`——超时返回后线程仍可能 `set_value`，引用栈帧即 UAF。

VST3 侧同构的「栈引用 promise + 超时泄漏线程」一并消除；
**VST3 的 `IPlugView` 调用位置未改**（实测无死锁证据，不做无依据的重构）。

### 验证结果

| 指标 | 修复前 | 修复后 |
|---|---|---|
| CLAP `closeEditor` | 300ms → 超时 detach | **8ms → 正常 join** |
| CLAP `unloadPluginSlot` | 永久挂死 | **38ms 完成** |
| `test_plugin_direct.exe` 退出码 | 1 | **0**（连跑 2 次） |

三插件全生命周期（load → editor → close → unload）走通：
- `KV-Element-FX.clap` 103/250/8/38 ms
- `FabFilter Pro-Q 3.vst3` 29/212/18/1 ms
- `Ozone 12 Equalizer.vst3` 102/459/39/1034 ms（GUI 因缺 `ni-platform.dll` 内部降级）

门禁：`flutter analyze` 0 issue；`runner.py --smoke` **15/15 PASS**；
`flutter build windows --release --no-tree-shake-icons` 成功（23.6s）；
Release 版启动正常并自动恢复插件会话（VST3 load+activate）。

### 一处曾误判、需要留下辨伪方法的地方

## 插件模块全链路复审（用户实测反馈 6 项 + 复审 4 项）

产出方案：`docs/插件模块深度改良方案-2026-10-12.md`。**诊断全部基于实测，非推测。**

### 已复现的硬证据

- **元数据两套实现，结论矛盾**（本轮最重要的发现）。引擎 DLL 直调对比：
  | 插件 | 来源 | name | vendor | category | version |
  |---|---|---|---|---|---|
  | FabFilter Pro-Q 3 | 扫描 | `FabFilter Pro-Q 3` | `FabFilter` | `AudioEffect` | `1.0` |
  | | 加载后 | `Pro-Q 3` | **``（空）** | `Fx\|EQ` | `3.2.6.0` |
  | KV-Element-FX | 扫描 | `KV-Element-FX` | `Kushview` | `AudioEffect` | `1.0.0` |
  | | 加载后 | `Element FX` | `Kushview` | `Fx` | `1.0.0` |
  → 用户的"厂商读不出来 / 名字对不上（Element FX）"全部由此而来。**扫描路 vendor 是 76/76 全有**，
  所以问题不在引擎扫描，而在加载路回填缺失 + UI 取了 `active.name`（加载后元数据）。
- **32 位插件静默丢弃**：`resolveBundleBinary`（`auradsp_plugin_host.cpp:2351`）只探测 `Contents/x86_64-win`，
  不存在即 `return ""`，`Contents/x86-win` 从未被检查；`is64Bit` 在 `:2401` 硬编码 `true`。
  **不是"标记不兼容"，是根本扫不出来**——用户无法自行诊断。
- **VST3 在非主线程打开编辑器会卡死**：worker 线程调 `showEditor` → `view->attached` 阻塞 →
  3s 超时 → detach → 返回 0，单次耗时 6s。
- **`show_editor` 的 FFI 比 C ABI 多一个死参数**（`auradsp_ffi.dart:341` vs `auradsp_engine.cpp:2292`），
  `plugin_manager` 精心算出的 `title` 整条通路空转。
- **UI 显示"自报名"**：`chain_page.dart:459` 用 `active.name`，与用户选择的列表项不是同一份数据。

### 未能复现（不谎报）

- **CLAP 打开就卡死**：worker 线程对 `KV-Element-FX.clap` 走完 load→showEditor→close→unload **全部成功**
  （0.27s）。同一路径在 VST3 上确实卡死，故"非主线程"**不是** CLAP 卡死的充分条件。需在真实 App + isolate 中带日志复现。
- **卸载崩溃**：`test_plugin_direct` 连跑 2 次 exit 0。但代码里有**机制成立的崩溃路径**：
  `closeEditor` 超时后 `detach()`，线程仍写 `this` 成员，随后 `instance.reset()` → UAF。

### 架构根因（一句话）

`auradsp_engine.h` 声称"UI 不感知引擎所在进程与形态"，但**插件 GUI 有线程亲缘性**，
而 ABI 把 GUI 调用做成**同步接口、由任意线程执行**（实机上是音频 isolate）——
约束被泄漏给了最不该承担的线程。`test_plugin_direct` 用 C++ main 线程所以全绿，
App 用 isolate 线程所以出问题。**"编辑器线程 + 调用线程分工"隐含假设了调用者是 main thread。**

### 方案要点

宿主 GUI 线程（单例、拥有消息泵、`is_main_thread()` 恒 true）+ GUI ABI 异步化（投递即返回，
结果走既有 evt 回执）+ **删除 per-editor 线程与 detach** + 元数据单一真相源 + PE 头架构判定 +
logo 三合一 + 命名规则统一。分 5 批次，B5 专门用于"复现后再宣称修复"。
