
# 2026-10-12 工作日志

## CLAP 编辑器线程死锁 → 卸载永久挂死（已修复）

延续 2026-10-11 的插件宿主收尾。目标：`test_plugin_direct.exe` 退出码归 0。

### 第一轮定位得到的**假根因**

现象是"日志停在 `closeEditorSlot`"，据此判断"closeEditor 卡住"。
**错。** `std::cout` 重定向到文件时是全缓冲，进程被 `timeout` 杀掉后缓冲区整段丢失，
日志恰好停在最后一个 flush 点，把**更后面**的挂死伪装成"上一步之后就没输出"。

> **教训（可复用）**：诊断挂死类问题时，先确认日志通道本身是实时的。
> 给测试加 `std::cout << std::unitbuf` + 阶段耗时打点后，真实卡点立刻现形。
> 这一步不做，后面所有推理都建立在假地基上。

### 真根因

```
[DBG CLAP closeEditor] WaitForSingleObject -> 258 (TIMEOUT)   ← 800ms 内线程没退出
[DBG CLAP closeEditor] WM_QUIT -> tid 15420
[DBG CLAP closeEditor] DETACHED (thread still alive!)         ← detach，线程仍在跑
[DBG CLAP unload] step 3: plugin->destroy                     ← ★ 永久挂死
```

编辑器线程的消息泵退出路径上调用了插件 `gui->hide()` / `gui->destroy()`。
这两个同样受 JUCE `MessageManagerLock` 约束，**必须在 CLAP 认可的 main thread 上执行**；
在编辑器线程里调用 → 永久阻塞 → 宿主 800ms 超时后 detach →
随后 `plugin->destroy()` 等待该 GUI 资源释放 → 整条卸载链挂死。

**这与前一天 `set_parent` 死锁是同一根因的第二次发作**：凡是插件的 GUI 调用，
位置比顺序更重要——必须落在 CLAP 认可的 main thread 上。

### 修复四件套（`core/desktop/engine_api/auradsp_plugin_host.cpp`）

1. **GUI 调用归位**：`gui->hide` / `gui->destroy` 移出编辑器线程，改由调用线程在 `closeEditor()` 执行。
   编辑器线程职责收敛为「建窗口 → 泵消息 → 销毁自己的窗口」，全程不碰插件对象。
2. **退出握手**：`WM_CLOSE`（走窗口过程）+ `PostThreadMessage(WM_QUIT)`（兜底线程队列）双信号，
   等待 800ms → 3000ms。线程此时只做纯 Win32 清理，必然及时退出。
3. **只关一次**：`closeEditor` 会被调用两次（`unloadPluginSlotLocked` 一次 + `unload()` 内部一次），
   新增 `m_guiCreated` 原子标志守卫 `hide`/`destroy` 对一次 `create` 只执行一次。
4. **超时不泄漏**：新增 `m_editorAbort` 标志，编辑器线程在拿到 HWND 后立即检查并退出，
   不再进入永远等不到 `WM_CLOSE` 的消息泵；跨线程 `std::promise` 由「栈上对象引用捕获」
   改为 `std::shared_ptr`——超时返回后线程仍可能 `set_value`，引用栈帧即 UAF。

VST3 侧同构的「栈引用 promise + 超时泄漏线程」一并消除；
**VST3 的 `IPlugView` 调用位置未改**（实测无死锁证据，不做无依据的重构）。

门禁：`flutter analyze` 0 issue；`runner.py --smoke` **15/15 PASS**；
`flutter build windows --release --no-tree-shake-icons` 成功（23.6s）；
Release 版启动正常并自动恢复插件会话（VST3 load+activate）。

## 插件模块全链路复审（用户实测反馈 6 项 + 复审 4 项）

### 已复现的硬证据

- **元数据两套实现，结论矛盾**（本轮最重要的发现）。引擎 DLL 直调对比：
  | 插件 | 来源 | name | vendor | category | version |

  | FabFilter Pro-Q 3 | 扫描 | `FabFilter Pro-Q 3` | `FabFilter` | `AudioEffect` | `1.0` |
  | | 加载后 | `Pro-Q 3` | **``（空）** | `Fx\|EQ` | `3.2.6.0` |
  | KV-Element-FX | 扫描 | `KV-Element-FX` | `Kushview` | `AudioEffect` | `1.0.0` |
  | | 加载后 | `Element FX` | `Kushview` | `Fx` | `1.0.0` |
  → 用户的"厂商读不出来 / 名字对不上（Element FX）"全部由此而来。**扫描路 vendor 是 76/76 全有**，
  所以问题不在引擎扫描，而在加载路回填缺失 + UI 取了 `active.name`（加载后元数据）。
- **32 位插件静默丢弃**：`resolveBundleBinary`（`auradsp_plugin_host.cpp:2351`）只探测 `Contents/x86_64-win`，
  不存在即 `return ""`，`Contents/x86-win` 从未被检查；`is64Bit` 在 `:2401` 硬编码 `true`。
  **不是"标记不兼容"，是根本扫不出来**——用户无法自行诊断。
- **VST3 在非主线程打开编辑器会卡死**：worker 线程调 `showEditor` → `view->attached` 阻塞 →
  3s 超时 → detach → 返回 0，单次耗时 6s。
- **`show_editor` 的 FFI 比 C ABI 多一个死参数**（`auradsp_ffi.dart:341` vs `auradsp_engine.cpp:2292`），
  `plugin_manager` 精心算出的 `title` 整条通路空转。
- **UI 显示"自报名"**：`chain_page.dart:459` 用 `active.name`，与用户选择的列表项不是同一份数据。

### 未能复现（不谎报）

- **CLAP 打开就卡死**：worker 线程对 `KV-Element-FX.clap` 走完 load→showEditor→close→unload **全部成功**
  （0.27s）。同一路径在 VST3 上确实卡死，故"非主线程"**不是** CLAP 卡死的充分条件。需在真实 App + isolate 中带日志复现。
- **卸载崩溃**：`test_plugin_direct` 连跑 2 次 exit 0。但代码里有**机制成立的崩溃路径**：
  `closeEditor` 超时后 `detach()`，线程仍写 `this` 成员，随后 `instance.reset()` → UAF。

### 架构根因（一句话）

`auradsp_engine.h` 声称"UI 不感知引擎所在进程与形态"，但**插件 GUI 有线程亲缘性**，
而 ABI 把 GUI 调用做成**同步接口、由任意线程执行**（实机上是音频 isolate）——
约束被泄漏给了最不该承担的线程。`test_plugin_direct` 用 C++ main 线程所以全绿，
App 用 isolate 线程所以出问题。**"编辑器线程 + 调用线程分工"隐含假设了调用者是 main thread。**

### 方案要点

宿主 GUI 线程（单例、拥有消息泵、`is_main_thread()` 恒 true）+ GUI ABI 异步化（投递即返回，
结果走既有 evt 回执）+ **删除 per-editor 线程与 detach** + 元数据单一真相源 + PE 头架构判定 +
logo 三合一 + 命名规则统一。分 5 批次，B5 专门用于"复现后再宣称修复"。

### E-1 VST3 编辑器 **3/3 全打不开**（不是 Auto-Tune 个例）

| 插件 | showEditor | unload | 退出码 |
|---|---|---|---|
| Auto-Tune EFX+ | 0（6.04s，超时+detach） | **崩溃** | **`0xC0000374` 堆损坏** |
| ConvologyXT_64 | 0（6.16s） | rc=1（0.04s） | 0 |
| KV-Element-FX.vst3 | 0（6.02s） | rc=1（0.03s） | 0 |

`view->attached()` **阻塞、从未返回**。判别依据：日志里**没有** `attached returned non-ok`、**没有**异常行
→ 是阻塞不是失败。

> 坑：`isPlatformTypeSupported(HWND)` 打印 `0` 看着像"不支持"，但
> `core/desktop/vendor-src/plugin-api/steinberg/vst3/base/TUID.h:71` 写着 `kResultTrue = kResultOk`
> → **`0` 是"支持"**。这行日志不是问题点。

### E-2 卸载崩溃已复现（`0xC0000374` STATUS_HEAP_CORRUPTION）

退出码 `3221226356`，日志死在 `unloadLocked[0] unload`（之后无 `reset/complete`、无 `DONE-OK`）。
**三插件同代码路径，只有 1/3 崩溃 → 竞态**，正好解释用户"偶发一次闪退"。

机制：`showEditor` 超时 → `detach()` → 线程**仍在 `view->attached()` 内**、握着 `view` 与插件对象；
宿主随即 `unload` 释放同一批对象 → 线程稍后返回时触碰已释放内存 → 堆损坏。
**`detach` 不是"放弃等待"，是"放弃 join 但保留引用"。**

### E-3 CLAP 白框 = 父子窗口**跨线程**（含自纠错）

**先纠错**：我第一版把 `GetWindowThreadProcessId` 的 **out 参数（进程 ID）** 当成线程 ID，
得出"同线程、白框另有原因"的错误结论并写进了记录。**该结论作废。**

| 窗口 | 创建线程 |
|---|---|
| 宿主父窗口 | **21876**（编辑器线程） |
| 插件 JUCE 子窗口 | **4548**（调用线程）← 跨线程 |

泵只在编辑器线程上跑，只泵**父窗口**消息；插件子窗口属于调用线程（App 中＝音频 isolate，
从不泵 Windows 消息）→ 收不到 `WM_PAINT` → **白框**；拖父窗口时子窗口仍不重绘 → **"很快无响应"**。
窗口本身完全正常（1230×730、`visible=True`）→ 既非尺寸也非可见性问题。

### E-4 CLAP 元数据字段错位（新发现）

实测：`format=CLAP name='Element FX' vendor='Kushview' category='KV-Element-FX'`
—— **`category` 里装的是 descriptor 的 `description`**（自由文本，恰为 bundle 名；实测 description=b'KV-Element-FX'、features=['audio-effect']。早前记为 id，已按实测更正）；`name` 是自报名，真 bundle 名只在 `path` 里。
所以"选 `KV-Element-FX.clap` 却显示 `Element FX`"**在数据层就错了**，不只是 UI 取错字段。
本机 CLAP 插件**只有 2 个**（都是 Kushview）→ CLAP 通路只被一个厂商验证过。

`%APPDATA%\AuraDSP\plugins\plugin_cache.json`：mtime **2026-10-10 17:14**、76 条、
**裸 list 无 schema 戳**、`vendor` **76/76 全为字面量 `"Unknown"`**、`id` 全空、**连 `is64Bit` 键都没有**。

## VDC 资源线巡检（2026-10-12，只读盘查，未改代码）

**格式（实测）**：`resource/ddc/<Brand>/<Model>.vdc` = 纯文本单行。

Dart 侧镜像解析在 `app/.../core/state.dart:1189 parseVdcMetadata`（按行 `SR_` 前缀 + `:` 切分，

## 新增工具：校准曲线 → VDC 转换器（2026-10-12）

用户买了 Behringer ECM8000 测量麦克风，要把三方校准文件转成 VDC 放进 `resource/`。
新建 **`tools/calibration/cal2vdc.py`**（依赖 numpy+scipy；本机 `C:\Program Files\Python\Python312\python.exe`
有 numpy 2.3.5 / scipy 1.18，managed 3.13 **无 scipy**，别用错解释器）。

### VDC 系数符号约定（本次推导并实测确认，务必照此生成）
- 输出每个 5 元组 = `b0,b1,b2,a1_out,a2_out`，其中 **`a1_out = -a1_scipy`、`a2_out = -a2_scipy`**
  （scipy 标准形 `H(z)=(b0+b1 z⁻¹+b2 z⁻²)/(1+a1 z⁻¹+a2 z⁻²)`，a0=1）。
  依据：`vdc.c:76/79` 存 `df.a1 = -val`，而 `SOS_DF2Process` 算 `w = x - a1*v1 - a2*v2`。
- **`SR_44100` 段必须在前、`SR_48000` 在后，末尾不能有逗号**：`DDCParser` 用
  `countChars(fs48, ',')+1` 反推节数，若 48k 段在前会把两段逗号一起数进去 → 节数翻倍。
- 两端必须是 `b0..` 紧接冒号（`SR_44100:`），冒号与数字间无空格。
- 交叉验证：解析 `resource/ddc/AKG/AKG K240.vdc` 得典型耳机补偿曲线（20-40Hz +3.7dB、
  100-400Hz -2.8dB、1.5-5k +2~3dB），两采样率响应一致、极点稳定 → 约定正确。

### 三种源格式（统一解析器，勿再按格式分叉）
| 来源 | 特征 |
|---|---|
| REW / LUOLAN | 制表符 4 列 Frequency/Magnitude/Phase/Coherence；首行设备名 |
| Studio Six Digital | `*` 注释头 + `freq, dB` CSV |
| MATAA | `%` 注释 + `name=`/`type=`/`sensitivity=` 元数据 + **空格对齐**两列 |

**通用解析判据（两条就够）**：① strip 后首字符必须是数字（吃掉表头/`name=`注释/`*`）；
② 分隔符正则必须含空格 `[\s,;]+` —— MATAA 大量文件用等宽空格对齐（`15          0`），
只认 tab/逗号会让 **57/61 文件解析为空**。③ MATAA 元数据值要用 `.split("\t")[0].split("%")[0]`
剥掉行尾注释，否则把 `"GENERIC MICROPHONE\t% name / descriptor"` 当型号名 → 非法文件名崩溃。

### 拟合设计（踩过的坑）
- **更多节 ≠ 更好**：ECM8000 从 8 节加到 10 节 RMS 仅 0.319→0.316，但峰增益从 5.2 飙到
  **16.6 dB**——优化器在用大增益+大 Q 追测量纹波。默认 **8 节**（库内既有文件主流为 5 节）。
- **taper 区必须低权重**：peaking 在 DC/Nyquist 增益恒 0 dB，故目标曲线两端要收敛到 0；
  但那段是人为构造的、无真实数据，权重压到 0.15，否则优化器为迎合端点牺牲数据区精度，
  且 RMS 被端点伪影污染（加权后 ECM8000 RMS 0.404→0.319，过拟合消失）。
- `--smooth` 分数倍频程平滑（默认 0=不平滑）：对 ECM8000 几乎无影响，对剧烈波动的
  StudioSixDigital 示例能把 RMS 从 2.4 压到 1.3，但峰增益仍撞 24dB 上限 → 那条曲线本身
  不适合级联 peaking 拟合，已如实标注而非粉饰。
- **SDS 节数扫描实测（耗时 14 分钟，别再重跑）**：8/12/16/20/24 节 →
  RMS 2.435 / 1.596 / 1.533 / 1.369 / 1.217 dB；其中 12/16/20 节**峰增益全部撞 24 dB 上限**，
  24 节才回落到 19.6 dB。即堆到 24 节 RMS 仍有 1.2 dB（其它文件是 0.05~0.32 dB），
  而节数是库主流 5 节的近 5 倍、每采样 24 节双精度 DF2。
  → 结论：维持 8 节交付，此扫描仅为给用户决策的量化依据。

### 极性未决（需要用户拍板，勿自行假定）
