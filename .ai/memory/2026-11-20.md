### 教训（本机实测，务必记住）

1. **断点 ≠ 内容宽度**：480 档页面留白更大，内容区可能比 360 更窄。首页 hero 与视效 HUD 都因只用 `isCompactWidth` 在 480 漏判（hero 溢出 89、HUD 59）。争宽布局一律用 `LayoutBuilder` 的 `maxWidth` 判定。
2. **`Row(mainAxisSize.min)` 给子项无界主轴约束**，内层 `Flexible` 不生效——胶囊/按钮要可压缩，必须处在有界父约束下。
3. `FittedBox.scaleDown` 优于横向滚动：等价必须全见的控件（页签）等比缩小比藏起来更可发现。
4. 测试基建抖动确认为环境级：`shell_layout_test` 未经改动同样 1/5 概率 `did-not-complete`，与窄屏无关，别误判为回归。

## 打包工具链规范化 / 平台化 / 统一化（同日续）

### 结构（pack.py 1319 行 → 60 行薄壳 + 21 个模块）

- `installer/packkit/`：平台无关内核（common/paths/version/naming/hashing/
  archives/resources/defaults/manifest/staging/deliver）。
- `installer/packkit/windows/`：平台层（toolchain 产物发现、driver 新鲜度、
  driver_payload 组装、signing 签名门、setup_image 尾块、installer_build、
  payload、modes、cli）。
- `installer/windows/pack.py`：只注入 sys.path 并转发 `packkit.windows.cli.main`。
- `installer/release.py`：统一发布编排（预检门禁表 → 可选构建 → light 先/
  full 后 → deliver-rNN 归集 → 大写 LF 清单 + 说明卡 → Setup 自检）。
- 依赖单向：`windows/ → packkit/*.py`，内核不得 import 平台层（Linux 复用前提）。

### 命名收口（naming.py 唯一真相）

构建名带 tag；交付名不带 tag，portable 按档位分 `-Full-` / `-Light-`。
两条硬规则：full 与 light 交付名必须不同；打包顺序恒 light 先、full 后
（`TIER_PLANS` 顺序即执行顺序）。

### 门禁未变，只是归位

新鲜度门（driver.py）/ 载荷签名门（signing.py，验 dest 不验源）/ 重编
mtime 硬断言（build_driver）三处集中；staging 路径只降级为警告，发行路径
必拒绝——与拆分前逐字一致。

### 踩到的真实集成点

`tools/resource_pipeline/merge_resources.py` 原先把 `pack.py` 当模块
`spec_from_file_location` 加载并直调 `apply_resources`；pack.py 降为薄壳后
必断。已改为直接 `from packkit.resources import apply_resources`。教训：
**「脚本降为薄壳」前先全仓搜动态导入**（grep `spec_from_file_location`），
否则 Linux 侧资源合并会静默失效。
