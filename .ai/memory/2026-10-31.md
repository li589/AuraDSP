## 工具教训（本轮真实踩坑，全部已修）

### python 字节级替换脚本的四个坑

1. **校验了命中却忘了执行替换**：脚本里 `staged.append((path, rel, norm, crlf))` 存的是**原文快照**，
   写回时只做了换行转换 → 等于没改。但文件 mtime 变了、字节数未变，极易误判为"已生效"。
   修正：必须 `cur = cur.replace(ob, nb)` 后再入队。
2. **同文件多条编辑互相覆盖**：每条编辑各自基于原始快照写回 → 后一条覆盖前一条。修正：**按文件分组**，
   在上一条结果上继续应用。
3. **残留检查把"新串以旧串开头"误判为失败**：编辑"在原句后追加一行"时，新串以旧串开头，
   "旧串必须消失"的校验必然报错。修正：改为"旧串**不是**新串前缀时才要求旧串消失"。
4. **多行新串需按文件换行风格转换**：CRLF 文件直接写 `\n` 会插入混行。修正：按文件实际风格转换后再替换。
   本仓 4 个目标文档均为纯 CRLF（CRLF 数 == LF 数），改后仍是纯 CRLF。

### PowerShell here-string 会破坏反斜杠与引号

- `@'...'@` / `@"..."@` 里的 `` ` `` 是转义符（`assets/` 里的反引号被吞），中文在 `python -c` 传参时
  也被控制台编码破坏（表现为诊断脚本匹配不到目标行）。
- **正解**：诊断/替换脚本一律用 Write 写成 `.py` 文件再 `python file.py` 执行，不走 `-c` 与 here-string。
  这与本仓既有纪律「带反斜杠的代码一律用 Write/Edit，不用 heredoc」同源。

### git 统计非 ASCII 路径必须关 quotepath

`git ls-files` 默认对非 ASCII 路径加引号转义，`Get-Item` 收到的是 `"assets/convolver/.../xxx.irs"`
这样的带引号转义串 → 报「路径不存在」，误判成"文件丢了"。
**正解**：`git -c core.quotepath=false ls-tree -r -l HEAD -- assets`（按大小统计）或 `-z`（NUL 分隔）。

### 登记类数字必须标测量日期与测量命令

文件数/体积这类"登记数字"会随资源持续补入而失真（本次 2214→2443 就是这么漂的）。
**范式**：凡是写入真相源文档的统计数字，一律附「测量日期 + 测量命令」，并在口径变更时显式标注旧值作废。

## 工具坑与教训

- **撕裂检测只能用极值统计，不能用 mean**：修复版因 `stage_arbmag` 取锁而变慢，
  单位块内换曲线次数上升 → 合法瞬态的 mean 反而更高（19.4% vs 11.3%），与撕裂信号混淆。

  多次观测才敢定阈值。
- **`auradsp_process` 的 `frames` 会被 `max_block` 钳制**：一次喂 12288 帧只处理前
  `max_block`(=256) 帧，其余输出保持 0 —— 测增益会得到 −120dB 的假失败。必须按块喂。

# D-2 / D-3 落地 —— assets 大二进制去跟踪 + dev→main 合并（2026-10-31 夜）

## 裁定

- **D-3**：dev→main 走 PR 合并（沿用 PR #12–#14 惯例），不直推 main。
- **D-2**：对**全部 ref**（`dev` / `main` / 两个 tag）执行 `filter-repo` 重写并
  force-push 到**公开**仓（唯一贡献者就是 owner，无外部协作者克隆失效风险）。
- **插件 stage 4（Post-Limiter）**：owner 裁定**暂时保留、不退役** → ADR-010 的该项例外
  维持，该待裁定项关闭。

## 先核事实：三处「想当然」都差点出错

1. **过滤器只写 `assets/*` 会漏掉一半**。全历史共 4428 条 `.irs`/`.vdc` 路径，P3b 改名
   之前它们叫 `resource/`（2214 条）。只过滤 `assets/**` ⇒ 旧 `resource/**` 的 blob 原样
   留在历史里，而 `size-pack` 看不出差别（大部分是压缩后的重复内容）——必须显式加两条
   `--path-glob 'resource/*.irs'` / `'resource/*.vdc'`。
2. **`filter-repo` 会删掉工作区的资源文件且剪掉旧 blob**。其 `cleanup()` 依次执行
   `git reset --hard` → `reflog expire --expire=now --all` → `git gc --prune=now`；
   前者删掉那 2443 个文件，后者让「从旧 SHA 还原」这条路彻底失效 ⇒ **重写前必须做
   文件系统级备份**（本轮放 `.git/assets_backup/`，逐文件 SHA256 校验）。
3. **`filter-repo` 会删掉 `refs/remotes/origin/*`**，那些 ref 上的提交**不参与导出**、
   因而**不被重写**——本轮远端 main 的 4 个 PR 合并提交（PR #11–#14）就是这样丢的。
   补救：先验证「内容中性」（合并树 == dev 侧父提交树），再取重写后 dev 侧提交的树 +
   重写后的父 SHA + GitHub API 取回的 message/author/date 逐个重建，重建后树摘要与
   基线逐个匹配才算数。

## 交付与验证

- **过滤器**：`git filter-repo --force --invert-paths --path-glob 'assets/*.irs'
  --path-glob 'assets/*.vdc' --path-glob 'resource/*.irs' --path-glob 'resource/*.vdc'`
- **验证（双轴 + 逐提交）**：工作区 2501 文件 SHA256 与重写前**全等**；2493 个资源条目
  按 `* text=auto` 归一化后 blob SHA 与原始 blob **全等**；645 提交的「剔除 `.irs`/`.vdc`
  后的树摘要」基线 vs `commit-map` 逐对比对 → **641 对零失配**；远端 `main`/`dev` 树中
  `.irs`/`.vdc` 条目 **0**；本地 `.git` **203.6 MB → 50.6 MB**。
- **重建的合并提交**：PR #11–#15 共 5 个（`4b33fd6` / `a8fe6f6` / `7999b3e` / `325af5d` /
  `45f4824`），逐个验证树摘要匹配基线。重写后 `dev`（`3138fb83`）是 `main`（`45f4824`）
  的祖先 ⇒ **D-3 的合并关系完整保留**。
- **门禁**：`tools/bin/assets_untracked_scan.py`（5 项断言）。反向验证：强制

- **远端**：force-push `dev` / `main` / `v0.5.0` 三个 ref 成功；PR #15 在重写前已由
  owner 合并（merge commit `cc0d0989`），重写后其等价物为 `45f4824`。

## 工具坑（本轮实踩）

- **`filter-repo` 遇多 worktree 直接 abort**：本机还留着 `%TEMP%/auradsp_baseline`
  （detached @ `3c92fb5`）这个 10-29 的基线快照。先确认它干净（0 未提交改动）且其提交是
  两分支的共同祖先（内容可从历史恢复）再 `git worktree remove --force`。
- **annotated tag 的本地副本可能与远端分叉**：本地 `v0.5.0` 指向 `5fb999d`，远端指向
  `2593aa1`。直接重写会把**错的提交**推上去 ⇒ 重写前先 `git tag -d` 再从远端 fetch。
- **`fnmatch` 的 `*` 跨 `/`**：filter-repo 的 `--path-glob` 走 `fnmatch.fnmatch`，
  `assets/*.irs` 能覆盖任意深度嵌套；但 Windows 下 `normcase` 会把 `/` 转成 `\`，
  路径匹配不受影响。
- **不要用 fast-export 文本做路径差分**：`git fast-export` 的路径**在需要转义时才用 TAB
  分隔**，且原文件对非 ASCII 路径用 C 风格八进制转义、filter-repo 重写后又还原成原始
  UTF-8 ⇒ 文本差分必然误判。**改为逐提交树摘要比对**（剔除目标扩展名后 sha256 整棵树），
  与文本格式无关，才是可靠证据。
- **GitHub 的 `refs/pull/*` 是隐藏命名空间**：`git push origin :refs/pull/15/head` 被拒
  （`deny updating a hidden ref`）。9 个 PR 头提交（PR #7–#15）的树里仍有 2443 个
  `.irs`/`.vdc` ⇒ **GitHub 对象库仍保留这些 blob，远端 `diskUsage` 不降**（199013 →
  199053 KB）。要清只能删旧 PR（丢讨论历史）或申请 GitHub Support purge——**未擅动**。
