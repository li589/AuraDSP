# 打包工具链分层与发布编排（2026-11-20）

> 状态：**已落地**（工具层；本轮不发布）。迁移后 `pack.py` 的 CLI 契约与
> 错误文案逐字不变，`installer/windows/tests/test_pack_fixture.py` 全绿。

## 1. 为什么要动

原 `installer/windows/pack.py` 是 1318 行单体，四类关注点缠在一起：

| 关注点 | 原先的位置 | 问题 |
|---|---|---|
| 版本/命名 | 脚本内联拼字符串 | 交付名靠手工改，light 与 full 同名互覆盖（r52 实测中招） |
| 驱动域 | 与资源合并相邻 | 新鲜度门、签名门、devcon 补齐、BOM/CR 纪律散落四处 |
| 资源档位 | 与 Setup 拼装相邻 | 修改档位要通读打包与安装两段 |
| 交付归集 | 仓库外的临时脚本 | 每轮手写 `cp` + 手写 SHA256SUMS，轮次记在文件名里 |

后果是「改一处要读全篇」「同一次构建的产物名不一致」「门禁只存在于
某条路径上」。本轮把它拆成三层，并把交付归集收进仓库。

## 2. 分层结构

```text

│   ├── paths.py               # 全部输入输出路径的唯一解析点
```

依赖方向是单向的：`windows/`、`linux/` → `packkit/*.py`，内核层**不得**
import 平台层，平台层之间也互不 import。这条约束是「平台化」的实质：
Linux 收编时命名、哈希、资源档位、交付归集全部原样复用，只有产物发现与
封装步骤是新写的（详见 §7）。

## 3. 命名规范（唯一真相源 `naming.py`）

| 类别 | 形态 | 例 |
|---|---|---|
| 构建名 driver | `AuraDSP-Driver-x64-<tag>.zip` | `AuraDSP-Driver-x64-v0.1.0.zip` |
| 构建名 portable | `AuraDSP-Windows-x64-<tag>.zip` | 同左 |
| 构建名 setup | `AuraDSP-Setup-x64-<tag>.exe` | 同左 |
| 交付名 driver | `AuraDSP-Driver-Windows-x64.zip` | 不带 tag |
| 交付名 setup | `AuraDSP-Setup.exe` | 不带 tag |
| 交付名 portable full | `AuraDSP-Windows-x64-Full-<tag>.zip` | 带档位 |
| 交付名 portable light | `AuraDSP-Windows-x64-Light-<tag>.zip` | 带档位 |
| 包内清单 | `SHA256SUMS.txt` | 小写、LF、合并式 |
| 交付清单 | `SHA256SUMS-r<NN>.txt` | 大写、LF、给定顺序 |

两条硬规则：

1. **full 与 light 交付名必须不同**（`test_packkit_unit.py` 有断言钉住）。
   两者的构建名相同，交付时必须按档位改名，否则后打的覆盖先打的。
2. **打包顺序恒为 light 先、full 后**。`TIER_PLANS` 的顺序就是执行顺序，
   `release.py` 不接受调用方交换。

### 3.1 Linux 产物名（`LinuxArtifactNames`）

| 模式 | 产物名 | 备注 |
|---|---|---|
| deb | `auradsp_<ver>_amd64.deb` | 用**版本号**不用 tag（dpkg 不认 `v` 前缀） |
| driver | `auradsp-driver-loopback_<ver>_all.deb` | `Architecture: all` |
| appimage | `AuraDSP-v<ver>-x86_64.AppImage` | 便携 |
| portable | `AuraDSP-Linux-x64-v<ver>.tar.gz` | 便携补充形态 |

**Linux 的交付名 = 构建名**：这些名字本身就是用户下载页上的名字（deb 由
apt 直接消费），归集时改名只会制造「交付目录名 ≠ 下载页名」的困惑。

第三条硬规则（Linux 专有）：**一次只能打一个资源档位**。产物名不含档位
后缀，`light` 与 `full` 会产出同名文件，后打的静默覆盖先打的。Windows 用
`-Full-`/`-Light-` 后缀解决，Linux 用「`resolve_tiers` 拒绝多档」解决
（`test_packkit_linux_unit.py` 与 CI 都有断言）。

## 4. 驱动打包、签名与命名

驱动相关的门禁集中在三处，语义不同：

| 门 | 位置 | 触发 | 失败后果 |
|---|---|---|---|
| 新鲜度门 | `windows/driver.py:check_driver_freshness` | `driver`/`setup` 模式 | 拒绝打包（staging 降级为警告） |
| 载荷签名门 | `windows/signing.py:check_driver_payload_signed` | 每次组装 `driver/` | 拒绝打包（staging 降级为警告） |
| 重编硬断言 | `windows/driver.py:build_driver` | `--build-driver` | 中止（防「脚本报成功但 .sys 未重写」） |

签名门验的是**要发出去的那份载荷**，不是源目录：r52 事故就是壳层验过源
目录、载荷里却是 Inf2Cat 重生成的裸 `.cat`（无签名者），宾机 testsigning
开着仍报 Code 52、VAIO 永不启动。门禁因此有三条断言：`.cat` 必须
Authenticode `Valid` 且有签名者；随包 `.cer` 指纹必须与签名者一致；
`.cer` 缺失只警告（与 `install_vaio.ps1` 的 WARN 口径一致）。

命名侧的两个历史坑也在此收口：ASIO DLL 一律归一化为规范名
`auraasio_driver.dll`（`AuraAsioDriver.dll` 仅作识别别名）；驱动产物名
必须是 WDK 工程实际输出 `AuraVaioDriver.sys` / `auravaiodriver.cat`。

`.ps1` 落盘纪律（`driver_payload.py`）：UTF-8 BOM 必带；模板字节中出现
`\r` 即拒绝打包（`\r` 转义事故会把注释行劈开、后半截被 PowerShell 当命令）。

## 5. 发布编排 `release.py`

```bash
# 只看计划与门禁（只读，不写任何文件）
python installer/release.py --plan --out-root D:/temp_desktop

# 资产探测（各模式 --what-if，不落产物、不触发真构建）
python installer/release.py --dry-run --out-root D:/temp_desktop

# 真正打一轮：复用现有 staging，产出 deliver-rNN
python installer/release.py --round 60 --out-root D:/temp_desktop

# 先全栈构建再打包（Windows）
python installer/release.py --round 60 --build

# Linux（须在 Linux/WSL 执行）：四件一次全出，单档位
python installer/release.py --platform linux --plan
python installer/release.py --platform linux --round 60 --out-root /data/dist
python installer/release.py --platform linux --bundle <bundle> --resources-tiers core
```

执行步骤（平台无关部分）：

1. 预检——`FAIL` 即中止，`WARN` 只提示；
2. 可选 `--build`（各平台自己的构建链）；
3. 按平台档位计划顺序打包；
4. 归集 `deliver-r<NN>/`：按交付名摆齐（**拷贝**，来源保留可复算）；
5. `SHA256SUMS-r<NN>.txt`（大写、LF）+ `RELEASE-r<NN>.txt`（提交/脏度/档位）；
6. 平台自检。

平台差异全部在 `packkit/<platform>/release_plan.py`，`release.py` 本身
**不含任何 `if 平台` 分支**：

| 环节 | Windows | Linux |
|---|---|---|
| 预检 | staging、VAIO 驱动新鲜度、ASIO、APO 四件、安装器构建、两档资源包 | 平台、dpkg-deb/gzip/du/tar、bundle 四件载荷、单档资源包、AppImage 钉版与 `file` 依赖、flatpak/snap 清单 |
| 档位 | `light` → `full`（顺序即执行序） | 唯一一档（默认 `full`） |
| 模式 | driver / portable / setup | deb / driver / appimage / portable |
| 构建 | `build_windows.ps1 -BuildType Release` | `cmake --preset linux-x64` → `flutter build linux` → `sync_artifacts.py` |
| 自检 | Setup 尾块、偏移、载荷哈希、双 zip | `dpkg-deb --info/--contents`、`tar -tzf`、AppImage ELF magic + 可执行位 |

**发布未接线**：`--publish` 会明确失败并提示手工投放。这是 2026-11-20 的
裁定——本轮只落工具，不产出、不上传、不投放。

## 7. Linux 收编实录（2026-11-20）

原实现是 `installer/linux/` 下 5 个 shell 脚本（`pack.sh` + deb/driver/
appimage/portable 各一），合计约 400 行。收编后：

| 变化 | 前 | 后 |
|---|---|---|
| 入口 | `pack.sh`（114 行，含流程编排） | `linux/pack.sh` 转发壳 + `linux/pack.py` 薄壳 + `packkit/linux/cli.py` |
| 流程编排 | 写在 bash 里 | `packkit/linux/bundle.py` + `modes.py` |
| 权限规范化 | `find -exec sh -c 'file ... \| grep ELF'` | `packkit/linux/perms.py` 读 ELF magic |
| 交付归集 | 手工 `cp` + 手写哈希（r59 实测） | `release.py --platform linux` 复用 `deliver.py` |
| 跨平台 | 只在 Linux 有实现 | `release.py` 一条命令两平台，`--platform` 切换 |

**复用了多少**：命名、哈希、资源档位、默认层、交付归集、清单写入六件全部
原样复用（占 Linux 打包逻辑的一半以上）；只有产物发现与封装是新写的。

### 7.1 收编时修掉的两个真实缺陷

**缺陷 1（严重）：缺 `file` 命令会静默产出跑不起来的包。**
原实现靠 `find -exec sh -c 'if file "$f" | grep -q ELF; then chmod 755'`
判可执行文件。最小化容器/WSL 常常没装 `file`：此时 `file` 返回 127，
`grep` 不匹配，**所有 ELF 被 chmod 644**，而脚本退出码仍是 0、无任何警告。

实测（Debian WSL，无 `file`）：

```
旧实现: -rw-r--r--  ./usr/lib/auradsp/auradsp_app      ← 装完点不开
        -rw-r--r--  ./usr/lib/auradsp/lib/libauradsp_engine.so
新实现: -rwxr-xr-x  ./usr/lib/auradsp/auradsp_app
        -rwxr-xr-x  ./usr/lib/auradsp/lib/libauradsp_engine.so
```

改为读 ELF magic 后零外部依赖；顺带把「每文件 fork 一次 `file`」变成单遍
遍历（bundle 数千文件，这项从数千次进程创建降到 1 次）。

注意 `file` **仍是 AppImage 的硬依赖**——`appimagetool` 内部会调它。因此
`appimage.preflight()` 把「缺 file」列为 FAIL、`appimage.build()` 在组装
AppDir 之前就拒绝，而不是等压缩完 16MB 才报
`file command is missing but required`。

**缺陷 2：`auradsp.desktop` 的换行随工作区漂移。**
`git ls-files --eol` 显示该文件 `i/lf w/crlf`：仓库里存 LF，Windows 工作区
checkout 成 CRLF。Linux 原生 checkout 没问题，但在 **WSL 里从 `/mnt/d`
打包时读到的是 CRLF**，于是：

```
ERROR: Desktop file contains errors.
```

appimagetool 直接拒绝。同一个文件进 deb 不报错，只是装到系统上属于不合规的
desktop entry（部分桌面环境会不显示图标）。

修法：出口处规范化——`linux/textio.py` 按 UTF-8（去 BOM）+ LF 写，desktop
文件、便携包 README 都走它。刻意**不改 `.gitattributes`**：那会让所有开发者
下次 checkout 遇到大面积换行 diff，代价远大于收益。

### 7.2 验证方式与结果

平台差异不能只靠「读代码看着对」，所以做了三层验证：

1. **新旧对拍**（同一 fake bundle，旧 shell 实现 vs 新 packkit 实现）：

   | 产物 | 条目数 | 内容+权限 |
   |---|---|---|
   | `auradsp_0.1.0_amd64.deb` | 61 / 61 | 逐条一致 |
   | `auradsp-driver-loopback_0.1.0_all.deb` | 15 / 15 | 逐条一致 |
   | `control` / `postinst` / `postrm` | — | 逐字一致 |
   | `AuraDSP-Linux-x64-v0.1.0.tar.gz` | 22 / 22 | 逐条一致 |

   对拍时给旧实现补了一个只按 magic 判型的 `file` 垫片（本机 `file` 装不
   上，sudo 需密码），目的是让旧实现按其设计正常工作，而不是借环境差异
   制造「新实现更好」的假象。缺陷 1 的实证是单独一组对照（刻意不给垫片）。

2. **真实封装**（Debian WSL，dpkg 1.22）：`dpkg-deb --info/--contents` 校验
   control 字段、t64 双写依赖、维护脚本、`/usr/bin/auradsp` 链接、载荷权限；
   `tar -tzf` 校验便携包结构与权限。

3. **AppImage 端到端**：按 pins 下载 appimagetool 1.9.1 + type2-runtime
   20251108 → SHA256 与钉版表一致 → 组装 AppDir → 产出 997,880 B 的
   AppImage → `--appimage-extract` 解出 `AppRun/auradsp.desktop/auradsp.png/usr`
   → 铁律自检（无 `libpulse*`/`libasound*`）通过。

4. **发布编排端到端**：`release.py --platform linux --round 1` 产出四件到
   `deliver-r1/`，大写 LF 清单可被 GNU `sha256sum -c` 直接校验，四个 OK。

### 7.3 后续平台（macOS）的接入步骤

Linux 收编验证了这套接缝够用，macOS 按同样四步即可：

1. `naming.py` 加 `MacArtifactNames`（`.dmg` / `.pkg` 命名）；
2. `packkit/macos/`：产物发现（`.app` bundle）、签名（codesign + notarize）、
   封装（hdiutil），复用 `bundle.py` 同型的 staging 逻辑；
3. `packkit/macos/release_plan.py` 实现 `PlatformPlan`，`release.py` 加一个
   `--platform macos` 分支（就一行 `if`，因为策略是外置的）；
4. 测试沿用两层：平台层纯函数单测 + 一项端到端 workflow。
