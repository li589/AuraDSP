**三条阻断级发现全部由实测坐实**（非纸面推演）：

1. **自研 DSP 链的采样率域错位**——自研链位于 ASRC 之外，处理设备率样本却用工作率算系数。实测：自研 filter（LP f0=1000Hz）的 -3dB 频率在 48k/96k/192k 分别为 **1000Hz / 2000Hz / 3986Hz**。同期 vendor EQ 对照组三档均为 -6.0dB（ASRC 内自洽）——证明架构本身没错，错的是跨域那一侧。**已修（P-029）**。
2. **`eq.enable=0` 关不掉 vendor EQ**——上游 `MultimodalEqualizerEnable` 只有 `if (enable)` 没有 else，标志位永不归零。实测：enable=1 → -6.01dB，enable=0 → **-6.01dB（完全不变）**。**已修（P-030）**。
3. **多声道 IR 静默失效**——宿主门卫放行 1..8 声道 IR，vendor 卷积器只实现 1/2/4 声道分支；3/5/6/7/8 声道时 API 返回**成功**、`convolver.ready=1`、UI 显示"就绪"，实际输出**完全没有卷积**。**已修（P-030，收紧门卫为 {1,2,4}）**。

**架构根因（三条主线）**：

- **双采样率域**：设备率 `h->sample_rate` 与工作率 `h->jdsp.fs` 并存，无单一权威；vendor 链整体被 ASRC 包裹故用工作率正确，自研链在 ASRC 外却也用工作率 → 错位。
- **双掩码语义**：11 个 `*.channels` 参数中 9 个是逐声道位掩码，comp/eq 却是**声道对**语义（必须成对置位）；UI 一律用同一个选择器 → 勾选单个声道被引擎静默忽略。
- **三条多声道路径**：矩阵（mode=0）/ 离散（mode=1）/ 双耳（`spatial.binaural`）并存，双耳路径**完全跳过** mode 判定，其余声道被写零；两页两个开关互不告知。

## 1. 架构事实基线

### 1.1 两个采样率域

| 名称 | 位置 | 语义 | 取值 |
| --- | --- | --- | --- |
| 设备率 | `engine/engine_internal.h`（create 时设定） | 驱动缓冲实际速率，RT 链处理的就是它 | 任意（如 96000） |
| 工作率 | `engine/legacy/jdsp/jdsp_header.h` | ASRC 之后 vendor 链的速率 | 非常见率时恒 48000/44100 |

`engine/legacy/jdsp/jdspController.c:1486-1518`：设备率落在 [44100,48000] 时 `enableASRC=0` 且 `fs = sample_rate`；否则 `enableASRC=1` 且 `fs` 重选为 48000/44100。

### 1.2 两条处理链，ASRC 边界在中间

- **vendor 链**（`kAuraStages[]` 12 个 stage）：`JamesDSPProcessMultiplexedStageSet` 内 `DoASRC_fwd → stage 循环 → DoASRC_bwd`（`jdspController.c:1283-1313`）→ **全程工作率域**，用 `jdsp->fs` 算系数是**自洽的**。
- **自研链**（`engine/dsp/` 12 个模块 + `engine_chain.cpp` 的 `*_process_mc`）：直接处理驱动缓冲（**设备率域**），但旧代码用 `jdsp.fs` 算系数 → **跨域错位**（P-029 的根因）。
- 唯一例外：`dsp_freeverb.cpp` 与 `limiter_process_mc` 本来就用 `h->sample_rate`——它们是**正确的样板**，本次统一了其余 10 个模块。

### 1.3 多声道三条路径

`engine/auradsp_engine.cpp:312-350` 的裁决顺序：

1. `spatial.binaural=1` 且 `spatial.enable=1` → **双耳路径**：`channels.mode` **完全不读**，6/8ch 渲染为双耳，其余声道**写零**；
2. 否则 `channels.mode=1` → **离散 MC 路径**（`process_multichannel_chain`）；
3. 否则 `channels.mode=0` → **矩阵路径**（下混 → 立体声链 → 上混）。

## 2. 实测数据

`test/smoke/smoke_sr_rate_alignment.py`（本轮新建，ctypes 直驱引擎 DLL）：

```
[A] 自研 filter (LP f0=1000Hz) 的 -3dB 频率
     48000 Hz : gain@1000Hz = -3.00 dB   -3dB @ 1000 Hz
     96000 Hz : gain@1000Hz = -0.29 dB   -3dB @ 2000 Hz     ← 修复前
    192000 Hz : gain@1000Hz = -0.06 dB   -3dB @ 3986 Hz     ← 修复前
[B] 对照组 vendor EQ（曲线 1000Hz:-6dB）
     48000/96000/192000 Hz : -6.00 / -6.01 / -6.04 dB      ← 三档一致，ASRC 内自洽
[C] eq.enable=0 的关闭语义
    enable=1 -> -6.01 dB ; enable=0 -> -6.01 dB            ← 修复前（完全不变）
```

修复后：[A] 三档均为 1000Hz（192k 为 1005Hz，数值容差内），[B] 不变，[C] 为 -0.01dB。

**反向验证**（还原 pre-fix 行为重建 DLL）：[A] 96k/192k 与 [C] 三条**判红**（2000Hz / 3986Hz / -6.01dB），证明断言非空转。

### 3.5 移植效果器与 LiveProg 适配

**LiveProg（`liveprogWrapper.c` + `eel2/`）**：

- `srate` 变量三处赋值全部取 `jdsp->fs`（工作率），**从无 `trueSampleRate`** → 脚本作者按"设备率"理解的 `srate` 实为工作率，且**无任何文档说明**（`liveprogWrapper.c:97/137/165`）。
- `@init` 段系数**编译期烘焙**（`:190-197`），即使 `srate` 被更新也不会重算 → 采样率热切后不可修复（Android 侧可达路径）。
- 影子 VM 槽选择**不校验采样率/声道布局快照**（`:222-235`）→ 与上条叠加造成跨配置串味。
- EEL 引擎**未注册声道数变量**，脚本无法感知多声道。

**vendor stage 采样率取值总表**（全部用 `jdsp->fs`，因 vendor 链整体在 ASRC 内，**均自洽**）：tube(`vacuumTube.c:152`)、comp(`dynamic.c:2017`)、bass(`dbb.c:441`)、eq(`multimodalEQ.c:13/177`)、arbmag(`arbEqConv.c:28`)、ddc(`vdc.c:391/404`)、liveprog(`liveprogWrapper.c:97`)、crossfeed(`crossfeed.c:79`)、stereo(`stereoEnhancement.c:9`)、reverb(`reverb.c:925`)、convolver(IR 不含采样率，宿主重采样到 `jdsp.fs`)、output(不涉及)。

**结论：vendor 家族在采样率维度表现良好**——12 个 stage 全部统一使用工作率且都在 ASRC 包裹内运行。真正的断裂点只有三处：跨出 ASRC 边界的 `arbmag_pool`（已修 P-029）、采样率热切路径的不完整（Android 侧）、以及多声道维度的 comp/eq 语义与单实例复用。
