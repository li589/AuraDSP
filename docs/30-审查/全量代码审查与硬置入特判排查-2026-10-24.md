## TL;DR

- **用户最关心的"机械式特判"：运行时只有 1 处真硬置入**（iZotope 安装路径，P1 边界 P0），另有 2 处"弱式"（已外置为可编辑数据 + 崩溃日志自愈，P2）。**另有 4 组"看起来像特判、经核查是通用实现"**——这个仓库在这个最易腐化的点上治理水平高于同类项目，值得先肯定。
- **发现 2 个 RT 级 P0（既存，非本次引入）**：① RT 回调内取 `jdsp_lock`，而持锁方在控制线程做 EEL 编译，实测可达秒级 → 音频整段阻塞；② VM 泵 fan-in 的自旋兜底上界 `4×10^8` 次 `YieldProcessor` ≈ 秒级。
- **上一提交（Phase B）自审出 4 处收尾缺口**，其中 3 处是**内存越界**：`tools/` 下 2 个 python 脚本 + 1 个 C++ 测试工具仍按 536B 接收 1600B 帧；1 处是**默认矩阵模式漏采样**（MC 用户默认路径上 6 柱电平假死）。
- **门禁缺口 5 项**：桥无 ABI 协商（帧长靠口头契约）、结构体尺寸与 ABI 号无编译期耦合、python/C++ 镜像无 CI 检查、17 处 `PATCHED` 缺补丁编号、桥 `.def` 与头文件三处失准。
- 处置：本次立即修"自己刚引入/漏掉"的 6 项（越界 ×3、矩阵模式、测试空转、桥注释 + ABI 联动断言）；深层 P0/P1 列专项（改动面大、需独立验证，不在审查轮里动）。

## 2. 专项一：机械式硬置入特判（用户核心关切）

### 2.1 结论先行

| 类别 | 数量 | 判定 |
|---|---|---|
| 真硬置入（按特定插件名/厂商/路径走特殊分支） | **1** | F1，P1 |
| 弱式（触发键仍是插件名，但数据外置 + 有自愈路径） | 2 | F2/F3，P2 |
| 看似特判、实为通用实现 | 4 组 | E1-E4，P2，**无需修改** |
| 测试夹具层插件路径（SKIP 兜底） | 7 | P2，可接受实践 |

**为什么"只有 1 处"值得说**：音频宿主这个领域最容易长出的正是这类代码（`if (name == "Ozone") skipLatencyReport()`）。本仓库在这个点上做了三件正确的事：① 最容易被写成点名的三处（旁路、编辑器布局、`setProcessing`）全部用了通用判据；② 隔离名单已从引擎硬编码迁出为外置 JSON；③ 卡顿治理用 **CPU 预算实测 EMA** 替代"某插件太慢所以限它"，这是范式级的正确选择。

### 2.2 F1（P1，边界 P0）iZotope 安装路径硬编码 ✅亲验

`engine/plugins/platform/win32/win32_util.cpp:198-223`

```cpp
        std::string pLow = pluginPath;
        std::transform(pLow.begin(), pLow.end(), pLow.begin(), ::tolower);
        if (pLow.find("izotope") != std::string::npos || pLow.find("ozone") != std::string::npos) {
            const wchar_t* izDirs[] = {
                L"C:\\Program Files\\iZotope\\Ozone 12\\Cores",
                L"C:\\Program Files\\iZotope\\Ozone 12\\win64",
                ...
                L"C:\\Program Files\\iZotope\\RX 12 Audio Editor\\win64"
```

**它要解决的问题**（真实）：iZotope 的 VST3 wrapper 把依赖 DLL 放在安装根的 `Cores\` / `win64\`，而不是 `.vst3` bundle 内部。宿主用 `LoadLibraryExW(..., LOAD_WITH_ALTERED_SEARCH_PATH)` 只搜插件自身目录 → 依赖解析失败 → 插件加载不出来。

**为什么是硬置入**（四个具体脆点）：
1. **版本钉死**："Ozone 12" / "RX 12" 是字面量 → 用户升级 Ozone 13 后失效（当前最常见的真实场景）。
2. **盘符钉死**：`C:\Program Files\` → 装 D 盘或 `Program Files (x86)` 的用户拿不到修复。
3. **子串误判**：`find("ozone")` 会命中 `C:\Users\ozone\...`；`find("izotope")` 把 Neutron 也算进来，但目录表只覆盖两个产品。
4. **进程级副作用不可回收**：`AddDllDirectory` 返回的 cookie 被丢弃，且每次 `showEditor` 路径还会再调一次 → 搜索路径单调增长。后续任何插件解析同名 DLL（`libcurl`/`ffmpeg`/`json`）时可能绑到 iZotope 的私有副本 → ABI 不匹配崩溃。**这条是潜在的 P0 通道。**

**通用化修法（三步，不点名任何厂商）**：
```cpp
// 1. 加目录：插件所在目录 + 其父目录 + 常见子目录（win64 / Cores / bin / x64）
// 2. 加目录：环境变量 AURADSP_PLUGIN_DLL_DIRS（分号分隔）——用户/客服可配置
// 3. 保存 cookie，插件卸载 / 编辑器关闭时 RemoveDllDirectory 回收
```
iZotope 场景被"父目录 + 子目录扫描"自然覆盖，且对 FabFilter/Waves/u-he 同样生效。

## 3. 专项二：RT 安全（2 P0 + 2 P1，全部既存）

### B1（P0）RT 回调内取锁，而持锁方做秒级重活 ✅亲验

`engine/legacy/jdsp/jdspController.c:618-626`

```c
	for (int i = 0; i < jdsp->chainLen; ++i)
	{
		if (jdsp->chain[i].lock)
			jdsp_lock(jdsp);
		jdsp->chain[i].fn(jdsp, n);
		if (jdsp->chain[i].lock)
			jdsp_unlock(jdsp);
```

`kAuraStages`（同文件 462-479）里 `comp / convolver / ddc / liveprog` 四个 stage `lock=1`。同一把锁的持有方（控制线程）在：
- `jdspController.c:463`（Z13）`CompressorSetParam(forceRefresh=1)` 全量重置
- `jdspController.c:1553` `JamesDSPSetSampleRate`（ASRC 初始化 + 全部效果重建）
- `liveprogWrapper.c:108-142` **NSEEL_code_compile ×2**——按 `features/liveprog_page.dart:650` 自述可达 ≥2s

**后果**：EEL 编译期间音频回调在 `EnterCriticalSection` 上无限期等待（无超时/无优先级继承）→ 整段音频卡死，等同"RT 里 Sleep 2 秒"。这正是用户长期抱怨的"改参数/加载脚本时爆音卡顿"的可能根因之一（与 Z13 修的是同一把锁，但 Z13 只修了数据竞争，没修**等待时长**）。

**修法**：liveprog 改"控制侧编译到影子 VM → RT 原子换指针"（P-006 的 EQ 双缓冲已有现成范式）；comp/ddc 同法。这是**结构性改动，需独立专项 + 长时压测**，不在本轮修。

> **处置记录（2026-10-24，B1-a 已落地）**：liveprog 部分已完成——影子 VM 编译 +
> 块边界原子换指针 + `eelInFlight`/`eelProcCount` 双条件在途守卫 + stage lock 置 0，
> 见 `engine/legacy/PATCHES.md` B1 条与 `test/smoke/smoke_liveprog_race.py`
> （RT×UI 并发 17 断言 + pre-B1 反向验证）。comp/ddc 仍持锁（持锁时长亚毫秒~毫秒级，
> 非秒级），列 B1-b/B1-c 后续；`JamesDSPSetSampleRate` 全效果重建与它们共用该锁，
> 属同一把锁的剩余暴露面。

### B2（P0）VM 泵 fan-in 自旋上界 4×10^8 ✅亲验

`core/desktop/windows-drivers/02_voicemeeter_client/VmPumpCore.h:589-600`

```cpp
        uint64_t spins = 0;
        while (InterlockedCompareExchange(&c->workDone, 0, 0) < expect) {
            YieldProcessor();
            if (++spins > 400000000ull) {
                InterlockedExchange64(&c->workClaimPacked, 0);
                InterlockedExchange(&c->parallelOn, 0);
                break;
            }
        }
```

注释自认"永不发生"，但 4×10^8 次 `PAUSE`（~10-30ns/次，含争用）≈ **4-12 秒**。一旦 worker 被插件崩溃杀掉，音频线程被钉死数秒——比它想避免的"永久自旋"只差一个数量级。

**修法**：改 QPC 截止（`> 2ms` 即放弃本块并回串行），上界降到 ~2×10^5 次；且超时路径**不要 mutate `parallelOn`**（RT 侧改配置状态本身也是隐患）。

### B3（P1）强制排空与契约矛盾 → UAF 窗口 ✅亲验

`engine/plugins/driver/plugin_host_manager.cpp:104-111`

```cpp
    while (s.inFlight.load(...) != 0 && spins < kQuiesceSpinLimit) { ... }
    s.destroyPending.store(false, std::memory_order_relaxed);
    // 强制排空安全兜底：... 绝不能锁死用户卸载
    s.inFlight.store(0, std::memory_order_relaxed);     // ← 硬清零
    ...  s.instance->closeEditor(); deactivate(); unload(); s.instance.reset();  // L122-137 照常销毁
```

而契约（`inflight_guard.h:26-28`）明写：**"超过上限视为 RT 异常滞留，此时选择保留实例而不是冒险释放"**。

实现与契约相反：硬清零计数后仍销毁实例。若 RT 真的在途（inFlight 非零的原始原因），`reset()` 就是 use-after-free。L113-141 还带缩进错位（`}` 在 L142），是插入事故痕迹（E6）。

**修法**：超限时走已有现成函数 `quarantineAbandonedInstance()`（同文件 L129-133 就在正确使用），不要清零后照常销毁。

### B4（P1）RT 改写 vendor 开关 → lost update ✅亲验

`engine/chain/engine_chain.cpp:778-789`（MC 链 Category B 段）

```cpp
        const int tube_saved = h->jdsp.tubeEnabled;
        ...
        h->jdsp.tubeEnabled = 0;           // RT 为"只跑 FL/FR"临时关
        ...
        h->jdsp.tubeEnabled = tube_saved;  // 再恢复
```

控制线程 `apply_tube()`（同文件 ~140）随时写同一字段。若用户操作落在 save 与 restore 之间 → **被静默回滚**（界面显示开着，实际关了）。且这些字段非 atomic（同仓 P-010 的 `fxOutGain` 反而用了对齐 float 原子，此处是退化）。

**修法**：`JamesDSPProcessMultiplexedStageSet` 本来就支持 `ids` 参数（L794 就在用），把"只跑哪些 stage"作为参数传入，不要在 RT 内改全局状态。

1. `viz_write` 的"有效列数"与 `channel_count` 解耦：handle 新增 `last_viz_ch`（viz_write 参数值）；`channel_count` 报 `last_block_ch`（设备真实声道数），但 `stage_ch_levels` 的 `c` 上限改用 `stage_ch_active`（`process_stereo_chain` 入口置 2、`process_multichannel_chain` 入口置 ch）→ 矩阵/双耳/stereo 的 stage 列诚实 -120。

### D1（P1）延迟表 48k 假设 vs Dart 注释直接矛盾 ✅亲验

`engine/engine_internal.h:371-379`
