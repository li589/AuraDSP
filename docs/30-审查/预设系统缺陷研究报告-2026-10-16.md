# 预设系统缺陷研究报告

- 日期：2026-10-16
- 范围：`app/auradsp_app/lib/core/presets.dart`、`session_memory.dart`、`state.dart`、`engine/audio_isolate.dart`、`engine/engine_internal.h`
- 方法：全量代码审计 + 一次性诊断探针 `test/zz_preset_defect_probe.dart`（13 个用例，其中 5 个失败即缺陷实证）
- 结论速览：**7 类缺陷确认成立**，全部有文件+行号+复现路径；预设系统的「出厂硬置入」「测试缺口」「记忆/预设打架」「UI 与实际参数不符」四个方向均发现实证问题

---

## 0. 根因总图：三套互不一致的默认值

预设系统不存在「唯一真相源」，同一参数有三套默认值，任何修复必须先统一口径：

| 层 | 位置 | 作用 | 问题 |
|---|---|---|---|
| Dart `ParamDefaults` | `state.dart` L64-171 | UI 初始显示值 | 与引擎默认值有 5 项不一致（见 §4.1） |
| 引擎 `struct Params` | `engine/engine_internal.h` L101-227 | 引擎实际运行默认值 | 注释与自身默认值矛盾（L213） |
| isolate `getParams` fallback | `audio_isolate.dart` L565-665 | 引擎回读缺失时的兜底 | 第三套值（如 `limiterEnable ?? 1`，L575） |

此外 **snapshot ↔ apply 契约是隐式的**：`snapshot()` 写 110 个叶子字段 / 23 个顶层节，`apply()` 逐节 `if (x.isNotEmpty)` 读回——没有声明式 schema，字段对称性全靠人工对齐，已经出现写而不读（§2.1）。

## 1. 代码自带硬置入问题

### 1.1 出厂预设硬编码在 Dart 源码里（设计缺陷）

`_builtInPresets`（`presets.dart` L850-1117）把 6 个出厂预设（Pop Vocal Clarity / Rock Bass Impact / Symphonic Concert Hall / Vintage Vinyl Tube / V-Shape Smile Hi-Fi / Studio Flat Monitor）完整写在源码中。

### 1.2 出厂 JSON 落盘后永不更新（实证：探针 B3）

`ensureInitialized()`（`presets.dart` L72-87）L81 为 `if (!f.existsSync())`：

```dart
if (!f.existsSync()) {          // ← 只在文件不存在时写盘
  f.writeAsStringSync(jsonEncode(preset.toJson()));
}
```

**实证**：探针 B3 在沙箱内先跑 A2（触发 `ensureInitialized` 落盘），再查 `studio_flat_monitor.json` 已存在 → `true`。即**代码内 `_builtInPresets` 的任何后续修改都不会同步到老用户磁盘**。出厂预设只能首次安装时定版，运营期无法热修。

### 1.3 出厂预设缺 16-17/23 个效果节（实证：探针 A2）

| 出厂预设 | schema | 缺失节数 | 缺失清单 |
|---|---|---|---|
| Pop Vocal Clarity | v2 | 17/23 | arbmag, bassmono, chainOrder, comp, convolver, crossfeed, ddc, deesser, dyneq, exciter, filter, gate, haas, **input**, liveprog, loudness, shelf |
| Rock Bass Impact | v2 | 17/23 | 同上 |
| V-Shape Smile Hi-Fi | v2 | 17/23 | 同上 |
| Vintage Vinyl Tube | v2 | 17/23 | 同上 |
| Studio Flat Monitor | v2 | 16/23 | 同上（少 shelf） |
| Symphonic Concert Hall | v2 | 16/23 | 同上（少 shelf） |

注意 **input 节全部缺失**——输入增益/声道平衡属于全局链路，不在任何出厂预设内。

### 1.4 `preset: -1` 分支用硬编码兜底覆盖用户自调值（实证：探针 B1）

`presets.dart` L488-500，`apply()` 的 reverb 节：

```dart
final pr = (rev['preset'] as num?)?.toInt() ?? -1;
if (pr >= 0) {
  m.setReverbPreset(pr);
} else {
  m.setReverbCustomParam('decay',    (rev['decay']    as num?)?.toDouble() ?? 0.5);   // ← 硬编码
  m.setReverbCustomParam('damp',     (rev['damp']     as num?)?.toDouble() ?? 0.5);
  m.setReverbCustomParam('wet',      (rev['wet']      as num?)?.toDouble() ?? 0.35);
  m.setReverbCustomParam('dry',      (rev['dry']      as num?)?.toDouble() ?? 1.0);
  m.setReverbCustomParam('roomSize', (rev['roomSize'] as num?)?.toDouble() ?? 1.2);
  m.setReverbCustomParam('width',    (rev['stereoWidth'] as num?)?.toDouble() ?? 1.0);
}
```

4/6 出厂预设的 reverb 节只有 `{'enable': false, 'preset': -1}` 两个键（L920/L1015/L1058/L1097）——预设本意是「关混响」，但 apply 走 -1 分支时**仍无条件把 6 个 customParam 全部写成硬编码默认值**。

**实证**：探针 B1 用户先自调 `decay=0.9 / wet=0.8 / roomSize=2.2`，apply「Rock Bass Impact」后变为 **0.5 / 0.35 / 1.2**。用户手动重新打开混响时，拿到的是出厂默认值而非自己调好的值。

### 1.5 出厂预设 EQ 无频率信息（实证：探针 B2）

探针 B2：出厂预设 eq keys = `[enable, bandsCount, gains, q, filter, interp, presetName]`，**无 frequencies、无 qs**。`apply()`（`presets.dart` L539-580）只能退化为「按段数 + 下标灌 gains」的老路。代码注释 C4（L562-569）已自承此问题：

> snapshot 写了 'frequencies'，apply 却一直只按 bandsCount 重建网格再按下标灌 gains。跨采样率/跨段数时这会把增益贴到错误的频点上

用户预设有 frequencies 可走频率重映射；**出厂预设永远走不了**。

## 2. 测试覆盖参数

### 2.1 名义覆盖 vs 实际缺口

现有测试：`config_and_presets_test.dart` 66 例 + `eq_preset_curve_test.dart` 6 例 + `comp_and_ddc_chain_test.dart` 5 例。逐节往返（shelf / convolver / ddc / crossfeed / bassmono / haas / liveprog 等）名义上都有用例，**但以下七类问题零覆盖**，每一类都有探针实证：

| # | 缺口 | 对应缺陷 | 严重度 |
|---|---|---|---|
| 1 | `bass.gain` snapshot→apply 不对称 | §2.2 | **高** |
| 2 | 出厂预设完整度 | §1.3 | 高 |
| 3 | apply 合并语义残留（缺节≠归零） | §3.2 | 高 |
| 4 | reverb -1 分支覆盖用户值 | §1.4 | 高 |
| 5 | 出厂预设 eq 无 frequencies | §1.5 | 中 |
| 6 | UI 默认值 vs 引擎默认值一致性 | §4.1 | **高** |
| 7 | getParams 回读完整性 / 自动保存覆盖 | §4.2 / §3.4 | 中 |

### 2.2 `bass.gain` 写而不读（实证：探针 A1，代码层已定位）

- `snapshot()` L260 写出 `'gain': m.bassGain`；
- `apply()` 的 bass 节（L456-479）依次处理 intensity / mode / cutoff / harmonics / harmonicBlend / subFloor / autoGain / outputGain / enable——**唯独没有 `bass['gain']` 的读回分支**。

探针 A1：写入 `bassGain = 7.5`，apply 后 MISMATCH。同类的 `stereo.bandUsed` 也是只写不读（A1 第二项）。

> 教训对照：`eqGains` 早期犯过完全相同的错（按下标赋值被吞），修复时补了专项测试 `'apply() 后 eqGains 真正落到 model'`；`bass.gain` 至今无任何测试覆盖，所以缺陷一直活着。

## 3. 用户记忆与预设打架

### 3.1 会话与预设共用同一份 schema（结构性耦合）

`SessionMemory.save()`（`session_memory.dart` L23-66）内部调 `PresetLibrary.snapshot(m, name: '__session_memory__')`——**§2 中 snapshot 的每一个缺陷同时污染预设保存与会话记忆两条链路**。会话额外在顶层存 `convIrPath / ddcPath / lpCode / arbmagString / slots` 等资源路径。

### 3.2 apply 是「合并」不是「替换」（实证：探针 A3）

`apply()` 逐节 `if (x.isNotEmpty)` 守卫 → **缺节 = 不碰该效果，而非关闭该效果**。

**实证**：用户开 gate/dyneq/haas/exciter/bassmono 五个效果，apply「Studio Flat Monitor」（缺这 5 节）后**五个全部仍为 true**。出厂预设只有 6-7/23 节（§1.3），意味着应用任何出厂预设后，用户态在其余 16-17 个效果上**原样残留**。UI（`features/effects/preset_card.dart`）只提示「已应用」，没有任何「将合并/保留未覆盖效果」的告知。

### 3.3 apply 的隐藏副作用：改写 activePresetName

`apply()` 末尾（`presets.dart` L845）执行 `m.activePresetName = preset.name`。任何调用方都会被污染；`restoreMemoryImage` 靠「先存后还原」（`session_memory.dart` L146-154，`__restored__` 傀儡预设）绕开。此坑已用注释固化，但**没有测试守护**——重构 `apply()` 时两处会同时静默劣化。

### 3.4 启动恢复无回放保护，立即回写自身（实证：探针 C2，静态确认）

autoSave 链：`scheduleAutoSave()`（`state.dart` L707-714，500ms 防抖）→ `SessionMemory.save(this)`，守卫为 `if (_testing || _isReplayingSession) return`。

但 `_isReplayingSession` **只在 `replaySessionToEngine()`（L1323-1534）内置位**；启动路径 `restoreMemoryImage`（构造期 L665 调用）**不置位**。结果：每次冷启动恢复会话 → apply 触发全部 setter → 每个 setter 调 `scheduleAutoSave()` → 500ms 后把刚读进来的数据原样写回磁盘。当前数据同源所以无害，但这是每个启动周期一次的**无意义磁盘写 + 时序竞猜窗口**（恢复期间若引擎 getParams 异步到达，写回内容可能是「恢复值 × 引擎默认值」的混合体）。

### 3.5 自动保存覆盖缺口：三个用户动作不持久化（实证：探针 E1 + 代码直读）

`scheduleAutoSave` 在 `state.dart` 共 47 处（3 个通用 dispatcher `setInt` L1232 / `setFloat` L1245 / `setStringParam` L1872 + 各效果小 setter 内联）。确认**不触发**的用户动作：

| 方法 | 行号 | 缺失后果 |
|---|---|---|
| `setGraphOrder` | L1753 | 处理链重排**不持久化**，重启后丢 |
| `setSource` | L3522 | 音源/file 路径选择不持久化 |
| `toggleBypass` | L3538 | 旁路开关不持久化 |
| `resetConfig` | L3591 | 见 §3.6 |

（EQ 曲线路径经 `_flushEqCurve` → `setStringParam('eq.curve')` → 可达自动保存，无缺口。）

### 3.6 「恢复默认」不清会话记忆（实证：探针 E2）

`resetConfig()`（L3591）只重置 `config.json`，不连带 `SessionMemory.clear()`。设置页两个按钮（「清除记忆」/「恢复默认」，`settings_page.dart` L197-220）各自为政。用户点「恢复默认」后**下次启动旧参数全回来**——与心智模型直接冲突。

另：`setAutoRestoreSession` 关开关时只 clear 一次，若自动保存缺口（§3.5）中的动作在关闭后发生，残留仍可写入。

## 4. 初始化的 UI 显示参数 vs 实际参数冲突

### 4.1 默认值三方不一致（实证：探针 D1，36 项比对 5 项不符）

| 参数 | UI 初始显示（Dart） | 引擎实际默认（C++） | 影响 |
|---|---|---|---|
| `stereoOn` | false | **1**（`engine_internal.h` L106） | UI 显示立体声关，引擎实际开着跑 |
| `limiterOn` | true | **0**（L108） | UI 显示限幅器开，引擎实际关着 |
| `tubeGain` | 4.5 | **0.0**（L123） | UI 显示 4.5dB 驱动，引擎 0dB |
| `fvWet` | 0.35 | **0.3**（L211） | 混响湿度显示偏差 |
| `fvRoomSize` | 1.2 | **1.0**（L213） | 房间尺寸显示偏差 |

L213 的注释是**自相矛盾**的铁证：`fv_roomsize{1.0f} /* 0.5..2.5 × tuning（UI 默认 1.2，session 回放对齐）*/`——默认值写 1.0，注释说 UI 默认 1.2。第三套值在 isolate 兜底（L575 `limiterEnable ?? 1`，与 UI 一致但与引擎矛盾）。

**用户可见场景**：全新安装、未开会话恢复时，UI 显示的开关/数值与引擎真实状态不一致；用户「什么都没点」听到的效果和看到的界面是两套。

### 4.2 getParams 回读不完整：UI 永远得不到引擎真相（实证：探针 D2）

`audio_isolate.dart` L566-665 的 `params` 事件只回读约 30 项，**14 类参数缺失**：

```
stereo.enable / tube.gain / stereo.band1..5 / input.gain / input.balance.1/2
fv.roomsize / fv.width / eq.band gains, qs, filter, interp, bandsCount
graph.order / bass.intensity / bass.mode / arbmag.string / liveprog.code
```

其中 `graph.order`（处理链顺序）、`bass.intensity/mode`、`eq.*` 全部缺失。叠加 `_mirror`/`_markSent` 乐观镜像设计（UI 只信自己发出去的值），不回读 = **盲飞**：引擎侧若因任何原因（守卫拒绝、脚本改写、真机差异）偏离 UI 值，用户界面永远显示错误的态且无从发现。

## 5. 修复优先级建议

> 以下为研究方向报告的建议，**尚未执行任何修复**，等待决策。

### P0（一行级，低风险高收益）
1. `presets.dart` apply bass 节补 `if (bass['gain'] != null) m.setFloat('bass.gain', ...)` 读回（对齐 L260 snapshot）——同时补回归测试
2. reverb -1 分支（L494-499）改为「preset 未提供该键则不动用户值」，去掉 6 个硬编码兜底
3. `setGraphOrder` / `setSource` / `toggleBypass` 补 `scheduleAutoSave()`；`resetConfig()` 追加 `SessionMemory.clear()`

### P1（需设计决策）
4. `ensureInitialized()` 加版本化：比较文件内 schemaVersion/内容摘要与代码内出厂版，不一致才重写（修 §1.2）
5. 出厂预设补全 23 节（至少 input/chainOrder 必补），eq 补 frequencies（修 §1.3/§1.5）
6. apply 语义定版：缺节 = 保留（合并，需 UI 明示）或 = 关闭（替换，需全节填充）二选一，写进 `engine/AGENT.md` 铁律

### P2（口径统一工程）
7. 默认值三方对齐：以引擎 `struct Params` 为唯一真相，Dart `ParamDefaults` + isolate fallback 由引擎生成或加 D1 测试守护；删除 L213 矛盾注释
8. getParams 补齐 14 类回读（至少 graph.order / bass.intensity / bass.mode / eq 网格）
9. `restoreMemoryImage` 入口置 `_isReplayingSession`（与 `replaySessionToEngine` 对齐），消除启动回写自身
10. 把探针 13 个用例翻转为正式回归测试（当前断言方向即缺陷的 acceptance criteria）

结果：**5 FAIL / 8 PASS**。FAIL 的 5 个（A1 / A3 / B1 / B2 / D1）即缺陷成立的直接证据；PASS 的 8 个为信息性快照（A2 缺节清单、B3 落盘不同步、C1 activePresetName 污染、C2 无回放保护、C3 首帧窗口、D2 回读清单、E1/E2 持久化缺口）。

**门禁安全性（已验证）**：该文件是 `test/` 下唯一不以 `_test.dart` 结尾的文件，`flutter test` 裸跑默认只匹配 `*_test.dart`，天然跳过它——全量门禁实测 **206 PASS / 0 FAIL / 4 SKIP**（2026-10-16），不受探针影响。这种方式可以长期保留「按需手动运行」的诊断能力：`flutter test test/zz_preset_defect_probe.dart`。

**后续转正注意事项**：修复落地时若要转为回归测试，新文件必须以 `*_test.dart` 命名才会进门禁，且断言方向要从「缺陷存在」（当前 expect 失败）翻转为「缺陷已修」（修复后 expect 通过），否则一进门禁就是 5 条红。

（测试沙箱说明：`flutter test` 下 `ConfigManager.baseDir` 默认指向系统临时目录，探针未污染真实 `%APPDATA%`。）
