## 1. F-1（P0）process 模式音频数据置乱

### 1.1 现象

`AURA_PLUGIN_HOST_MODE=process` 下，插件音频在**代理 scratch 缓冲边界**被置乱：约 7/8 的样本为静音/陈旧值，剩余 1/8 是错误帧、错误声道的样本。进程内模式（默认）不受影响。

### 1.2 证据链

代理侧 scratch 缓冲的**写与读使用不同布局**，且输入/输出两个缓冲的不一致方向相反：

| 路径 | 写侧 | 读侧 | 是否一致 |
|------|------|------|----------|
| 输入 | `process_plugin_proxy.cpp` L240 `m_inInterleaved[m_inFill * ipc::kChannels + ch]` —— **帧交错，stride 8** | L134 `m_inInterleaved + ch * ipc::kTransportFrames` —— **平面** | ❌ |
| 输出 | L160 `m_outInterleaved + ch * ipc::kTransportFrames` —— **平面** | L248 `m_outInterleaved[m_outPos * ipc::kChannels + ch]` —— **帧交错，stride 8** | ❌ |

宿主侧（`auradsp_plugin_host_main.cpp` L447-462）与 `ipc::AudioBlock` 交互**两侧均为平面**（输入 `interleaved[i*channels+ch] = in.samples[ch][i]`，输出反向）——自洽。**证明代理侧是唯一破坏方**，协议与宿主无需改动。

置乱推演（立体声插件，plugChannels=2，kChannels=8，kTransportFrames=128）：

- scratch 写入：第 i 帧 ch0 落 `i*8`、ch1 落 `i*8+1`，`i*8+2..7` 六个位置保持零/陈旧。
- submitChunk 平面读：`block.samples[0] = scratch[0..127]` → 仅含第 0-15 号帧的 ch0（每隔 8 个样本一个），其余为零；`block.samples[1] = scratch[128..255]` → 混入第 16-31 号帧的 ch0/ch1。
- 宿主插件收到：frame 0 的 L=帧0ch0、R=帧16ch0；frame 1 的 L=0、R=帧16ch1……1/8 占空比的数据流。

### 1.3 根因（git blame 定性）

| 提交 | 日期 | 状态 |
|------|------|------|
| `1f5b752`（P4 引入） | 10-20 21:07 | **自洽**——`m_inL/m_inR/m_outL/m_outR` 分声道缓冲，读写皆平面 |
| `70869d7`（P5 多总线，IPC v2） | 10-21 早 | **仍自洽**——未动 scratch 缓冲 |
| `e4580931`（P5 通道掩码与多声道适配，IPC v3/8ch） | 10-21 14:41 | **改坏**——统一为 `m_inInterleaved/m_outInterleaved` 大数组时，写侧交错/读侧平面，两侧半边在同一提交内互斥 |

即：不是 P4 潜伏，而是 **P5 多声道扩展一次性引入**，且被常量信号冒烟测试放行（见 F-3）。

### 1.4 影响面

- 进程模式为**环境变量 opt-in**（`plugin_host_client.cpp` L73-74），默认进程内——日常使用不受影响。
- 但 `auradsp_engine` DLL **不定义** `AURADSP_HOST_INPROC`（`core/desktop/windows/CMakeLists.txt` L78-84 无此宏；仅宿主 exe L121 与两个单测 L139/L156 定义）——进程模式分支在**出厂引擎中真实编译**，任何设置该环境变量的用户/测试都会命中。
- `smoke_plugin_host_process.py` 正是该模式的唯一守卫，且它是绿的（F-3）。

### 1.5 修复方案（diff 级）

工作区 WIP 已指明方向（`.h` L77-84：改名 `m_inPlanar/m_outPlanar` + PLANAR 布局注释——"sample index for channel ch at frame i is ch * kTransportFrames + i"）。剩余动作：

1. `.cpp` 4 处改名：L134、L160、L240、L248（消 F-2）；
2. L240 改索引：`m_inInterleaved[m_inFill * ipc::kChannels + ch]` → `m_inPlanar[ch * ipc::kTransportFrames + m_inFill]`；
3. L248 改索引：`m_outInterleaved[m_outPos * ipc::kChannels + ch]` → `m_outPlanar[ch * ipc::kTransportFrames + m_outPos]`；
4. L134/L160 已是平面读/写，仅需随改名同步。

修复后**必须**先升级测试向量（F-3）再验证，否则常量信号下修前修后都是绿的，无法证明修复有效。

## 3. F-3（P1）假绿测试：常量 0.5 对置换不变

- **位置**：`test/smoke/smoke_plugin_host_process.py` L67 `samples = [0.5] * (frames * 2)`；L84 `if max(abs(v - 0.5) for v in out) > 1e-3: return out`（`wait_for_processed` 的"插件已生效"探针）。
- **数学事实**：常量信号经任何线性变换仍是同常量；任何样本**置换/置乱/静音-稀疏化**都不改变"输出≠0.5"的真值（只要插件有非单位增益）。该断言对布局错误、通道交换、时序错位**全部不变**。
- **后果**：F-1 从 e4580931 引入到本次审查，穿过 `test/runner.py --smoke`（L35 在册）全程绿灯。测试的实际保证仅剩"音频路径存活"，无法保证"音频正确"。
- **处置建议**：
  1. 增加**布局敏感向量**：ch0=+0.5 递增斜坡、ch1=-0.5 递减斜坡、ch2..ch7 各自独特常值/静音，逐样本断言输出（插件若为单位增益则全等；若为增益 g 则按比例可预测）；
  2. 增加**时序敏感断言**：利用现有 seq 字段或已知延迟，验证首非零样本位置；
  3. 该向量对进程内模式同样适用，建议下沉为共享 fixture。
- **流程教训**（建议入 `.ai/memory`）：**常量信号测试对结构错误零分辨力**；凡涉及缓冲布局/通道映射/时序的路径，测试向量必须携带位置信息（斜坡/脉冲/分声道标记）。

## 4. F-4（P1）输入环溢出静默丢块 + 无 seq 连续性校验

- **位置**：`process_plugin_proxy.cpp` L258 `submitChunk();` —— 返回值（环满=false）被忽略，128 帧输入块**静默丢弃**（`inputOverflows` 有计数但无行为）；L142-170 `pumpOutput` 不校验 `block.seq` 与期望序列的关系（submitChunk L129 写了 `block.seq = m_nextSeq++`，输出侧从不读）。
- **组合后果**：输入丢块 → 宿主无感知继续处理 → 输出块时序整体前移 → 代理侧无感知继续消费 → **隐性时序偏移持续累积**，直到 missStreak≥64（≈170ms）才触发 failed+bypassed 恢复。期间用户听到的是"音调轻微错位但仍在响"的受损音频，且无任何计数器暴露（inputOverflows 有值但无人看）。
- **处置建议**：① 丢块时计入 missStreak 或至少 `AURADSP_DBG_LOG` 记录；② pumpOutput 校验 seq 连续性（代理侧维护 `m_nextSeqOut`，间隙即丢块检测）；③ 宿主侧输出环满（host main L466-472）已有 outputOverflows 计数，代理侧可读取并在超限时主动重建会话。

## 5. F-5（P2）m_transportChannels 语义被 processInterleaved 覆写

- **语义约定**：`setChannelHint` 链路（引擎 `plugin_chain_adapter.cpp` L19/L42 → `PluginHostManager` L332-346 → 实例与 remoteClient 双层下发）传递的是**总线声道数**。
- **问题**：`process()` L205 传给 `processInterleaved` 的是 **plugChannels**（插件主入声道，L183-187），而 L234 `m_transportChannels = channels;` 直接覆写。
- **后果**：
  - a) `copyBypass` L108 `channels = max(2, min(m_transportChannels, 8))` 退化为插件声道数——多总线下（如 8ch 总线 + 立体声插件）旁路时超出声道不再直通，**阶段二 f85134c 的"超出部分直通"修复在旁路路径被绕过**；
  - b) `packTransportFlags(m_transportChannels, ...)`（L131）上报值与宿主侧 setChannelHint 下发值（总线数）不一致，pumpOutput L155 的 `channels != m_transportChannels` 丢弃逻辑在参数抖动期误丢块。
- **处置建议**：`m_transportChannels/m_transportMask` 只应由 `setChannelHint` 维护；`processInterleaved` 改用局部变量携带本次调用的 channels/mask。

## 6. F-6（P2）宿主音频线程无优先级提升 + 忙时全速自旋

- **位置**：`auradsp_plugin_host_main.cpp` L427-478。音频线程仅 `SetThreadDescription`，**无 `SetThreadPriority`/MMCSS（AVRT "Pro Audio"）注册**；有块处理时全速自旋，无块时 `Sleep(1)`。
- **后果**：普通优先级线程可被其它用户态活动抢占 → 环饥饿 → 代理侧 missStreak 累积 → 170ms 后**误判宿主死亡**转旁路（音频掉效果）。忙旋同时让一个核心跑满。
- **处置建议**：音频线程提升至 `THREAD_PRIORITY_TIME_CRITICAL` 或注册 MMCSS；忙旋改事件驱动（输入侧 release store 后 `SetEvent`，宿主 `WaitForSingleObject` + 超时兜底）。

## 7. F-7（P2）latency 上报少算一段传输缓冲 → PDC 时序偏差

- **位置**：`process_plugin_proxy.cpp` L65/L337 `m_latency.store(info.latency + ipc::kTransportFrames, ...)`；消费者 `plugin_chain_component.cpp` L131/L218（PDC 延迟线设定值）。
- **事实**：进程模式实际管线延迟 ≈ **2×kTransportFrames**（输入侧积满 128 + 输出侧 128 缓冲）+ 插件延迟；上报只加了 1×128。**R-1 复核实测确认**：脉冲落于全局帧 544 = 288（插件）+ 256（2×128），上报值 416 = 288+128，低估恰为一段 128。
- **后果**：process 模式下旁路切换时 PDC 对不齐 ~128 样本（≈2.7ms@48k）——低于人耳时延感知阈值但高于专业 PDC 精度要求；冒烟测试 L120-122 的 `latency >= 128` / `transportLatency == 128` 断言固化了该低估口径。
- **处置建议**：process 模式 latency 上报改为 `info.latency + 2 * kTransportFrames`；或在代理侧实测首块往返动态校准。

## 11. R-1（P0）进程模式宿主侧静默单位直通（F-1 修复后脉冲复核新发现）

### 11.1 现象

F-1（代理 scratch 布局）修复后，进程模式脉冲复核**仍未对齐进程内**：宿主侧插件不生效，引擎收到的是宿主对输入的**原样回声**——近似单位增益、零插件延迟（观测量：`0.988553@帧0` 预热直通 + `0.988553@帧256` 宿主回声；`remoteFailed=false`、输入/输出环零溢出、load 成功且上报 latency=416=288+128）。进程内模式始终正确（`0.600000@帧288`，两种块大小一致）。

### 11.2 证据链（红）

1. **排除法**：块大小（activate/proc 四种组合全测）、种子元数据（纯描述性）、PDC（默认关）、auraConv（默认不启用）、CWD（E9 假设，已证伪）、插件配置跨运行演化（连续 4 次稳定）——全部排除后，「位移」本身被证明是**探针索引假象**（`nz` 未加块偏移 `b*frames`，「帧 32」实为块 1 的全局帧 288）：进程内路径本来就是对的，问题唯一集中在宿主侧。
2. **宿主音频线程**（`auradsp_plugin_host_main.cpp` L427-478）逻辑正确：读环 → 解交织 → `manager.processSlotInterleaved(slot, interleaved, 128, channels, mask)` → 写回。
3. **`processSlotInterleaved` 入口守卫**（`plugin_host_manager.cpp` L400-403）：`numFrames > m_channelScratchBlock || !m_channelIn[0] || !m_channelOut[0] || !m_channelZero` → **直接 return，不写输出缓冲**。宿主 scratch 为空时，音频线程写回的就是输入——unity 回声，且不走任何失败路径（无遥测、无 remoteFailed）。
4. **宿主 scratch 的唯一分配入口**是 `PluginHostManager::updateFormat`（L601-605）内的 `ensureChannelScratch`，而宿主只在收到 `Op::UpdateFormat` 时执行它。
5. **`Op::UpdateFormat` 从未到达宿主**：`PluginHostClient::start()`（L72-79）只置 `m_processMode`，宿主进程**懒启动于首个客户端请求**（`request()` L270 `ensureHostLocked`）。引擎 create 期的 `updateFormat` 转发被 `alive()` 守卫跳过（L608，宿主未启动）；此后再无补发——`loadPluginSlot` 远程分支只发 `SetChannelHint` + `Op::Load`，代理的 `activate()`（唯一另一处会发 UpdateFormat 的路径）在该分支不被调用；宿主 `Op::Load` 处理器只手动赋值 `m_sampleRate/m_maxBlockSize`（L198-199），**不调 `ensureChannelScratch`**。

### 11.3 根因

宿主进程的 `PluginHostManager` **通道 scratch 永远为零**：`Op::UpdateFormat`（唯一分配入口）因「懒启动 × alive() 守卫 × 加载路径不补发」三重错位从未送达。于是 `processSlotInterleaved` 在每个音频块入口静默返回，宿主把输入原样写回输出环——**插件在宿主侧从未被调用**，而所有状态量（load 成功、latency 416、零溢出、remoteFailed=false）均正常，故障完全不可观测。E9（CWD）假设随之证伪：unity 回声与 CWD 无关，CWD 修复（继承引擎工作目录）语义正确、予以保留，但不是本根因。

### 11.4 修复（diff 级，两处互为兜底）

1. **宿主自愈（根因修复）**：`auradsp_plugin_host_main.cpp` `Op::Load` 处理器——手动赋值格式改为 `manager.updateFormat(sampleRate, maxBlock)`。宿主构建含 `AURADSP_HOST_INPROC=1`（CMakeLists L121），该调用走本地分支：`ensureChannelScratch(maxBlock)` + 槽位重激活（加载时无槽，为空转）。**任何加载路径上宿主 scratch 必然就绪。**
2. **引擎补发（兜底）**：`plugin_host_manager.cpp` `loadPluginSlot` 远程分支——代理 load 成功后补发 `m_remoteClient->updateFormat(sampleRate, maxBlockSize)`。覆盖 create 之后、load 之前发生过格式变更的场景；与 `Op::Load` 消息携带格式形成双保险。

| 进程模式（远程） | 0.988553@0 + @256（unity 回声） | **0.593867@544（宿主插件生效）** |

- **544 = 288（插件延迟）+ 256（实测管线 = 2×128 传输块）**：直接量化确认 F-7「上报 416 少算一段 128」——实测管线为 2×kTransportFrames。
- **0.593867 = 0.6 × 0.98978**：限幅器对帧 0 预热直通脉冲（1.0 超 -0.1dBFS 门限，`limiter_threshold{-0.1f}` = 0.988553）的 release 恢复残压，属预期引擎行为（进程内无预热脉冲，故精确 0.600000）。
- **冒烟测试全绿**：`smoke_plugin_host_process.py` 8/8 节通过——[4] 远程处理变换门控、[4a] ramp 密度 100%、[4b]/[4c] 替换与异步替换后仍处理、[6] 杀宿主引擎幸存+自动旁路+remoteFailed 上报、[7] 重载重启宿主恢复处理、[8] 销毁回收宿主。

### 11.6 遗留观察（不随 R-1 修复，建议入后续轮次）
