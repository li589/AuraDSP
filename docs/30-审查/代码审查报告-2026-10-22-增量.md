## 1. F-1（P0）ABI 一致性门禁持续报红并污染主门禁

### 1.1 现象（实测）

```
$ python tools/bin/abi_consistency.py
[FAIL] ABI 不一致（导出 56 个，问题 2 项）：
  - 导出 auradsp_plugin_chain_get_enabled 在 auradsp_ffi.dart 无绑定
  - 导出 auradsp_plugin_chain_set_enabled 在 auradsp_ffi.dart 无绑定
EXIT=1
```

`test/smoke/smoke_abi_consistency.py` 是该脚本的 smoke 包装，**同样报红（exit=1）**，且它**已登记在 `test/runner.py` L60** —— 意味着 `python test/runner.py --smoke` 当前**整体判定失败**。

### 1.2 引入点（git 逐提交定位）

| 提交 | `.def` 导出数 | `auradsp_ffi.dart` 绑定数 | 门禁 |
|------|-------------|----------------------|------|
| `60430b3~1` | 0 | 0 | 🟢 |
| `60430b3`（VB 按路插件处理底座） | 2 | **0** | 🔴 |
| `13d13a2` | 2 | 0 | 🔴 |
| HEAD | 2 | 0 | 🔴 |

**根因**：`60430b3` 新增链级开关 ABI 时，只做了「引擎导出 + 桥可选符号解析」两件事，**遗漏了 Dart FFI 绑定**。因该 ABI 在当前产品形态上**只经 Windows 桥（`vb_plugin_group_enable` → `PluginBridge.h` 的 `chainSetEnabled`）调用**，Dart 侧走桥而非 FFI，功能上不受影响——**但门禁按「导出集合必须与 FFI 绑定集合一一对应」判定，故报红**。

### 1.3 为什么长期未被发现

门禁脚本本身正确（`.def` / `engine.h` / `ffi.dart` 三处逐一比对 + 元数校验），但：

- 该提交同时新增了 `smoke_plugin_chain_enable.py`（PASS），**给人「已覆盖」的错觉**；
- `runner.py` 里 `smoke_abi_consistency.py` 排在 L60，前序测试若中断则**后续不再执行**；
- 既有审查报告（`代码审查报告-2026-10-21` / `插件系统全面审查报告-2026-10-22`）**均未运行 ABI 门禁**——这是审查流程的覆盖盲区。

### 1.4 处置建议（三选一，推荐第 1 项）

1. **补 Dart FFI 绑定**（推荐）：`auradsp_ffi.dart` 增两条 `lookupFunction`，并在 `AuraDspLib` 侧增对应 wrapper。理由——`auradsp_plugin_chain_set_enabled` 是**公共 ABI**（`.h` 已声明、`.def` 已导出），非 VB 模式（ASIO/VAIO/WASAPI 单引擎）未来必然需要它；先补齐可避免二次回头。
2. **降级为「允许未绑定导出」白名单**：改脚本，新增「仅桥可达的导出」豁免列表。**不推荐**——豁免机制会让门禁从此只能拦「已绑定但符号不存在」单向错误，失去 E1 类漂移防护。
3. **从 `.def` 移除**：`auradsp_plugin_chain_*` 不再是引擎 DLL 公共导出。**不可行**——桥的 `GetProcAddress(mod, "auradsp_plugin_chain_set_enabled")` 依赖该导出（`PluginBridge.h` L119-122），移除即桥失效。

> 无论选哪项，**必须先让 `python test/runner.py --smoke` 恢复全绿**，再谈其它。

## 2. F-2（P1）真旁路改造引入与音频线程并发的生命周期调用

### 2.1 变更内容（`13d13a2`，2026-10-22 18:37）

为解决用户实测「Ozone 旁路仍持续卡顿」，旁路实现做了二次加强：

| 格式 | 旧（仅置标志） | 新（真旁路） |
|------|---------------|-------------|
| VST3 | `m_bypassed = bypass;` + `setProcessing(!bypass)` | 同上 **+ `m_component->setActive(!bypass)`** |
| CLAP | `m_bypassed = bypass;` + `stop_processing/start_processing` | `deactivate()` / `activate()`（含全套生命周期） |

### 2.2 问题一：VST3/CLAP 规范禁止与 `process()` 并发

- **VST3 规范**：`IComponent::setActive(false)` 与 `IAudioProcessor::process()` **不得并发**。宿主须在音频线程停止处理后再调用。
- **CLAP 规范**：`clap_plugin_deactivate` 须在 `stop_processing` 之后、且不在处理期间调用。

**实际线程模型（取证）**：

```
音频线程 (RT)                                  控制线程
────────────────────────────────────────      ──────────────────────────
auradsp_process()                                audio_isolate 命令循环
 └ plugin_chain_process_n()                      └ 'pluginSlotSetBypass'
    └ PluginChainComponent::processInterleavedN    └ pb.setBypass(slot, bypass)
       └ m_host->isBypassedSlot(slot)               └ PluginHostManager::setBypassSlot()
       └ instance->process(...)  ← 读 m_bypassed       └ instance->setBypass(bypass)  ← 写 m_bypassed
                                                 └ m_processor->setProcessing(false)
                                                 └ m_component->setActive(false)  ← 与上面并发！
```

进程内模式（默认）下，**控制线程的 `setActive(false)` 与音频线程的 `m_processor->process()` 直接并发**。

**后果**：

- 插件内部状态（延迟线、分析线程、缓冲）在 `process()` 执行中被拆除 → **崩溃/越界风险**（尤其 Ozone 级重插件）；
- 即便不崩，也会出现**一块音频的撕裂**（`process()` 读到 `m_isActive` 已翻转但 `m_processor` 仍在处理）。

### 2.3 问题二：`m_bypassed` 是非原子 bool（数据竞争，UB）

```cpp
// vst3_instance.cpp
bool m_bypassed = false;   // L1545 —— 非原子
// 写：控制线程 setBypass() L1171
m_bypassed = bypass;
// 读：音频线程 process() L1063
if (!m_isActive || !m_processor || m_bypassed) { ... }
```

同一问题存在于 `clap_instance.cpp` L988（`m_bypassed`）与 L987（`m_isActive`），CLAP `process()` L393 读取。

`m_isActive` 亦然：`deactivate()` L361 写、`process()` L393 读。

这是标准 C++ **数据竞争（data race → 未定义行为）**。虽然 x86 上单字节读写实际不会撕裂，但：

- **编译器有权把该值缓存到寄存器**（跨越 `process()` 内的多次分支）→ 旁路切换延迟生效；
- **TSan 会报**；`-O2` 下不可预测；
- 与本仓库既有规范冲突——`PluginHostManager::setBypassSlot` 用的 `std::atomic<bool> bypassed`（L221）、`ProcessPluginProxy::m_bypassed` 用的 `std::atomic<bool>`（L412）**都是原子**。**唯独 VST3/CLAP 实例层这两个是裸 bool**，属实现不一致。

### 2.4 处置建议

**方案 A（推荐，最小且安全）：把真旁路改为「音频线程安全」的两段式。**

1. 控制线程只写**原子**请求标志：`std::atomic<bool> m_bypassRequested`；
2. 音频线程 `process()` **开头**检查该标志，若变化则在**音频线程内**执行 `setProcessing/setActive` 的切换。

这样既达成「停掉插件内部线程」的目的，又完全满足 VST3/CLAP 的线程约束。代价：切换有 1 块（~2.7ms @48k）延迟，用户无感。

**方案 B：把 `setActive` 挪到模块泵线程（`module_pump.h`）。**
仓库已有 `module_pump.h` 机制（VST3 的 `postTaskAndWait`），可在泵线程执行生命周期切换。改动面较大，且需处理与音频线程的握手。

**方案 C：回退到只置标志 + `setProcessing(false)`。**
最安全，但**不解决用户实测的残余卡顿**（Ozone 分析线程不停）——这是本次改造的初衷，等于放弃收益。

**无论选哪方案，必须同步做**：

- `m_bypassed` / `m_isActive` 改为 `std::atomic<bool>`（或统一由一个原子状态位承载）；
- 与 `PluginHostManager::bypassed`（已原子）口径统一。

> **注**：进程外模式**不受影响**——`ProcessPluginProxy::setBypass` 只写原子标志 + 发 IPC，**不触碰插件生命周期**（代理不是 VST3 实例）。故 F-2 **仅影响进程内模式**（默认路径），影响面反而更大。

## 3. F-3（P2）A1 修复后残留：VB 下 `-1` 路落盘仍写 eng[0]

### 3.1 现象

A1 修复把 isolate 的 `group<0` 路径改为「单组 0」语义（不再全组扇出），**杜绝了 load 侧污染**。但**写入侧的对称漏洞仍在**：

```dart
// plugin_manager.dart L577（unloadPlugin）
autoSaveAb(s, group: _editorRoute[s] >= 0 ? _editorRoute[s] : -1);
// plugin_manager.dart L730（onAudioModeSwitching）
autoSaveAb(s, group: -1);
```

VB 模式下 `_editorRoute[s]` 通常为 `-1`（用户未开过编辑器），于是**必然**走 `group:-1` → isolate `pluginSlotSavePresetG` → 新桥 `pb.hasPresetG` 为真 → `pb.savePresetG(slot, 0, path)` → **`vb_plugin_slot_save_preset_g(slot, 0, path)` → `PluginEngineAt(0)` = eng[0]**。

### 3.2 后果链

`_restoreAbAfterLoad`（L1574-1596）的 `routes` 集合**恒含 `-1`**：

```dart
final routes = <int>{-1};                       // ← 恒含 -1
for (var g = 0; g < 8; g++) { /* 仅加入有 meta 的路 */ }
for (final route in routes) {
  final m = _abMetaOf(slot, route, ab);
  if (m['hasState'] != true) continue;
  _commandSender?.call({'cmd': 'pluginSlotLoadPresetG', 'group': route, ...});
  setSlotChannels(ch, slot: slot, group: route);
}
```

即：`-1` 路被恢复时 → isolate `group<0` → 新桥「单组 0」→ **把 `-1` 路（= eng[0] 的快照）写进 eng[0]**。

**净效果**：eng[0] 的状态与 `-1` 路的预设内容互相覆盖，形成**自我强化的循环**——每次挂载/卸载都让 eng[0] 的状态被 `-1` 路快照替换。

**对比正确路径**：VB 各路 `g >= 0` 的预设走 `pluginSlotLoadPresetG` → `pb.loadPresetG(slot, g, path)` → `PluginEngineAt(g)`，**每路独立、互不干扰**。故 F-3 **只污染 route 0**（因为 `-1` 映射到组 0），其余路不受影响——这与 A1 原报告描述的「未编辑路由被 eng[0] 污染」**范围已大幅收窄**（原为全组，现为单组 route 0）。

### 3.3 处置建议

1. **VB 模式下跳过 `-1` 路**（推荐）：`autoSaveAb` / `_restoreAbAfterLoad` 增加「当前是 VB 多总线模式」判断——VB 下 `-1` 不是合法路，**既不落盘也不恢复**。这与 A1 报告的原始建议一致（「`-1` 在 VB 下不再是合法路，两条回落路径都成了语义孤儿」）。
2. **VB 下把 `-1` 映射到「当前编辑路」**：若编辑器正开着某路（`_editorRoute[s] >= 0`），落盘到该路而非 `-1`。但 `unloadPlugin` 场景下编辑器可能已关，语义不稳。
3. **记档不改**：`-1` 路在 VB 下语义冗余但无害（只影响 route 0，且 route 0 自己有独立预设会覆盖）。**不推荐**——「无害」依赖执行顺序，用户可见行为仍不稳定。

> **需产品裁定**：VB 下 `-1` 路是否应存在。既有报告 C6 已记档「VB 下 -1 路预设 = eng[0] 备份（语义冗余）」，本轮 F-3 证明它**不只是冗余，还会实际覆盖 route 0**。

## 4. F-4（P2）宿主进程整体降优先级外溢到 RT 音频处理

### 4.1 变更内容（`13d13a2`）

```cpp
// engine/plugins/host/plugin_host_client.cpp L187-188
if (m_job) AssignProcessToJobObject(m_job, pi.hProcess);
// P2 防抖（2026-10-22）：宿主进程整体 BELOW_NORMAL——插件内部分析线程
// （Ozone 级）与宿主工作线程都不与 RT 音频线程抢 CPU。
SetPriorityClass(pi.hProcess, BELOW_NORMAL_PRIORITY_CLASS);
```

**意图**：让 Ozone 级插件的内部分析线程不与宿主音频线程抢 CPU。

### 4.2 问题

进程外模式下，**引擎的 `auradsp_process` 与插件实例同处一个宿主进程**（`auradsp_plugin_host_main.cpp` 内直接持有 `manager` + 实例）。`SetPriorityClass` 作用于**整个进程**，因此：

- 宿主进程内的**音频处理线程也被降为 BELOW_NORMAL**；
- 该进程内**没有** TIME_CRITICAL 补偿（`SetThreadPriority` 只作用于宿主自己的音频线程；插件实例的 `process()` 若跑在宿主音频线程上，则一并被降级）；
- 与 2026-10-21 轮已确立的「宿主音频线程 MMCSS『Pro Audio』+ TIME_CRITICAL」策略（F-6/E6）**方向相反**——该策略正是为保证宿主音频线程不被抢占。

**后果**：在 CPU 紧张时（Ozone 等重插件 + 多路 VB 总线），宿主音频线程被降级 → **音频卡顿/爆音**，与本次改造想解决的问题同源。

### 4.3 处置建议

1. **保留进程降级 + 提升宿主音频线程优先级**（推荐）：进程 BELOW_NORMAL 后，用 `SetThreadPriority(audioThread, THREAD_PRIORITY_TIME_CRITICAL)` + MMCSS 提升宿主音频线程，**使降级只作用在插件的工作/分析线程上**。这是对既有 E6 策略的兼容叠加，改动小。
2. **只降插件线程，不降整个进程**：改为在插件实例的分析线程上单独降级。但插件内部线程对宿主不可见（黑盒）——此路对 VST3/CLAP **不可行**。
3. **撤回该改动**：若实测残余卡顿的收益不明显，则撤销最省事。

> **需实测裁定**：本项需在真机上对比「有/无 `SetPriorityClass`」两种情形下的 Ozone 旁路期 CPU 占用与音频卡顿率，再定方案。

## 5. F-5（P2）老桥上 A1 缺陷原样存在

### 5.1 现象

```dart
// bridge_plugin_ffi.dart L309
bool get hasPresetG => _savePresetG != null && _loadPresetG != null;
```

`hasPresetG` 要求 **save 与 load 的 `_g` 导出同时存在**。桥的 `_g` 导出是**逐个新增**的（`vb_plugin_slot_save_preset_g` / `load_preset_g` / `set_channels_g`），因此现实中存在**中间态桥 DLL**（只有 save_g 没有 load_g，或只有 set_channels_g）。

在该中间态下：

- `hasPresetG` → **false** → isolate 回落 `pb.savePreset(slot, path)`（eng[0] 单发）与 `pb.loadPreset(slot, path)`（**全组扇出**）→ **A1 缺陷原样存在**；
- `hasSetChannelsG` → **false** → 回落 `pb.setChannels(slot, mask)`（全组扇出）→ **Ch 污染原样存在**。

A1 报告的原始描述是「桥支持 `_g` 导出则走单组 0；老桥保持原回落，行为不变」——该设计**有意保留**了老桥的缺陷。但既有报告 C1 已记档「**老桥 DLL 回落使 per-route 预设/编辑器静默错组**」，说明部署陈旧场景**是真实存在的**（用户机器上的 DLL 可能来自旧构建）。

### 5.2 处置建议

1. **能力探测改为逐项独立**（推荐）：`hasSavePresetG` / `hasLoadPresetG` / `hasSetChannelsG` 三个独立 getter，isolate 按**各自**能力决定走 `_g` 还是回落。这样中间态桥也能获得正确行为（save_g 与 load_g 各自对称）。
2. **桥端版本号**：给 `VmBridge.dll` 加导出版本号，Dart 侧比对，版本过低时**明确提示用户更新**（而非静默错组）。
3. **记档**：若接受「部署陈旧 = 已知限制」，应在用户可见处（插件页）给出提示。

## 6. F-6 ~ F-8（P3）观察组

### F-6（P3）`_routeChannels` 不随会话持久化

- **位置**：`plugin_manager.dart` L315（`_routeChannels` 声明）、`session_memory.dart` L38（持久化取 `getSlotChannels(s)`）。
- **现象**：会话持久化只写 `_slotChannels`（group=-1 口径），**VB 各路的 `_routeChannels[slot][group]` 不入盘**。重启应用后，VB 各路 Ch 记忆回落 `0xFF`。
- **影响**：VB 用户需重启后重新设置各路 Ch。**不影响**音频正确性（引擎侧 Ch 由 `pluginSlotSetChannels` 下发后即生效）。
- **处置建议**：若产品要求「Ch 记忆跨重启」，需把 `_routeChannels` 纳入会话 schema（**注意向后兼容**：旧会话文件无此字段，回落 `0xFF`）。

### F-7（P3）`setSlotChannels` 乐观写入失败不回滚

- **位置**：`plugin_manager.dart` L762-783。
- **现象**：`setSlotChannels` 先写记忆（`_routeChannels` / `_slotChannels`）再发命令；命令失败时记忆**不回滚**（代码注释自陈此设计）。`onPluginSlotChannels` 仅在 `rc == 1` 时写入——但它写的是**同一处**记忆，等于失败路径下记忆停留在乐观值。
- **影响**：引擎拒绝该 Ch 值时，UI 显示的 Ch 与实际生效的 Ch 不一致，直到下次成功回执。
- **对比**：插入阶段有回滚机制（`_pendingStages` + `onPluginSlotInsertStage` 的 `rc != 1` 回滚，L1127-1131）。**Ch 缺同等机制**，属一致性缺口。
- **处置建议**：仿照阶段回滚，为 Ch 加 `_pendingChannels` 乐观值 + 失败回滚。

### F-8（P3）`kVbRouteAll = -2` 成为无语义哨兵

- **位置**：`plugin_manager.dart` L280（注释已订正为「未选择哨兵」）。
- **现象**：v3.3 撤除「全部」后，`kVbRouteAll` 仅作为 `state.vbPluginEditorGroup` 的初值，**不再承载任何语义**。但它仍是文件顶层的公开常量，其它模块若传入 `-2` 给 `setSlotChannels(group: -2)`，会落入 `else` 分支（非 VB 单路口径）——**静默走错路径**。
- **处置建议**：改名为 `kVbRouteUnselected`，或直接删除并用 `-1`/`-2` 字面量表达未选态；同时给 `setSlotChannels` / `getSlotChannels` 的 `group` 参数加**范围断言**（`group >= -1 && group < 8`）。

### 10.4 G-3：11 个 public static 迁为 part 顶层 = 公共 API 破坏性变更（与文档「零 API 变更」冲突）

**事实**：拆分前 `AppModel` 类体持有 11 个 **public static** 成员：

**影响评估**：
- ✅ **当前无实际破坏**——全仓库检索证实：所有引用点均在库内（`state.dart` L578 字段初始化器 + `state_eq.dart` 内部），**无任何外部调用者**；测试侧 37 处 `AppModel.xxx` 已同步改为裸名（3 个测试文件）。
- ⚠️ **但这是契约破坏**：`AppModel.eqGridFor` 等曾是**可被外部模块引用的公开静态 API**，现已不可达。若后续有外部消费者（其他 package、插件、示例代码）依赖该形式，将**编译失败**。
