## S1 持久化根修

- 根因（代码定罪）：启动恢复以 session 快照为权威并覆盖 config，而模式/
  管线/设备/APO 目标/ASIO 参数类 setter 只写 config、session 只随参数
  编辑刷新——纯切模式的会话重启后必被旧快照回滚。
- 修：新增 `AppModel.persistRoutingChange()`（config + scheduleAutoSave
  同刷）；state_audio_modes / state_vb_asio 全部 24 处裸
  `ConfigManager.save(config)` 改走此口；构造期恢复完成后立即对齐保存
  一次（规范化/派生结果落盘，防旧快照后续启动继续回滚）。
- 测试（config_and_presets_test，J6）：round-trip 功能断言（管线输入/
  输出/设备 + APO 目标 + VAIO 输出端点）+ 源码不变量（两文件零裸存、
  关键 setter 体内必有 persistRoutingChange、其定义必含 config 保存 +
  scheduleAutoSave）。
- S6 自审另修该测试一处潜伏缺陷：setter 源码窗口 `substring(i, i+3000)`
  对居聚合源码尾部的 state_vb_asio 四个 setter 越界（RangeError），
  本地以同口径聚合复算发现并夹紧窗口（`df618a48`）——CI 判读之前先行
  修正，属自审战果而非 CI 战果，如实登记。

## S2 WASAPI 失效自愈

- 根因（日志实证）：APO 附加重启端点栈 → 本地 WasapiOut 客户端被
  0x88890004 打死 → 泵通用 400 轮死亡计数触发 wasapiLost → 整条
  audio isolate 重启（APO 发布器陪葬、UI ready 800ms 超时）。
- 修：泵错误按 HRESULT 分流——WasapiOut 且文案含 0x88890004 时进恢
  复窗口（30s）：按退避表（0.5/1/2/4s）经捕获控制器既有回滚链
  （`WindowsCaptureController.reinitOutput`：目标端点 → 组建前锚点
  → 默认端点）原地重建输出；窗口内错误被吸收（不落 PUMP ERROR、
  不发 error 事件、不计死亡计数）；超窗回落既有 400 轮语义。非
  INVALIDATED 错误口径不变（不回退细审 R-B 2）。状态层 wasapiLost
  的 isolate 重启条件收窄：sysapo 与 vbcallback/asio 同列忽略（附
  加模式下本地输出无职责）。
- 口径纯函数（分类/退避/窗口）独立成 `out_recovery.dart` + 单测
  （out_recovery_test，J6）。

## S3 APO 就绪三态 + telemetry v4

- 背景机制：TryStart 先 ClaimSeat（建 telemetry）后 LoadEngine、参数
  块在引擎创建后才建——加载失败的旧指纹（心跳活/座位空/参数块缺席）
  与面板口径（心跳即报「活跃处理中」）叠加成项 7 的误导显示。
- 宿主侧：LoadEngine/TryStart 全失败出口记诊断（阶段码：1 自目录失
  败 / 2 三候选加载失败（err=首候选 GetLastError）/ 3 ABI 或符号不
  符 / 4 create 失败 / 5 就绪），telemetry 升 **v4**（736 起追加
  loadStage/loadErr，块总 744B；ApoShared.h static_assert、Dart 镜像
  常量、布局门三方同步）。J5b apo_engine_test 增断言：起链成功后
  version>=4 且 loadStage=READY。
- App 侧：读者解析 v4 并入 apotelemetry 事件（stage 变化即发 + 落
  dbgLog）；面板引擎状态行四级口径：故障 > 加载失败（附
  `[stage=N err=M]` 原始码）> 处理中 > 等待；原心跳芯片文案由
  「活跃处理中」改述为「心跳活跃」（setApoHeartbeat，三语）——心跳
  不再冒充处理状态。
- **项 7 首要嫌疑复盘改判（S6 复核 r2 日志）**：telemetry 读者对块缺
  席全程静默，但块若存在且 seat 空，首个成功 tick 必落
  `apo telemetry: seat=free`（_lastSeat 初值 −1）；r2 两段会话均无此
  行、参数块缺席行却两现 ⇒ telemetry 块从未存在 ⇒ **装机
  AuraApo.dll 疑为真处理之前的 v1 透传版（只有心跳）**，LoadEngine
  失败降为次席（其口径下块会被 ClaimSeat 先建）。装机侧动作见真机
  验收清单第 2 项。读者另补「块缺席 5s 一次性落盘行」，下次一瞥分清。

## S4 取证埋点（不定罪、不猜修）

- VAIO 桥：每次 start 采集一次首块证据并入 status 的 `forensics` 对
  象——起始 TotalBytesWritten/消费指针/环尺寸/对齐、首块采样几何、
  前 16 原始字节 hex、正位转换统计（peak/meanAbs）与**错位一字节重
  释统计**（仅 PCM16）。isolate 首见落 `vaio-forensics:` 一行。判读：
  正位噪而错位呈音乐形态 ⇒ 读游标错位定罪；双口径皆噪 ⇒ 环内容
  本身已噪（源侧/写入侧）；双口径皆净而听感噪 ⇒ 嫌疑移出环读取段。
- ASIO：`AsioHost::open` 在 loadAsioDriver 前加纯注册表预查（无
  COM/SDK 副作用）：失败 why 分步——在册仍失败 = `COM step`（附
  CLSID），不在册 = `registry step`。isolate 既有 note 通道落盘。
- CI 覆盖（执行偏差登记）：计划原拟 J5b 全味构建两桥——runner 无
  Steinberg ASIO SDK、全量配置 FATAL，不可达。改为新增
  `core/desktop/windows-drivers/ci_check` 小工程：真实 MSVC 编译
  VAIO 桥 TU + 运行 vaio_pump_wait_test。**ASIO 桥 TU 仍无 CI 编
  译覆盖**（SDK 许可不入仓），其编译仲裁为用户本机全量构建；取证
  面由源码契约门 `smoke_round5_forensics`（runner 双登记）钉住。
- S6 附带加固：VAIO status 的 Dart 侧缓冲 4096→8192（forensics 增
  容后防长路径布局顶格丢整份 status）。

## S6 重审查结论（六面）

1. **双存储一致性**：全量枚举 lib/core/state* 的 config 字段突变点
   ——两模式文件外仅四处（channelsCount/Mode 经 setInt 必走
   scheduleAutoSave；visualizerConfig 自带 scheduleAutoSave；构造期
   归一化由 S1 对齐保存覆盖；dispose 双保存）。**无新增泄漏**。
2. **泵错误分类学**：S2 分流与 400 轮计数相互作用已推演（交替错误
   下非 INVALIDATED 异常仍可独立累计触发 latch；窗口内吸收不产
   生 busy-spin，循环顶延迟照常）。捕获链在场时重建经控制器缝换
   入、捕获源不受影响。**无缺陷发现**。
3. **桥 start/stop 记账**：asio_stop 的 stop→close→
   release_active_driver→DestroyEngine 链完整；start 各失败出口
   （−2…−7）均 DestroyEngine，host 侧由 open 的幂等 close 自愈。
   rc=−2 二次失败的剩余嫌疑收敛为 SDK 单例在 release 后的内部状
   态 / enumerate 的 CoUninitialize 扰动——S4 分步口径回证后定修，
   本轮**只登记不猜修**。
4. **APO TryStart 全失败路径**：ClaimSeat/OpenParams 降级口径与设
   计一致；PublishLoadDiag 只在抢座成功后写（败者不污染胜者诊
   断）；v3/v4 双向版本兼容核对通过（尾追加 + 读者版本门）。
   worker 线程创建失败时 loadStage 留 READY——seat 为主信号，面
   板口径不受影响，**登记为可接受**。
5. **安装链完整性**：pack.py 的 stage_driver_files 把
   auradsp_engine_apo.dll 与 AuraApo.dll 同级落入 driver/（四模式
   同口径，注释明示 D1 首选位）。**打包无缺陷**；项 7 的装机旧件
   属用户侧重装范畴。
6. **常规面**：本地 smoke 24 PASS / 0 FAIL（含新门）；D4-b 门 31
   项过；l10n 新键三语齐备且 gen 已同步；telemetry 布局三方钉死。

**观察项（交用户裁定，本轮未动）**：LoadEngine 第三候选（上一级目录
的主引擎 auradsp_engine.dll）在装机布局下真实存在（App 根目录）——
纪律版 DLL 缺失时 APO 会退而加载**非纪律版主引擎**（/MD、无
/guard:cf）进 audiodg，与 P0 的 APO 风味纪律相悖；该三候选序为
P0 设计明文（开发布局便利），本轮不擅改。若裁定收紧，建议只保留
候选 1/2 或给候选 3 加「装机布局禁用」判据，另起一阶执行。

## 真机验收清单（用户侧）

1. **持久化**：切输入 VAIO / 输出 VAIO / 选 APO 目标端点后重启
   App——三者应原样恢复（S1）。
2. **APO 装机核对**（项 7）：看安装目录 `driver\` 下 AuraApo.dll 与
   auradsp_engine_apo.dll 的**文件日期**；若为旧件，用当前构建重装
   后复测附加——面板状态行应显示「APO 引擎处理中」、电平/频谱应
   动；若显示「引擎加载失败 [stage=… err=…]」，把该行原文回我。
3. **附加稳定性**：sysapo 下反复附加/分离，观察是否还有 isolate
   重启（iso 日志整段重开）与 WasapiOut 相关 PUMP ERROR（S2）。
4. **白噪复现取证**：VAIO 输入再现白噪时，保留当次 iso 日志——
   `vaio-forensics:` 行随日志回传即可定罪/脱罪（S4）。
5. **ASIO 二次启动**：若再现启动失败，asiomode 的 note 应带
   `COM step` 或 `registry step` 字样，原样回我（S4）。
6. **刷新闪退**：若再现，UI 日志尾看 `vaiodetect: ui handled` 与
   `vaiodetect: frame settled` 两行的存缺，并取事件查看器的故障
   模块名（两轮未取，本轮再提醒）（S5）。
