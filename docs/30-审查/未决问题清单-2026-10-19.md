### B2. 8 个孤儿 spec + comp 14 个动态 spec 未挂 section

- **代码位置**：
  - 孤儿清单：`app/auradsp_app/test/param_contract_test.dart` L278-284 `kOrphanStaticSpecIds`（Part E 精确差集断言）；spec 定义本体在 `lib/core/param_schema.dart` L499-563（stereo 族）与 L1200-1215（comp.threshold/ratio）。
  - comp 动态 spec：`lib/core/param_schema.dart` L1216-1236 —— `compFreqs`/`compGains` 由 `List.generate(7, ...)` 工厂生成 14 个 spec（comp.freq1..7、comp.gain1..7）；comp section 定义在 L1690-1694，**只挂了 6 个 spec**（timeconstant/granularity/tfresolution/autogain/outputgain/enable），14 个动态 spec 全部不在其中。
- **影响原因**：
  - 8 个孤儿 spec 不在 registry.allParams → 不进 spec 驱动的预设/会话路径，UI 若改走 registry 消费会突然摸空。
  - comp 的 14 个动态 spec 更特殊：`List.generate` 不产生字面 `id:`，**静态解析器连它们存在都解析不到**——Part E 门禁对它们是绝对盲区，这正是门禁"源码解析"路线的已知局限。
- **建议处置**：stereo.band.1..5 与 B3 一并决策（挂 section 需先统一键名）；bass_shaping.enable 与 shelf.enable 二选一删一个；comp.ratio 引擎无此参应删 spec 或标 neverSend；comp.freq/gain 14 个决定注册或显式豁免，并在门禁注释里写明"List.generate 盲区"的原因。
- **处置（2026-10-19，B1 批，✅ 主体已解决）**：
  - stereo.band.1..5 → 统一 `stereo.band1..5` 并挂进 stereo section（见 B3）；`bass_shaping.enable` → **删除**（假参数，开关由卡直接驱动 `setBassShapingEnabled`）。
  - comp.freq/gain 14 动态 spec → `List.generate` 改写为**显式字面量 id 静态 spec**（消除解析器盲区）并注册进 comp section，**真实驱动引擎**（引擎表 comp.freq1..7/gain1..7 一一对应）；fixture 重生成。
  - comp.ratio / comp.threshold → **保留 UI + 保留孤儿登记**（压缩卡核心滑块 + 传递曲线可视化依赖；引擎 FFTCompander 无宏观语义），**登记"待引擎补充"排期**（方案文档 §2.2：外围"阈值输入偏移 + 比率增益标度"宏控映射，需 vendor 语义验证 + 听感校准）。
  - 契约同步：`kOrphanStaticSpecIds` 删 6 条（stereo×5 + bass_shaping）、`kEngineOnlyIds` 删 19 条（stereo×5 + comp 14）、`kKnownMemberConflicts` 登记 `comp_freq`（数组成员多槽位默认，设计预期）。param_contract 21/21 绿。

### B3. stereo band 键名分裂：`stereo.band.1` vs `stereo.band1`（潜伏高危）

- **代码位置**（同一条物理参数、两种字符串 id）：
  - spec 层（带中间点）：`lib/core/param_schema.dart` L521-560 —— `stereoBand1..5` 的 id 是 `stereo.band.1`…`stereo.band.5`（key 为 band0..band4）。
  - 引擎/镜像/直发层（无点）：`lib/core/state.dart` L2290 `_mirror` 正则 `r'^stereo\.band([1-5])$'`（无点，L2288 有防呆注释解释此正则的历史坑）；L2032、L2440 直发 id `'stereo.band${i+1}'`（无点）。
- **影响原因**：当前因 band spec 是孤儿（B2，未挂 section、不在 registry）而**未实际相撞**。但只要按 B2 把它们挂进 registry，`getParamById('stereo.band.1')`（spec 键）与引擎回读/镜像键 `stereo.band1` 将对不上号——预设写入用带点 id 落 `_paramValues`，镜像与直发用无点 id，两套键位永久分裂，届时会复现一类"值写了却不生效/回读对不上"的隐形缺陷。
- **建议处置**：统一为无点 `stereo.band1..5`（与引擎表、`_mirror` 正则、直发 id 三处既有约定一致），只改 spec id 一侧；反向全改（镜像+直发+引擎）代价大且引擎已对外，不推荐。**此项应排 B 组第一优先。**
- **处置（2026-10-19，B1 批）**：✅ **已解决**——spec id 统一为 `stereo.band1..5`（5 条），挂进 stereo section（`specs: [...stereoBands]`），孤儿/引擎白名单同步，旧预设经 `customSnapshot['bands']` 兼容（双轨并存，apply 以 bands 为准）。param_contract 21/21 绿。

### B4. stereo 分带值无引擎回读对账

- **处置（2026-10-19，B2 批）**：✅ **已解决**——回读已有 `stereoBands` 列表写回，缺口是**逆换算**（下发 `(band*mix*2).clamp(0,1)*widen*k`，回读直写 raw 无还原）。已在 `case 'params'` 分支补逆换算（`norm=eff/widen` → `band=norm/(mix*2)`）并带 `stereoOn && stereoMix>0` 守卫（关闭/静音态保留 UI 记忆）；对账作为设计规范 **D-2** 写入开发规范 §8。

- **代码位置**：回读处理 `case 'params'`（`lib/core/state.dart` L1290 起）——对账了 `stereoMix`（L1308 附近，带 `stereoOn` 守卫，10-19 修复点）与 `stereoBandUsed`（L1351 附近），**唯独不回读 stereoBands[0..4]**。
- **影响原因**：`_pushStereoChain`（L2422-2447）下发分带时做了 `(stereoBands[i] * stereoMix * 2.0).clamp(0.0, 1.0) * stereoWidenMax * k` 换算，引擎侧实际生效值经钳位/换算后可能与 UI 滑块记忆出现单向漂移；且任何引擎侧的分带值变化（拒收回退、外部写入）UI 不可见。与 stereo.mix 已有的 roundtrip 对账不对称。
- **建议处置**：仿 stereo.mix 的对账写法，在回读处理补 stereoBand0..4（引擎 raw 键，注意换算回 UI 刻度）映射回 `stereoBands[]`，同样带 `stereoOn` 守卫；并补 ui_stereo_restore_test 对应用例。

### E10. ✅ P0：进程模式宿主侧 scratch 从未分配 → processSlotInterleaved 静默直通 —— 已修复（2026-10-21，R-1）

- **现象**：进程模式（`AURA_PLUGIN_HOST_MODE=process`）宿主侧插件完全不生效——引擎收到宿主对输入的原样回声（近似单位增益、零插件延迟）。观测量：`0.988553@帧0`（代理预热直通）+ `0.988553@帧256`（宿主回声）；`remoteFailed=false`、环零溢出、load 成功且上报 latency=416=288+128——**故障全程静默**。进程内模式始终正确（`0.600000@帧288`）。
- **根因链**：宿主 scratch 的唯一分配入口是 `PluginHostManager::updateFormat` 内的 `ensureChannelScratch`，而宿主只在收到 `Op::UpdateFormat` 时执行它。`PluginHostClient::start()` 只置 `m_processMode`——宿主**懒启动于首个客户端请求**（`request()` → `ensureHostLocked`）。引擎 create 期的 `updateFormat` 转发被 `alive()` 守卫跳过（宿主未启动）；`loadPluginSlot` 远程分支只发 `SetChannelHint` + `Op::Load`；代理 `activate()`（唯一另一处会发 UpdateFormat 的路径）在该分支不被调用；宿主 `Op::Load` 处理器只手动赋值 `m_sampleRate/m_maxBlockSize`，**不调 `ensureChannelScratch`**。→ 宿主 scratch 永远为零 → `processSlotInterleaved` L400-403 入口守卫直接 return → 音频线程写回输入 = unity 回声。
- **表症归零**：「0.988553 基线增益」实为限幅器把 1.0 钳到 -0.1dBFS 门限（`limiter_threshold{-0.1f}` = 0.988553）；「-256 帧位移」实为探针索引假象（`nz` 未加块偏移）——进程内路径本来就是对的。
- **修复（两处互为兜底）**：
  1. 宿主 `Op::Load` 处理器（`auradsp_plugin_host_main.cpp`）：手动赋值格式改为 `manager.updateFormat(sampleRate, maxBlock)`——宿主构建含 `AURADSP_HOST_INPROC=1`，走本地分支完成 `ensureChannelScratch`，任何加载路径 scratch 必然就绪；
  2. 引擎 `loadPluginSlot` 远程分支（`plugin_host_manager.cpp`）：代理 load 成功后补发 `m_remoteClient->updateFormat(...)`——覆盖 create 后格式变更场景。
- **红→绿实证**：修复前远程 = unity 回声（0.988553@0/@256）；修复后远程 = **0.593867@544**（= 插件 0.6 增益 × 限幅器对帧 0 预热脉冲的 release 残压 0.98978；544 = 288+256 实测管线，同时量化确认 E7）。进程内两种块大小均 0.600000@288 无变化（回归通过）。冒烟测试 `smoke_plugin_host_process.py` 8/8 节全绿。
- **遗留观察**（建议入后续轮次）：① 遥测盲区——远程模式引擎侧 `processCalls=0`（代理路径不递增），建议 status 合并宿主侧计数（`Op::GetStatus` 已存在）；② 代理预热直通与插件输出叠加致脉冲双发（帧 0 与 544），属 E7 同族时序设计问题。
