## 2. 分维度结论

### D-a 正确性 ✅（修复 P1-1/P1-2 后）

- PE 解析保守策略正确：截断 DOS 头（<64 字节置 failbit）、坏 e_lfanew、坏 PE 签名、
  非 PE 文本——一律按 64 位且不崩溃，与 `peMachineType` 注释一致。
- ARM64（0xAA64）判 64 位正确；双架构 bundle 只报 x86_64-win 一条正确。
- **P1-1**：`resolveBundleBinary` 对 bundle 内二进制扩展名做严格小写比较，
  `Upper.VST3` 这类大写内层文件匹配失败 → 整包静默消失，违反 D 类契约"不消失"。
  Windows 文件系统不区分大小写，`scan()` 入口有 `::tolower` 归一化而内层探测没有——
  归一化断层。**已修**（见 §3）。
- **P1-2**：`extractVendorFromPath` 的剥离循环同样严格比较，大写 bundle 目录
  （`Foo.VST3/Contents/x86_64-win/Foo.vst3`）走剥不到 bundle 层，vendor 退化为
  bundle 目录名。**已修**（同函数）。

### D-b 线程与生命周期 ✅

- `m_editorTitle` 写于 `std::thread` 创建之前、读于线程入口，happens-before 关系
  完整（CLAP/VST3 两侧成员声明处的注释与代码事实一致）。
- 编辑器线程不触碰插件 GUI API（仅 PostMessage 投递），`closeEditor` 与
  `showEditor` 交叉路径有锁保护，无 join 自等。
- P3-1（登记）：`m_editorTitle = title` 位于"编辑器已开→前台化"早返回分支之前，
  该分支赋值无意义但无竞争，仅语义不紧。

### D-c 资源与错误处理 ✅

- 32 位早分支不 LoadLibrary，无句柄可漏；`fill32BitIncompatible` 纯内存构造。
- 每个新 return 路径（`queryMetadata` 早分支、`makeQuickMeta`）无双释；
  异常路径 `catch (...)` 守卫与文件系统迭代异常处理在位。

### D-d 一致性契约 ✅（修复 P2-1 后）

- 扫描/加载逐字段比对 68 插件 0 分歧；32 位两路文案逐字相同（同一字符串常量）。
- **P2-1**：`applyVstAudioEffectClass` 末端缺 `vendor→"Unknown"`/`version→"1.0"`
  兜底——工厂、PE 版本资源、目录、签名全链落空时产出**空串**，而
  `applyClapDescriptor`/`fill32BitIncompatible`/`makeQuickMeta` 三处都有占位。
  本机 76 插件未触发（vendor 卫生 smoke 可兜底捕获），属结构性裂缝。**已修**。

### D-e 测试覆盖 ✅（修复 P1-3/P2-2 后）

- 失败注入 1：`peIs64Bit` 恒 false → `smoke_plugin_arch_detect` 6 项变红，证明
  位数判定测试非空转；已还原重建。
- 失败注入 2：旁路 schema 门禁 → 15/15 仍全绿，**证明两个缓存丢弃测试空转**（P1-3）。
- **P1-3**：'loadCache 丢弃旧版裸 list' / '丢弃被篡改 schema' 两条测试的条目路径
  是磁盘上不存在的 `C:\VST3\...`——门禁被旁路时条目被 `_dropMissingPaths` 清掉，
  测试照样绿。改用 tempDir 下真实 stub 文件后重新注入：schema 测试按预期变红
  （`Actual: [Instance of 'PluginMetadata']`），门禁机制被真正钉住。
- **P2-2**：门禁自身曾被瞬态污染——`saveCache` 是 fire-and-forget，轮询在文件
  **open 时刻**即返回（早于 flush/close），测试同步读完立即递归删除 →
  Windows errno 32（"另一个程序正在使用此文件"），复现率约 1/3。
  机制在新旧两版测试中都存在，加固版额外的磁盘 I/O 放大了触发概率。
  **已修**：tearDown 有限重试（40×50ms）+ 读缓存前 200ms 沉降。修复后单文件 5/5、
  全量 3 连绿。
