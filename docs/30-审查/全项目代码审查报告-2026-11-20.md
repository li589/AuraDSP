## 3. 新发现

### AUD-01：进程外插件加载 preset 后 PDC 延迟状态不一致

**严重度：P1（功能正确性 / 延迟补偿）**  
**位置：** `engine/plugins/platform/win32/host/process_plugin_proxy.cpp:550`，配合 `:369-377`；消费者为 `engine/plugins/driver/plugin_host_manager.cpp:468-479` 和 `engine/plugins/driver/plugin_chain_component.cpp:101-108`。

`ProcessPluginProxy::loadPreset()` 成功后重新向宿主查询插件延迟，但只执行：

```cpp
m_latency.store(latency + ipc::kTransportFrames,
                std::memory_order_release);
```

与 E15 v2 的正常处理路径不同，未写入 `m_pluginLatency`，并固定只加一个 128 帧传输块。正常音频路径计算为：

```cpp
m_pluginLatency + chunks * ipc::kTransportFrames
```

其中 `chunks = ceil(numFrames / 128)`，且只有 `chunks != m_targetInFlight` 时才更新 `m_latency`。因此：

- 若设备当前回调包含多个传输块，preset 成功后公开的 PDC 延迟会暂时或持续少报传输部分；
- 即使下一次音频回调继续使用相同块数，重算分支不会执行，固定 128 帧值可能持续保留；
- 若之后块数发生变化，音频路径会用旧 `m_pluginLatency` 重新计算，可能覆盖新 preset 的实际插件延迟。

该值不是仅供 UI 显示：`getLatencySlot()` 对进程外实例直接返回实例实时 `getLatency()`，插件链 PDC 随后把它传入 `setDelay()`。因此属于真实补偿路径。

**历史去重：** 旧 E15、E15 v2 的传输深度问题已关闭。历史验证证明常规处理按块深计算，在 128/256/512/1024 帧下延迟分别为 416/544/800/1312，误差为 0。AUD-01 不重复登记已关闭的“常规动态流水深”问题；它针对 preset 改变插件延迟时，preset 路径未同步更新 E15 v2 的分层状态。历史记录未见对该状态转换的明确覆盖。

**证据等级：** 静态控制流证据充分；没有在本次审查中运行可变延迟插件，尚未量出 preset 后的实际 PDC 错位时长。建议以可设定插件延迟的测试插件，在 128/256/512/1024 帧回调下先稳定运行，再加载改变延迟的 preset；读取 `getLatencySlot()`、`transportLatency()` 与脉冲旁路对齐结果，并覆盖同块数连续回调和块数切换两种情况。

### AUD-02：`--clean-work` 可递归删除任意指定目录

**严重度：P1（潜在数据丢失；需显式组合参数触发）**  
**位置：** `installer/release.py:111-112`、`:149-152`、`:223-227`。

`--work-dir` 由用户传入后直接用作中间目录。若同时提供 `--clean-work`，发布完成后调用 `shutil.rmtree(work_dir, ignore_errors=True)`。实现没有把路径解析/规范化后与仓库内专用工作区、`out-root` 下约定目录比较，也没有拒绝仓库根、交付目录、文件系统根目录或其他非预期目标。

正常默认值为 `<out-root>/.release-rNN`，但显式参数可以覆盖。此项是命令组合导致的高影响风险，不表示默认发布流程会删除任意目录。审查期间没有传入危险路径或执行删除。

**建议验证/修复方向：** 清理前解析真实路径并强制限制在专用发布临时目录之下；拒绝仓库根、`out-root`、`deliver-r*`、文件系统根和包含符号链接逃逸的路径；增加纯临时目录单测覆盖合法清理、越界拒绝、符号链接及路径别名。失败时应停止并明确报错，不应静默忽略。
