## W4 宾机 0x7A 蓝屏专案 — 取证与结论

### 证据

4. **guest 存储构成**：单块 VMware Virtual NVMe 盘（60 GB，guest 内报 Healthy）；页面文件仅 `C:\pagefile.sys`（自动管理，本次启动后 alloc 1280 MB、peak 0）；0x7A param1=1 即失败页来自页面文件。
5. **系统盘运行于快照增量盘**：宿主机 .vmx 指向 `Windows 10 x64-000001.vmdk`，基盘与 Snapshot2 均为 **2026-10-16**；增量盘 16 个 extent、当晚 21:59 仍在写入。即该 guest 近一个月所有 I/O 都经快照增量层。

7. **同晚文件写入丢失多次实证**：诊断脚本副本与多份结果文件在 guest 内读回全零字节（写入未落盘），与读入失败同属该存储路径的间歇性 I/O 异常。

### 结论（分级）

- **定罪层级：该 guest 的虚拟存储路径（VMware 快照增量盘 + NVMe 呈现）在 I/O burst 下间歇性失败**（证据 1/3/5/7）。未能进一步区分是 VMware 层、增量盘文件还是宿主机盘/文件系统——宿主机盘面健康报告与日志均无异常（证据 6），到此为止。
- **明确排除 AuraDSP 任何组件**：VAIO 驱动为 WaveRT 音频驱动、不在存储栈；六次触发场景（探针启动 ×4、APO 卸载/切模式 ×2）无共同软件因子，共同因子只有 I/O burst。APO 卸载路径的产品代码无错误证据。
- **「内存压力」解释正式撤销**：8 GB 下仍复现（22:09、23:18、23:19），内存量至多影响触发概率，不是根源。
- **处置**：该 guest 就此**退役于存储敏感类验证**（APO 附加/卸载、驱动装卸、切模式），冻结令继续有效；根治选项（用户资产，待用户裁定）：删除/合并快照使系统盘回到基盘，或新建无快照 VM。在此之前，该 guest 内的任何验证结论须对结果文件做内容校验（全零判无效）。

## W1 矩阵下混规格核对 — 结论：与实测全符，判设计如此

引擎多声道架构为 ADR-003 两期制（代码实证：`engine/chain/engine_chain.cpp` mx_downmix/mx_upmix、`engine/auradsp_engine.cpp` 模式分发、`engine/chain/speaker_layout.h`）：

- **声道序**：引擎布局固定 FL FR C LFE SL SR [BL BR]（6ch 的环绕位是 SL/SR；8ch 追加 BL/BR）。4ch Quad 为 FL FR BL BR（桥侧 `BusChForSlot` 有对应换位）。
- **矩阵模式（channels.mode=0，Phase A）**：引擎外层 M→2 下混后走立体声 DSP 链，再 2→M 上混回写：
  - 下混：`L = FL + 0.7071·C + 0.7071·SL + 0.7071·BL`，`R = FR + 0.7071·C + 0.7071·SR + 0.7071·BR`；**LFE 直通、完全不进 DSP**。
  - 上混：FL/FR 写处理后 L/R；**C = (L+R)·0.5·0.7071（由处理后立体声派生，非原始 C）**；SL/BL = L·0.7071，SR/BR = R·0.7071（同为派生）；LFE 原样还原。上混回填默认受源活动门控（`channels.upmix_fill=0`：源声道本块非零或 250 ms 保持窗内才回填，否则写 0）。
  - 产品语义（ADR-003 已载明）：矩阵模式下 C/环绕在输出端是「处理后立体声的派生声像」，不保留原始独立内容；立体声增强/Crossfeed 对 C/环绕的作用是间接的（经矩阵）。
- **离散模式（channels.mode=1，Phase B）**：`process_multichannel_chain` 逐声道独立处理，无折叠、无派生。
- **双耳模式**（spatial binaural 生效且 ≥4ch）：6/8ch 先双耳化为立体声再走全链，其余声道置零（物理立体声端点语义）。
- **与用户实测对照（P1/P2）**：矩阵下 C 亮且 FL/FR 同亮、SL→SL+FL、SR→SR+FR、BL→BL+FL、BR→BR+FR、LFE 独立直通——逐项与上表相符；离散全声道独立正常。二者均为**设计如此**，无系数错误，无代码变更。

## W2 VB 桥代码审读 — 未见声道截断缺陷；P3 头号嫌疑为 VB 总线声道模式

审读对象：`core/desktop/windows-drivers/bridge/vm_bridge/VmBridge.cpp` + `core/desktop/windows-drivers/02_voicemeeter_client/VmPumpCore.h`。

- **架构**：VmBridge 注册 Voicemeeter OUTPUT INSERT 回调（master 前）；回调缓冲按**组**组织——每条输出总线占 8 个槽（组 g = 槽 [8g, 8g+8)，组内序固定 7.1 FL FR C LFE SL SR BL BR），每组一个独立引擎实例。组内 base+2..base+7 先透传拷贝，主对与第 2..procCh-1 路经引擎处理后回写（`ProcessGroupVm` 多声道分支逐路 gather/scatter，无 2/4 声道截断）。
- **procCh 来源**：`vb_set_param("channels.count")` → `ApplyWorkChannels` 归一（4/6/8 合法、余按 2）→ 全部组引擎与泵影子同步——通路完整。
- **审读结论**：桥与泵代码内**未发现**会单独吞掉 5–8 声道的缺陷。结合用户拓扑（App 启用 A1/A2 两组、VB 路由 A1/A2/B3、B3 全程正常），头号嫌疑是 **VB 侧 A1/A2 总线的声道模式为立体声**（Voicemeeter 每条总线有独立声道模式；总线为立体声模式时，插入点槽 2–7 本就无源信号，引擎与 App 电平自然皆空，齐鸣段用户所见「都亮」可能来自输入条/B3）——此为推断，须受控复测证伪/证实。
- **用户侧复测协议**（随新发行包执行，约 5 分钟）：① 在 VB 中把 A1、A2 总线声道模式设为 7.1（或改用已确认多声道的总线）；② App VB 模式、离散、播 7.1 测试文件，逐声道段观察 App 内 chLevels 与 VB 回送条；③ 若环绕仍无电平 → 以「拓扑混杂已排除」为前提按桥缺陷重开 W2，并附当次桥状态 JSON；④ 矩阵模式同法复测一遍（预期：环绕以派生声像出现在对应槽，系数 0.7071，电平低于源约 3 dB 起）。
- **ASIO 附带审读**：`bridge/asio_bridge/AsioBridge.cpp` 的 ioCh 在 start 时按驱动 caps（inChannels/outChannels 与 outPair 余量）协商，引擎 `channels.count` 与 ioCh 等宽（代码注释明示），状态 JSON 带 `ioCh/inCh/outCh`；viz 帧经 `bridge_manager.vizRead` 与其它桥同形上报 chLevels/stageCh——**数据通路完整**。用户实测 ASIO 电平不扩展的判读键就是 ioCh：若当次 ioCh=2（宿主只开 2 声道），立体声电平即正确行为；复测时请回告桥状态中的 ioCh 值。
