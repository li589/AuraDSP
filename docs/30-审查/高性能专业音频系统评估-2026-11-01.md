# AuraDSP 高性能专业音频系统评估（2026-11-01）

> 范围：`engine/`（C++20 DSP/链）、`app/auradsp_app` 出厂预设资产、Windows Release DLL。
> 被测产物：`core/desktop/windows/out/Release/auradsp_engine.dll`，版本 **1.1.0**，ABI **2**。
> 方法：ctypes 直调 Release DLL + 稳态正弦频响 / 脉冲 RT60 / THD+N / 噪声底 /
> 限幅余量 / 采样率矩阵 / 6 声道离散与矩阵 / 逐块 CPU 计时。
> 测量脚本：[`tools/probe/audio_quality_eval.py`](../../tools/probe/audio_quality_eval.py)；
> 原始数据：`build/audio_quality_eval.json`（不入库）。
> 基线提交：`2f814a1`（工作区干净；本轮修复见 §9）。

## 1. 结论摘要

1. **透明基线达标**：全效果关闭时 20 Hz–20 kHz 频响 0.00 dB、THD < -150 dB、
   0 dBFS 输入输出 0.00 dBFS（限幅开 -0.10 dBFS）、报告延迟 0 ms、单块 CPU
   p50 20.4 µs / p99 80.7 µs（0.35% 单核，48 kHz/480 帧）。
2. **出厂预设 6 套全部存在“参数与实测不一致”**：两套混响预设的
   `decay/damp/wet/roomSize/width` 在 `reverb.preset >= 0` 时根本不生效，
   界面显示的数值是死的；实测 RT60 与标注值不符，并在 400/630 Hz 产生
   -9 ~ -13 dB 的梳状深坑。
3. **低频余量与调音严重超标**：5 套非空预设把 0 dBFS 输入的 40–100 Hz
   推到 **+12 ~ +23 dBFS**（限幅器承担 12–23 dB 增益衰减）；
   V-Shape / Rock / Symphonic 的 0 dBFS 白噪声 RMS 也达到 +1.5 ~ +3.0 dBFS。
   这不是“安全余量”，而是靠限幅器硬压，播放低频密集素材会产生抽吸/互调。
4. **同一预设在不同采样率下音色漂移**：V-Shape 在 10 kHz 的实测响应
   44.1k/48k/96k/192k = +5.9 / +7.0 / +8.0 / +8.3 dB；20 kHz 从 -8.35 到
   +0.72 dB（差 9 dB）。Pop Vocal 在 10 kHz 从 -3.34 到 +6.11 dB（差 9.5 dB）。
5. **立体声路径存在双限幅器串联**（已在本轮修复）：vendor `stage_output`
   的 legacy limiter 与链尾 `limiter_process_mc` 同时工作；Pop Vocal 实测
   限幅前 +5.99 dBFS、输出 -0.10 dBFS，但 `gr.limiter` 只报 0.12 dB。
   修复后同一工况 GR 报 5.41 dB，计量恢复真实。
6. **延迟上报漏计低音模块 4.0 ms**（已在本轮修复）：44.1/48/96/192k 实测
   onset 均 4.0 ms，修复前 `auradsp_get_latency_ms()` 对 V-Shape/Rock/Vintage
   报 0 ms；修复后报 4.0 ms，带混响的 Pop/Symphonic 报 34.0 ms（4+30）。
7. **立体声与离散多声道使用两套电子管算法**：立体声走 vendor 六频带
   `VacuumTubeProcess`，离散多声道走 `tube_process_mc` 记忆less waveshaper；
   `tube.oversample` 只影响后者。同一 `tube.gain` 在两模式下的频响/失真不同。
8. **CPU/内存/实时余量仍充足**：最重预设 Pop Vocal 单块 p99 646 µs
   （6.5% 单核，含 Python 调用开销）；全链基准 2026-10-30 为 p50 619 µs /
   p99 863 µs / 6.41%，无 xrun。内存基线见 2026-10-31 专项 ~1.0 GB。

**总评**：引擎透明链路与实时性达到专业级；**预设层尚未达到“以数据说话”的
专业交付标准**——存在参数失效、低频过载、声部梳状、跨采样率漂移与电平
不一致。建议按 §6 的 P0/P1 清单先修数据与链路，再按 §7 目标重调六套预设。

## 2. 测量方法

| 项目 | 方法 | 条件 |
|---|---|---|
| 频响 | 稳态正弦逐点法：每个 1/3 倍频程中心频率注入 -24 dBFS 正弦，预热 0.5 s，取 2.0 s 基波 bin | 48 kHz/480 帧；2 s 保证 0.5 Hz 分辨率，所有网格点为整 bin，消除栅栏效应 |
| 脉冲/RT60 | 0.05 幅度单位脉冲，2.5 s 捕获，跳过前 50 ms 直达/早期反射，Schroeder 反向能量 -5/-25 dB 斜率 ×3 | 同上 |
| THD/THD+N | -12 dBFS 正弦，预热 1 s，测量 1 s，Hann 窗，2–10 次谐波 | 1 kHz / 100 Hz / 10 kHz |
| 噪声底 | 数字零输入，静置 1 s，测量 1 s RMS/峰值/谱峰 | 含混响尾音时另注 |
| 限幅前余量 | 关闭 `limiter.enable`，0 dBFS 正弦 40/100/1 kHz 与 0 dBFS RMS 白噪声，测输出峰值/RMS | 用于暴露预设自身增益结构 |
| 限幅后 | 开启限幅，threshold -0.1 dB、release 100 ms、link on | 读 `gr.limiter` |
| 延迟 | 报告值 vs 脉冲首个非零样本 | 44.1/48/96/192 kHz |
| CPU | 每块 480 帧，2 s（200 块），记录 p50/p95/p99/max | Python ctypes 开销计入，故绝对值偏高，仅做横向比较 |
| 多声道 | 6 声道不同频率正弦，离散 mode=1 / 矩阵 mode=0 | 预热 10 块，测 RMS 与通道间相关 |

**未覆盖/局限**：
- 没有随仓库分发的 VST3/CLAP 测试插件，插件链只引用既有 smoke 的功能结论，
  未做真实插件的延迟/CPU/音质定量。
- THD+N 对含混响/调制效果的预设不是“噪声”指标：混响的相位调制会以边带
  形式计入，需结合 RT60 与听感解释。
- 频率网格为 1/3 倍频程 31 点；未做 1/24 倍频程细扫。

## 5. 引擎与链路问题

### 5.1 立体声双限幅器串联（已修，P0）

**证据（修复前）**：
- Pop Vocal，0 dBFS/1 kHz，关闭限幅时输出 **+5.99 dBFS**；
  开启限幅（threshold -0.1）后输出 -0.10 dBFS，但 `gr.limiter` 仅 **0.12 dB**。
- 代码路径：
  1. 立体声链调用 `processFloatMultiplexd`，vendor `stage_output`
     在 `jdsp->limiterEnabled` 为真时执行 legacy limiter
     [`jdspController.c`](../../engine/legacy/jdsp/jdspController.c) `stage_output`；
     `hook_limiter_enable` 把 `limiter.enable` 同步进 `jdsp.limiterEnabled`
     [`engine_param_table.h`](../../engine/engine_param_table.h)。
  2. 链尾再执行 `limiter_process_mc`
     [`engine_chain.cpp`](../../engine/chain/engine_chain.cpp)；
     它只能看到 legacy 已压到 1.0 的信号，因此 GR 计量偏小。

**影响**：
- 两套限幅器的 attack/release/门限不同（legacy 固定 vendor 默认 1.0，
  不跟随 `limiter.threshold`），同一 `limiter.enable` 在立体声与离散
  多声道下行为不一致；
- GR 表失真，用户无法判断预设到底压了多少；
- `limiter.threshold` 低于 0 dBFS 时，legacy 仍先把信号压到 1.0，
  现代限幅器再做第二段增益，等效双段压缩，低频素材更易抽吸。

**修复**：立体声 vendor 链改走 `JamesDSPProcessMultiplexedStageSet`，
显式 `gates.limiter = 0`，post gain 仍在 `stage_output` 内施加，
链尾只保留一次 `limiter_process_mc`。见
[`engine_chain.cpp`](../../engine/chain/engine_chain.cpp) 的 `[ADR-010]` 段。
修复后同一 Pop 工况 `gr.limiter` 从 0.12 dB → **5.41 dB**，输出仍 -0.10 dBFS。
`smoke_limiter_final_gate.py` 四路径仍全绿。

### 5.2 预设混响参数失效与梳状深坑（P0，待修）

**证据**：
- Pop Vocal `reverb.preset=1`，`decay=0.35`、`wet=0.25`；实测 RT60 **0.875 s**。
- 把 `wet` 依次改为 0.05 / 0.10 / 0.15 / 0.25，频响逐点几乎完全相同
  （400 Hz 均约 -10.2 dB，630 Hz 均约 -12.7 dB）——说明 `wet` 没有进入 DSP。
- 原因是 `reverb.preset >= 0` 时只下发预设 ID，`freeverb.*` 自定义参数
  仅由 `-2` 路径消费：
  [`param_schema.dart`](../../app/auradsp_app/lib/core/param_schema.dart)
  的 `reverb` 节 `postApply`；[`engine_chain.cpp`](../../engine/chain/engine_chain.cpp)
  的 `apply_reverb`。
- 改用 `preset=-2, decay=0.2, wet=0.15` 后，400/630 深坑消失（分别 +2.35 /
  +2.82 dB），RT60 约 0.19–0.33 s，THD+N 从 -24.8 改善到约 -31 dB。
- Symphonic 同型：`preset=3`、`decay=0.75`，实测 RT60 **0.857 s**；
  自定义路径 RT60 可做到 0.63 / 0.96 / 1.34 s（decay 0.25/0.4/0.55）。

**影响**：
- 用户在混响卡片上拖动 decay/damp/wet/roomSize/width，在预设模式下
  **没有任何声学变化**；一旦拖动又会切到自定义态，声音突变为完全不同的
  RT60 与相位响应。
- “Pop Vocal Clarity”的 400/630 Hz 深坑恰好落在人声清晰度的关键频段，
  是听感“空、闷”的直接原因。
- RT60 与界面数值不对应，预设无法按数据验收。

**建议修复**（本轮实施）：
1. 将两套带混响的出厂预设改为 `preset=-2` 自定义路径，
   `decay/damp/wet/roomSize/width` 全部真实下发；
2. 用实测 RT60 标定：Pop 目标 0.30–0.40 s（decay≈0.2，wet≈0.15），
   Symphonic 目标 0.9–1.1 s（decay≈0.4，wet≈0.25–0.35）；
3. 或者保留预设 ID，但 UI 在预设模式下锁定自定义滑杆并注明“预设固定参数”，
   二者择一，不能继续让滑杆看起来可调。
本轮选择方案 1（数据可验收、参数真实）。

### 5.3 低频过载与限幅器依赖（P0，待调音）

**证据**：见 §4.1 的“限幅前 40/100/1k”。Rock Bass 40 Hz +18.9 dBFS、
V-Shape +15.8、Symphonic 100 Hz +18.3、Vintage +12.2、Pop 100 Hz +10.6。
0 dBFS 白噪声 RMS 在 Rock/Symphonic/V-Shape 已达 +1.5/+1.9/+3.0 dBFS。

**根因**：
- `bass.intensity` 直接映射 `bass.gain = intensity × 15 dB`；
  实测 intensity 0.85 时 20–200 Hz 抬升 **+14.5 dB** 左右；
- 预设又在该频段叠加 EQ +2 ~ +5 dB（Rock 25/40 Hz +5/+4.5，V-Shape +5/+4），
  再叠加 `tube.gain` 5.5/3.5 dB 与混响湿声，总低频增益达到 +20 dB 量级；
- 所有预设的 `post.gain` 均为 0，没有任何输出补偿；限幅器成为唯一电平控制。

**影响**：低频密集音乐（鼓、贝斯、电子）触发 15–23 dB 增益衰减，
release 100 ms 下产生明显抽吸；限幅前的硬压还会带来互调失真，
THD 在 100 Hz Rock 为 -45 dB、V-Shape -50 dB，虽不算高，但这是在被压缩后测得。

**修复方向**：降低 `bass.intensity` 与 EQ 低频增益，使 0 dBFS 输入的
40/100 Hz 限幅前峰值 ≤ +6 dBFS；必要时增加 `post.gain` 负补偿；
保留“低频增强”的听感但不把限幅器当音量控制器。

### 5.4 延迟上报漏计低音（已修，P1）

- `bass.enable=1` 时实测 onset 44.1k 176 样本、48k 192、96k 384、192k 771，
  均为 **4.0 ms**；修复前 `auradsp_get_latency_ms()` 报 0 ms。
- 根因：`compute_latency` 只累加 reverb/convolver/crossfeed/ddc/comp/arbmag/
  haas/spatial/ASRC/limiter，没有 bass；`auradsp_probe_component('bass')`
  本身能测出 192 样本，说明测量能力在、汇总漏项。
- 修复：新增 `kLatBass {frames=192}` 并在 `bass.enable` 时累加。
  修复后 V-Shape/Rock/Vintage 报 4.0 ms，Pop/Symphonic 报 34.0 ms（4+30）。
- 注意：报告值仍是“名义链延迟”；脉冲首个非零样本测到的是干声直达路径
  （4 ms），混响 30 ms 是湿声结构延迟，两者口径不同，文档需明确。

### 5.5 立体声 vs 离散多声道电子管分叉（P1）

- 立体声路径走 vendor `stage_tube` → `VacuumTubeProcess`
  （六频带 crossover + 每频带谐波 + 2x 过采样 + Tape 阻尼），
  [`vacuumTube.c`](../../engine/legacy/jdsp/Effects/vacuumTube.c)；
- 离散多声道走 `tube_process_mc`，是简单的记忆less waveshaper +
  `HalfbandOversampler2x`，[`engine_chain.cpp`](../../engine/chain/engine_chain.cpp)；
- `tube.oversample` 参数只被 `tube_process_mc` 读取；立体声的
  `VTInit` 按采样率自行决定是否过采样，UI 开关在立体声下无效。
- 实测：Pop Vocal 1 kHz 输出在 44.1/48/96/192k 为 +2.47/+3.73/+3.76/+3.80 dB
  （44.1 与 48 差 1.26 dB，10 kHz 差 9.2 dB），部分来自该分叉与重采样路径。
- 结论：同一预设切到 5.1 离散模式会听到不同的电子管音色/失真；
  “Tube 卡片”上的 oversample 开关在立体声下是假控件。
- **同日新增实测（A-12）**：`tube.mix<1` 时干声与过采样湿声没有延迟对齐，
  形成梳状滤波。48 kHz、`tube.gain=3.5`、style=0：
  `mix=1.0` 时 1k/4k/8k/12.5k/16k 均为 0.0 dB；`mix=0.8` 时
  -1.9 / -1.6 / -3.2 / -4.4 / -1.7 dB；`mix=0.6` 时
  -3.3 / -2.6 / -6.6 / **-13.6** / -2.9 dB。立体声 legacy 与离散
  `tube_process_mc` 两条路径均复现。出厂预设此前 mix 0.6–0.85，正是
  §4.2 中 400–630 Hz 与 12.5 kHz 深坑的来源之一。

**建议**：二选一——
1. 统一到 `tube_process_mc`（立体声也逐声道走同一算法，vendor `stage_tube` 关闭）；
2. 或统一到 vendor 算法，`tube.oversample` 只作为全局 2x 开关并在两条路径都生效。
前者改动小、可测；后者音色更接近旧版。需先做一次听感 A/B 再定。
**2026-11-01 裁定：保留双算法，登记为设计差异。** 立体声保留 vendor
Triode/Pentode/Tape 六频带染色，离散保留逐声道现代 waveshaper；
`tube.oversample` 在立体声下仍由 vendor `VTInit` 按采样率决定。同日已移除
Tube 卡片上的过采样开关（立体声下是假控件），引擎默认保持 1——离散多声道
恒为 2x 高精度；A-12 的 legacy `mix<1` 梳状作为
已知残余（预设已统一 mix=1.0 规避）。

### 5.6 限幅器 GR 计量（随 5.1 修复）

修复前立体声 GR 系统性偏低（Pop 0.12 vs 实际约 6 dB）；修复后 5.41 dB。
离散多声道路径本来只走 `limiter_process_mc`，GR 正确（smoke 实测 4.02 dB）。

## 10. 附录：口径说明

1. **频响**：稳态正弦基波，不含谐波/噪声；因此与“脉冲 FFT”在混响预设上
   会出现差异，后者受 IR 截断/梳状影响，仅用于 RT60 与 onset。
2. **THD+N**：2–10 次谐波以外的全部能量计入 N；混响的相位调制/边带会被
   计为 N，不应简单解释为“底噪”。
3. **噪声底**：数字零输入下的输出；含混响时若前一步测试留下尾音，
   静置 1 s 可能未完全衰减，故只在非混响预设作为硬指标。
4. **限幅前**：关闭 `limiter.enable` 后测输出，代表预设自身的增益结构；
   正式播放不会出现，但它是“限幅器要压多少”的直接证据。
5. **CPU**：Python ctypes 调用与系统调度计入；同一机器横向比较有效，
   绝对值应按 2026-10-30 的全链基准（p50 619 µs / 6.41%）校准。
