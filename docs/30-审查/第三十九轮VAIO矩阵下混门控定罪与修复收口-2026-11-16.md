## 定罪

`mx_upmix` 的源活动门控用**严格判零**（样本 != 0 即判
有源）。VAIO 链路的源头是 Windows 混音器向 **int16 端
点**渲染的信号，「静音」声道并非严格 0，而是恒带
±1~2 LSB 的量化抖动（约 3~6e-5，取证日志 %.3f 精度下
打印为 0.000、不可见）。于是每个声道都被误判有源、
250ms 保持窗恒开，门控退化为无条件铺满——填充开关自
然无区别。探针决定性复现（fill_probe5，出厂引擎）：静
音声道严格 0 时门控正常；注入 ±1 LSB 抖动后输出立即
变为 [FL, C, SL, BL] 铺满形态，与宾机症状逐项一致。

与全部实测的吻合：APO 宿主端点为 float32 混音格式、
VB 为 float 总线，静音严格为 0，故门控正常、仅 VAIO
中招；LFE 直通不经门控，故 LFE 单亮一直正常、C 段 LFE
不亮亦然。

## 修复（S4 `dc6ba64f`）

- `engine/chain/engine_chain.cpp`：新增
  `kMxActivityEps = 1.0e-4f`（约 −80 dBFS，高于 int16
  抖动上限 ±2 LSB≈6.1e-5、远低于任何可闻信号），活动
  判定改 `fabsf(sp[c]) > kMxActivityEps`。阈值只决定回
  填开/关，不影响声道本音的下混折入。
- **口径反转记录**：原注释明文「判零沿用仓库严格 0 语
  义（极弱信号也算有声）」系既定口径，本修复将其反转
  为 ε 阈值语义，注释已同步改版并写明定罪依据。−80
  dBFS 以下的真实信号自此不触发回填（折入不受影响），
  此为有意取舍。
- 回归测试（`smoke_config_and_matrix.py` [4b] 增两
  例）：±1 LSB 抖动下门控仍成立（C/SL/SR/BL/BR max
  = 0）；2e-3（−54 dBFS）微弱真实信号仍判有源（SL 回
  填与 FL 折入均出现），防阈值误吞。

## ASIO / WASAPI 复核（立项第三项）

修复位于引擎共享上混路径，三桥一并继承。WASAPI 本地
路径为 float 混音格式、静音严格 0，等同探针 CLEAN
例，行为不变、本就无此缺陷。ASIO 绕过 Windows 混音
器（宿主直渲 ASIO 缓冲，无 int16 端点抖动级），且 ε
门控对其同样生效——无同类缺陷路径。VB（float 总线）
同理无此问题；其离散后四声道单发不亮为既有登记 B1
（疑总线声道模式），与本轮无关。
