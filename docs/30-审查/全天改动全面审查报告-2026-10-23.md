## 1. R-1（P3）分层守卫测试名实不符

### 1.1 现象

`test/layering_guard_test.dart` 第三项：

```dart
test('core/ 不得依赖 features/ 与 ui/', () {
  ...
  for (final l in _importLines(f)) {
    if (l.contains('features/')) bad.add(...);   // ← 只查 features/
  }
```

测试名与文件头注释（「core/ 状态/主题，不得依赖 features」）宣称守两个方向，断言体只实现一个。

### 1.2 现状核实

- `lib/core/` 对 `ui/` 的 import：**0 处**（grep 实证，含 `../ui/` 与包路径两种形式）；
- 即当前**无 live 违规**，缺口是休眠的——将来有人在 core/ 里 import ui/ 不会被这项测试拦下。

### 1.3 处置建议（二选一）

1. **补断言**（若约定确实是双向禁止）：`if (l.contains('features/') || l.contains("'../ui/")) bad.add(...)`，与 engine/ 项同构；
2. **改测试名**为「core/ 不得依赖 features/」（若 core→ui 是有意放行——注意 `design.dart`/`theme.dart` 的令牌消费都在 core/ 内闭环，core 并无引用 ui/ 的必要，故倾向第 1 项）。

> 优先第 1 项：`ui/` 是设计系统落地层，core/ 反向依赖它会形成「状态层→展示层」倒挂，正是分层要防的方向。

## 2. R-2（P3）IndexedStack 离屏高频残余成本

### 2.1 SDK 源码取证（非推测）

`packages/flutter/lib/src/rendering/stack.dart`：

- `RenderIndexedStack` 覆写 `paint` / `hitTestChildren` / `visitChildrenForSemantics` / `computeDistanceToActualBaseline`——**只放行 index 子节点**；
- 但 layout 走 `RenderStackBase._computeSize`：`while (child != null) { ... layoutChild(child, ...) }`——**全部非定位子节点都参与 layout**。

结论：离屏页 = build 在（element 树保活）+ layout 在 + **paint/命中/语义被裁**。

### 2.2 实际影响面

30fps 高频 ValueNotifier 的消费者分布（grep 实证）：

| 页面 | 高频消费者 | 离屏时 |
|------|-----------|--------|
| home_page | `model.spectrum`（SpectrumView）/ `levelL/R`（LevelMeter） | 仍 30fps build+layout |
| chain_page | `stageLevelsL/R`（Listenable.merge） | 仍 30fps build+layout |
| visualizer_page | 自有 notifier | 仍 30fps build+layout |
| effects/liveprog/plugins | 无高频消费 | 零成本 |

P0 的三项措施中：hbTick 级联解决的是「1s 心跳整页重建」；visiblePage 门控解决的是「离屏页周期定时器」；**TickerMode 只静默 AnimationController**——对 ValueNotifier 驱动的频谱/电平组件无效。这是保活设计的已知残余，非缺陷（用户实测「变得非常快」即含此状态）。

### 2.3 可选优化（不排期，记档）

把高频监听也按可见性门控，例如 SpectrumView/LevelMeter 的 `ValueListenableBuilder` 外层包一层 `visiblePage` 判断（离屏时停 lister 或返回静态占位）。收益 = 离屏页 30fps build+layout 归零；成本 = 每处高频入口加门控样板。待有实测性能诉求时再做。

## 3. E15 v2 流水深记账审查（通过）

逐行复核 `9883ecc`（+ `96ee615` 前置、`793c194` 修边）：

1. **深度模型自洽**：`chunks = ceil(numFrames / kTransportFrames)`，钳 `[1, kRingBlocks]`；延迟 = `m_pluginLatency + chunks×128`，块大小变更时重算（音频线程 release 写、控制线程 acquire 读）——与「帧到即取」消费模型相容，实测误差全 0（416/544/800/1312）。
2. **不变量守住了**：硬上限 `m_inFlight >= target → 本块不提交（直通）+ depthDrops++`——宿主算力不足表现为直通而非隐性加深；`depthViolations` 哨兵保留（越界即遥测可见）。
3. **无饿死风险**：满深度丢块保「宿主手上有活」——E14 的 prime 补位语义不被破坏（提交路径只在非直通块触发）。
4. **跨线程正确**：`m_targetInFlight`/`m_latency`/`m_pluginLatency` 均 release/acquire；RT 路径内比较用 relaxed（单音频线程写）。
5. **首块前口径**：load 时按 128 帧回调保守写 `+128`，首块后重算——多块设备有 ≤1 回调的欠报窗（≈8ms@512），注释已明示，可接受。
6. **冒烟背书**：host_process 新增 256 帧口径断言（精确 544 + transportLatency 256）；cross_mode 128 帧逐位一致 0/32192 保持。
