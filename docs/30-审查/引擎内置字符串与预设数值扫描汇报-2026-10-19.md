**风险研判**：
1. 诊断字符串（尤其 legacy + `[DBG]`）散落于 C 源码，无统一错误码体系；排障时只能靠 grep。
2. 部分用户可见错误（如 `convolver.ir: file too large (exceeds configured gate.maxFileMb)`）泄露了内部配置名与路径风格，建议对终端用户做脱敏后展示。
3. **无 i18n 体系**：全部英文硬编码，与项目多语言 UI（zh/en/ja arb）不配套——当前引擎层错误无法本地化。

## A3. 版本 / 标识字符串

- 引擎版本锚点：`auradsp_engine.h` = `1.0.0`、`engine_internal.h` = `1.1.0`（注意两处不一致）。
  > ⚠️ **勘误 E3**：本条系误报——`auradsp_engine.h` 的 `1.0.0` 仅是注释示例，真实版本唯一 = `AURADSP_VERSION "1.1.0"`；真问题是 `host_instances.cpp` 的 `m_host.version = "1.0.0"` 硬编码不同步（计划 S1-1/B-5），见文首勘误。
- host 侧大量 `version.lib`（Windows 导入库）与 `ProductVersion`/`FileVersion` 资源提取逻辑（host_metadata_scan.cpp），用于读取第三方插件版本——属宿主基础设施，非引擎自身版本。
- 未发现运行时可加载的巨型内嵌脚本（`>200` 字符的长字符串为 0）：说明 **EEL/Liveprog 脚本是资源文件运行时加载，而非 C 源码内嵌**，符合之前未决清单的推测；这类内置字符串不在此树，应到 `assets/`/`dsp/` 资源目录另行审计。

## A4. legacy / host 字符串体量说明

`legacy/jdsp`（1392 个）与 `host`（424 个）占全部字符串的 78%。构成主要是：
- legacy：EEL2 脚本引擎、RBJ biquad、reverb/FDN 等 DSP 内的变量名/格式串/注释串（技术性，非用户面向）。
- host：CLAP/VST3 插件宿主的加载/编辑器错误（`Failed to load CLAP library`、`createView returned null` 等），多为 `[DBG]` 调试串。

**与 Dart 侧对照（关联未决清单 C4）**：Dart `state.dart` 的 `componentLatency` 硬编码了其中 `kLatComp=85.0 / kLatSpatial=1.0 / kLatArbMag=2.67 / kLatDdc=6.0` 四个估算值；而 `kLatReverb=30 / kLatConvolver=10 / kLatCrossfeed=3 / kLatLimiter=2` 在 Dart 侧走实测或引擎链计算，未硬编码镜像。**风险**：引擎调结构改了 kLat 值，Dart 不会自动跟随——C4 建议把 kLat 纳入契约测试。

## B6. 其他调音常数

- `reverb.c` 内 `sf_reverb_process`：`modnoise1=0.09`、`modnoise2=0.06`、`crossfeed=0.4` 等内联调音常数；混响输出混合系数 `D/B = 0.469/0.219/0.064/0.045`（delay 加权）。
- legacy 各 Effect 文件内大量 RBJ biquad 默认系数、噪声整形常量——技术性，建议后续按文件产出'DSP 常数清单'二级审计。

## B7. 别名 / 重复字段（24 组）—— 与未决清单 A1/B1/B2 互证

**关键结论**：`kEngineParamTable` 中存在同一底层字段被多个 id 引用的情况，共 **24** 组。直接解释之前未决清单的几条：

1. **dyneq 三别名打架（A1 实证）**：`dyneq_b1_attack` 同时被 `dyneq.b1.attack`、`dyneq.low.attack`、`dyneq.band1.attack`三个 id 指向——这正是 A1 里'Dart 2.0ms vs 引擎 20.0ms 且与同成员 dyneq.low.attack 打架'的根因：UI 用哪个名字，默认值取哪条，全看路径。
2. **channels / channel_mask 双名（B1 实证）**：tube/comp/arbmag/eq/dyneq/shelf/filter/exciter/gate/loudness/limiter 共 11 个效果器，每个都有 `.channels` 与 `.channel_mask` 两个 id 指向同一 int 字段——与未决清单 B1'11 个 *.channels 绕过 registry'完全对应，且此处证明它们本质是同一字段的两个名字。
3. **comp.freq1-7 / comp.gain1-7（B2 实证）**：14 个 id 指向 `comp_freq[]` / `comp_gain[]` 数组成员——印证 B2'comp 14 个动态 spec 未在 param_schema 挂 section'，且它们是数组型，静态契约解析器天然盲区。
4. **gate.hold / gate.hold_ms、limiter.release / limiter.release_ms**：同字段双名——A1 默认值分歧里成对出现的原因。

# 结论与建议

## 字符串侧
1. 参数 ID（214）是当前最高价值的'内置字符串'，已与 UI 契约绑定，建议维持单一来源（`engine_param_table.h`）。
2. 诊断字符串无统一错误码、无 i18n、部分泄露内部路径/配置名——建议建立错误码枚举 + 用户面向脱敏层。
3. EEL/Liveprog 脚本不在本树内嵌，需改到资源目录审计（不计入本次）。

## 预设数值侧
1. **范围（B1）与默认值（B2）是引擎侧的两套'预设'，应作为 Dart param_schema 的强制对照基准**——Part F 门禁已覆盖有界参数，建议把 B3 默认∈范围校验也固化成测试。
2. **B7 的 24 组别名**：dyneq 三别名、`*.channels`/`*.channel_mask` 双名是真实一致性风险点，建议在引擎侧保留单一规范 id、其余作为 deprecated 别名显式标注，并在 Dart 侧收敛到规范名。
3. **混响 19 套预设（B4）与 kLat 延迟表（B5）** 是高价值调音数据，建议导出为可读 JSON 资源，便于 UI 展示预设名与跨层一致性比对。
4. kLat 与 Dart 硬编码的对照（C4）应落地为契约测试，防止引擎改结构后 Dart 读数失准。
