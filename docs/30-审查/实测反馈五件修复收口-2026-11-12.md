# 实测反馈五件修复收口（2026-11-12）

> 来源：业主 2026-11-12 上午对 @8e108480 包的实测反馈（ASIO 注销失败、浅色歌词仍看不清、APO 输入门控无电平、声道增益 L/R 上限不一致、APO 一键卸载口径）+ 一项咨询（稀疏保存释义，见文末）。修复头 `b40999cf`，验证以开发机为主仲裁。

## 逐件定罪与修复

### 1. ASIO 一键注销失败（弹窗「register_asio.ps1 无法被识别为 cmdlet/函数/脚本文件」）— 定罪修复 `470bf2b8`

- **机理**：App 提权调用 `Start-Process powershell -Verb RunAs -ArgumentList <数组>`。数组形态下 Start-Process 以空格拼接且不保内嵌引号；子进程又是 powershell.exe（自有命令行解析），安装路径含空格（Program Files）时 `-File` 后的脚本路径被拆断，碎片（含 register_asio.ps1 的那段）被当作命令名执行 → CommandNotFound 弹窗。注册/注销同病，含空格路径下双向都坏；便携目录无空格时不发作，与实测环境吻合。
- **开发机实证**：含空格路径下数组形态脚本根本不执行（回执文件不生成）；单字符串 ArgumentList 形态参数完整到达（Unregister=True、ResultFile 原样）。目标为 exe 的 apo_config 走 CommandLineToArgvW 解析不受影响，APO 侧不改。
- **修复**：`asioDriverScript` 两个提权分支（bundled 随包脚本 + dev 脚本）统一改单字符串预拼接 ArgumentList。

### 2. 浅色主题歌词仍看不清 — 定罪修复 `e2721055`（真凶非遮罩）

- **机理**：`lyric_view.dart` 两处以 `Theme.of(context).extension<AuraPalette>()` 取 palette——注册的 ThemeExtension 类型是 design.dart 的私有包装类 `_Aura`（正规通道 `paletteOf()`），按 AuraPalette 查恒为 null、恒回退 **auraDark**。于是歌词文字恒用深色主题配色：深色主题下恰好接近正确（实测「深色没问题」），浅色主题下当前行近白（#E8EAF0）、非当前行为近白低透明，压在浅色遮罩上必然看不清。**第十一轮的对比度调整（0.88/遮罩加实）写在回退后的深色分支上，从未真正生效**——舞台侧 `p` 走 paletteOf 是对的，所以遮罩本身一直正常，此前归因遮罩/透明度属误判。
- **修复**：两处改 `paletteOf(context)`；新增回归测试钉死浅色 palette 下当前行 = auraLight.text、非当前行 = 其 0.88（lyrics_subsystem_test，既有两条无主题夹具用例同步补 auraDark 扩展）。

### 3. APO 模式输入门控卡无电平 — 定罪修复 `0108e6ed` + `b40999cf`

- **机理**：输入门控卡 IN/OUT 电平读 `inputMeterIn/Out` 四值，状态层只从 viz 事件的 `inputInL/R、inputOutL/R` 四键更新；进程内/桥接事件都带（FFI 帧 stageLevels[12]=gate 输入级、[13]=输出级派生），**APO 合成事件漏带这四键** → APO 模式恒不更新。
- **修复**：APO 事件按同一口径从 telemetry stageLevels[12]/[13] 派生补键（数据本就在块内流动，无需 telemetry 升版）。
- **附带事故**：四值以内联三元 `hasStage ? f32[…] : -120.0` 写进事件字面量时触发 **Dart AOT 编译器崩溃**（flow_graph untagged->tagged，gen_snapshot 期），开发机二分定位到本提交；改先落局部变量（与同函数 levelL/levelR 既有写法一致）后构建恢复。analyze 与测试对此无感，只有 release AOT 构建能逮到——已记为教训。

### 4. 声道增益 L/R 最大 100%、其余声道可超 — 定罪修复 `3abfceb9`

- **机理**：引擎 indexed 处理对 `input.balance.1–8` 一律钳 [0, 2]（input_ch_gain 全声道同口径）；Dart 侧只有 .1/.2 有 ParamSpec 且误写 `max: 1.0`，AppModel.setParam 按 spec 钳位 → L/R 止于 100%；.3–.8 无 spec 走引擎钳位可达 200%。滑块控件本身 max 本就是 2.0。
- **修复**：两条 spec 的 max 改 2.0（引擎表无该参数的静态条目，契约夹具不钉此范围，无连带）；param_schema_test 新增回归（1.5/2.0 可达、3.0 仍钳 2.0）。

### 5. APO 一键卸载应卸全部附加设备 — 现行代码已是全端点（无代码变更）

- 面板按钮（sections.dart）→ `detachSystemApo()` 无参 → `apoUninstall(target: '')` 省略 target → apo_config 无 target 即全端点（台账还原 ∪ 实时扫描剥离），Stage 0（§8.2）已落此口径且裁定 = 复查清单为空，三层代码复核无单端点残留路径。
- 业主实测到的「只卸选中」与**开发机 Program Files 内旧装机版**（Stage 0 之前的单端点实现）的行为一致；新 Setup 覆盖安装后应即为全端点。若新包仍复现，保留 `%TEMP%\auradsp_debug.log`——其中有 `apo detach: target=(all)` 取证行，可直接定罪走的是哪条路。

## 附：用户配置「稀疏保存」释义（业主咨询）

Part D 落地后用户 config.json 仍是整表保存——含从默认层合并进来的值。稀疏保存指用户层只写「与默认层不同」的键：文件更小，且默认层随版本升级新默认值时，没被用户改过的项能自然吃到新默认（整表保存会把旧默认冻在用户文件里、永远盖住新默认）。当时定为后置步：动保存路径前必须先建「保存→重读等价」回归（合并语义下删键 = 回落默认，等价性需证明），未实施。
