10-31 全量复核记 L-04 为"参数/预设切换缺少块首淡出清零"。本轮复核发现**机制侧早已具备**：

- `engine/dsp/dsp_mc_reverb.cpp:110-112` 已有 `mc_rev.reset_req` 请求位；RT 侧 `dsp_mc_reverb.cpp:214-218` 消费该请求 → `fading_out` → 5ms 淡出 → `mc_clear_state` 后重新起尾。

因此 L-04 的真实缺口收窄为**"参数/预设切换路径未触发该请求位"**，而非"没有淡出机制"。这让 L-04 的改法成本显著低于 10-31 记录时的估计——但**该项本身仍未修**，故 L-04 保留在 §3.4，仅表述被更正。

### 2.5 L-05 —— 前提不成立，改判为误报；已按 ADR-010 固化为门禁

10-31 全量复核的 L-05 描述为「引擎链里 `post_gain_process_mc` 是限幅之后（step 15）」。本轮逐行复核确认**该前提不成立**：

- 离散多声道路径：`post_gain_process_mc` 位于 step 15，限幅器 `limiter_process_mc` 在本链**末尾**（loudness 之后）——post gain 本就早于限幅器。
- 立体声 / 矩阵 / 双耳路径：post gain 与逐声道 trim 在 vendor `stage_output` 内施加（`postGain × postGainCh`），vendor 限幅器紧随其后，wrapper 前瞻限幅器在链尾——同样早于限幅器。

**但复核暴露了更本质的问题**：这条链序契约此前**只写在注释里，无任何测试执行**。

**处置（2026-10-31 当日，用户裁定 D-1「限幅器应该是最后一道门」）**：

1. 新开 [ADR-010](../adr/ADR-010-limiter-as-final-gate.md)：限幅器是内置信号链最后一道门；post gain / 逐声道 trim / 响度补偿全部排在它之前；并登记四项例外（插件 stage 4 Post-Limiter、`limiter.channels` 掩码、样本安全卫士、vendor 内部限幅器）。
2. 新增门禁 `test/smoke/smoke_limiter_final_gate.py`（已挂 `runner.py`）：四条路径 ×「限幅开 → 峰值 ≤ 门限」×「限幅关 → 峰值显著超门限」反向对照；立体声 / 离散多声道另做精确比例核对与 GR 断言。
3. **反向验证已做**：临时把 `post_gain_process_mc` 移到限幅器之后并重建引擎 → 多声道路径 3 项断言精确转红（peak 0.796 > 门限 0.501、gr.limiter = 0、LFE trim 1.589 > 门限），立体声 / 矩阵 / 双耳仍绿（它们走 vendor 实现）——证明门禁覆盖了两套不同的 post gain 实现，非空转。验证后已还原并重建。
4. UI 提示三语更新（`postHintGain`）：说明该参数作用于限幅器之前，限幅开启时上推会被门限兜住（表现为 LIMIT 表下坠）。

**销账**：D-1 已裁定并落地，L-05 从待裁定移入销账。

## 3. 确认仍在册（8 项）

### 3.1 L-01（高危并发）—— eq 逐声道池与 RT 共享同一卷积实例

**位置**：`engine/chain/engine_chain.cpp:752` `eq_pool_reload()`。

**实况**：控制线程对池内 `FFTConvolver1x1` 直接调 `LoadImpulseResponse`；RT 线程可能在同一实例上 `Process`。`EqPool.loaded` 为普通 `int`（`engine/engine_internal.h` EqPool 结构体），跨线程读写无原子保护。

**改法（未实施）**：等长双池 + acquire/release 原子指针发布 + 旧池延迟回收。

### 3.2 L-03（高危并发）—— arbmag 池与主 conv 原位刷新

**位置**：`engine/chain/engine_chain.cpp:646` `arbmag_pool_reload()`；主 `arbMag` 卷积为原位刷新（`engine_param_table.h:555` 触发路径）。

**实况**：与 L-01 同型——控制线程重载共享实例，`arbmag_pool.loaded` 同样是普通 `int`。

**改法**：与 L-01 合并处理（先池后主）。

### 3.3 L-02（高危并发）—— reset_channel_state 跨线程清 RT 状态

**位置**：`engine/chain/engine_chain.cpp:214` `reset_channel_state()`。

**实况**：控制线程直接清 gate / filter / dyneq / tube 等 RT 正在使用的非原子状态。调用点：`set_channels_mode`（`engine_param_table.h:657`）、`set_channels_count`（`engine_param_table.h:687`）、`hook_spatial_enable`（`:182`）、`hook_spatial_binaural`（`:188`）。

**改法**：参照 `mc_rev.reset_req`（见 §2.4）为其余模块补 request 位 + 淡出，RT 侧消费。

> L-01 / L-02 / L-03 是本仓目前**唯一**的已知高危并发遗留，且三者同源于"控制线程与 RT 线程共享可变 DSP 状态"。建议合并为一个专项。

### 3.4 L-04（中危）—— mc_reverb 参数/预设切换未接淡出请求

**位置**：`engine/dsp/dsp_mc_reverb.cpp`。

**实况**：淡出机制已具备（§2.4），缺的是参数/预设切换路径触发 `reset_req`。10-31 复核时试过块首清与块尾清两种时机，`Category B：中置有 MC FDN 尾音` 的 rms 归零（smoke 回归），故回退至基线实现。

**改法**：参数/预设切换时置 `reset_req`（走已有淡出路径），而非直接清状态——这与前两次尝试的差别在于"清"换成"淡出后清"，理论上可同时满足 smoke 与听感。

**阻塞**：需 5.1 实机试听确认爆音条件。

### 3.5 VST2 / AU / LV2 插件格式 —— 引擎侧无驱动

**实况**：

- 引擎侧仅两个格式驱动目录：`engine/plugins/formats/{clap,vst3}`。无 VST2 / AU / LV2 驱动实现。
- Dart 侧 `PluginFormat` 枚举**已含** vst2 / au / lv2，但注释明确其定位是"引擎产出这些格式时列表角标/筛选即刻可用"的预留，不是挂载支持。
- 扫描目录侧已为 VST2 预留（`lib/core/plugins/plugin_scan_dirs.dart:64-67` 提到 VST2 常见目录与注册表探测）。

**结论**：枚举与扫描已就位，**驱动与挂载未实现**。补驱动前需先做授权与 ABI 取舍（VST2 需 `fst` 头，AU 仅 macOS，LV2 与 CLAP 有 ABI 冲突面）。
