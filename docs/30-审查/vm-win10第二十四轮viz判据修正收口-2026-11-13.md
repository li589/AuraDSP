# vm-win10 第二十四轮收口：viz 来源判据改范式类别优先（2026-11-13）

## 1. 起因（第二十五诊定罪，第二十三轮回归）

vm-win10 重建基线实测 @f2b6c8d1：效果处理正常（切换效果可闻变化），
但应用内**全程无可视化**。guest 取证定罪（`r25_triage`）：

- 调试日志 `viz: dropped local frame (expected sysapo)`——管线帧
  被第二十三轮来源过滤全数丢弃；
- 事故态为**混合态**：audioMode='sysapo' 而 modeCategory='pipeline'。
  成因：配置默认 audioMode 原始值 'auto' → 类别派生 pipeline；
  AppModel 构造把 audioMode 归一为 'sysapo' 却不重派类别；用户在
  设备页只点管线选择器时 setPipelineInput 也不改写 audioMode。
  **每个鲜装 Windows 用户走管线范式都会中招**，直到手动重选模式。

根源在第二十三轮判据的判定顺序：以「附加模式优先」判源，但喂数者
由 isolate 按 **modeCategory** 分发——类别为 pipeline 时跑的是
管线链（桥/进程内泵），audioMode 只是可滞后的合成值。

## 2. 修复（`7e05d28b`）

`expectedVizBackend` 改为**范式类别优先**：

1. modeCategory == pipeline → 按合成链判（asio→'asio'、
   vaio→'vaio'、capture→'local'）；
2. 其后才按 audioMode 判附加模式（sysapo/vbcallback）与直连
   模式（asio/vaio），缺省 'local'。

getter 注释同步改写（含事故引用）。`_syncVizSourceOnSwitch` 与
'viz' 过滤逻辑不变——判据对了，切换清零与异源丢弃即各归其位。

## 3. 回归测试

`test/viz_source_governance_test.dart` 新增两例（Windows 门），
以 config 直写复刻事故态（先例 apo_mode_switch_gate_test 同法）：

- 滞后 sysapo + vaio 链 → 期望 'vaio'，vaio 帧放行、sysapo 帧
  按异源丢弃；
- 滞后 sysapo + capture 链 → 期望 'local'，local 帧放行、
  sysapo 帧丢弃（即 14:59:00 日志行的字面场景）。

两例在旧判据下均失败（期望值即错）。原四例在新判据下全过
（setAudioMode 路径同时写类别与合成值，行为不变）。
