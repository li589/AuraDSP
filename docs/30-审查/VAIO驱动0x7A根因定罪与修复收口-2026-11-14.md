# VAIO 驱动 0x7A 根因定罪与修复收口（2026-11-14）

## 1. 定罪（owner 实机取证）

历次 `0x7A KERNEL_DATA_INPAGE_ERROR (1, 0xFFFFFFFFD0000006)` 的
真正根源是 **VAIO 驱动自身的 IRQL 违规**，不是虚拟机存储：

- 2026-11-14，owner 在**物理宿主机**（稳定 NVMe、无快照）首次
  加载驱动并调用 `IOCTL_AURAVAIO_MAP_SHARED_RING`，物理机连续
  两次同签名绿屏——存储理论当场死亡；
- cdb 分析物理机 minidump，崩溃线程栈确凿：
  `AuraControlDevice_DispatchDeviceControl` →
  `MmMapLockedPagesSpecifyCache(..., UserMode, ...)`；
- 机理：`MmMapLockedPagesSpecifyCache` 向用户模式映射必须修改
  目标进程页表，要求 **IRQL ≤ APC_LEVEL**；驱动在
  `KeAcquireSpinLock(&g_RingLock)` 后处于 **DISPATCH_LEVEL**
  调用之，页面调度器禁用 → 页表页页入失败 → 0x7A
  （Arg1=1 = 页表页、Arg2=D0000006 = STATUS_IN_PAGE_ERROR）。
- 追溯定罪：vm-win10 内记录的全部同签名崩溃（多声道计划 W4
  起累计十余份转储）**同源于此**——每次崩溃的触发动作（起 VAIO
  栈、驱动装卸、切离 VAIO 的清理路径、探针启动）无一例外都伴随
  共享环的 MAP/UNMAP/Cleanup，即映射冷路径的调用。

完整评估与分阶段实机记录见 owner 文档
`docs/20-执行/VAIO驱动未竟任务与实机操作危险性评估-2026-11-13.md`
（§3 风险 1 之 3、§4 阶段 0–6）。

## 4. 正式更正（Lux）

以下既往结论**作废**：

- 《多声道计划 W4W1W2 审读纪要》（2026-11-13）的蓝屏定罪
  （「宾机虚拟存储路径间歇失败、AuraDSP 组件排除」）；
- 第二十五诊、第二十六诊（2026-11-13）的同口径判读，以及
  「切 VAIO 必崩 = 起栈 I/O 最重故必触发存储失败」的解释。

错因复盘（记档防再犯）：

1. 取证手段只有转储**头部解析**（bugcheck 码 + 参数），从未
   取得崩溃线程栈——cdb 在宾机 SSH 会话内跑不起来、MEMORY.DMP
   未做全量解析；以签名模式匹配代替栈证据，是本次误判的
   方法论根源。**今后内核崩溃定罪必须以栈/模块证据为准，
   头部签名只作分级参考。**
2. 「磁盘错误事件为零」本是反对存储理论的证据，被降权处理；
   「新基线近空增量仍复现」被误读为快照机制本身有罪，其实
   与「确定性驱动缺陷」完全一致。
3. guest 文件读回全零等 I/O 异象为真实现象（崩溃时在途写入
   丢失可解释其大部），但不足以支撑存储路径定罪。
