# 引擎侧两项扩展调研（2026-10-16）

> 承接《预设系统缺陷研究报告 v1.2》§8「登记后续」的两项引擎 ABI 扩展。
> 本文逐文件核实现状，修正摘要中的误判，给出改动量、风险与方案取舍。
> **本文件为调研，不含实现改动。**
> **现状复核（2026-10-17，HEAD 5a9b344）**：§1.1 / §2.1 逐项实测仍成立——FFI `getString`、isolate `lpCode`/`arbmagString`/`eqCurve` 转发、`assets/presets/reverb_legacy.json` 均未落地；`liveprog.code` 的 get 分支行号漂移至 `auradsp_engine.cpp` L1347。两项调研截至复核时**未开工**。

---

## 0. 调研结论速览

| 项 | 摘要原判定 | 核实结论 |
|---|---|---|
| 字符串回读（eq.curve / liveprog.code / arbmag.string） | 引擎 `get_param` 无字符串路径，需新增 API | **误判**：`liveprog.code` 引擎 `get_param` 早已支持回读（L1268-1273）；`eq.curve`、`arbmag.string` 确无回读分支，但只需各加 2 行 if 分支 + 1 个 handle 字段，**不加导出符号、不升 ABI** |
| 混响 18×16 预设表外置 | 需引擎新 API | C 层表已定位（`engine/legacy/jdsp/Effects/reverb.c` L740-759，18 预设 × 16 维）；**"彻底移除 C 表"** 才需引擎改动（暴露全 16 维或新 API）；折中方案（转录为资产供 UI 展示、仍走引擎索引）零引擎改动 |

> 一句话：**字符串回读是低风险补丁（且 liveprog.code 已是接线任务）；混响外置是产品取舍问题，引擎改动只在"要从 C 删表"时才必要。**

## 1. 字符串回读 API 调研

### 1.1 现状盘点（逐 id，实锤）

引擎 `get_param` C 实现：`engine/auradsp_engine.cpp` L1192-1379，按 `id` 分发。

| 参数 id | set_param（写） | get_param（读） | isolate→Dart 转发 | 备注 |
|---|---|---|---|---|
| `liveprog.code` | ✅ L724（解析+应用，不存裸串，但句柄另存 `h->lp_code`） | ✅ **L1268-1273 已支持**（memcpy `h->lp_code`，要求 `bytes ≥ len+1`） | ❌ 不转发 | 引擎已具备回读能力，只是上层未取 |
| `arbmag.string` | ✅ L838-856（解析+应用，**不存裸串**） | ❌ 无分支 | ❌ 不转发 | 需存串 + 加 get 分支 |
| `eq.curve` | ✅ L417-437（解析、应用，解析后 `free(txt)`，**不存裸串**） | ❌ 无分支；且 EQ gains **不单独可读**（get_param 仅 `eq.enable`） | ❌ 不转发 | 需存串 + 加 get 分支；重构式重序列化不可行（gains 不可读） |

补充证据：
- 引擎 `get_param` **已有返回字符串的范式** —— `graph.effects` 用 `snprintf` 回吐 JSON（L1343-1377），证明字符串回读在 C 层是成熟路径。
- 句柄存储：`engine_internal.h` L360-361 已定义 `char* lp_code` / `size_t lp_code_len`，析构与 set 都在 `auradsp_engine.cpp`（L220/745-750）。`arbmag.string`、`eq.curve` **无对应字段**。
- FFI：`auradsp_ffi.dart` 已有 `setString`（L765）；**`getString`（读缓冲）缺失**，但可由现有 `get_param` 包装出来（无需新 C 导出，沿用 `lib.getParam` 同签名）。
- isolate `getParams`（`audio_isolate.dart` L575+ 的 `'evt':'params'`）：只发数值/布尔 + `convSpectrum`，**完全不发** `lpCode`/`arbmagString`/`eqCurve` —— 这是 liveprog.code 虽已支持却"读不到"的根因。

### 1.2 改动量（按 id 分）

**引擎 C（低风险，不加符号、不升 ABI）：**
- `arbmag.string`：`engine_internal.h` 加 `char* arbmag_string` + `free()`；`set_param` L843 处 `malloc` 拷贝；`get_param` 加分支（memcpy，同 `liveprog.code` 模式）。
- `eq.curve`：`engine_internal.h` 加 `char* eq_curve` + 长度；`set_param` L424 处将 `txt` 移交句柄（不 `free`）；`get_param` 加 `eq.curve` 分支。
- `liveprog.code`：引擎零改动。

**桥接 / FFI：**
- `auradsp_ffi.dart`：新增 `getString(lib, handle, id, capBytes)` —— 分配 `capBytes+1` 缓冲、调现有 `get_param`、按 RC 回传（参考 `setString` 写法）。

**isolate（`audio_isolate.dart` getParams case 末尾追加）：**
- 3 次 `lib.getString` 读 `lpCode` / `arbmagString` / `eqCurve`，随 `'evt':'params'` 一并发出。
- 注意每 id 的 cap 不同：liveprog 256 KiB、arbmag 256 KiB、eq.curve ≈ 1.5 KB（`15 点 × "f:g;"`）。超 cap 走 `E_PARAM`，须按 id 设上限。

**Dart 模型（`state.dart` `'params'` 分支 + 已建的 #21 过期守卫）：**
- 接收 `lpCode → m.lpCode`、`arbmagString → m.arbmagString`、`eqCurve →` 解析回 `eqGains/eqFreqs`（或直接存 `m.eqCurve` 原串）。
- #21 的防抖回读对账分支自动覆盖这三类（此前 #21 只能核对数值类，这三类是盲区）。

### 1.3 风险与注意

- **eq.curve 格式漂移**：回读后若走"重序列化"会与 `_pushEqCurve` 输出（含 `eqm:` 头、特定精度）产生双向不一致。**建议存原始串而非重序列化**。
- **buffer 上限**：`get_param` 要求 `bytes ≥ len+1`，isolate 端需先按 id 给定足够 cap；liveprog/arbmag 上限高（256 KiB），eq.curve 低（≈1.5 KB），不可统一用同一大缓冲（浪费 / 越界）。
- **不改 ABI**：`get_param`/`set_param` 签名不变，仅分支新增 → 与既有 47 导出符号兼容，DLL 增量替换无需升 ABI 版本。
- **lpCode 优先级最低**：它是会话级字段（Dart 已有 `m.lpCode` 副本），回读主要用于"检测引擎编译脚本与本地副本是否分叉"；eq.curve / arbmag.string 引擎才是真相源（Dart 推送后引擎可能钳位/规范化，副本会漂移），对账价值更高。

## 2. 混响 18×16 预设表外置调研

### 2.1 现状盘点（实锤）

- **桌面引擎实际编译**：`engine/legacy/jdsp/Effects/reverb.c` 的 `sf_presetreverb`（L730-788）。`engine/chain/engine_chain.cpp` 注释（L47）指的就是它。
- **表本体**：L740-759，18 预设（索引 0-17，对应 `SF_REVERB_PRESET_*`），每预设 17 字段 = `osf` + `p1..p16`（**16 个声学参数**）。
- **参数含义**（L740 注释）：OSF ERtoLt ERWet Dry ERFac ERWdth Wdth Wet Wander BassB Spin InpLP BasLP DmpLP OutLP RT60 Delay。
- **应用路径**：`engine_chain.cpp` L64-73 `apply_reverb` → `Reverb_SetParam(j, rv)`（L923-925 调 `sf_presetreverb`）。
- **UI**：`reverb_card.dart` L20-29 仅映射索引 0-7 + l10n 名；出厂预设引用索引 1 / 3（`MEDIUMHALL1` / `SMALLHALL1` 等，见 v1.2 §1）。
- **app 自定义混响**：`setReverbCustomParam` 仅暴露 **6/16 维**（decay/damp/wet/dry/roomSize/width，Freeverb 风格 customParam），**不等于** `sf_advancereverb` 的全部 16 维。

### 2.2 三种外置方案

**方案 A —— 纯展示外置（零引擎改动）**
- 把 **19×16** 表转录为 `assets/presets/reverb_legacy.json`（仅 UI 展示预设名 + 参数预览），应用仍走引擎索引 `Reverb_SetParam(index)`。
- 价值有限（参数仍硬编码在 C），**不解决"代码不在代码中存储预设"的硬要求**；仅消除"UI 对索引的魔法认知"。不推荐作为终态，可作铺垫。
- **状态：已完成** → `app/auradsp_app/assets/presets/reverb_legacy.json`（19 预设 × 17 字段，UTF-8 验证通过，零引擎改动，可被 UI 按索引 0-18 展示预设名与参数预览）。

**方案 B —— 全参数驱动（需引擎 + app 改动）**
- 暴露全部 16 维为可写引擎参数（或直接 `setReverbCustomParam` 扩到 16 维），app 把 18 预设展开为 16 维参数集，应用走 `setReverbCustomParam` 全量写入，**废弃索引路径**。
- 改动面最大：引擎需加 16 个 get/set 分支（或一组 `reverb.paramN`）+ app 侧重映射 + 自定义卡扩到 16 维。
- 代价：16 维中 `ERtoLt/ERFac/InpLP/BasLP/DmpLP/OutLP` 等当前 app **完全无 UI 控件**，外置后要么暴露给用户（产品表达变化），要么固定为预设值。

**方案 C —— 新引擎 API（中等改动）**
- 加 `auradsp_apply_reverb_by_params(const float p[16])`（或 `set_reverb_preset_params(int index, const float[16])`），把外部预设参数灌入 `sf_advancereverb`，**C 内 `ps[]` 表删除**。
- 需新导出符号（**ABI 升版**）+ isolate/FFI 接线 + app 把预设表移到 assets。
- 相比 B：不污染 set_param 的 16 维命名空间，ABI 边界更清晰，但升版要协调桥侧（VB/ASIO/VAIO 三桥）。

**推荐路径**：先做 **A**（转录资产、消去索引魔法、为 B/C 供给数据），再据产品是否要"完全数据驱动 + 全维度暴露"决定 B 或 C。B/C 的取舍 = 「保留按索引快速切换」vs「彻底数据驱动」。

### 2.3 关键约束

- 16 维的部分维度 app 无控件，外置后这些维度要么暴露、要么固定为预设值——**影响产品表达**，需产品拍板。
- 索引语义耦合：factory 预设引用索引 1/3；外置后须改为预设名 / 参数集引用，避免"索引漂移"（C 表增删预设会错位）。

## 3. 实施建议优先级

1. **字符串回读（并入下一轮）**：`liveprog.code` 接线 + `eq.curve`/`arbmag.string` 补 2×2 小分支。
