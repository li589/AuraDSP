## S1 持久化根修（分诊项 4 + 项 6 后半，已定罪）

根因：启动恢复以 `session_state.json` 为权威（restoreMemoryImage 覆盖
config），但 session 保存只由参数编辑触发（`scheduleAutoSave` 只挂在
state_chain 的参数 setter 上）；`setPipelineInput/Output`、
`setPipelineInputDevice/OutputDevice`、`setApoTargetEndpoint`、
`setAttachmentMode/setAudioMode` 等模式/管线类 setter 只写 config.json，
纯切模式的会话重启后必被旧 session 快照覆盖（config 里实际是对的）。

改动：
- state_audio_modes.dart / state_vb_asio.dart 中全部模式、管线、设备、
  APO 目标、ASIO 参数类 setter 统一在落盘点后调 `scheduleAutoSave()`
  （防抖，与参数同口径）；逐个核对清单在实现时以 grep 全量枚举为准。
- 兜底加固：restoreMemoryImage 的字段恢复顺序维持不变，但启动回放完成
  后立即 `SessionMemory.save` 一次对齐（防旧快照在新版首启后继续残留）；
  dispose 兜底保存保留。
- 测试（test/，J6 口径）：新增用例钉住「setPipelineInput('vaio') 后
  scheduleAutoSave 的防抖保存产出的 session 快照含 pipelineInput=vaio」
  「setApoTargetEndpoint 后快照含目标端点」「setPipelineOutput 同理」。
  实现手法以现有 state 测试的 fake/内存盘设施为准，不引入新框架。

## S2 WASAPI 失效自愈（分诊项 6 前半，日志实证）

现状：本地 WasapiOut 客户端被端点栈重启打死（0x88890004
DEVICE_INVALIDATED）后，pump 每轮抛 StateError → 通用 400 轮死亡计数
（细审 R-B 2）触发 wasapiLost → 状态层整条 audio isolate 重启；r2 实测
在 APO 一键附加后发生，且伴 UI ready 800ms 超时。失效客户端按 WASAPI
语义永不自愈，400 轮纯属陪跑；整 isolate 重启又殃及 APO 发布器/桥状态。

改动（audio_isolate.dart pump + audio_out_wasapi.dart）：
- pump 捕获端按 HRESULT 分流：错误消息含 `0x88890004` 时走**输出重初始
  化路径**——停旧 AudioOut、按启动同口径重建（createAudioOut + init +
  start，端点跟随当前默认/已选端点），退避 0.5s→1s→2s→4s（封顶 4s），
  期间 pump 以静默轮转等待（不计死亡计数、不发 error 事件，只落采样
  dbgLog）；重建成功即恢复正常泵轮并落 `wasapi: out reinit ok` 一行。
- 重建连续失败约 30s 才回落既有 wasapiLost 语义；非 INVALIDATED 错误
  的 400 轮口径**原样保留**（不回退 R-B 2）。
- 捕获链在场时的所有权约束：capturemode 激活期间 audioOut 由捕获控制
  器托管（setAudioOut 缝），重初始化必须经同一缝换入新实例，禁止旁路
  直接赋值造成双持有；实现时以该缝为唯一换入点。
- 状态层（state_events.dart 'wasapiLost'）：重启 isolate 的条件收窄为
  「本地渲染是该模式的实际输出路径」（管线 WASAPI 输出）；sysapo 等附
  加模式忽略（本地输出在附加模式无职责，APO 通道不受其生死影响），
  vbcallback/asio 的既有忽略口径保留。

验证：本地无法跑 Windows WASAPI——以 Dart 静态分析 + J6 既有测试不回
归为准绳；重初始化分流逻辑抽纯函数（错误分类 + 退避表）单测覆盖；
真机验收 = APO 附加/分离反复操作时不再出现 isolate 重启与 ready 超时。

## S3 APO 就绪三态（分诊项 7，首要嫌疑 + 可观测性缺口）

背景机制（代码核对）：TryStart 先 ClaimSeat（建 telemetry 块）后
LoadEngine，参数块在引擎创建成功后才建；LoadEngine 三候选（APO 同目录
纪律版 → 同目录主引擎 → 上一级主引擎）任一失败均静默。由此 audiodg 内
引擎加载失败的指纹 = 心跳活（status 查心跳判「活跃处理中」）、座位恒
空、参数块永不存在、电平/viz 全无、声音直通——与 r2 项 7 全对。

改动：
- ApoEngineHost：LoadEngine 记录诊断——每候选的 LoadLibrary 结果与
  GetLastError、符号/ABI 校验失败步、auradsp_create 失败，编码为
  `loadDiag`（u32：低 8 位阶段码 0 未试/1 自目录缺失/2 加载失败/3 ABI
  或符号不符/4 create 失败/5 就绪，高 24 位 Win32 错误码）；TryStart 各
  失败出口与成功路径均写入 telemetry。telemetry 升 **v4**：v3 尾后追加
  loadDiag + loadErr 两 u32（块总长 736→744，映射页 4096 不变）。
  ApoShared.h、Dart 镜像常量、布局门（smoke_apo_plugin_layout）同步。
- Dart 读端（ApoTelemetryReader）：version>=4 时解析 loadDiag 并入
  'apotelemetry' 事件（loadStage/loadErr 字段）。
- 面板口径（sections.dart APO 状态行 + state_events 消费）：三态分级
  ——seat 已占且 applied 增长 = 「处理中」；心跳活但 seat 空且 loadStage
  为失败码 = 「已附加，引擎未就绪（引擎加载失败）」；心跳活 seat 空无
  失败码 = 「已附加，等待音频流」。「活跃处理中」不再单凭心跳下判。
  文案走 arb 三语。
- J5b：apo_engine_test 增断言——正常起链后 telemetry v4 loadStage=5
  （就绪）；失败路径（构建树内改名引擎 DLL 的子场景若可行为止）不强求，
  失败面真机验收。
- 并行用户侧证伪（不阻塞实现）：安装目录 driver\ 下 AuraApo.dll 旁是否
  有 auradsp_engine_apo.dll——若缺失，另查安装链为何漏装（dist 完整性
  2079f9b9 之后仍漏则属安装器复制面问题，在 S6 一并审）。

## S4 白噪 / ASIO 取证埋点（分诊项 2/3，未定罪，只取证不猜修）

- VaioBridge（bridge/vaio_bridge/VaioBridge.cpp）：每次 start 在 status
  JSON 增 `forensics` 一次性对象：起始 TotalBytesWritten、读游标初值、
  dataSize、blockAlign、首采样 hdr（bits/rate/channels/BlockAlign 原
  值）、首转换块的样本统计（peak、meanAbs）与**错位一字节对照统计**

  计形态差异即字节错位定罪/脱罪证据。isolate 侧 vaiostatus 首帧含
  forensics 时落一行 `vaio-forensics: ...`（与 vaio-geometry 同风格）。

  先查注册表枚举：目标名在册却加载失败 = COM 步失败；不在册 = 注册/
  名称步失败；why 串带步名 + CLSID（若有）。AsioBridge 的 start 失败
  note 透传该串（现有通道），isolate 既有 `asiomode: start failed
  note=...` 日志即落盘。
- CI 覆盖补强：桥 DLL（auraasio_bridge/auravaio_bridge）现无 CI 编译覆

## S6 重审查（本轮改动面 + 相邻状态机）

范围（逐面过，沿用细审分级口径）：
1. 双存储一致性全扫：config↔session 字段全表比对（save payload 键 vs
   restoreMemoryImage 恢复键 vs config 字段），找「存了不恢复/恢复了

   loadDiag 写入与 worker/reader 的版本门（v3 旧 App 读 v4 块、v4 App
