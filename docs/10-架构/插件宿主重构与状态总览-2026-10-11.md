## 2. CLAP GUI 挂载与卸载时序（已解决）

### 2.1 问题

JUCE 编写的 CLAP 插件（如 KV-Element-FX）在 `gui->set_parent()` 内部会尝试获取 `MessageManagerLock`。
**若调用线程不是 JUCE MessageThread，该锁永不释放 → 死锁。**

### 2.2 挂载：已尝试方案

| 方案 | 做法 | 结果 |
|---|---|---|
| A | 子线程执行 `create` + `get_size` + `set_parent` + `show` | ❌ `set_parent` 死锁 |
| B | 主调用线程 `create` + `get_size`，子线程 `set_parent` + `show` | ❌ 子线程仍非 JUCE MessageThread，`set_parent` 死锁 |
| C | 子线程先建 HWND 并启动消息泵，主调用线程 `set_parent` + `show` | ❌ `set_parent` 阻塞（其内部等待 JUCE 消息线程回调） |
| **D（采用）** | 子线程创建 HWND 并**立即进入消息泵循环**，HWND 就绪后**发信号**给主调用线程执行 `set_parent` + `show` | ✅ `set_parent` 返回 1，`show` 成功 |

### 2.3 方案 D 实测输出（首次成功）

```
[DBG CLAP showEditor] gui->create returned: 1
[DBG CLAP showEditor] gui->get_size on caller thread: 1230x730
[DBG CLAP showEditor] in lambda, hwnd created: 000000000206095C
[DBG CLAP showEditor] gui->set_parent returned: 1        ← 首次成功!
[DBG CLAP showEditor] gui->show done.
Final mgr.showEditorSlot returned: 1                      ← 首次成功!
```

### 2.4 卸载挂死：根因与修复（2026-10-12 凌晨定位）

挂载成功之后，`test_plugin_direct.exe` 仍然退出码 1。**第一轮定位得到的"卡在 `closeEditorSlot`"是假根因**：
`std::cout` 重定向到文件时是全缓冲，进程被超时杀掉后缓冲区整段丢失，日志恰好停在最后一个 flush 点，
把一个位于**更后面**的挂死伪装成了"上一步之后就没输出"。

给测试加 `std::unitbuf` 与阶段耗时打点后，真实调用链暴露出来：

```
[DBG CLAP closeEditor] WaitForSingleObject -> 258 (TIMEOUT)   ← 编辑器线程 800ms 内没退出
[DBG CLAP closeEditor] WM_QUIT -> tid 15420
[DBG CLAP closeEditor] DETACHED (thread still alive!)         ← 被 detach，线程仍在跑
[DBG Slot] unloadLocked[0] unload
[DBG CLAP unload] step 3: plugin->destroy                     ← ★ 永久挂死在这里
```

**根因**：编辑器线程的消息泵退出路径上调用了插件的 `gui->hide()` / `gui->destroy()`。
这两个调用同样受 JUCE `MessageManagerLock` 约束，**必须在 CLAP 认可的 main thread 上执行**；
放在编辑器线程里会永久阻塞。于是线程卡死 → 宿主 800ms 超时后 detach →
随后 `plugin->destroy()` 等待该 GUI 资源释放 → 整个卸载流程挂死。
**与 `set_parent` 是同一根因的第二次发作。**

**修复（四条）**：

1. **GUI 调用归位**：`gui->hide` / `gui->destroy` 移出编辑器线程，改由调用线程在 `closeEditor()` 中执行。
   编辑器线程职责收敛为「建窗口 → 泵消息 → 销毁自己的窗口」，全程不碰插件对象。
2. **退出握手**：`closeEditor` 先发 `WM_CLOSE`（走窗口过程）再补 `PostThreadMessage(WM_QUIT)`（兜底线程队列），
   等待时间 800ms → 3000ms。线程此时只做纯 Win32 清理，必然及时退出。
3. **只关一次**：`closeEditor` 会被调用两次（`unloadPluginSlotLocked` 一次 + `unload()` 内部一次），
   新增 `m_guiCreated` 原子标志守卫，保证 `hide`/`destroy` 对一次 `create` 只执行一次。
4. **超时不泄漏**：`unload` 路径与 `showEditor` 的失败/超时路径都会回收线程；
   新增 `m_editorAbort` 标志让编辑器线程在拿到 HWND 后立即检查并退出，
   不再进入一个永远等不到 `WM_CLOSE` 的消息泵。同时把跨线程 `std::promise` 由「栈上对象引用捕获」
   改为 `std::shared_ptr` 持有——超时返回后线程仍可能 `set_value`，引用栈帧即 UAF。

VST3 侧同构的「栈引用 `promise` + 超时泄漏线程」隐患一并按同样方式消除；
VST3 的 `IPlugView` 调用位置**未改动**（实测无死锁证据，不做无依据的重构）。

## 5. Element 源码给予的关键启示

| 主题 | Element 做法 | 本项目对标 |
|---|---|---|
| **线程模型** | `thread_local ThreadType gThreadType` 全局标记；JUCE MessageThread 永远报告 MainThread | `ClapHostThreadType` 等效实现 |
| **GUI 生命周期** | `CLAPEditor` 在 JUCE Component **构造函数**中调 `gui->create` / `gui->get_size`，在 `parentHierarchyChanged` / `visibilityChanged` 回调中调 `gui->set_parent` 与 `gui->show` | **所有 GUI 调用必须发生在 CLAP 认可的 main thread 上** —— 这是方案 A/B/C 全部失败的根因 |
| **定时器** | Linux 用 JUCE Timer 轮询 `on_timer`；Windows/macOS 由原生消息泵自动派发 | Win32 `SetTimer` + `WM_TIMER` 等效映射 |

**核心结论**：CLAP GUI 的正确挂载时序 = 「先在专用线程把 HWND 与消息泵跑起来，再回到 CLAP 认可的 main thread 上做 `set_parent` / `show`」。
