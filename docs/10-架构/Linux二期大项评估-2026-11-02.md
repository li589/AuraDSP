## 1. ALSA 直连低延迟专家模式（D-6 二期）

### 1.1 现状与价值

- 一期音频走 PulseAudio simple API：输出 `tlength` 2048 帧
  （48k 下 ≈43ms），采集侧同量级；virtual/driver 模式往返延迟是
  两侧之和再加服务端缓冲——对「听湿录干」类实时监听场景偏大。
- ADR-012 D-6 原文定位：ALSA 直连是**低延迟专家模式**，与 PA
  并存、不替代 PA（PA 仍是默认与三模式语义的载体）。
- 端口面现成：App 侧 `AudioOut` 只有 8 个成员（init/start/stop/
  write/currentPadding + 三个属性），`PulseAudioIn` 同构；新实现
  是往既有工厂分派里加一个实现类，不动泵与引擎。
- 额外红利：driver 模式可直连 `hw:Loopback`，绕开一期在 PA 侧
  踩过的全部枚举坑（`.monitor` 源选择、卡序问题），且回环延迟
  远低于经 PA 中转。

### 1.2 工作分解与量级（估算，工作日）

| 阶段 | 内容 | 量级 |
|---|---|---|
| A0 探针 | libasound FFI 面验证：对 ALSA `null` PCM 设备（无硬件可跑通全流程）验证 open/hw_params/period 协商/writei/XRUN 恢复；量可达 period 下限 | 0.5–1 |
| A1 输出 | `audio_out_alsa.dart`：`hw:` 设备直开、period 256 帧默认、`snd_pcm_delay` 做 padding、XRUN 自恢复；工厂分派 + 设置页专家开关（默认仍 PA） | 2–3 |
| A2 采集 | `audio_in_alsa.dart` + driver 模式专家路径直采 `hw:Loopback`（与 PA 路径并存、设置里选） | 2 |
| A3 收尾 | 设备枚举（`snd_device_name_hint`）进设置页、EBUSY 等错误文案与指引、门禁（null 设备活体门禁 + 决策纯函数单测）、CI 接入 | 1–2 |

合计约 **6–8 个工作日**，可按阶段独立提交、独立验收。
（执行注记：A1 实际交付时 A3 的枚举被拆开——设备名字段先行，
`snd_device_name_hint` 下拉枚举并入 A3 统一做。）

### 1.3 风险与未知

- **PipeWire 共存（最大风险）**：PipeWire 系统上声卡由 WirePlumber
  持有，直开 `hw:` 可能 EBUSY，或与会话管理器抢设备。缓解：
  专家模式自带「设备被占用」明确报错与指引（释放设备/选独立
  接口）；snd-aloop 不受 PipeWire 声卡策略影响，driver 直连路
  径不受此风险。真机（用户 Ubuntu）需验一轮 PipeWire 下的实际
  行为，列入验收。
- **硬件差异**：hw_params 协商（格式/period/buffer 可用组合）因
  卡而异；以「协商失败即回退并报错」为口径，不追求全覆盖。
- **无热插拔**：ALSA 无设备事件，专家模式以「打开时定设备」为
  语义（与服务端跟随默认设备的 PA 模式形成对照，文档写明）。
- VM 可验范围：`null` 设备全流程 + API 语义；真实延迟数字与
  PipeWire 行为必须真机验收（沿用真机验证清单模式）。

### 1.4 隔离方式

新文件 `audio_out/audio_out_alsa.dart`、`audio_in_alsa.dart` +
工厂一行分派 + 设置页一个专家区；PA 路径零改动；Windows 零
感知（PlatformProfile 门控）。引擎 C ABI 不动。

## 2. Linux 插件宿主（D-7 二期 / CP-24）

### 2.1 现状取证

- 一期以 `AURADSP_ENABLE_PLUGINS=OFF` 整体裁剪（Linux CMake 强制
  OFF 并有守卫），stub 与真实实现 C ABI 56 符号全等——启用宿主
  不碰引擎导出集，这点已在一期验证过。
- 插件子系统结构：`engine/plugins/{api, driver, formats/{clap,
  vst3}, integration, platform/win32, tests}`。耦合分布：
  - **platform/win32 平台层**（约 2.7k 行）：进程外宿主
    （host_main 564 + host_client 544 + shared_region 67 +
    process_plugin_proxy 565）、模块加载、路径、GUI。
    进程外设计是 Windows 侧的崩溃隔离方案（有 quarantine 测试
    守）。Linux 需整套 POSIX 对应物（posix_spawn、shm_open/mmap、
    socketpair/eventfd 同步）——**这是本项最大的单块工作**。
  - **formats 层**：clap_instance.cpp 1110 行、vst3_instance.cpp
    1679 行。主体是格式 API 逻辑（可移植），Win32 集中在编辑器
    GUI 段（clap 614–679、vst3 364–388）与少量平台调用。
  - **元数据（CP-24）**：plugin_scanner.cpp（529 行）读 PE 版本
    资源枚举插件；Linux 无 PE 资源。务实路径是**进程外探测**：
    在牺牲型宿主进程里加载 .so 查工厂信息（VST3/CLAP 都有标准
    工厂查询），不必写 ELF 解析器；clap/vst3_metadata.cpp
    （147/197 行）随之改造。
  - **可复用资产**：`engine/platform/port/module.h` 已有 dlopen
    的 Linux 实现（引擎在用）；VST3 SDK 与 CLAP 头文件已 vendored
    （`vendor/plugin-api/{steinberg, clap}`），SDK 本身跨平台。
  - **App 侧**：A6-1 `PluginHostPort` 能力端口已落地（插件页按
    能力降级）；`supportsPlugins` 在 Linux 打开 + 取消隐藏目录
    UI（S5c 的反向操作）即可接线。
  - **编辑器 GUI**：插件自带编辑器在 Linux 走 X11 窗口嵌入，
    与 Flutter/GTK 的合成是独立难题；**建议首版宿主不带编辑器**
    （参数走通用 UI），编辑器单列后续阶段。
  - LV2：当前 formats 层根本没有 LV2 驱动，属新增格式，**不
    建议并入本项**，如需另行立项。

### 2.2 工作分解与量级（估算，工作日）

| 阶段 | 内容 | 量级 |
|---|---|---|
| P0 探针 | Linux 下以 `AURADSP_ENABLE_PLUGINS=ON` 编通 formats+driver（GUI/元数据先桩）、进程内加载一个自建最小 CLAP 测试插件并跑通 process | 2–3 |
| P1 元数据 | CP-24：进程外探测式扫描替代 PE 资源读取；扫描结果结构与 Windows 对齐 | 2–4 |
| P2 宿主平台层 | platform/posix：宿主进程、共享内存、代理协议移植（Win32 共享区协议在 POSIX 原语上重表达） | 5–8 |
| P3 formats 解耦 | GUI 段端口隔离（无编辑器实现）、模块加载走 port/module、VST3 继 CLAP 之后接入 | 4–6 |
| P4 App 接线 | supportsPlugins 打开、目录 UI 恢复、PluginHostPort 实接、门禁与 CI（自建测试插件入 CI 构建） | 1–2 |

合计（不含编辑器 GUI）约 **14–23 个工作日**；编辑器（X11 嵌入）
另估 5+ 且不确定性高。CLAP 先行可让 P3 的首个格式更快见效。

### 2.3 风险与未知

- P2 的协议移植是全项最不确定处：Win32 共享区协议里的事件/
  锁语义在 POSIX 上的等价物需要逐项核对，探针（P0）覆盖不到
  这一层——**P2 开工前应有一次专门的设计核对**。
- 进程内 vs 进程外是架构抉择：若 Linux 首版改进程内直载，
  P2 大幅缩水（省 5–8 日），但放弃崩溃隔离（Windows 侧为此
  付过 quarantine 测试的代价，插件崩溃会带走主进程）。建议
  保持进程外，与既有设计一致——请 owner 在立项时确认。
- 第三方插件的 ABI/线程行为不可控，测试只能以自建插件 +
  少量知名开源插件（CLAP 生态）抽样，真机验收清单需扩一节。

### 2.4 隔离方式

全部落在 `engine/plugins/platform/posix/`（新）+ formats 的
GUI 端口守卫 + Linux CMake 的开关放行；Windows 构建路径与
源文件零改动（platform/win32 不动）；App 侧以 supportsPlugins
为总闸。C ABI 导出集不变（stub/真实实现的恒等关系在一期已
证，启用后由既有 ABI 门禁持续守）。

## 3. 立项建议

1. **先立 ALSA 专家模式（二期-1）**：量级小、确定性高、VM 可
   探针、真机一轮可验收；且让 driver 模式多一条不依赖 PA
   枚举的 robust 路径。建议按 A0→A3 直接排期。
2. **插件宿主（二期-2）先只批 P0 探针**：探针用 2–3 日回答
   「formats+driver 在 Linux 编通 + 进程内跑通一个 CLAP 插件」
   的可行性，并顺带摸清 P3 的真实耦合面；探针报告回来后，
   再就 P1–P4 全量立项与「进程外保持不变」一并裁定。这样
   最贵的一笔投入（P2）是在信息最全时做的决定。
3. 两项无相互依赖，可任意排序；若 owner 只想先动一项，按
   上序。若两项都暂缓，本评估归档，二期不开工亦无沉没成本
   （一期形态完整可用）。
