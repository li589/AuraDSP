## 0. 现状要点（取证结论，只列与计划相关的）

**我方插件链**：4 槽（`engine/plugins/plugin_limits.h` `kMaxSlots=4` 为跨语言单一真相），链序 =（插入级 0–4，槽序）；其他模式下插件由「当前处理引擎」托管，默认**进程外隔离宿主**（plugin_host_x64/x86），VB 模式为每总线一个引擎（Potato 8 组 × 8 通道，`vbBusMask` 管引擎存废、`vbPluginGroupMask` 管各组插件链开关）。编辑器与处理是**同一实例**（隔离宿主内），不存在状态回写问题。既有故障概念只有 `remoteFailed`（隔离宿主传输层失联→自动直通+UI 标记），**没有逐槽进程内崩溃的 SEH 闩锁**（本计划 Part I 补此机制，用户裁定为全平台通用，见 I.2 D4）；另有三张隔离表（加载崩/开编辑器崩/关闭崩）由 App 侧日志驱动预拦截。

**sysapo 现状**：APO 引擎变体为 NO_PLUGINS stub（全部 `auradsp_plugin_*` 返回不可用）；插件栈**零模式感知**——插件命令被 isolate 静默路由到不发声的本地句柄，**界面看起来能操作、实际什么都不发生**。这是本计划必须消除的第一现状（无论插件托管做不做，模式能力必须显式）。

**EqualizerAPO 实证**（源码级）：
- 编辑/处理分离 = **双实例 + 配置文件唯一通道**：编辑器进程内自建 GUI 实例（种子 = chunk/参数名值对），点 Apply/OK 才把状态序列化进 config.txt；APO 侧 FilterEngine 监听目录变化，全量重建处理图并以 10 ms 交叉淡化切换。没有实时参数推送、没有回传——**APO 侧插件崩溃只写日志**（且日志落在 audiodg 的 LocalService %TEMP%，用户侧编辑器根本读不到），界面无任何感知。
- 插件保护：VST 托管层三处 SEH（实例化、prepare、process）。init/prepare 崩 → 该实例本会话永久跳过；**process 崩不闩锁**——只记一次日志、当次调用改直通、下个块重试（与我方先前转述的「崩后跳过」有出入，以此次源码复核为准）。
- 多声道 = 按插件声道数**扇出 N 个独立实例**、喂同一份 chunk，无环绕感知。
- 安装（DeviceAPOInfo）：三档模式为每设备状态（LFX/GFX=,1/,2；SFX/MFX=,5/,6；SFX/EFX=,5/,7），**装一档删其他代槽位**；前后混独立开关；原厂 APO 以「子 APO 链」方式被其 APO 在运行时重新托管（被顶替者继续运行）；原厂 GUID 跨代映射（LFX↔SFX、GFX↔MFX/EFX，带 Win8.1 门槛）；安装状态可由注册表内容**反推**（模式推断 + 按 OS/驱动槽位/Win11 合并蓝牙设备的推荐档启发式）；书签键带 Version 并对更高版本硬报错；FxProperties 建不出时有 takeOwnership 自修复；另有 DisableProtectedAudioDG 与注册状态的检查/修复函数。其短板：卸载不还原 ProcModes/FxTitle、DisableEnhancements 安装时直接删且不快照（永久丢失）、复合槽（,13/14/15）只读不写不管、每次 install 重快照（靠 load 时把自身 CLSID 译为「无值」部分缓解）。

**社区/文档侧关键事实**（分级见调研报告）：
- 微软口径：APO 定位是驱动捆绑、签名、实时、进程内 COM DSP；**无明文禁止托管插件**，但实时契约（不阻塞、不用分页内存）与稳定性计量（崩溃/禁用计入驱动提交质量）都指向反面；APO 异常 → 音频引擎崩溃、看门狗强制重启、全系统音频丢失至引擎重启（Audio measures 文档）。失败计数达 10 → 端点 SysFx 被禁用（两处文档口径：HRESULT 失败计数 / 连续崩溃计数，未见文档将二者等同，计划按「两种都可能触发」保守处理）。
- LocalService 身份的真实痛点**不是**沙箱而是**文件与许可**：插件要读用户目录下的预置/许可文件时在 APO 内必失败（ProcMon ACCESS_DENIED 为社区标准诊断法）；EqualizerAPO 编辑器自带警告「音频服务读不到此库文件」并建议把 DLL 复制进其 Program Files\VSTPlugins；许可类插件（FabFilter 案例）编辑器实例看得见许可、引擎实例看不见 → 试用模式/30 天后静音。引擎实例无任何实时数据显示（频谱/采样率不动）是双实例架构的固有表现，与用户描述一致。
- 未证实项（不作为计划依据）：audiodg 的 LPAC 归属（无来源）、iLok 在 APO 内的具体行为（仅机制推断）、CFG/CET 是 audiodg 的实际拦截者（仅机制存在）。

## Part I — System APO 模式插件托管升级

### I.1 目标形态（用户口径落位）

- sysapo 下插件链**真处理**：处理在 APO 侧引擎内（audiodg），界面在 App 侧——编辑器可正常打开（App 侧影子实例），但**不显示该插件的实时处理可视化/音频流**（与 EqualizerAPO 的实际形态一致且为双实例架构的固有边界）；整机频谱/电平仍由 telemetry 回传，不受影响。
- **逐槽防护（通用机制，用户裁定）**：逐槽崩溃防护**与引擎/宿主无关**——任何平台、任何驱动/模式的插件托管路径都同一套语义：某槽插件在加载/处理时崩 → 故障闩锁到该槽、该槽自动旁路、其余槽与链路继续。sysapo 只是该机制的一个宿主形态（机制本体与各宿主分工见 I.2 D4）。**显示与恢复口径（用户裁定）**：故障旁路的文字与正常旁路**完全一致**——挂载时旁路、用户手动旁路、安全卸载旁路、故障旁路都显示「旁路」；区别只有视觉：故障旁路加**呼吸闪动**示异常；**重新点击故障旁路即尝试重新加载该插件**，成功则解除故障旁路恢复处理，失败则维持故障旁路。故障边沿另经 NoticeHost 发**低栏通知**（一次/边沿）。此套「闩锁 + 回传 + 可见 + 可恢复」**优于 EqualizerAPO**（它无回传、process 崩不闩锁、用户无感知），按用户口径执行，不照抄。
- 其他模式维持现状（隔离宿主、实时处理、实时流显示全保留）；VB 的每总线接线维持现状。
- **VB 专属 UI 不进 sysapo**：插件页的路线下拉（`plugins_hero.dart`，现已按 `vbcallback` 门控）在 sysapo 不出现——本计划将其改挂到模式能力模型上（见 I.4），并用测试钉死「sysapo 下无此下拉」；频谱分析仪的 VB 总线行同理。
- 声道形态从简（用户口径）：sysapo 按端点流声道（2/4/6/8）走引擎既有链路语义（插入级 + 槽位 channelMask），不做 VB 式每总线扇出。

### I.2 架构决策

- **D1 托管形态 = APO 引擎内进程内托管**。`auradsp_engine_apo` 新增构建风味：核心以真实插件子系统编译（/MT + /guard:cf 不变），但源表做 APO 裁剪——**纳入**：host manager、chain component、bundle、driver registry、json、三种格式的 instance/metadata；**排除**：编辑器 GUI（win32/x11）、scanner 与 plugin_paths（扫描永留 App 侧）、远程宿主三件套（audiodg 内不 spawn 子进程）、plugin_thread 的编辑器泵部分（异步加载任务保留）。编辑器类 C ABI 在 APO 风味内返回不支持（影子实例在 App 侧开编辑器，见 D3）。
- **D2 插件身份经通道下发**。参数块新增**插件段**：每槽 {格式， DLL 路径（UTF-8）， 插入级， 声道掩码， 旁路位} + 链总开关/PDC。APO worker 与参数应用同一 diff 机制：身份变化 → 卸载旧/加载新（worker 线程，非 RT）；加载结果（成功/失败类别）经 telemetry 回传。失败类别借 EqualizerAPO 工厂的分类法：未找到 / 读不到（权限）/ 加载失败 / 入口缺失 / 架构不符 / 初始化崩溃。
- **D3 编辑器与状态同步 = 影子实例 + chunk 经块回传**。App 侧本地链在 sysapo 下转为**影子链**：同一槽位配置在本机引擎（隔离宿主照旧）加载同一插件，仅供开编辑器与调参，音频不经它（本地句柄本就不发声）。编辑器关闭/点应用时，经既有状态存取机制取出该槽 chunk 字节 → 发布者写入参数块插件段的**状态区** → APO worker 对其侧实例做 setState。⚖ **取舍点 1**：状态区形态——(a) 块内 blob（每槽上限 512 KB，超限槽标记「状态过大」并通知）；(b) 文件中转（走 Part III 的共享目录基建，块内只放文件名）。推荐 (a) 为主、(b) 为超限兜底，两者不互斥；若只许选一，选 (a) 并把上限写进已知边界。
- **D4 逐槽防护 = 插件托管通用机制（用户裁定，与引擎/宿主无关）**。落点是各风味共用的 `PluginChainComponent`：逐槽 process 与加载/初始化路径经**单点包裹函数**守卫；异常 → 槽故障闩锁（槽 status JSON 新增 `fault` + `faultStage` + 失败类别），链内该槽按旁路继续、其余槽照常，故障状态经槽状态通道回传 UI（D5）。语义全平台一致；守卫技术按平台：Windows = SEH，POSIX 进程内托管以隔离宿主为主要守卫、闩锁接口（fault 字段与状态语义）共用，信号级守卫是否补齐由 Q0 设计附记定（不预先承诺不存在的实现）。
  **与既有隔离手段的分工（不重复造层）**：① **隔离宿主（默认远程）**：进程边界是外墙——宿主进程死亡走既有 `remoteFailed` 传输层判定与自动直通；逐槽 SEH 是其**内层**，先于进程死亡把异常收在槽内，保住宿主进程与其余槽，只有 CFG 快速失败类不可捕获异常才升级到 remoteFailed。② **本进程回退（本地引擎进程内托管）**：逐槽 SEH 是**唯一**的槽级防护——现状下一只插件崩会带走整个引擎，本机制正补此洞。③ **桥引擎（VAIO/ASIO/VB）**：插件在各桥引擎内进程内托管，与本地引擎同构，共用同一链组件与闩锁。④ **APO**：槽级闩锁（本机制）+ ApoEngineHost 整机 SEH（粒度不同：整机故障闩锁回透传）两层并存，不重叠。⑤ **隔离表（Dart 侧三张表）**：事前预拦截（已知肇事者不加载），与事中收容正交。
- **D5 故障状态回传与 UI 口径（全模式同一条路）**：槽故障状态不造 APO 专属通道——它就是 D4 槽 status 的 `fault` 字段：本地/桥模式经既有 `pluginSlotStatus` 事件回传；sysapo 经 telemetry v3 的插件段（每槽 {已加载， 旁路， 故障， 故障类别， 延迟样本， in/out RMS， processCalls}）回传，isolate 合成同形状事件。PluginManager 槽状态统一带故障标记（`PluginHostStatus` 增 fault 字段，不另设 APO 专属字段），渲染与交互单点决定、所有模式一致：**文案恒为「旁路」**（不区分旁路成因）；故障槽的旁路指示**呼吸闪动**；**点击故障槽的旁路 = 发起重新加载**（走既有加载命令路径与状态对账，不另设恢复机制；成功 → 清闩锁恢复处理，失败 → 维持故障旁路并以失败类别发通知）；普通旁路的点击仍是既有旁路开关语义，两种点击由 fault 字段分流。故障边沿由状态层发 NoticeHost 通知。槽 RMS 只作「在处理」证据（~2 Hz 刷新），不冒充实时流。
- **D6 兼容与预拦截**：x86 插件在 x64 audiodg 内不可加载（无桥可言）→ sysapo 下槽位加载前由 App 侧按架构预判并通知；既有三张隔离表扩展适用 sysapo（加载崩日志命中 → APO 侧不再尝试该插件）。插件 DLL 及其依赖的**可读性**以 APO 侧实际加载结果为准（App 侧无法代测 LocalService 视角），失败类别如实回传展示。

### I.3 已知边界（写进收口与面板文案，不藏着）

- 许可/预置在用户目录的插件可能在 APO 侧以试用模式运行或加载失败（社区实证的固有边界，非本计划可解；状态文件类问题可由 D3 的 chunk 同步缓解，许可文件不在此列）。
- 插件编辑器内自带的电平/频谱不动（影子实例无音频），属预期形态，编辑器标题区/插件页在 sysapo 下有明确标注。
- CFG 类快速失败（0xC0000409）SEH 兜不住，极端情况下仍可能带崩 audiodg（系统会重启音频引擎；反复触发有端点 SysFx 被禁风险）——隔离表预拦截是主要对冲，面板文案如实说明。

### I.4 平台收敛（用户硬要求：拒绝特调/硬置入）

- 在模式层（`lib/core/audio_modes.dart`）引入**模式能力模型** `ModeCaps`（按模式 id 查表）：`pluginProcessing ∈ {local, apo, none}`、`pluginEditors ∈ {liveInstance, shadowInstance, none}`、`pluginLiveMeters ∈ bool`、`routeSelector ∈ bool`（VB 下拉类）、`fileEffects ∈ bool`、`mcScript ∈ bool`、`chainVizLive ∈ bool`。features 与插件栈**只问能力、不再写模式字符串判断**；现存 6 处 `audioMode ==` 散点在本计划触及范围内迁到能力查询（其余散点登记为后续清理项，不在本计划扩围）。
- Windows 专属实现（APO 通道、桥、注册表）继续只住在 platform/ 与 isolate 层；插件段的块布局仍由生成器从单一真相产出（与参数布局同一机制），不手写第二份。
- 引擎侧 APO 风味差异收敛在构建风味源表一处；逐槽 SEH 闩锁是全风味共用的链组件机制（单点包裹函数），**不算 APO 差异**，禁止在共享 DSP 代码里散布 `#ifdef` 行为分叉。
- 故障旁路的呈现与恢复语义**与模式无关，不进 ModeCaps**：ModeCaps 只收随模式变化的能力（处理位置/编辑器形态/实时表头/路线选择器/文件类效果等）；故障呈现由槽状态的 fault 字段在插件栈一处决定，全模式同一套——这是「通用机制」在 UI 侧的对应落位。

## Part I Q0 设计附记（2026-11-10 定稿，实施前取证）

> 本附记是 I.5 中 Q0 的交付物：把 Part I 的布局、状态机与风味源表逐项定到可实施粒度。取证均为代码实读（`feature/linux` @ Part II 收口头）。

### Q0-1 故障模型：守卫已有、闩锁未有（Q1 的真实工作量）

取证：`plugin_host_manager.cpp` 已有逐槽 SEH/C++ 异常守卫（`processSlotGuarded` / `processInterleavedGuarded`，F-8a 落地）——进程内 process 崩溃今天**不会**带走引擎，但恢复动作是 `bypassed.store(true)`：**静默的永久自动旁路**，与手动旁路无任何区别、无类别、无恢复语义（用户解除旁路 = 直接重新启用肇事插件，下个块再崩再旁路）。加载路径只有 C++ `catch(...)`（/EHa 下兼收 SEH），失败只回 bool。

Q1 定版的状态机（落点 `PluginSlot`，与既有原子字段同置）：
- 新增三原子：`fault`（bool）、`faultStage`（0 无 / 1 加载 / 2 处理）、`faultCategory`（见下表）。
- **有效旁路 = bypassed || fault**，单点收敛于 `PluginHostManager::isBypassedSlot`（状态 JSON 的 `bypassed` 字段报有效值——UI 文案恒「旁路」由此自动成立）；process 两条路径的早退检查改走同一判定。故障槽的 PDC/延迟口径与手动旁路完全一致（音频不断流）。
- 置位点：process 守卫捕获 → fault(stage=2, category=process_crash) 并保留既有遥测门复位；加载守卫捕获（Q1 为 create/load/activate 包一层与 process 同构的守卫函数）→ fault(stage=1, category=init_crash)；加载分类失败（非崩溃）→ fault(stage=1, 对应类别）。远端模式下宿主进程内的同一管理器同构置位（见 Q0-6 的转发核查项）。
- 清除点：`unloadPluginSlot` 清 fault；加载成功在 `commitInstanceLocked` 清 fault。`setBypassSlot(false)` **不**清 fault（故障槽解除旁路的唯一路径是重新加载——App 侧点击分流见 D5，引擎侧只保证语义不被旁路开关短路）。
- 状态 JSON 增三字段（附加式）：`fault` / `faultStage`（字符串）/ `faultCategory`（字符串）。Dart 解析按缺省无故障兼容旧引擎。

失败类别枚举（D2 落位，字符串即线上口径）：`not_found`（无驱动认领路径 / 二进制解析为空 / 文件不存在）、`unreadable`（文件在位但加载器拒绝：权限或 OS 加载错误）、`load_failed`（实例创建失败或 load 泛化失败）、`entry_missing`（格式入口缺失：CLAP entry / VST3 工厂 / VST2 主入口为空——驱动可判处给值、判不出归 load_failed）、`arch_mismatch`（加载器映像格式错误：Win32 ERROR_BAD_EXE_FORMAT / POSIX ELF 类不符——bundle 加载处可判）、`init_crash`（加载期守卫捕获）、`process_crash`（处理期守卫捕获）。类别以宿主管理器落点判定为主，格式驱动能细化时经实例 `lastLoadCategory` 上报（Q1 只做管理器粒度 + bundle 加载的 arch/unreadable 两类细化，其余归并，不为类别完整性扩围到逐格式改造）。

### Q0-2 POSIX 守卫裁定：不补信号级守卫

裁定：**POSIX 不补 sigaction/siglongjmp 信号级守卫**。理由：① 从任意插件 AV 以 siglongjmp 跳回无法保证堆与锁完整性，恢复后的进程是「活着但可能已腐化」，比宿主进程干脆死亡更危险；② POSIX 的默认形态是隔离宿主进程（死亡走既有 remoteFailed 外墙，爆炸半径 = 宿主进程），进程内只是回退形态；③ 闩锁的状态机、类别与状态 JSON 全平台共用——POSIX 侧 fault 由 C++ 异常捕获与加载分类置位，硬件崩溃由进程隔离收容，两条路在 UI 呈现上汇合（fault 与 remoteFailed 都是「该槽/该宿主不可用」的可见状态）。本裁定为可撤销项：若将来有专门 spike + 崩溃插件实证证明信号恢复在本代码库可控，可另行立项，不在本 Part 扩围。

### Q0-3 插件块布局：独立映射（不长参数块）

参数块映射 32768B 已用 27028B，塞不下状态 blob；且其布局由生成器 + 漂移门钉死，动它即动 P1–P5 全部既有机械。故插件通道用**独立映射**（与参数块/遥测块并列的第三块，循 P2d 先例由 APO 创建、App 打开）：

- 名称 `Global\AuraDSP_ApoPlugins`；头 64B：magic `0x47505541`（"AUPG"）、version=1、writeSeq（seqlock：奇=写中、偶=稳定；纪律同参数块）、blockBytes、chainEnabled、pdcEnabled、预留。
- 每槽定长 525,376B：槽头 64B（format：0 无 / 1 VST3 / 2 CLAP / 3 VST2；insertStage；channelMask；bypass；loadGen；stateGen；pathBytes；stateBytes；预留 ×8）+ 路径区 1,024B（UTF-8，NUL 结尾）+ 状态区 524,288B（512KB，D3 取舍点 1 的块内上限）。
- 映射总大小 64 + 4 × 525,376 = 2,101,568B，向上取整 2,105,344B（514 页）。
- loadGen/stateGen 由发布者单调递增：worker 记录已应用代次，loadGen 变 → 按身份重载（卸载旧 → 加载新 → 若 stateGen 已随同发布则顺带应用状态）；stateGen 单独变 → 仅应用状态。链开关/PDC 在块头，worker 与参数应用同周期读取。
- 布局常量 C 侧落 `ApoShared.h`（static_assert 钉死偏移/大小），Dart 侧落 `apo_plugin_block.dart` 手写镜像 + 新增 `smoke_apo_plugin_layout.py` 交叉断言（与参数布局门同模式，不另造生成器——本块字段是人工契约而非引擎表派生）。

### Q0-4 telemetry v3：尾追加插件段

`ApoTelemetryBlock` 在 v2 的 608B 后尾追加（v1/v2 字段偏移不变）：每槽 32B × 4 = 128B，总 736B，version=3。每槽字段：loaded(u8)、bypass(u8，有效旁路)、fault(u8)、faultCategory(u8)、latencySamples(u32)、inRms(f32)、outRms(f32)、processCalls(u32)、appliedLoadGen(u32)、appliedStateGen(u32)。Dart 读者按 version>=3 读插件段（旧 APO DLL 混跑时该段缺席、插件页按「无回传」呈现），并合成为与本地同形状的 `pluginSlotStatus` 事件（D5）。映射大小不变（遥测映射本就整页粒度，736B 内含）。

### Q0-5 APO 风味源表（D1 落位）

`auradsp_engine_apo` 改为真实插件子系统裁剪版（/MT + /guard:cf 不变）：
- **纳入**（自主引擎源表按名取舍）：plugin_host_manager、plugin_chain_component、plugin_bundle、plugin_driver_registry、plugin_json、plugin_thread（见下）、clap/vst3/vst2 的 driver+instance+metadata 各三件、integration 四件（plugin_host / plugin_engine_state / plugin_chain_adapter / plugin_abi）、win32_util、plugin_module。
- **排除**：plugin_gui_win32（编辑器 GUI）、plugin_scanner、plugin_paths（扫描永留 App 侧）、远程三件套（shared_region / host_client / process_proxy）——并对 APO 目标定义 `AURADSP_HOST_INPROC=1` 使管理器远端分支整体不编译。
- **单点行为定义** `AURADSP_NO_PLUGIN_EDITOR`（仅 APO 目标定义一次）：plugin_thread 不启编辑器泵；plugin_abi 的编辑器与扫描入口返回不支持（影子实例在 App 侧，见 D3）。差异只存在于托管层 ABI 边界，不进共享 DSP/链代码（I.4）。
- **去 NO_PLUGINS**：`auradsp_core_apo` 与 `auradsp_engine_apo` 摘除 `AURADSP_NO_PLUGINS=1`（handle 恢复 PluginEngineState，与主引擎同构），两个 stub 退出 APO 源表。
- **纪律复核**（Q1 门禁）：插件子系统进 audiodg 后重跑 PE 纪律门——导入表不得出现动态 VCRUNTIME/MSVCP（/MT 保证）、CFG 表在位；新增系统 DLL 导入（VST3 的 COM 类）逐项登记于收口，不以「能跑」代替审查。

> **Q1 执行偏差登记（2026-11-10）**：Q0-5 源表里 plugin_scanner / plugin_paths 定为排除，实施时改为**保留编入**——PluginScanner 声明在 plugin_host.h、管理器扫描方法与其同 TU 耦合，剔除必须在共享管理器代码中散布 #ifdef（违 I.4 单点原则）；能力面改由 ABI 门关闭（`AURADSP_NO_PLUGIN_EDITOR` 下 scan 入口返回不支持），扫描代码在 APO 内无调用方、永不执行。plugin_gui_win32 按原定排除，其五个 win32_util 辅助符号由 APO 专用空实现 TU（plugin_gui_apo_stub.cpp）顶替链接。全局插件开关 OFF 的配置自动回落 CP-02 两 stub 形态（CMake 条件守护，handle 布局一致性优先）。

### Q0-6 状态同步 = preset 文件导管（D3 的既有机制就是它）

取证：`IPluginInstance` 无内存 chunk 接口，状态存取的既有机制只有 `savePreset(path)` / `loadPreset(path)`（App 会话恢复亦走此路）。故 D3 的 chunk 字节 = savePreset 产出的文件内容：App 侧对影子实例 savePreset 到临时文件 → 读字节写块状态区（超 512KB → 该槽标「状态过大」+ 通知，不截断硬塞）；APO 侧 worker 把块内字节落其自有临时文件 → 对处理实例 loadPreset。临时文件两侧均为进程自有目录（APO 侧是 LocalService 临时目录，进程自写自读无权限问题），不构成 Part III 的用户文件中转。已知口径：状态同步时机为编辑器关闭/点应用（D3 既定），非实时；若某格式 savePreset 产物不完整（如个别 VST2 的 bank/program 语义差），登记为已知边界而非本 Part 扩围项。

## Part III — IR/VDC 文件类中转（排期设计，本轮不实施）

**设计要点（先行定稿骨架，实施前再过一遍细化评审）**：

- 中转目录 `%ProgramData%\AuraDSP\apo-assets\`，由 installer/向导在安装期创建并设 ACL（LocalService 读、管理员与本机用户写）；便携版无安装期 → 首次进 sysapo 时由提权通道创建（复用 apo result-file 裁定）。
- App 在用户选定 IR/VDC 文件时（不限 sysapo，进任何模式都可预置）把文件复制为内容哈希命名（`sha256.<ext>`，同内容去重）；参数块的字符串槽**新增** `convolver.ir.path` / `ddc.load` 两条「中转路径专用」通道（v1 排除项在此解除，但只接受中转目录内的路径）。
- APO worker 应用中转路径时做**路径围栏校验**：规范化后必须以中转根为前缀，否则拒绝并回传故障类别（防块被篡改指向任意文件）。
- 生命周期：中转件引用计数跟随预设/会话引用；孤儿清理在 App 启动时按哈希清单对账（保留最近使用集，余者删）。IR 内容校验（引擎既有 NaN/时长门）在 APO 侧加载时照常，失败回传类别。
- 与 Part I D3 取舍点 1 的 (b) 兜底共用同一基建（插件状态超限时落中转文件）——故 Part III 的目录/ACL/围栏三件套在 Part I Q2 若选 (b) 则提前落地最小子集，Part III 实施时复用不重建。

**排期**：Part I、II 收口后单独立项评审实施；本计划书只锁定骨架与复用关系。
