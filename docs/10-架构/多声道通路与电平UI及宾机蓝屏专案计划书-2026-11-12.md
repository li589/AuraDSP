# 多声道通路、电平 UI 与宾机蓝屏专案计划书（2026-11-12）

状态：**待用户裁定**。本计划书只做分级与立项，不动代码；裁定通过后按 §5 顺序分阶段实施、逐阶段提交推送。

## 1. 背景与实测来源

第二十轮（VAIO 格式升级一期）交付后，用户于 2026-11-12 晚在开发机（VB + 发行包 @62483038）与 vm-win10 宾机（APO / VAIO 模式）用 Lux 生成的三份 24 位多声道测试文件（5.1 / 7.1 / 立体声 96k）做真机实测，回报一批现象；23:25 用户两处更正/补充：

- **更正**：矩阵下混实测「BR→FL」系手误，实为 BR→FR。
- **补充**：ASIO 模式同样存在「选了多声道，主页与输入门控的声道数量不变」。

先行结论：三份测试文件经 VB+WMP 逐声道电平核验**正常**（此前 VLC/WMP/PotPlayer 只出双声道，系输出端点设备格式为立体声时的系统下混，与文件无关）。

## 3. 代码现状（已定位，2026-11-12）

- **声道模式语义**：`app/auradsp_app/lib/engine/local_channel_policy.dart`（B2b）——`channelsMode` 0=矩阵（引擎内下混，`channels.count` 喂真实声道数、引擎折 L/R）、1=离散（逐声道原样输出）；本地文件通路如此，桥/APO 通路由同一模式参数驱动引擎。
- **引擎内部有全量多声道电平**：`engine/engine_internal.h` 有 `stage_peak_ch[AURADSP_STAGE_MAX][AURADSP_CH_MAX]` 与 `ch_out_peak[AURADSP_CH_MAX]`。
- **但 viz ABI 只导出立体声**：`engine/auradsp_engine.h` 的 viz 帧仅 `stage_levels_l/r[AURADSP_STAGE_MAX]`——这是 P4 的结构性根源：凡走 viz 帧的通路（APO telemetry、ASIO 桥 `ab_viz_read`）在 App 侧都只能合成双声道电平。
- **APO telemetry v4**：`core/desktop/windows-drivers/03_system_apo/ApoShared.h` 的 `ApoTelemetryBlock`（744 B）只有 `levelLDb/levelRDb` 与 `stageLevelsL/R[32]`。
- **桥清单**：`core/desktop/windows-drivers/bridge/{vm_bridge,asio_bridge,vaio_bridge}` + `common` 统一 `ab_*` ABI。VB 模式主页能扩展声道电平，说明 vm 桥另有一条声道电平来源（W2/W3 审读确认）。
- **自动卸载 APO**：第十六轮 `setAudioMode` 漏斗（离开 sysapo 且仍有附加 → 全端点卸载后才续行），P5 的两次蓝屏均发生在此路径上（产品侧暂无代码错误证据，触发的是卸载伴随的系统 I/O 活动）。

## 4. 工作项

### W1 矩阵下混规格核对（纯审读，不动代码）

- 审读引擎矩阵通路（channels/spatial 相关实现与参数），写出 de-facto 规格：各输入声道的折叠系数、LFE 处理、与 `channelsMode=0` 在各通路（本地/VB/VAIO/ASIO/APO）的一致性。
- 与 P1 实测逐项对照：全符 → P1 正式判「设计如此」并把规格落进活文档；有出入 → 出入点转修复项，另行报用户裁定。

### W2 VB 桥离散模式环绕声道受控复测与定罪（P3）

- 复测协议（开发机，固定拓扑后逐段对表）：预先声明 VB 各总线挂载与声道数（A1/A2/B3 各接什么、几声道）、判读条目区分 VB 输入条 vs 回送条；同步抓取 VmBridge 状态/viz 中的声道与电平数据，与 App 内电平、VB 条三方对照。
- 定罪分支：① 桥/管线代码问题 → 立修复项（声道映射/缓冲/状态上报），开发机回归后随阶段提交；② VB 拓扑/设置问题 → 形成「VB 多声道正确接法」说明落文档，不动代码；③ 复现不出 → 如实记录并挂观察。

### W3 多声道电平回传与 UI 扩展（P4，APO + ASIO）

- **viz ABI 扩展**：帧内追加多声道电平段（候选内容：每 stage 的 per-channel 峰值摘要或至少 in/out per-channel 峰值 + 门控 in/out per-channel；上限 8 声道）。须守 ABI 版本纪律（追加字段 + 长度/版本协商，旧宿主/旧桥不误读）。
- **宿主侧转发**：APO telemetry 升 v5（块大小与偏移重排须有 static_assert 与双端版本校验）；ASIO 桥按新帧转发；VAIO/VB 两桥现状核对后决定是否统一到同一形状。
- **App 消费**：主页声道电平按 viz 声道数扩展（沿用 VB 模式现有扩展形态）；输入门控卡 in/out 计按声道数渲染（已有声道增益 8 通道 UI 的先例形态可复用）。
- **验收口径**：APO 与 ASIO 模式下播 5.1 测试文件，主页出现 6 声道电平且逐声道辨识段与发声声道一一对应；输入门控 in/out 计同。立体声回归不变。

### W4 宾机 0x7A 蓝屏专案（P5，与 W1–W3 并行，取证优先）

- 取证：解析两份新 minidump（DUMP_HEADER64 bugcheck 与四参数，与前三份比对）；查 guest 事件日志中 Disk/Ntfs/storport/VMware 相关错误；查宿主机该 VM 的 `vmware.log` I/O 记录与 vmdk 所在物理盘健康（SMART/事件）。
- 分级结论三选一：① 存储路径定罪（给出证据链）→ 该 guest 退役于 APO/驱动类测试，后续同类验证走真机或重建 guest；② 仍未定罪 → 给出剩余嫌疑与下一步取证手段；③ 若证据指向 AuraDSP 组件 → 立即转修复项并升最高优先级。
- 纪律：取证完成前**冻结该 guest 内一切 APO 附加/卸载与切模式操作**（含自动卸载路径）；结论落第二十轮收口文档的更正附记（修正「8 GB 无复现」的阶段性表述）。

## 5. 顺序与依赖

1. **W4 取证**（最先启动：转储与日志会滚动，且结论影响后续所有宾机验证的可信度）。
2. **W1 规格核对**（纯审读、快；为 W2 判读与 W3 范围提供规格基线）。
3. **W2 受控复测**（依赖 W1 的规格基线；结论决定是否有 VB 桥修复项）。
4. **W3 电平扩展**（最大工作块；范围在 W1/W2 结论后最终确认，APO+ASIO 为必做，VAIO/VB 统一与否按核对结果定）。
5. 每阶段完成即提交推送（feature/linux），收口文档汇总五项分级结论的最终状态。

## 6. 不在范围

- 引擎效果算法与声道处理语义本身的改版（W1 只核对规格，不改行为；行为变更须另行裁定）。
- 在该宾机内继续以 APO 附加/卸载复现蓝屏（冻结，见 W4）。
