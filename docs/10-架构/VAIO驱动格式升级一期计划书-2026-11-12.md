# VAIO 驱动格式升级一期计划书（2026-11-12）

用户裁定（2026-11-12 20:41，一期立项）：VAIO 驱动做 **24 位支持 + 环扩容 + 多声道真机验证**。
独占模式不在一期范围（另行实测裁定后再议）；多采样率经核查已由现行引脚表覆盖，不立项。

## 0. 现状实证（代码核查，2026-11-12）

- 引脚表 `AuraVaoTables.h` 的 streaming 引脚（渲染 sink 与捕获 sink 共用）现有 8 条范围：
  声道 2/4/6/8 × {32 位 IEEE float, 16 位 PCM}，采样率一律 44100–192000。
  拓扑默认声道配置 = 7.1 SURROUND，`KSPROPERTY_AUDIO_CHANNEL_CONFIG` 已实现。
  **多声道与多采样率在驱动声明层已具备**，缺的是 24 位与真机端到端验证。
- 交集处理器 `CMiniportWaveRT::DataRangeIntersection` 为自实现：按客户端
  WAVEFORMATEXTENSIBLE 的 `wBitsPerSample`（容器位深）校验范围，且构造 resultant 时
  把 `wValidBitsPerSample` 硬写为容器位深——24-in-32 客户端（容器 32 / 有效 24）
  今天在 PCM 侧无范围可落（PCM 只有 16），float 侧子类型不符，双侧皆 NO_MATCH。
- `AuraControlDevice_OnFormatChange` 只传（采样率， 声道， 容器位深）三元组，
  不传子类型与有效位深；共享头 `AURA_VAIO_SHARED_HEADER.BitsPerSample` 同义。
- 桥 `ConvertRingToFloat` 按位深分发（32=float 直通、16=int16），即「位深即类型」
  的隐含契约——该契约由引脚表 32↔float、16↔PCM 的一一对应撑着，加 24 位必破。
- 共享环：`AURA_VAIO_DEFAULT_RING_SIZE` = 64KB，有效数据 69,504 B
  （页对齐后总 69,632 − 头 128）。8 声道 float @192k 下仅约 11 ms 缓冲深度。
- 共享头留有 `Reserved[15]`，MAP_RESPONSE 为 IOCTL 缓冲结构——两者都有不动
  结构尺寸/版本的扩展位。

## 1. 设计

### D1 格式模型（IPC 扩展，向后兼容）

- 语义钉死：`BitsPerSample` 恒为**容器位深**（= WAVEFORMATEX.wBitsPerSample）。
- 共享头 `Reserved[0]` 改名 `FormatKind`：0=未指定（旧驱动），1=PCM 整数，2=IEEE float；
  `Reserved[1]` 改名 `ValidBitsPerSample`：0=与容器位深相同。余 `Reserved[13]`。
- `AURA_VAIO_MAP_RESPONSE` **尾部追加**同两字段；桥仅当 IOCTL 返回字节数覆盖
  追加字段时才采信，否则走降级推断。
- 降级推断（新桥 × 旧驱动，FormatKind==0）：bits 32→float、16→PCM、valid=bits。
  旧桥 × 新驱动：只读 BitsPerSample，24 位流会被旧桥按既有规则拒/误读——驱动与桥
  同包交付，不支持混装（与现行口径一致）。
- GET_STATUS / STATUS_INFO 不动（detect 报告容器位深，语义已在上条钉死）。

### D2 引脚范围新增（驱动）

每个声道数（2/4/6/8）新增两条 PCM 范围，采样率仍 44100–192000：

- **PCM 24-packed**：min=max=24（紧密 3 字节/样本）；
- **PCM 32-container**：min=max=32（容器内整数，含 24-in-32 与真 int32，
  两者由协商格式的 ValidBitsPerSample 区分，范围层不区分）。

合计 8+8=16 条。渲染/捕获两 sink 共用同一表，一处生效。

### D3 交集处理器修正（驱动）

- 客户端为 WAVEFORMATEXTENSIBLE 时读 `Samples.wValidBitsPerSample` 为
  `reqValidBits`（0 时取容器位深）；纯 KSDATARANGE_AUDIO 探询路径 reqValidBits=容器位深。
- resultant 的 `Samples.wValidBitsPerSample` 改写为 `reqValidBits`（现行硬写容器
  位深会把 24-in-32 谎报成 32，属本次顺带定罪的缺陷）。
- 其余校验（声道精确匹配、位深对范围 min/max、采样率区间）不变：
  24-packed 客户端（容器 24）落 24 范围；24-in-32（容器 32、子类型 PCM）落
  32-container 范围；float 客户端子类型校验照旧走 float 范围，无串扰。

### D4 格式变更通道扩参（驱动）

- `AuraControlDevice_OnFormatChange` 增加 `FormatKind` 与 `ValidBitsPerSample` 两参，
  同步写 `g_ulCurrent*` 与共享头新字段；捕获方向「直接返回」的渲染真源纪律不变。
- 调用点（MiniportWaveRTStream 的 Init/SetFormat）从 KSDATAFORMAT 提取：
  EXTENSIBLE 时 SubFormat GUID 定 kind、Samples 定 validBits；普通
  WAVEFORMATEX 按 wFormatTag 定 kind、validBits=容器位深。

### D5 环扩容（驱动）

- `AURA_VAIO_DEFAULT_RING_SIZE` 64KB → 1MiB（非分页池约 1MB，常驻成本可忽略）。
- 新增内核真值 `g_ulRingDataSize` =（总尺寸 − 头尺寸）**向下取整到 288 的倍数**：
  288 = 全部可达 BlockAlign {4,6,8,12,16,18,24,32}（声道 2/4/6/8 × 每样本
  2/3/4 字节）的最小公倍数，保证捕获 snap 距离与钳制丢弃的帧格不变量在新
  格式集下继续成立（白噪声专项 S1/S3a 的纪律延伸）。头的 DataSizeBytes、
  MAP 响应、读写路径统一改用该真值（DRV-03：几何只从内核真值派生）。
- 环变大不增加链路延迟：桥按 TW/WO 相对锚消费，环只是 conduit；增的是
  抖动/卡顿容错深度（8 声道 float @192k 约 170 ms）。

### D6 桥改造

- 几何元组扩为（率， 声道， 容器位深， FormatKind, ValidBits），泵的双读一致性
  比较与格式重同步触发都含新字段——**同形切换**（float32 ↔ int32-PCM，
  率/声道/位深/帧宽全同）必须被察觉，否则静默误转换。
- 转换函数抽为共享头 `VaioSampleConvert.h`（纯函数、无平台依赖），按
  (kind, 容器位深， 有效位深）分发：
  float32 直通；PCM16 → int16/2^15；PCM24-packed → 3 字节小端组装符号扩展
  /2^23；PCM 容器（32）→ 取高 ValidBits 位 / 2^(valid-1)（valid 32 时即
  int32/2^31，valid 24 时即 >>8/2^23）；其余组合返回「不支持」。
- 支持集外的格式维持诚实失败路径（状态文案 `ring-format-unsupported`）。
- S3b 字节旋转自检保持**仅 PCM16** 触发（其余格式不适用该指纹）。
- 状态 JSON 追加 `ringValidBits`、`ringFmt`（pcm/float）两字段供取证；
  App 不消费，纯增量。

### D7 验证工具（仓库 tools/）

新增 `vaio_set_format.cpp`：经 IPolicyConfig::SetDeviceFormat 把指定端点的
设备格式设为（采样率， 声道， 容器位深， 有效位深， 类型），供真机格式矩阵
验证使用；登记 windows-drivers README 工具表。仅开发验证用途，不进发行包。

## 3. 真机验证矩阵（vm-win10，新驱动装机后）

每行：vaio_set_format 设端点格式 → loopback 探针 driver 模式 6s →
核桥状态几何（率/声道/容器位深/validBits/fmt 与设定一致）+ 分析器洁净
判据（目标幅值 ≈0.5、ac1 ≈0.99、peak ≈0.5、无字节旋转指纹）：

| # | 格式 | 性质 |
|---|------|------|
| 1 | 立体声 float 48k | 回归 |
| 2 | 立体声 PCM16 48k | 回归（含 S3b 通路） |
| 3 | 立体声 PCM 24-in-32 96k | 新增主项 |
| 4 | 立体声 PCM24-packed 44.1k | 新增 |
| 5 | 立体声 float 192k | 高采样率 |
| 6 | 5.1 float 48k | 多声道 |
| 7 | 7.1 PCM16 48k | 多声道 |
| 8 | 5.1 PCM 24-in-32 48k | 多声道 × 24 位 |

外加 App 在 5.1 格式下 VAIO 模式启动冒烟（不崩、电平/可视化在动）。
若某格式 audiosrv 侧拒绝建流（SetDeviceFormat 成功但混音格式不跟随），
如实记录为 Windows 呈现层限制，不回滚驱动侧范围。

## 4. 风险与回滚

- 驱动仍为测试签名，装机流程与现行一致；出问题回装上一版驱动包即回滚。
- 环扩容改变 DataSizeBytes：桥与探针都从 MAP 响应/共享头读真值，无硬编码
  69,504 的消费方（已 grep 核查桥与 tools；App 不读环）。
- 交集处理器是格式协商的唯一关口，改动限于 validBits 的读取与回写，
  既有 8 条范围的行为不变（回归行 1/2 覆盖）。

## 5. 不在范围

- 独占模式（未立项；待后续可行性实测裁定）；
- APO / ASIO 路径的 24 位（各自独立，不在本期）；
- Linux 侧（无 VAIO 概念）；
- 端点默认格式的产品化 UI（App 内切换 VAIO 格式）——本期只做驱动能力
  与开发验证工具，格式切换走系统声音设置/验证工具。
