## 0. 结论摘要

1. **目录迁移本身不等于崩溃隔离。** 插件 DLL 只要仍在 `auradsp_app.exe` 进程内，SEH 只能兜住可捕获异常；AV、堆损坏、线程挂死仍会带走 APP/桥/音频线程。真正的隔离必须走 **Phase 4 独立插件宿主进程**。
2. 推荐顺序：**Phase 0 冻结基线 → Phase 1 纯机械搬迁 → Phase 2 格式驱动统一 → Phase 3 链组件/ABI 收口 → Phase 4 独立宿主进程 → Phase 5 多总线/状态/PDC**。
3. **Phase 1 只允许移动文件和改路径，不允许顺手改行为。** 混合格式 TU 的拆分放到 Phase 2，避免“搬 + 改”混在一个提交里无法回滚。
4. 当前已验证的 Pro-Q 4 链路是回归基线：UI Slot 1（内部 slot0）自动恢复，遥测 `proc=244 / in=0.3062 / out=0.2692 / Δ=0.2720`，stage=Post-Reverb(3)，latency=0 spl。
5. 迁移期间保持 **C ABI 与 `.def` 导出白名单不变**；`auradsp_engine.h` 是外部唯一稳定契约，内部 C++ 头文件不承诺兼容。

### 1.4 结构问题（按优先级）

- **P1 格式耦合**：VST3/CLAP 头、实例、扫描器互相 include，新增格式必须改管理器。
- **P2 公共头过重**：`auradsp_plugin_host.h` 同时暴露扫描、实例、管理器、平台细节，DSP/集成层被迫看到 VST3/CLAP 概念。
- **P3 平台细节下沉不足**：Win32 窗口、DLL 目录、SEH、消息泵与驱动逻辑混放，未来 Linux/Android 路径难以抽离。
- **P4 链耦合**：`engine_chain.cpp` 直接知道 `PluginHostManager` 与 5 个插入阶段，PDC/多总线扩展会继续膨胀。
- **P5 桥重复**：三桥各自复制 13 个包装与镜像回放，新增一个 ABI 要改三处。
- **P6 无进程隔离**：进程内宿主无法满足“第三方代码不得与引擎同生共死”的长期原则。
- **P7 构建/文档漂移**：`test_plugin_direct` 源列表与主库重复；`engine/AGENT.md`、根 `CLAUDE.md`、README、审查文档都记录旧 `host/` 路径，搬迁后必须同步。

### 1.5 不可破坏的约束

1. **RT 安全**：音频线程零分配、零锁、零 syscall；`process` 路径只读原子状态与预分配缓冲。
2. **C ABI 稳定**：`auradsp_engine.h` + `auradsp_engine.def` 的导出集合不变；Dart FFI 不改函数签名。
3. **GUI 线程亲缘性**：插件编辑器必须在单一宿主 GUI/泵线程上创建、resize、销毁；不得跨线程 `detach`。
4. **会话兼容**：现有 `session_state.json`（version 5）中的 4 槽插件路径/id/bypass/stage 必须可继续恢复。
5. **许可证**：项目 GPL-3.0；VST3 SDK 走 GPLv3 路线；CLAP MIT；商业插件 DLL 不入库。

## 3. 目标架构

### 3.1 分层

```
engine/plugins/
├── api/            纯接口与数据类型（无 SDK、无 Win32）
├── driver/         槽位管理、扫描调度、链组件、驱动注册
├── formats/        格式实现（VST3 / CLAP），SDK 头只在这里出现
├── platform/       平台能力（Win32 GUI、DLL 路径、SEH、UTF）
├── integration/    引擎 C ABI / engine_chain 适配
├── third_party/    小型兼容 shim / 静态锚点（不是完整 SDK）
└── tests/          C++ 宿主直调测试、fake driver、fixtures
```

依赖方向（只允许向右/向下）：

```
api  ←  driver  ←  formats
 ↑        ↑
platform  integration
```

- `api`：只依赖 C++ 标准库。
- `driver`：依赖 `api`，不 include VST3/CLAP 头。
- `formats/vst3`、`formats/clap`：依赖 `api` + 各自 SDK，实现 `IPluginFormatDriver` / `IPluginInstance`。
- `platform/win32`：依赖 `api`，供 formats/driver 调用；不反向依赖 driver。
- `integration`：依赖 `api` + `driver`，把插件链暴露给 `engine_chain`/C ABI。
- `tests`：可依赖以上全部。

### 3.2 核心接口（Phase 2/3 落地）

```cpp
// api/plugin_format_driver.h
class IPluginFormatDriver {
public:
    virtual ~IPluginFormatDriver() = default;
    virtual PluginFormat format() const = 0;
    virtual bool canHandle(const std::string& path) const = 0;
    virtual std::vector<ScanCandidate> enumerate(
        const std::vector<std::string>& searchPaths) const = 0;
    virtual bool queryMetadata(const std::string& path,
                               std::vector<PluginMetadata>& out) const = 0;
    virtual std::unique_ptr<IPluginInstance> createInstance() const = 0;
    virtual std::string resolveBundleBinary(
        const std::string& bundlePath, std::string* outArch) const = 0;
};
```

```cpp
// driver/plugin_chain_component.h
class PluginChainComponent {
public:
    bool prepare(double sampleRate, uint32_t maxBlockSize);
    void reset();
    void process(int stage, float* const* in, float* const* out,
                 uint32_t frames) noexcept; // RT：零分配/零锁
    void setBypass(int slot, bool bypass) noexcept;
    bool bypass(int slot) const noexcept;
    uint32_t latency(int slot) const noexcept;
};
```

`engine_chain.cpp` 只保留 5 个阶段调用点：

```
Stage 0 Pre-DSP
Stage 1 Pre-Vendor
Stage 2 Post-Vendor
Stage 3 Post-Reverb
Stage 4 Post-Limiter
```

具体槽位遍历、in-flight 握手、遥测、SEH 包装全部在 `PluginChainComponent`/`PluginHostManager` 内。

### 3.4 外部 SDK 与许可证

- `vendor/plugin-api/steinberg`、`vendor/plugin-api/clap` **暂不搬**：体量大、许可证边界敏感，且现有 CMake 已稳定。
- `engine/plugins/third_party/` 只放宿主侧小型 shim、静态锚点、兼容头；不复制完整 SDK。
- 商业插件 DLL 永不入库；测试只引用本机已安装路径，缺失时按环境失败处理。
- 若未来要闭源分发，VST3 SDK 需重新评估 Steinberg 专有许可；本方案默认继续 GPL-3.0。

### Phase 3：链组件与 ABI 收口（2–4 天）

**目标**：DSP 链与插件 ABI 解耦，为独立宿主进程铺路。

### Phase 4：独立插件宿主进程（5–8 天）

**目标**：真正满足“第三方代码不得与引擎同生共死”。

架构：
```
auradsp_app.exe
  └─ engine (auradsp_engine.dll)
       └─ ProcessPluginProxy : IPluginInstance
            ├─ 共享内存音频环（固定容量，零 RT 分配）
            └─ 控制 IPC（参数/状态/编辑器/崩溃事件）
                 ↕
       auradsp_plugin_host.exe
            ├─ PluginHostManager（复用 Phase 2/3）
            ├─ VST3/CLAP 实例
            └─ 插件 GUI 线程 + 消息泵
```

工作：
1. 新增 `auradsp_plugin_host.exe`（x64；32 位后续单独进程）。
2. 共享内存音频环：双缓冲/环形，固定帧数；引擎 RT 侧只读写环，不做 IPC 系统调用。
3. 控制通道：加载/卸载/bypass/stage/preset/editor/telemetry；版本化协议。
4. 进程生命周期：启动、健康检查、崩溃检测、自动旁路、重载、状态回灌。
5. GUI 策略：**推荐宿主进程持有插件窗口**，APP 只发 show/hide/embed 请求；跨进程 `SetParent` 作为备选，不作为默认。
6. 特性开关：`AURA_PLUGIN_HOST_MODE=inproc|process`，默认先 `inproc`，E2E 稳定后切 `process`。
7. 失败语义：宿主崩溃 → 引擎 200ms 内 bypass → UI 事件条“插件 X 已崩溃，已旁路，点此重载”。

**验收（硬指标）**：
- E2E 中 `taskkill /F auradsp_plugin_host.exe`：APP 不倒、音频不断流、自动旁路、UI 报错、可重载。
- 音频附加延迟在可接受预算内（目标 < 5ms，实测记录）。
- RT 线程无锁/无分配/无 syscall；共享内存环无溢出（有计数器）。
- Pro-Q 4 编辑器在宿主进程内可开/关/缩放；崩溃不拖垮 APP。
- 会话恢复、预设保存/加载在进程模式下与进程内一致。

**回滚**：保留 `inproc` 路径与开关；进程模式失败可一键切回。
