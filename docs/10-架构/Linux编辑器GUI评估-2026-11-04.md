# Linux 插件编辑器 GUI 评估（2026-11-04，P0 探针已实证）

> 背景：Linux 插件宿主已全链落地（进程内 + x64/x86 隔离宿主，
> VST3/CLAP/VST2 扫描/深扫/加载/出声均有门禁活体断言），唯一
> 剩下的功能对等缺口是**插件编辑器窗口**：三格式在 Linux 一律
> `canEdit=false` 诚实占位（引擎的 POSIX GUI 兼容层是桩，编辑器
> 调用失败即干净返回）。本文档给出 P0 探针结论、实施设计、
> 风险与分阶段估算，供立项决策。

## 1. 结论先行

**可行，且比预想简单**——关键在于先看清 Windows 的编辑器模型：

- Windows 上编辑器**不是嵌进 Flutter 窗口的**：三格式都是宿主
  先建一个独立顶层窗口（`CreateWindowExW`，父窗口为 NULL，
  `WS_OVERLAPPEDWINDOW`），再把该 HWND 交给插件挂载
  （VST3 `view->attached(hwnd)`、CLAP `gui->set_parent(hwnd)`
  后 `show`、VST2 `EDITOR_OPEN(hwnd)`），插件在容器内建自己的
  子窗口；尺寸稳定化、置顶、WM_CLOSE 回派、CLAP 定时器支持都
  围绕这个容器展开（见各 `*_instance.cpp` 的 showEditor 路径）。
- Linux 的对等物一一对应：宿主自建**顶层 X11 窗口**作容器，
  XID 交给插件（VST3 平台类型串为 vendored 头的
  `kPlatformTypeX11EmbedWindowID` = `"X11EmbedWindowID"`；
  CLAP 用 `CLAP_WINDOW_API_X11` + `clap_window.x11`；VST2 的
  `EDITOR_OPEN` 由 ptr 携带父 XID——Linux 惯例，与净室头口径
  兼容）。
- 因此**不需要与 Flutter/GTK 做任何窗口合成**：进程内模式下
  引擎泵线程自开一条 X 连接管理编辑器窗口（与 GTK 的连接互不
  干扰）；隔离宿主模式下窗口完全在宿主进程内，App 侧只经既有
  C ABI（show/hide/isEditorOpen）与 IPC 指挥，协议零新增面。

## 2. P0 探针实证（2026-11-04，本 VM + Xvfb）

探针保存在 VM 的 `~/workspace/auradsp-probe/editor-p0/`（三对
插件+宿主 harness + `run.sh` 一键复现）。三组全部 ALL PASS：

| 格式 | 断言 | 验到的链 |
|---|---|---|
| VST3 | 18 | createView → isPlatformTypeSupported(X11EmbedWindowID) → getSize → attached(xid) → 插件以**独立 X 连接**在容器下建子窗口 → 宿主跨连接 XQueryTree 核验（子窗口在位、WM_NAME、几何 320x200、已映射）→ onSize 后子窗口跟随 400x260 → removed() 后子窗口消失 |
| CLAP | 21 | gui->is_api_supported(x11) → create → get_size 300x180 → set_parent(xid) → show → 跨连接核验 → hide 后不可见 → 再 show → destroy 后子窗口消失 |
| VST2 | 13 | VSTPluginMain（含宿主回调绊线）→ EDITOR_GET_RECT 280x160 → EDITOR_OPEN(xid) → 跨连接核验 → KEEP_ALIVE 泵事件 → EDITOR_CLOSE 后子窗口消失 |

探针证明的核心事实：**跨 X 连接的父子窗口关系成立且可从宿主
侧完整观测/管理**——这是整个方案的地基。两条连接同进程的形态
也同时覆盖了进程内模式的拓扑（引擎与插件同进程、各自持连接）。

## 3. 实施设计（正式阶段）

### 3.1 POSIX 窗口层（引擎，新文件域 `plugins/platform/posix/`）

- `X11EditorWindow`：在插件泵线程上惰性打开 Display（进程内与
  宿主共用同一实现）；建顶层窗口（标题 = 编辑器标题、初始尺寸
  = 插件首选尺寸）、`WM_DELETE_WINDOW` 协议、置顶对应物
  （`_NET_WM_STATE_ABOVE` 或 XRaiseWindow）、关闭回派到实例
  （对应 Windows 的 WM_CLOSE → onEditorWmClose）。
- 泵循环改造：POSIX ModulePump 现为任务队列 + 条件变量；编辑器
  打开期间需同时等 X 连接 fd——改 `poll(任务事件fd, X fd)` 双路
  等待，X 事件分发：ConfigureNotify（容器被用户拉伸 → 通知插件
  onSize/set_size/EDITOR 尺寸跟随）、ClientMessage 关闭、
  其余事件按窗口归属转发（插件子窗口的事件在其自有连接上，
  不经宿主连接——探针已证此分工自然成立）。
- 定时器面：CLAP timer_support 与 VST2 KEEP_ALIVE 需要周期
  回调——泵的等待超时在编辑器打开时钳到 20–30 ms 驱动 idle
  节拍（对应 Windows 的 SetTimer 方案），无编辑器时回到无限
  等待（不耗电空转）。

### 3.2 三格式实例的 POSIX 分支

- VST3：`showEditorOnPumpThread` 的平台段分叉：容器创建走 X11
  层；`isPlatformTypeSupported(kPlatformTypeX11EmbedWindowID)`；
  `attached((void*)xid, kPlatformTypeX11EmbedWindowID)`；
  IPlugFrame::resizeView 的 POSIX 实现改为调整容器 X 窗口
  （现有 `m_plugFrame` 的 hwnd 字段泛化为平台窗口句柄）。
- CLAP：同上分叉：`CLAP_WINDOW_API_X11`、`clap_window.x11`；
  尺寸稳定化轮询与 set_size 走 XGetGeometry/XResizeWindow。
- VST2：`EDITOR_OPEN` 传 XID；`EDITOR_KEEP_ALIVE` 由泵节拍
  驱动；GetRect 同步容器尺寸。
- Win32 路径零改动：分叉点在既有平台段内以 `#if defined(_WIN32)`
  / POSIX 实现文件划分，与当下的 compat 桩替换方式一致
  （桩函数逐一被真实现替换）。

### 3.3 宿主进程与 App 侧

- 隔离宿主：窗口层代码在宿主进程内直接生效（宿主与引擎共用
  插件层源文件——现状即如此）；编辑器打开/关闭状态经既有
  status JSON 回 App，无需新 IPC。
- 进程内：泵线程的 X 连接与 GTK 并存（见风险 R2 的处置）。
- App 侧：`linuxInProcess caps` 的 `canEdit` 改为由能力探测
  决定（DISPLAY 可达才 true），UI 不改结构（编辑器按钮的
  使能逻辑已就位）。无显示器/纯 Wayland 无 XWayland 时保持
  false 占位——与现状一致，不回归。

### 3.4 门禁

- 插件门禁加 `[editor]` 节：三组探针（即 P0 的三对文件迁入
  `test/smoke/`）在 Xvfb 下经**引擎真实通路**（slot_show_editor
  C ABI → 实例 → X11 容器）打开编辑器，断言容器窗口存在、
  插件子窗口挂载、关闭后清理；本机与 CI 同跑（Xvfb 在 J3/J8
  已有先例）。真机清单加编辑器验收项（真实插件 GUI 可见、
  可交互、调整大小、关闭、多开一个）。

## 4. 风险清单

| # | 风险 | 等级 | 处置 |
|---|---|---|---|
| R1 | **XEmbed 协议完整度**：正式 VST3 插件（JUCE 系等）期望宿主参与 XEmbed（焦点/键盘协商）；纯重挂（探针形态）对显示足够，但键盘焦点可能不全 | 中 | 实施阶段容器侧实现 XEmbed 宿主最小面（_XEMBED_EMBEDDED_NOTIFY、焦点进/出消息）；探针插件不验此项，真机验收以真实插件为准 |
| R2 | **进程内与 GTK 共存**：XInitThreads 时序（GDK 初始化时已调用，引擎再调用无害）；两条 X 连接并存已由探针同进程形态侧证 | 低 | 实施首阶段在真实 App 内冒烟（J8 式无头启动 + 打开编辑器） |
| R3 | **真实插件的 GUI 工具箱多样性**（GTK2/3、Qt、JUCE、OpenGL 上下文）：个别插件在容器/事件模型上有怪癖 | 中 | 与 Windows 侧同策略：失败干净降级（showEditor 返回 false → UI 提示），不拖垮音频链；问题插件逐个案处理 |
| R4 | **Wayland 会话**：无 XWayland 时 X11 不可用 | 低 | 能力探测决定 canEdit；纯 Wayland 支持不在本项范围（与业界 Linux 宿主现状一致） |
| R5 | **宿主进程崩溃面扩大**：编辑器代码在隔离宿主内崩溃只死宿主（现有隔离语义覆盖）；进程内模式崩溃带崩 App——与 Windows 进程内编辑器同险，现状默认远程模式已隔离 | 低 | 默认远程优先的既有策略不变 |

## 5. 分阶段估算（VM 工时，不含真机验收等待）

| 阶段 | 内容 | 估时 |
|---|---|---|
| E1 | X11 窗口层 + 泵循环双路等待 + CLAP 单格式打通（create→容器→set_parent→show→关闭回派）+ 探针级冒烟 | 1.5–2 天 |
| E2 | VST3 接入（attached/PlugFrame resize/尺寸稳定化）+ VST2 接入（OPEN/KEEP_ALIVE 节拍） | 1–1.5 天 |
| E3 | XEmbed 宿主最小面 + 定时器/idle 节拍完善 + 隔离宿主全链 + canEdit 能力探测与 App 接线 | 1 天 |
| E4 | 门禁 [editor] 节（三格式经引擎真链）+ CI + 文档与真机清单 | 0.5–1 天 |
| 合计 | | **4–5.5 天** |

真机验收（用户 Ubuntu + 真实商业插件）为必需收尾：探针只能证
协议链，真实插件的工具箱怪癖（R1/R3）只有真机能暴露。

## 6. 决策项

1. 是否立项（建议：立项——这是 Linux 功能对等的最后一块，
   且 P0 已把最险的协议链证完，剩余是工程量而非未知数）。
2. 立项口径：三格式一次做完（E1–E4），或先 CLAP+VST3、
   VST2 随其后（VST2 编辑器在 Linux 生态占比最低）。
