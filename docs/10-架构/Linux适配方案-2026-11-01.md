### D-5 —— Linux 音频后端选项集

> **裁定（2026-11-01）：追求功能对等。** Linux 保留与 Windows 同构的三种模式语义（`system` / `virtual` / `driver`），**不裁剪、不留空壳**；`composeMode()` 必须能真正产出这三个 id。
>
> **实测修正（推荐项的成本估算偏重）**：本方案 §1.3 原写「`driver` 需内核态开发」——**实测不然**：Linux **主线内核已自带**虚拟声卡模块 `snd-aloop`（`alsa-km`），且 PipeWire 的 ALSA 拦截层会把它自动暴露为 `pw-loopback-*` 节点；`module-null-sink` 则在原生 PulseAudio 与 `pipewire-pulse` 上**都可用**。
> ⇒ **三条路径全部落在 D-6 选定的 PulseAudio 栈上**，**不引第二套音频 API**，也**不需自研内核模块**。详见 ADR-012 §2。

**现状事实**（回代码核实，非采信文档）：

- `app/auradsp_app/lib/core/audio_modes.dart:67` 定义 `linux = ['system','virtual','driver']`，注释标「暂定」
- **但 `composeMode()`（`audio_modes.dart:121-136`）只输出 Windows 四个 id**（`vbcallback`/`sysapo`/`vaio`/`asio`）⇒ Linux 的 `system` 经 `setModeCategory`（`state_audio_modes.dart:93-97`）会被合成为 `'vaio'` ⇒ **三个 Linux id 是语义死路**
- 设置页 `features/settings/settings_audio_tab.dart:36-37,55-60,77-82` **硬编码六个 Windows 选项且不按 OS 过滤** ⇒ Linux 用户会看到一堆无效开关
- 四种 Windows 后端在 Linux 无对应物：`vaio`（PortCls 虚拟声卡）、`vbcallback`（Voicemeeter）、`sysapo`（系统 APO）、`asio`（ASIO 驱动）

**后果**：不裁定这一项，Linux 上要么出现「能选但无声」的假选项，要么实现一条语义混乱的路径。

**可选项**：

| 选项 | 内容 | 后果 |
|---|---|---|
| **A（推荐）** | Linux 只保留 `system` 一种模式，映射到新增的 `AudioOut` Linux 实现；`vaio`/`vbcallback`/`sysapo`/`asio` 在 Linux 上**从选项列表移除**（不保留空壳） | 语义干净；Linux 只有一个明确的能力。后续要加 virtual sink 再单独立项 |
| B | 保留 `system`/`virtual`/`driver` 三个 id，只实现 `system`，另两个显示「暂不可用」 | 保留未来路线图，但设置页有永久灰项 |
| C | 追求功能对等：`system` 走 ALSA/PulseAudio，`virtual` 走 PipeWire virtual sink，`driver` 走内核模块 | 工作量至少翻倍，且 `driver` 需内核态开发，不建议 |

### D-6 —— Linux 音频栈选型（延迟目标随之确定）

> **裁定（2026-11-01）：PulseAudio simple API 优先；ALSA 直连留给后续低延迟专家模式；不做原生 libpipewire。**
>
> 实现期必须记住的运行时事实：① Ubuntu 22.04+ 等 PipeWire 主导环境下实际承担 PulseAudio 协议的是 `pipewire-pulse`，**该服务未运行时 PulseAudio API 调用会静默失败**（`pactl` 仍可用但发现不到新设备）——实现须把「连接失败」与「无设备」分成两个错误码；② 同环境下 **`~/.config/pulse/default.pa` 不被读取**，生效的是 `/usr/share/pipewire/pipewire.conf.d/90-enable-alsa.conf` 与 `pipewire-pulse` 的设备发现机制 —— 诊断路径须区分「原生 PulseAudio」与「PipeWire 兼容模式」两条；③ 实时优先级由 **rtkit** 托管，不自行 `sched_setscheduler`，XRUN 用 `pw-top` / PA underflow 计数监控。

**现状事实**：

- `AudioOut` 端口契约（`lib/engine/audio_out/audio_out.dart:8-33`）是 **WASAPI 形状的拉模型**：`write(Float32List src, {frames})` + `currentPadding()`；`audio_out_wasapi.dart:443-450` 是 `GetBuffer` → 转换 → `ReleaseBuffer`
- WASAPI 实现是**纯 Dart FFI 直调 `ole32.dll` COM vtable**（`audio_out_wasapi.dart:172`），**不经 C++** ⇒ Linux 侧同样可在 Dart 侧 FFI 实现，**不改引擎 C ABI**
- 设备输出归 App 侧是 ADR-CP-3 已定的边界（`engine/platform/linux/README.md:14-16`）
- 本仓已有 Linux 参考实现 `source/JDSP4Linux`：用 **PulseAudio + GStreamer**（`src/audio/pulseaudio/`），有 `.deb` 与 Flatpak 打包（`.github/workflows/package-deb.yml`、`meta/flatpak/`）

**外部生态实测数据**（Linux 音频栈三层，ALSA 在底）：

| 栈 | 延迟（48 kHz） | 模型 | 备注 |
|---|---|---|---|
| ALSA 直连 | 64 样本 ≈ **1.3 ms** | 拉 | 直通硬件，最低延迟；独占设备 |
| JACK 独立跑 | 128 样本 × 2 周期 ≈ **5.3 ms** | 拉 | 专业标准；但与 Pulse 应用不兼容、需另配 |
| PipeWire（默认） | 128 quantum ≈ **2.7 ms**；**默认 quantum 2048 = 42.6 ms** | **推**（`pw_stream` `on_process` 回调） | 2022 起为发行版默认（Fedora / Ubuntu 22.04+ / Arch / openSUSE）；PipeWire 提供 PulseAudio 兼容层 |

**关键约束（决定选型）**：

1. **PipeWire 是「推」模型**（服务端回调客户端的 `on_process` 去填缓冲），而 `AudioOut` 是「拉」形状 ⇒ 需引入一层**环形缓冲做模型倒置**；且 PipeWire 客户端回调发生在 RT 线程，**从 RT 线程回调进 Dart VM**（FFI `NativeCallable.listener`）代价与稳定性都需实测。
2. **PulseAudio simple API 是「拉」模型**（`pa_simple_read`），4 个函数即完成，与现有 `AudioOut` 契约 **1:1 对应**，且**所有现代发行版都有**（PipeWire 自带 PA 兼容层）。
3. 实时优先级由 **rtkit** 托管（`sudo apt install rtkit`，无需 root 调 `sched_setscheduler`）；`pw-top` 可监控 XRUN。
4. XDG 目录：`$XDG_CONFIG_HOME`（默认 `~/.config`）/ `$XDG_DATA_HOME`（默认 `~/.local/share`）。

**可选项**：

| 选项 | 内容 | 后果 |
|---|---|---|
| **A（推荐）** | **PulseAudio simple API 优先**（Dart FFI → `libpulse-simple.so`），ALSA 直连作为后续「低延迟专家模式」 | 拉模型 1:1 对接现有端口；全发行版可用；与本仓 JDSP4Linux 经验一致。延迟 ≈ PA 默认（数十 ms～百 ms级，属「可用」非「专业低延迟」） |
| B | **ALSA 直连优先** | 延迟最低（1.3 ms 级）；但独占硬件设备、与其他应用互斥、设备枚举与热插拔要自己写，工作量与鲁棒性风险最大 |
| C | **PipeWire 原生 API 优先** | 延迟与兼容性最优（现代标准）；但需模型倒置 + RT 线程回调进 Dart，**首期不建议**。建议作为二期，在 A 打通后替换 |

### D-7 —— Linux 首期的插件能力边界

> **裁定（2026-11-01）：首期只做插件消费者，并隐藏 Linux 的插件目录 UI。**
>
> 具体：① Linux 不做 VST3/CLAP **宿主**（沿用 `AURADSP_ENABLE_PLUGINS=OFF` 整体裁掉，实测该 stub 与真实实现 **C ABI 56 符号全等**，导出集契约不破）；② 不做把 AuraDSP 自身导出为 LV2 / CLAP 插件（属全新产品形态，需独立立项）；③ **必须隐藏** `plugin_dirs_desktop.dart:34-51` 的 Linux 目录展示（宿主是 Windows-only，现状是「能看不能用」），消除预期落差。

**现状事实**：

- `engine/platform/linux/README.md:47` 已定调：Linux 用 `AURADSP_ENABLE_PLUGINS=OFF` **整体裁掉 VST3/CLAP 宿主**，编入 `plugin_chain_adapter_stub.cpp` / `plugin_abi_stub.cpp`，C ABI 导出集不变
- 实测该 stub 与真实实现**符号集与签名完全一致**（F2）
- 但 **UI 会显示 Linux 插件目录**（`lib/platform/plugins/plugin_dirs_desktop.dart:34-51` 列出 `/usr/lib/vst3`、`/usr/local/lib/clap` 等），而宿主是 Windows-only（`platform_profile.dart:25` `supportsPlugins => Platform.isWindows`）⇒ **不一致**
- 插件元数据读取是 Win32 PE 版本资源（`engine/plugins/driver/plugin_scanner.cpp:35-58`）⇒ Linux 需 ELF/元数据端口（CP-24）
- 外部生态：LV2 是 Linux 原生且生态成熟，但功能较基础、跨平台弱；CLAP 开源且跨平台；VST3 专有但 DAW 普遍支持

**可选项**：

| 选项 | 内容 | 后果 |
|---|---|---|
| **A（推荐）** | 首期 Linux **只做「插件消费者」**（加载并使用 Linux 上的 VST3/CLAP/LV2 插件），**暂不导出 AuraDSP 自身为 Linux 插件**；同时**隐藏 Linux 的插件目录 UI**（消除「能看不能用」） | 范围最小、与 `AURADSP_ENABLE_PLUGINS=OFF` 一致；但用户加载的插件不会被 AuraDSP 处理 ⇒ 首期 Linux 的插件能力为 0 |
| B | 首期 Linux 支持**加载 VST3/CLAP**（补 formats 层的 Win32 剥离 + ELF 元数据端口） | 能力显著；但需新增 `port/module_metadata.h`（CP-24）、编辑器 GUI 在 Linux 仍是空的（`clap_instance.cpp:614-679`、`vst3_instance.cpp:364-388` 是 Win32-only） |
| C | 首期 Linux **导出 AuraDSP 为 LV2/CLAP 插件** | 对 Linux 音乐人价值最大；但这是全新产品形态，需独立 ADR + 大量新代码，**不建议塞进 Linux 首期** |

### 4.0 分支策略（2026-11-01 owner 裁定）

```
feature/linux  ──(实现代码，验证通过)──▶  dev  ──(dev 验证合并后，dev 决定)──▶  main
```

| 阶段 | 承载内容 | 合并判据 |
|---|---|---|
| `feature/linux` | **仅 Linux 开发**（引擎 Linux 目标、端口实现、App 侧 Linux 适配、Linux 门禁） | 代码**验证通过**（Linux 构建 + smoke + ABI 门禁全绿） |
| `dev` | 集成验证 | dev 侧验证合并后**再由 dev 决定**是否合并 |
| `main` | 发行主分支 | 由 `dev` 决定，非自动 |

约束：① `feature/linux` 从 `dev` 切出，**不得**直连 `main`；合并方向单向 `feature/linux → dev → main`。② `main` 的合并不由 `feature/linux` 触发。③ 本方案文档与 ADR 等**决策记录**走 `dev → main` 的常规 PR 路径（不属 Linux 代码）；**代码**一律走 `feature/linux`。④ 分支命名 `feature/<主题>`。
