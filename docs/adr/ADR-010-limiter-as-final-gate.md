# ADR-010 — 限幅器是内置信号链的最后一道门

- 状态：**接受**（2026-10-31）
- 依据：用户裁定 D-1（2026-10-31「限幅器应该是最后一道门」）、`docs/30-审查/全量复核-2026-10-31.md` L-05 行、`docs/30-审查/未决任务复核-2026-10-31.md`
- 背景：
  1. 2026-10-31 全量复核登记的 L-05 描述为「总输出增益在 UI 排在限幅器之前，但引擎链里 `post_gain_process_mc` 排限幅之后」。本轮逐行复核引擎源码后确认：**该描述的前提不成立**——`post_gain_process_mc` 在多声道路径中位于 step 15，而限幅器在链尾（step 之后），post gain 本来就早于限幅器。L-05 因此改判为误报（详见 §2）。
  2. 但复核暴露了一个更本质的缺陷：**「post gain 早于 limiter」这条链序契约，此前只存在于代码注释里，没有任何测试执行**。本仓反复出现「契约写在标志/注释里但无人执行」的同型问题（见 `docs/30-审查/预设系统与硬置入复检-2026-10-28.md` 的 P1 记录）。
  3. 链序一旦定案为「限幅器是最后一道门」，就会产生一个用户可感知的直接后果：**限幅器开启时，上推总输出增益只会表现为 GR 上升，听感不变**。现有 UI 提示未说明这一点，属于必须显式告知的语义。
  4. 另一处此前未被点名的例外：**插件插入阶段 4（Post-Limiter / 总输出级）**位于限幅器之后，其输出不再经过本链限幅器。

- 决策：
  1. **限幅器是内置信号链的最后一道门**。所有会抬电平的环节——总输出增益 `post.gain`、逐声道 trim `post.gain.cN`、响度补偿 `loudness`——必须排在限幅器之前；限幅器之后内置链不得再存在任何增益级。
  2. **用户可感知语义（推论，不可省略）**：
     - 限幅器**开启**时：上推 `post.gain` 不抬高最终输出峰值，输出仍被门限兜住，表现为 LIMIT 表下坠 / GR 上升。
     - 限幅器**关闭**时：`post.gain` 是纯输出增益，精确线性（`10^(dB/20)`），逐声道 trim 与主增益叠加。
  3. **四条路径的落点**（post gain 有两套实现，调度有三条分支）：
     | 路径 | post gain 实现位置 | 限幅器位置 |
     |---|---|---|
     | 立体声 | vendor `stage_output` 内 `postGain × postGainCh` | wrapper `limiter_process_mc`（链尾） |
     | 矩阵混音（mode=0） | 同上（`mx_downmix` → 立体声链 → `mx_upmix`） | 同上 |
     | 双耳空间 | 同上（HRTF 渲染 → 立体声链，`skip_spatial=true`） | 同上 |
     | 离散多声道（mode=1） | `post_gain_process_mc`（step 15） | wrapper `limiter_process_mc`（链尾） |
  4. **契约门禁化**：新增 `test/smoke/smoke_limiter_final_gate.py` 并登记进 `test/runner.py` 的 `smoke_files`。门禁对四条路径各跑两组对照——限幅器开启时输出峰值必须 ≤ 门限；限幅器关闭时输出峰值必须显著超过门限（反向验证：若 post gain 被挪到限幅器之后，前者必然转红而后者仍成立，门禁因此非空转）。立体声与离散多声道另做精确比例核对与 `gr.limiter > 0` 断言。
  5. **UI 文案义务**：总输出增益的 `InfoBadge` 提示（zh / en / ja 三语）必须说明该参数**作用于限幅器之前**，否则用户会把「听感不变」误判为参数失效。

- 例外（明确登记，均不属本 ADR 管辖范围）：
  1. **插件插入阶段 4（Post-Limiter / 总输出级）**：属 ADR-004 的五级插件插入拓扑，是用户显式选择（opt-in）的插件槽位，其输出不再经过本链限幅器。理由：母带链惯例为「先限幅、后饱和/整形」，限幅后插件是行业标准做法。**若要求限幅器绝对兜底一切输出，须另行立项退役 stage 4**（触发 ADR-004 回退条件），不在本 ADR 范围。
  2. **`limiter.channels` 声道掩码**：用户在 UI 中把某些声道排除出限幅掩码时，这些声道不被限幅——属用户显式选择，不违反本 ADR。
  3. **全局样本安全卫士**（NaN/Inf 拦截 + `±10.0f` 硬钳位）：位于限幅器之后，属异常值防护而非增益级，不构成「门」。
  4. **vendor 内部限幅器**（`stage_output` 内，阈值实为 0 dBFS）：是立体声路径上更早的一道兜底，与本 ADR 的链序语义正交。

- 后果：
  - 链序从「注释约定」升级为「有门禁的契约」。今后任何把 post gain 挪到限幅器之后的改动，都会在 `python test/runner.py --smoke` 阶段转红。
  - 限幅器开启时用户上推总输出增益将出现「听感不变、GR 上升」——这是本决策的直接后果，UI 提示已显式说明。若产品后续要求总输出增益在限幅之后生效（真正的 master fader 语义），须新增 ADR 推翻本条，并把 `post_gain_process_mc` 与 vendor `stage_output` 的 postGain 一并移到限幅器之后，同时改写门禁的 A 组断言。
  - 插件 stage 4 的「总输出级」定位仍可越过限幅门限，属已登记例外。

- 门禁：
  - `test/smoke/smoke_limiter_final_gate.py`（已登记 `test/runner.py`）。
  - 反向验证：临时把 `post_gain_process_mc` 移至 `limiter_process_mc` 之后并重建引擎，核心断言必须转红；验证后还原。
