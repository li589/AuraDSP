# ADR-006 — 移除三档延迟硬约束，延迟改为纯测量与展示

- 状态：**已接受**（2026-10-12）
- 取代：**ADR-002**（三档延迟模式为硬约束，引擎侧守卫）。ADR-002 保留原文不改写，仅标记为被取代。
- 相关：ADR-003（多声道矩阵）、ADR-004（插件多插槽与阶段拓扑）

## 1. 背景

ADR-002 把延迟做成三档硬门槛（实时 ≤10ms / 音乐 ≤30ms / 品质不限），
由引擎侧 `compute_latency()` 按当前启用组合判定，超档即返回 `AURADSP_E_LATENCY_GUARD` 并
回滚 `mode.latency`。UI 的设置页「延迟模式」是写入该变量的唯一入口。

实机使用暴露三个致命缺陷（均为用户实测反馈，非推测）：

1. **选项调不动**：切档时若已启用 T2 效果（混响 / 卷积 / Freeverb），
   `auradsp_engine.cpp` 的 `mode.latency` 分支先 `exchange(v)` 再判定，失败即 `store(old)` 回滚
   并返回 `AURADSP_E_LATENCY_GUARD`。UI 只表现为「按了没反应」，无任何原因说明——
   用户必须先猜到「要先把混响关掉」才能完成一次切档。
2. **选了反而打不开效果器**：守卫的方向是「先开关、后切档」，
   于是用户改了档位再回来开效果时，必然撞上超档拒绝。选项与可用性互相锁死。
3. **收益与复杂度严重失衡**：该守卫实际拦截的只有 Reverb / Convolver / Freeverb 三个效果，
   而这三个恰恰是本项目对标 JamesDSP 的核心卖点。为让它们可用而设置的前置条件，
   反而成了使用它们的障碍。

同时，架构侧已先行废弃了拦截逻辑（`state.dart` 中相关注释「废除品质档拦截限制，
无条件自由放行」），改为启用效果时自动把档位拉到 2（quality）。
于是形成**半成品中间态**：UI 不再拦截却仍在自动改用户设置，引擎守卫仍在，
文档中 ADR-002 / 架构规范 / APP 设计三处仍描述为「引擎侧强制、UI 无法绕过」。
用户感知到的「设计很反人类」，正是这个中间态的外部表现。

## 2. 决策

**撤销 ADR-002 的全部硬约束设计。** 延迟在本产品中是**测量量与展示量**，不是**准入闸门**。

1. **删除 `mode.latency` 参数**：UI、FFI、引擎三处一并移除，不再有延迟档概念。
   `Params::latency_mode`、`kTierBudget`、`compute_latency()` 中的超档判定、
   `mode.latency` 分支的回滚逻辑一并删除。
2. **删除 `AURADSP_E_LATENCY_GUARD`**：不再存在「因延迟而拒绝」的失败路径。
   任何效果的使能都不会被延迟阻断。
3. **保留 `auradsp_get_latency_ms()`**：它仍按启用组合**如实累加并上报**总延迟，
   供底栏徽标与组件级徽标展示——这是测量与透明，不是守卫。
4. **保留组件级脉冲响应实测徽标**（ADR-004 之后的既有能力）：它提供毫秒级透明度，
   取代了「用户需要自己选档来预判延迟」这一鸡肋交互。
5. **所有效果自由使能**：不再有 T0/T1/T2 分档准入，档位元数据不再随预设保存。
   （`graph.effects` 中各节点的 `tier` 字段作为文档性标注保留，不参与任何判定。）

## 3. 后果

- **正面**：混响 / 卷积 / Freeverb 可直接开启，无需任何前置操作；设置页不再有
  「按了没反应」的死选项；预设不再携带档位元数据，跨档载入无降级提示。
- **代价**：**失去了「为低延迟场景主动限制延迟」的能力**。
  这是本次决策明确接受的损失——实测表明该能力以 90% 的可用性换取 10% 的少数场景，
  且实现方式（全局开关 + 静默回滚）比它解决的问题更糟。
  若将来确有强需求（例如游戏/直播场景需要硬上限），
  应以**场景预设**（一键切换整条链与延迟分配）而非**全局档位开关**的形式重新设计，
  且必须做到失败时明确告知原因。
- **兼容性**：`mode.latency` 属 v1.0 C ABI。删除该参数后，
  旧版 Dart 侧下发 `mode.latency` 会返回 `AURADSP_E_PARAM`（未知参数），
  不产生静默错误；新引擎不再回读该值。本仓 UI 与引擎同步更新，无版本错配场景。

## 4. 回退条件

若用户实测反馈「开启混响/卷积后出现不可接受的听感或稳定性问题」，
则重新评估延迟策略——但前提是必须先给出**具体故障现象**，
不得以「当初的 ADR-002 写得很完整」为理由回退。届时应新开 ADR，不得原地复活 ADR-002。
