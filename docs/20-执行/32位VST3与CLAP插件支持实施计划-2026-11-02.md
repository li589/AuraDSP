## 1. 背景与目标

在 2026-11-02 完成的插件双宿主架构定案中，系统确立了以 **`plugin_host_x64`（原 `auradsp_plugin_host`）** 作为 64 位沙箱宿主、以 **`plugin_host_x86`** 作为独立 32 位位桥（Bit-Bridge）宿主的分工体系。

当前主线代码（提交 `e553382`）已在路由层与架构分派上初步完成了抽象：
- `PluginHostClient` 支持 `HostArch::X64` 与 `HostArch::X86`；
- `PluginHostManager::remoteClientFor(path)` 通过 `pluginBinaryBitness`（ELF / PE 头探测）实现 32 位二进制自动向桥宿主分派；
- Linux 侧已实现了基于 `gcc -m32` 的 `plugin_host_x86` 构建及 CLAP 探针验证。

**本期目标**：
在 Windows（及跨平台）`dev` 分支上全面推进并落地 **32 位 VST3** 与 **32 位 CLAP** 插件支持：
1. **Windows 32 位宿主产出**：建立 Windows 平台 `plugin_host_x86.exe` 的编译构建与分发同步流水线；
2. **跨位数 IPC 契约加固**：确保 64 位主引擎（`auradsp_engine.dll`）与 32 位位桥宿主（`plugin_host_x86.exe`）之间的共享内存环（`SlotAudioRing`）与命名管道控制通道严格二进制对齐；
3. **格式驱动支持**：完成 32 位 VST3（COM vtable / `__stdcall` / bundle 目录）与 32 位 CLAP 的实例化、参数同步与音频流转；
4. **GUI 窗口嵌入**：通过 Win32 `SetParent` 实现跨位数窗口挂载；
5. **自动化门禁闭环**：提供本地自建 32 位探针插件，建立专属回归测试。

## 2. 核心技术攻坚与架构设计

### 2.1 构建体系：Windows 下 `plugin_host_x86.exe` 产出

- **现状与痛点**：
  AuraDSP Windows 引擎默认采用 `x64` Ninja/MSVC 工具链构建，产物位于 `core/desktop/windows/out/Release/`。MSVC 在单个构建配置下无法同时混合编译 x86 与 x64 目标。
- **实施方案**：
  1. **构建脚本分流**：
     - 在 `core/desktop/windows/` 建立独立 Win32 目标配置（或通过 `CMakePresets.json` 新增 `windows-x86` 配置预设，或编写专用轻量构建脚本 `build_host_x86.bat` / PowerShell）；
     - 使用 MSVC 32 位工具链（`x86` 环境）编译相同的宿主源码（`auradsp_plugin_host_main.cpp` + `AURADSP_PLUGIN_HOST_SOURCES`），产物命名为 **`plugin_host_x86.exe`**；
  2. **产物归集与同步**：
     - 将 `plugin_host_x86.exe` 输出到 `core/desktop/windows/out/Release/`；
     - 更新 [`tools/sync_artifacts.py`](../../tools/sync_artifacts.py)，在 Windows 产物清单中追加 `(engine_src, "plugin_host_x86.exe")`，确保应用打包与本地调试时位桥宿主自动随包分发。

### 2.2 跨位数 IPC 契约与结构体对齐（64位 ↔ 32位）

由于 64 位主引擎与 32 位位桥处于不同位数的进程中，共享内存的任何字段偏移漂移都将导致致命的内存破坏。

- **对齐审查矩阵**：
  1. **`MsgHeader` / `MsgResponse`**：
     - 显式 `uint32_t`、`uint16_t`，尾部无未显式对齐的指针，尺寸在 32 位与 64 位下恒为 16 字节；
  2. **`AudioBlock`**：
     - `uint64_t seq` + `uint32_t frames` + `uint32_t reserved` + `float samples[8][128]`；
     - 尺寸恒为 `8 + 4 + 4 + 8*128*4 = 4112` 字节；
  3. **`SlotAudioRing`**：
     - 各计数器使用 `std::atomic<uint32_t>` 与 `std::atomic<uint64_t>`；
     - 32 位 x86 下 `cmpxchg8b` 保证 `uint64` 原子的 lock-free 特性（已由 `static_assert(std::atomic<uint64_t>::is_always_lock_free)` 防护）；
     - 缓存行对齐：`alignas(64)` 保证环形缓冲与索引在双端拥有完全一致的内存布局与伪共享消除；
  4. **`SharedAudio` 全局头**：
     - 所有成员均固定位宽，无裸指针。
- **守卫机制**：
  在 `plugin_ipc_protocol.h` 中为关键共享结构体追加 `static_assert` 编译期硬断言，锁定 `sizeof` 与关键字段 `offsetof`，杜绝任何编译器填充漂移。

### 2.3 32 位 VST3 格式适配细节

1. **路径探测与 bundle 目录结构**：
   - 64 位 VST3 二进制位于 `Contents\x86_64-win\*.vst3`；
   - 32 位 VST3 二进制标准位于 `Contents\x86-win\*.vst3`，亦常见单 DLL 形态改名的 `*.vst3`；
   - 扫描器在调用 `pluginBinaryBitness` 时，递归解析 bundle 下正确的子架构二进制。
2. **COM ABI 调用约定**：
   - Windows 32 位 COM 接口函数采用标准 **`__stdcall`** 约定（函数指针修饰必须精确匹配，否则调用栈平衡被毁引起崩溃）；
   - 64 位下调用约定已统一，但 32 位宿主编译时必须严格遵循 Steinberg SDK 的宏定义 `SMTG_STDCALL`。
3. **内存寻址范围**：
   - 32 位宿主仅享有 2GB/4GB 用户空间，需注意大内存 IR 或样本库插件的边界保护。

### 2.4 32 位 CLAP 格式适配细节

1. **路径探测**：
   - 标准目录：`C:\Program Files (x86)\Common Files\CLAP\` 以及用户自定义目录；
   - 二进制为标准 PE 32 位 DLL（扩展名 `.clap`）。
2. **C-ABI 兼容性**：
   - CLAP 设计之初即采用清晰的 C-ABI，数据类型全为固定宽度（`uint32_t`、`int64_t`、`clap_id` 等）；
   - 在 32 位宿主内通过 `LoadLibraryW` 加载并提取 `clap_plugin_entry`，生命周期与 64 位完全同构。

### 2.5 跨位数 GUI 窗口嵌入机制

- **Win32 `SetParent` 互操作**：
  Windows 原生支持 32 位子窗口（HWND）嵌入 64 位父窗口（HWND），反之亦然；
- **消息循环（Message Pump）解耦**：
  - `plugin_host_x86.exe` 拥有自己的独立 UI 线程与 Win32 消息循环；
  - 插件界面的重绘、鼠标与键盘事件在 32 位子进程内部处理，其卡顿或崩溃不会冻结 64 位主引擎与 Flutter 主界面。
