# 插件扫描归属重构与崩溃隔离实施方案（2026-11-04）

## 1. 结论先行

把「**深扫归谁做**」从 `AURA_PLUGIN_HOST_MODE` 里摘出来，改成**按候选位数分派、深扫一律进宿主**：

- **快扫**：本地做（纯读文件头，不执行插件代码）——VST3/VST2 如此；CLAP 例外（见 §7 残留）。
- **深扫**：交给「能加载这个 DLL 的那个进程」——64 位→`plugin_host_x64`，32 位→`plugin_host_x86`；
  引擎进程内**不再**深扫 VST2，也不再整轮把扫描甩给宿主。
- 结果：进程内/进程外共用同一套扫描实现（`enumerate` 本地 + 快扫本地 + 深扫远程），
  「两种模式结果不一致」这一类 bug 从根上消失；32 位 VST3/CLAP 顺带拿到真实元数据。

配套两项修正：32 位条目的 `isCompatible`/文案按位桥可用性判定（不再写死「请装 64 位」）、
宿主内 `Op::QueryMetadata` 加 SEH 兜底（AV 只废掉该候选，不杀宿主、不丢整轮进度）。

## 2. 现状盘点（问题陈述）

| # | 现象 | 根因 | 影响 |
|---|---|---|---|
| P-1 | 32 位条目被写死 `isCompatible=false` + 文案「AuraDSP 是 64 位进程，请安装 64 位版本」 | `fill32BitIncompatible()` / `makeQuickMeta()` 是 2026-10 的「无位桥」时代结论 | 数据与事实相反（位桥能加载）。UI 靠 `isSupported` 兜住不灰显，但任何人加一句「不兼容禁止加载」的守卫就会全灭 |
| P-2 | 进程外模式下整轮扫描被 `m_remoteMode` 甩给 `plugin_host_x64`，32 位条目只剩快扫 | `scanPlugins/scanBegin/scanStep/...` 六处 `if (m_remoteMode) return client->...` | 同一份目录，进程内外两种结果；32 位 VST3/CLAP 永远拿不到真名 |
| P-3 | `Op::QueryMetadata` 响应是单条定长结构 | 2026-11-03 只为「32 位 VST2」开的窗口，VST2 是 1 DLL = 1 插件 | VST3 一个包多插件没法经此通道表达，于是 32 位 VST3/CLAP 干脆没接 |
| P-4 | 宿主深扫遇 AV → 宿主进程死 → 该轮扫描全丢 | 宿主内没有异常兜底，只有客户端的 2500ms 超时 + 杀宿主 | 扫描一崩就要从头再来；单个坏插件毁掉整轮 |

## 3. 关键决策

### D-1 扫描归属：快扫本地，深扫按位数进宿主

```
候选 c ──► 快扫（本地，读 PE/ELF 头）
        └─► 深扫
              ├─ 32 位 ──► plugin_host_x86（在位即可，不看 env）
              ├─ 64 位 ──► plugin_host_x64（见 D-2）
              └─ 无宿主 ─┬─ VST3/CLAP ──► 引擎内深扫（保留旧能力，2500ms 超时 + 放弃线程上限）
                         └─ VST2 ──────► 快扫 + 明示原因（安全铁律，见 D-4）
```

引擎侧 `scanPlugins/scanBegin/scanStep/scanProcessed/scanTotal/scanEnd/scanAbort/getScannedCount/getScannedItemJson/getAllScannedJson`
**全部去掉远程分支**，统一由本地 `m_scannedPlugins` 承载。宿主的 `Scan*` 系列 op 保留（诊断用），引擎不再调用。

### D-2 宿主可用性：`AURA_PLUGIN_DEEP_SCAN`，默认 `host`

- `host`（默认）：深扫优先用宿主。**X64 宿主允许「仅扫描」懒启动**——首次深扫请求才拉起，
  不改变 `AURA_PLUGIN_HOST_MODE` 对**加载**的语义（`m_remoteMode` 仍只在 `=process` 时为真）。
- `inproc`：回到旧行为（VST3/CLAP 进程内深扫、VST2 快扫）。用于「不想多一个常驻进程」的场景与回退。
- 新增 `PluginHostClient::start(bool allowScanHost = false)`：X64 客户端在 `allowScanHost` 时即使非
  `process` 模式也允许启动；`processMode()` 仍如实返回（避免被误当作加载宿主）。
- 32 位桥宿主不受此开关影响：文件在位即启用（`disabled/off/none` 才关），这是既有语义。

### D-3 协议 v5：一次查询返回多条目

- `kProtocolVersion` 4 → 5（旧宿主会被 `Hello` 版本检查拒掉并重启，混搭不可能）。
- `Op::QueryMetadata` 响应体改为：`u32 count` + `count × RemotePluginInfo`（`count ∈ [1, 512]`）。
- 宿主侧实现改用 **`driver->queryMetadata(filePath, binaryPath, metas)`**（格式无关、天然多条目），
  不再 `createInstance → load → 读 metadata → unload`。好处：VST3 一包多插件完整返回、CLAP 走描述符、
  VST2 仍走它自己的「建起来问」；且元数据查询不再占用实例/槽位语义。
- 失败一律 `status=0`（不带半成品条目），引擎侧落在各自的回退分支并写明原因。

### D-4 VST2 安全铁律（不变）

引擎进程内**永不** `LoadLibrary` 未知厂商 VST2。没有可用宿主时，VST2 深扫退化为快扫并在
`errorMessage` 写明「未启用插件宿主，VST2 跳过深度扫描」。`scanCandidateMeta()` 里的 VST2 短路保留，
作为 `PluginScanner::scan()` 静态路径与宿主自身（`AURADSP_HOST_INPROC`）的兜底。

### D-5 32 位标记按位桥可用性判定

- `PluginScanner` 新增进程级标记：`setArchBridgeAvailable(bool)` / `archBridgeAvailable()`。
- `PluginHostManager` 构造完成时写入（`m_remoteClientX86 != nullptr`）。
- `fill32BitIncompatible()` / `makeQuickMeta()`：
  - 位桥可用 → `isCompatible = true`、`errorMessage` 留空；
  - 位桥不可用 → `isCompatible = false`、文案改为「32 位插件需要 plugin_host_x86：位桥缺失或被禁用」
    （不再叫用户去装 64 位版本——那是错的建议）。
- Dart 侧 `isSupported` 逻辑不变（`isCompatible || 32位且Win/Linux`），只修注释：
  桥**不要求**进程外模式。

### D-6 宿主 SEH 兜底

- 宿主 `Op::QueryMetadata` 的插件加载段用 `__try/__except`（MSVC 专属）包住；
  抽出 `queryMetadataGuarded()`（只含 POD 局部量，避开 C2712）调用 `queryMetadataImpl()`。
- 命中 AV → 该候选返回 `status=0`，宿主继续服务；被 AV 打断的临时对象/模块句柄**不释放**
  （沿用「隔离区」语义：宁可泄漏，不在可能损坏的状态下 FreeLibrary）。
- 客户端超时杀宿主的能力 2026-10-28 已有（`killHostOnTimeout`），本次不动。

### D-7 不变量（本次明确不碰）

- `AURA_PLUGIN_HOST_MODE` 对**加载**的语义、`m_remoteMode` 的全部用法、`ProcessPluginProxy` 音频路径。
- 32 位桥宿主的启用条件（在位即启用）。
- VST2 加载/编辑器/预设路径。

### D-8 快扫种子不进加载路（2026-11-04 二次修正）

快扫不再载入模块后，快扫种子（文件名/目录/`Unknown`）若仍按 B1「种子为准」灌入加载路，
会把描述符真值钉死成猜测值——实测 KV-Element（CLAP）加载路 `vendor` 被 seed 钉成
`Unknown`（`applyClapDescriptor` 的 `fillMetadataIfEmpty` 只补空，非空不覆盖）。

- `PluginMetadata` 新增 `fromQuickScan`：`makeQuickMeta` / `fill32BitIncompatible` 置位；
  深扫直出与远程回条默认 false。
- 三个实例 load：`scanSeed->fromQuickScan == true` 时**跳过** `seedMetadataFromScan`
  （走纯描述符路径，等价于既有「无种子」分支）；深扫种子维持 B1「种子为准」。
- VST3 的占位放行逻辑（`wantVendor`/`wantVersion`）随之只剩「无种子」一种触发路径。

## 6. 测试计划

1. **深扫真值矩阵**（`test/vst2/x64` 与 `x86`）：
   - 进程内模式：64 位深扫 `vendor=AuraDSP`（新）、32 位深扫 `vendor=AuraDSP`（不变）；
   - 进程外模式：两者皆 `AuraDSP`；
   - `AURA_PLUGIN_DEEP_SCAN=inproc`：64 位退回快扫（`vendor` 为目录名）、32 位仍真值。
2. **快扫不回退**：快扫仍是文件名/目录推导（`vendor=x64`）。
3. **无宿主降级**：`inproc` + 64 位 VST2 深扫 → 快扫（`vendor` 退化为目录名、`id` 为空）；`errorMessage` 保持为空——元数据浅不等于不兼容，快扫条目本可正常挂载（2026-11-04 执行时修正：不再塞告警文案，避免污染 `isCompatible=true` 的条目）。
4. **多条目**：构造一个含两插件的 VST3 探针不现实，改用 CLAP/VST3 现有真实插件目录抽查条目数 > 1 的 bundle；
   至少断言「count 字段被正确解析」（用宿主返回值与 `get_all` 条数比对）。
5. **反向验证**：临时让 `remoteScanClientFor()` 返回 `nullptr` → 64 位深扫真值断言必须转红（证明门禁不是空转）。
6. **全量门禁**：`runner.py --smoke`（142 项）、`flutter test --concurrency=1`、`flutter analyze`、
   `abi_consistency.py`、`patch_id_scan.py`、`dart_swallow_scan.py`、`check_doc_links.py`。

## 7. 残留与边界

- **CLAP 快扫载入模块（已解决，2026-11-04 二次修正）**：`supportsQuickMetadata()` 已随
  接口删除，快扫全格式纯文件头、零代码执行；CLAP 真名/厂商由深扫或加载路给出。
  代价是快扫列表里 CLAP 显示文件名（与 VST3/VST2 口径一致）。
- **32 位宿主在 x64 宿主内不可达**：进程外模式下 32 位候选仍由引擎直接问 x86 桥（不经 x64 宿主），
  所以不再出现「x64 宿主扫不了 32 位」的空洞。
- **SEH 只覆盖同步 AV**：挂死（死循环/等锁）仍靠 2500ms 超时 + 杀宿主，语义不变。
- **多一个常驻进程**：默认 `host` 模式下首次深扫会拉起 `plugin_host_x64.exe` 并常驻；`inproc` 可关。

## 8. 回退

`AURA_PLUGIN_DEEP_SCAN=inproc` 一行回退到旧行为（引擎内深扫 VST3/CLAP、VST2 快扫），
协议 v5 与 SEH 保留（对回退路径无副作用）。彻底回退只需恢复六处扫描委托分支（git 可回溯本方案提交）。
