## 1. 根因复核（逐处验证，非推测）

### P1 · VST 缓存失效 — **已实测确证**

实测证据：

```
扫描器： scan() = 76，get_count() = 76，路径不存在 = 0 个   ← 扫描器完全正常
缓存：   %APPDATA%\AuraDSP\plugins\plugin_cache.json
         536 字节，mtime 2026/10/10 16:01:46，仅 3 条
         id = ["1","2","3"]（连续手工编号）
         path = C:\VST3\Valhalla.vst3
               C:\VST3\FabFilter.vst3
               C:\CLAP\Element.clap      ← 丢失 "Program Files\Common Files"
```

全仓检索一度误判为「手工/遗留脏数据」——**该结论错误，已更正**。

真正写入方是项目自己的单元测试：`test/plugin_manager_test.dart:136` 调用
`manager.onPluginScanned(3, samplePlugins)`，而 `plugin_manager.dart:503` 的
`onPluginScanned()` 会调 `saveCache()`。`flutter test` **不做沙箱隔离**，
`ConfigManager.baseDir` 指向真实 `%APPDATA%/AuraDSP`，于是 3 条 fixture 被写进
用户的 `plugin_cache.json`。**每次跑 `flutter test` 都会摧毁一次用户缓存。**

已用实验确证：重建缓存为 76 条 → 单独跑 `plugin_manager_test.dart` → 缓存退回 3 条
伪造路径（`C:\VST3\Valhalla.vst3` 等，与 fixture 完全一致）。

- 根因 1（主因）：单测直接写真实用户目录，缺沙箱隔离。
- 根因 2：`loadCache()` 读取后直接 `_parsePluginsJson`，**零 `File.existsSync()` 存在性校验**。
- 根因 3：启动流程**只读缓存、不触发扫描**，缓存优先级高于真实扫描。
- 根因 4：`plugin_manager.dart:515` 把 `rc=$rc, slot=$slot` 直接抛给用户；而
  `auradsp_plugin_slot_load`（`auradsp_engine.cpp:2000-2005`）只返回 0/1，
  **不含任何诊断信息**，故该文案永远只能显示 `rc=0`，等于什么都没说。

**实际影响大于截图所示**：启动后仅显示 3 个插件而非 76 个，且这 3 个永远加载失败。

### P2 · 插件单声道总线（`auradsp_plugin_host.cpp`）

- `:870-871` `activate()` 硬编码 `kStereo` 调用 `setBusArrangements()`，**且忽略返回值**。
- `:902` `process()` 硬要求 `inChannels[1]` / `outChannels[1]` 非空，对声明为单声道的插件是错误的。

未查询 `getBusCount()` / `getBusInfo()`，因此完全不知道插件声明了几个声道。

### P3 · EQ 爆音

- `auradsp_engine.cpp:1440-1500`：`eq.curve` 在**控制线程**被调用，但该线程同时承载 **WASAPI 泵**。实测重算 **760 µs/次**。
- `auradsp_engine.cpp:1438` 注释确认：曲线解析后**立即重建 IR**。
- `state.dart:1295`：每次增益变化都调 `_pushEqCurve()`；`presets.dart:398` 注明 `applyEqGains` 内部同样触发。

算术：760 µs × 60 fps ≈ **45.6 ms/s**，即在音频 isolate 上持续吃掉约 **4.5%** 的实时预算，且与 WASAPI 回调争用 → 必爆。

### P4 · 电平残留

`audio_isolate.dart:1128` 的 `if (avail <= 0) continue;` 同时跳过**音频处理**与 **viz 更新**，欠载后最后一帧电平被永久冻结。

### P5 · 频谱横坐标映射（**原判断有误，已更正**）

初版结论「`_SpectrumPainter` 与 `FreqAxis` 数学冲突，1k 标签下是 322 Hz 数据」
**不成立**——该分析错误地假设 `src` 是线性频率的 FFT bin。

实际：`auradsp_engine.cpp:118-121` 的 `kBandEdges` 定义了 **32 个对数频带**
（20 Hz~20 kHz），`emit_viz`（`:881-893`）已把线性 FFT bin 聚合成这 32 条对数带。
因此 `_SpectrumPainter` 的**均匀摆放是正确的**，`FreqAxis` 的对数定位也是正确的。

真正的病灶只有一个：**`chrome.dart:310` 的 `_AmbientPainter` 用
`pow(t, 1.6)` 幂律把 32 条重采样成 72 根氛围条**，把低频拉宽、高频压扁。

次要问题：`kBandEdges` 后 3 段（16k/18k/19k/20k）被压缩，非严格等比，
故均匀摆放与真实对数位置在高频端仍有 ≤3% 宽度偏差。

### P6 · EQ 预设

`state.dart:1300-1309` 硬编码 20 Hz / 20000 Hz 锚点；`auradsp_engine.cpp:1461` 只拒绝 `f > 96000`，**不按 Nyquist 钳位**。低采样率（如 32 kHz，Nyquist=16k）下 20k 锚点产生越界点。预设仅 9 个且不感知采样率/声道/链位。

### P7 · 卷积 / VDC

- `effects_page.dart:638,748` 与 `widgets.dart:108-123` 的 `SectionCard` 折叠裁剪构成循环死锁：折叠状态下点「浏览文件」按钮，按钮被裁剪不可见/不可点。
- 引擎侧 FileGate 会拒绝无资源的启用 → 用户看到的是「开关开不了」而非可操作提示。
- `loadVdc()` 缺少 `getParams` 刷新；`ddcFileName` / `ddcDetails` 计算后未展示。
- VDC 无频响可视化（IR 频谱管线与 vendor `DigitalFilterMagnitudeResponsedB` 均可复用）。

### P8/P9 · 宿主与延迟

- 缺 `IPlugViewContentScaleSupport`、置顶与 `attached()` 返回值处理。
- 插件 init/load **无超时**，且发生在音频 isolate → 最坏情况同时卡死音频与 UI。
- 插件槽位为编译期常量 2；UI 未调用 `auradsp_plugin_get_num_slots()`。
- 延迟汇总仅含限幅/混响/卷积/交叉反馈；`kLatDdc`、`kLatComp` 定义未用，插件延迟与设备缓冲未计入。

### P10 · 内存

实测（无 VST 加载）：Working Set **341 MB → 峰值 780 MB，稳定 ~760 MB**。非持续增长型泄漏，但稳态基线过高。

### P11 · `ui_verify_slider_reset` 低频搁架

`test/ui/ui_verify_slider_reset.py` 内部**自身不一致**：

- Step 2（低音，行 `:100-106`）**已**改造为 `find_thumb()` 动态定位。
- Step 3（低频搁架，行 `:133-136`）**仍是硬编码** `(866, 715)`，且 `:124` 用魔法像素 `getpixel((440,690))[0] < 50` 判展开、`:130` 硬编码开关 `(1275, 604)`。

文件 `:42-43` 自身的注释已写明铁律「严禁盲写假坐标」，并记录旧值 583 曾落在轨道空白处导致 0 差异 —— 低频搁架只是**漏改**。

`find_thumb` 定义于 `:54`，是**文件内私有函数**，其他 UI 测试无法复用，因此全项目 UI 测试硬编码问题无法收敛。

## 2. 相互影响分析（决定实施顺序的关键）

> 以下 7 条是本计划的核心。**忽略顺序约束会引入新故障。**

### X1 · P2 是 P1 的前置条件 ⚠️ 最重要

修好缓存 → 76 个插件从"不可见"变为"可加载" → **单声道总线缺陷首次可达**。
若先修缓存后修声道，等于把一个已知会写错声道数的路径暴露给全部用户。

> **约束：批次 A 内，`auradsp_plugin_host.cpp` 的总线协商必须先于/同时于缓存放行。**

### X2 · P3 方案 A 会放大 P4

方案 A 把 `eq.curve` 改为事件驱动。若 viz 更新仍被 `audio_isolate.dart:1128` 的 `avail<=0` 门控，则欠载后 EQ 曲线残留会比现在**更顽固**（现在至少被周期性覆盖）。

> **约束：批次 B 必须同时修 `:1128`，让欠载恢复路径仍刷新 viz。**

### X3 · 控制通道拥塞：EQ 抢占失败

批次 B（eq.curve）与批次 E（插件 init 超时）都要把负载移出音频线程，共用同一控制通道。若插件初始化阻塞满超时窗口，其后的 `eq.curve` 更新将排队 → EQ 调节冻结 → **产生"新"的卡顿/爆音假象**。

> **约束：批次 E 必须为控制消息引入优先级通道，`eq.curve` 为 RT 关键小消息，不得排在阻塞型插件 init 之后。**

### X4 · P7 会击穿 P11 与全部 UI 测试

修复卷积/VDC 折叠死锁必然改变 widget 树高度与展开行为 → **所有 UI 测试中的硬编码坐标一次性失效**。

> **约束：批次 D 必须同批完成 UI 测试坐标现代化（`find_thumb` / `find_row` 上提到 `ui_test_kit.py`），并重跑 `tools/probe_effects_geometry.py`。禁止先改布局后补坐标。**

### X5 · P3 方案 A 与 P5 的合并机会

当前 UI **自行推导**一条 EQ 曲线用于显示，与引擎实际系数是两套实现 —— 这正是"改了引擎 UI 不动"的根源。

若方案 A 在控制线程产出**规范化的 NUMPTS 系数**，UI 直接消费该系数绘制，可**同时**消灭 P5 的映射不一致（UI 与引擎共用唯一真相源）。

> **约束：批次 B 的交接缓冲区对外暴露只读系数视图，批次 C 的频谱/曲线绘制必须消费它，禁止 UI 侧二次推导。**

### X6 · P1/P8/P9/P10 的连锁

- 缓存修好 → 插件数量从 3 变 76 → **延迟必须变成事件驱动**，不能在初始化时算一次。
- 缓存修好 → 插件子系统从"近乎静默"变为满载 → **760 MB 这个内存基线随之失效**。

> **约束：批次 F 的内存定位必须在 A~E 全部完成后**重测基线，否则是对错误基线做优化。

### X7 · P7 的可视化会增加内存

VDC 频响复用 IR 频谱管线 → 额外常驻缓冲。在 760 MB 未解决前叠加可视化会放大 P10。

> **约束：VDC 频响可视化与内存治理同批次（F），且必须设定增量预算。**

### 批次 B — EQ 方案 A（P0，架构核心）

**方案 A 落地要点**：

1. 控制线程完成：解析 → 对数频率域重采样到 NUMPTS → 重建 IR。
2. 结果写入**预分配的双缓冲**，以原子指针交换交给音频线程。
3. 音频线程仅做 `memcpy` 到工作缓冲，**零分配、零锁、零解析**。
4. 暴露只读系数视图供 UI 绘制（见 X5）。
5. 同批修 `audio_isolate.dart:1128`，欠载恢复路径仍刷新 viz（见 X2）。

**RT 铁律**：音频线程禁止 `malloc`、禁止 `std::mutex`、禁止解析字符串；双缓冲切换必须是单次原子操作，不得出现"音频线程读到半构建 IR"。

**验收**：EQ 拖动全程无爆音（听测 + 音频线程超时计数不增长）；音频线程零分配（审计 + 工具验证）；曲线 viz 不残留。
**回退**：需保留开关以切回旧通路，直至冒烟与 UI 全绿。

## 9. 批次 B 实施结果（2026-10-10）

### 9.1 爆音机制坐实

```
state.dart:1311  setStringParam('eq.curve')
  → send({'cmd':'setParamStr'})
  → audio_isolate.dart:739  同步调用 AuraDspLib.setString   ← 与 WASAPI 泵同 isolate
  → auradsp_engine.cpp:1496 MultimodalEqualizerAxisInterpolation
  → multimodalEQ.c:172-175  makima → InterpolatingEqMinimumPhase
                            → FFTConvolver2x2RefreshImpulseResponse
```

760 µs 全程阻塞驱动 WASAPI 的那条线程 → 渲染回调赶不上 → underrun → 爆音。

### 9.2 计划漏项：重建对象与处理对象重叠（**措辞已于 §13.4.14 更正**）

> **更正**：本节原标题写作「数据竞争」，并称「足以解释爆音乃至状态写坏」。这**不准确**。
> 复核线程拓扑后确认：`setParamStr` 与音频泵同属 `audio_isolate.dart` 的同一 isolate，
> **同一 OS 线程**，故不存在跨线程数据竞争。真实成因是 ① 重建**阻塞音频泵**约 760µs、
> ② 重建与处理**操作同一块内存**（先刷新再处理）。以下为当时的（已知的）错误判断原文。

`multimodalEQ.c:149-161` 的 `MultimodalEqualizerAxisInterpolation` 与音频路径的
`MultimodalEqualizerProcess`（`multimodalEQ.c:262-265`）**操作同一个对象
`jdsp->mEQ.conv`，全程无锁**。`auradsp_engine.cpp:250` 的注释明确写着
`ctrl_mutex`「仅保护 init/teardown/参数应用，**不挡 process**」。

`operatingMode==0`（本项目配置）下音频路径为
`FFTConvolver2x2Process(&jdsp->mEQ.conv, ...)`，而控制侧同时在
`FFTConvolver2x2RefreshImpulseResponse` 里改写其 `_segmentsIRRe/Im`、`_current`、
`_overlap`（`FFTConvolver.h:23-40`）。这是**边处理边重建同一卷积器**的重叠。

### 9.3 本轮已交付

| 项 | 文件 | 内容 |
|---|---|---|
| **A3** | `core/state.dart` | `_pushEqCurve()` 改为**带尾部补发的节流**（50ms/20Hz）。拖拽期间 UI `notifyListeners` 仍即时，不影响手感。注意：不能用「每次取消并重建定时器」，否则持续拖拽下定时器被无限推迟、曲线永不更新——已用 `_eqCurveTimer ??=` 保证每周期必发 |

### 9.4 EQ 竞争修复方案（**已实施，见 §13.4 P-006**）

> 本节原为「未实施，需专项」的设计草案，现已被 P-006 实施完毕，保留作为设计溯源。
> 实际落地命名为 `mEQ.conv` / `mEQ.convB`（非草案中的 `convA`/`convB`），
> 外加 `activeConv` 指针与块计数守卫。草案中「`convState` 角色需先厘清」
> 的风险已消除：IR 构建在非活动卷积器上完成，块边界原子换指针，
> 两侧同属 `mEQ`、由析构统一释放，无跨线程释放。

`FFTConvolver2x2RefreshImpulseResponse(conv1, conv2, ir1, ir2, len)` 会**同时**刷新
两个卷积器，因此不能简单地把 `conv` 换成指针。

可行设计（需 vendor 补丁，登记到 `core/desktop/vendor-src/libjamesdsp/PATCHES.md`，
沿用 P-001/P-002/P-005 机制）：

1. `mEQ` 内预分配 `convA` / `convB` 两个 `FFTConvolver2x2`，外加 `activeConv` 指针；
   二者同属 `mEQ`、由析构函数统一释放 → **不存在跨线程释放**，生命周期安全。
2. `MultimodalEqualizerProcess` 改用 `jdsp->mEQ.activeConv`（块首一次原子读）。
3. 控制线程在非活动的那一个上完成 IR 构建 + 卷积刷新，仅在块边界原子换指针。
4. 换出的一侧下次复用；`convState` 的角色需先厘清（它是构建暂存还是也需双份）。

**风险：高。** vendor 内部生命周期语义（尤其 `convState`）未完全厘清，
仓促改动会导致崩溃或音频损坏，故不与 A3 混在同一批次。

## 13. L-01 EQ 数据竞争修复（2026-10-10，vendor 补丁 P-006）

### 13.1 关键澄清：`convState` 不需要双份

原计划担心 `FFTConvolver2x2RefreshImpulseResponse(conv1, conv2, ...)` 会同时刷新两个卷积器。
通读 `FFTConvolver.c:881-905` 后查明：

- `conv1` = `&mEQ.instance.convState` —— **仅作 FFT 暂存**（写 `conv1->_fftBuffer`，
  读 `bit`/`sine`），其 IR 段**不更新**；
- `conv2` = `&mEQ.conv` —— **真正的 IR 存储**（`_segmentsLLIRRe/...`）被覆写。

即 `convState` 是常驻工作区而非第二个活动卷积器。**故只需双缓冲 `mEQ.conv`**，
P-006 比原设想小得多。

### 13.2 改动内容

| 文件 | 改动 |
|---|---|
| `jdsp_header.h` | `MultimodalEQ` 新增 `convB` / `activeConv` / `convProcCount` / `convSwapProc` |
| `multimodalEQ.c` | Constructor/Destructor 增删 `convB` 的 Init/Free；`AxisInterpolation` 改为重建到非活动实例并换指针；`Process` 改用 `activeConv` 并递增块计数 |
| `PATCHES.md` | 登记 P-006 |

设计要点：

- **生命周期安全**：两实例内嵌于 `mEQ`，由析构统一释放，**不存在跨线程释放**。
- **在途守卫**：`convProcCount` 由音频线程递增，`convSwapProc` 记录上次换出快照；
  换出后需再跑满 1 块才允许把该实例重新投入重建，
  避免与换出瞬间尚未返回的 `Process` 调用竞争。
- **外部零影响**：`auradsp_set_param("eq.curve")` 语义不变，
  `operatingMode != 0` 的 IIR 分支未触及。

#### 13.4.1 残留爆音

- 切换任意音效器开关时有轻微爆音；
- 快速拖动低音滑块有「哒哒」声，停下来即恢复。

成因：每次换出卷积器实例，其 `_overlap` / `_current` 是全新的，滤波器尾音被截断，
形成阶跃不连续；拖动越快、单位时间换指针次数越多，越明显。
（节流 A3 已把 60Hz 降到 20Hz，但每次换指针本身仍是一次不连续。）

#### 13.4.2 修复：可视化高频闪烁（**本人引入的回归**）

现象：所有频谱柱快速闪烁；无声音时底部电平显示红色条；有声时红色满条与黄色条狂闪；
处理链右侧音量条同样狂闪。

根因是批次 B 的 `sendIdleViz` —— 初版在**每次进入空闲**时补发一帧零值。
WASAPI 下 `avail<=0` 是间歇常态，于是零帧与紧随其后的真实帧在 ~200Hz 上**交替**，
正是肉眼看到的疯狂闪烁；零帧的电平值 `0.0` 又被按满刻度解读，表现为「无声音时的红色条」。

修复：改为**持续空闲满 80 轮（400ms）才补发一次**，且补发值用 `-90.0`（与
`levelL/levelR` 的初值一致，单位 dBFS）而非 `0.0`。

#### 13.4.3 修复：VDC / 卷积开关反向（**本人 D1 改错了**）

现象：打开开关卡片反而收起、关闭反而展开。

根因：D1 把折叠判据改成 `convEnabled && convReady`，这是为了绕开「不启用→折叠→
加载按钮被藏」的死锁，但**方向反了**。

正确解法正是用户先前要求的 **auto-bypass**：
开关状态与引擎生效状态**解耦** —— 无资源时 UI 开关保持开启、对引擎下发 `enable=0`
（效果内部直通），待合格文件加载成功、`convReady/ddcReady` 翻真后**自动下发 `enable=1`**，
无需用户再拨一次开关。

据此：折叠判据回退为常规的 `!enabled`，auto-bypass 由 `state.dart` 承担。

band1 = 25–31 Hz（宽 6 Hz，比一个 bin 还窄）

if (hi <= lo) { f.spectrum[b] = 0; }      // ← band1 恒为 0

凡是窄于单个 FFT bin 的频带（20–25 / 25–31 / 31–40 Hz 三段都属此类）

#### 13.4.14 L-09 定性纠正与最终修法（2026-10-10）

**第三次尝试前先核对了线程拓扑，推翻了前两次的前提。**

`audio_isolate.dart` 中 `case 'setParam'`（:633）与 `pump()`（:1154）
位于**同一个 isolate 的同一个函数**内，由 `unawaited(pump())`（:1250）启动。

`BassBoostSetParam` ①阻塞音频泵、②造成系数阶跃不连续。
这也解释了前两次为何都破坏多声道：我在重构一个根本不存在竞争的东西。

> 同理需复核 **P-006**：EQ 的 `setParamStr`（:739）同样在该 isolate 内，
> 所以 EQ 的原问题也是**延迟**（760µs 阻塞泵）而非竞争。
> P-006 的双缓冲消除了该延迟，价值成立；但「数据竞争」这一措辞是错的，
> 应为「泵阻塞 + 重算对象与处理对象重叠」。L-13 建议据此修订 P-006 文档。

#### 13.4.20 C2：EQ 响应探针（2026-10-11）

**问题本质是两侧算法不同。**

| 侧 | 算法 |
|---|---|
| UI `interactive_eq.dart:860` | log-f 上的 **smoothstep 三次插值** |
| 引擎 | `MultimodalEqualizerAxisInterpolation`：**makima + 最小相位 IR + FFT 卷积** |

最小相位化会让实测幅度偏离用户锚点（过冲、振铃、频带间相互影响），
所以 UI 那条平滑曲线本来就不等于设备产生的响应。

**没有「导出系数」这条路**：这条链路上 EQ 不是解析式滤波器，它就是
一个卷积器，没有可导出的 biquad 系数。改为**直接实测**。

**新增 `auradsp_probe_eq_response(sample_rate, curve, n_points, f_min, f_max, out_db)`**
（`.h` / `.def` / 冒烟均已接）。设计要点：

1. **解析与重采样抽成共用的 `build_eq_axis()`**，探针与实时 `eq.curve`
   下发走同一段代码。两边各自实现的话，探针量到的就不是设备产生的曲线，
   C2 等于用另一套算法自证。
2. **不接受 handle，内部构造私有 jdsp 实例**。复用调用方的实例会和音频
   线程争同一个 `FFTConvolver2x2` 的内部历史（EQ 经 P-006 后 processing
   走 `activeConv`），构成数据竞争。私有实例走同一份 vendor 代码与同一份
   解析路径，结果等价且无副作用。
3. 走 `operatingMode=1`（IIR 直解）而非默认卷积路径：P-006 的守卫要求
   `convProcCount` 先被 Process 推进过，而 `FFTConvolver2x2LoadImpulseResponse`
   取的是 `jdsp->blockSize` 而非 `blockSizeMax`，在 8192 这种非 2 的幂块长上
   分段结构对不上。**且 operatingMode 必须从 `AxisInterpolation` 就传 1** ——
   `d0/d1/c1/c2` 只在该分支生成，先用 0 调用再改标志位会让系数全 0。

**三个非显然的坑**（都是靠逐阶段打印定位的）：

| 症状 | 真因 |
|---|---|
| `stack overflow` | `JamesDSPLib` 体积大，必须放堆 |
| 访问违例 `0x14A2D8` | 漏了 `global_init()` —— 它做 `JamesDSPGlobalMemoryAllocation()` + `WDL_fft_init()`，`JamesDSPInit` 直接用这些全局表 |
| 平坦曲线整条 **-120 dB** | **Hann 窗 `w[0] = 0`**，冲激放在 index 0 被窗乘成 0 |

第三个坑最误导：先怀疑 `overallGain` 未写入、再怀疑 `HSHOSVF` 在
`|gain| < 8·DBL_EPSILON` 时提前 return 0 导致 `sec[i]=0`，两处都改了、
数值纹丝不动。真正的证据是「有增益的曲线有信号、平坦的全静音」——
说明信号本身能通过，问题只出在增益为 0 的那条路径。

**smoke `smoke_eq_response.py` 12/12**，数值符合物理预期：

| 曲线 | 探针输出 |
|---|---|
| 平坦 `20:0 → 20000:0` | 全 **0.00 dB** |
| `100:0 / 1000:12 / 10000:0` | 峰值 **10.12 dB** @1499 Hz，两侧滚降 |
| 全局 `+6 dB` | 全 **6.00 dB** |

其中一条断言专门守住 C2 的前提本身：**「实测与 UI 近似确有差异」**，
要求最大偏差 > 0.8 dB（实测 2.61 dB）。若哪天偏差趋近 0，说明探针已经
退化成在复刻 UI 的近似，这条测试就会失败。

**门禁**：analyze 0 · flutter test 41/41 · smoke **14/14** ·
显式确认 `auradsp_engine.vcxproj -> ...auradsp_engine.dll` · 导出符号已验证。

**尚未完成**：UI 侧 `interactive_eq.dart` 仍用自己的 smoothstep 绘制，
尚未改为消费探针输出。原因是探针是同步 FFI 调用，而曲线随拖拽实时变化，
需要加节流与缓存策略 —— 这部分与 UI 绘制路径一并做，单独提交。

#### 13.4.21 C2 UI 消费链路（2026-10-11）

**探针开销决定了架构。** 实测 **28.6 ms** 一次（129 点，中位；p95 30.4ms）——
makima + 最小相位 IR 设计 + FFT 是固有开销，降不下来。由此：

- **绝不能放进音频 isolate**。那里正在驱动 WASAPI，29 ms 的调用必然
  underrun —— 这正是 P-006 爆音的成因，不能重犯。
- **不能逐帧调**。拖拽时每帧一次会直接卡死 UI。
- 因此：**UI isolate 直接调 FFI + 拖拽停下后 220ms 防抖 + 按曲线字符串缓存**。
  `state.dart` 里 `_scheduleEqResponse()` 在每次 `_pushEqCurve()` 后挂一个
  220ms 定时器；曲线未变则直接命中缓存跳过。

**painter 侧**（`_SpectrumEQPainter`）新增 `measuredResponse` /
`measuredForCurve`。采样时按探针的对数栅格（20Hz..20kHz）反查并线性内插；
拿不到就退回本地 smoothstep 插值。

> 本地插值**不是「旧代码残留」，而是必要的实时降级路径**：拖拽过程中必然
> 拿不到新值（防抖未到），若此时画空白或画旧曲线，手感会明显退化。

**探针调用在 UI isolate，用 `Arena` 托管原生内存**，作用域结束即释放。

**踩到的一个真实坑：FFI 绑定漏参数导致静默错位。**
Dart 侧最初写成
`probeEqResponse(text, out, sr, hi, out)` —— 把 `out_db` 当第 2 个参数传，
**漏了 `n_points`**。x64 上这不会崩，只会静默把 `n_points` 读成指针低位，
返回 `E_PARAM`，函数表现为一律 `null`。
因为它「安全地失败」，一度以为是引擎或 Arena 的问题。
用 `--enable-asserts` 把 `rc` 打出来才定位到。

> 与本项目已记录的 P-005/P-006 一脉相承：**ABI 层出错不崩溃，只是返回错值**。
> 任何新增 FFI 绑定都应配一条「返回码非 0 即失败」的断言，
> 否则错位会以「功能不工作」而非「签名不匹配」的形式出现。

为此在 `measureEqResponse` 里保留了一行注释说明「非法输入返回 null 是契约，
不是异常」，并刻意**不写 assert** —— 否则会把「预期被拒绝」变成崩溃，
而拒绝正是该测的行为。

**新增 `test/eq_response_ui_test.dart` 6/6**，守住三条不变式：

1. 非法曲线（单点 / 空串 / 采样率越界）返回 null，调用方据此回退而非画空白。
2. **实测值与 UI 的 smoothstep 近似确有差异**（> 0.8 dB）—— 守住 C2 本身的前提。
   若探针哪天退化成在复刻 UI 近似，这条会失败。

#### 13.4.22 真实 IR/VDC 资源接入与延迟探针修正（2026-10-11）

外部只读资源（`D:\myPrograms\AudioEffect`，**全程只读，测试内含指纹校验**）：

|---|---|---|
| `Impulse\JamesDSP\DDC\*.vdc` | 889 | 本引擎原生 VDC 校正文件 |
| `Impulse\Convolver\*.wav` | 3348 | 脉冲响应 |
| `VST\**` | 1462 DLL / 3 vst3 | 插件 |

**发现一：引擎的 `extra_dirs` 是分号分隔的纯路径，不是 JSON 数组。**
`PluginHostManager::scanPlugins` 用 `getline(iss, path, ';')` 解析，
我最初传 JSON 数组，整个数组被当成单个不存在的路径而**静默丢弃**。

**发现二：延迟探针会伪造「零延迟」。** 真实资源一上来就暴露：

`probe_component_impl` 只判 `!resource_path`，而 Dart 侧
`latencyProbeResource()` 无资源时传的是 **`''`**。空串是非空指针，
绕过检查后继续执行：组件未启用 → `first = 0`、能量与基线相同；
但拒绝条件是 `first < 0`，`first == 0` 不满足，于是返回
**`rc=0 / samples=0`** —— 把「无法测量」伪装成「零延迟」。
UI 会据此显示一个看似合理却错误的延迟值，比明确报「不可测」危险得多。
已加 `resource_path[0] == '\0'` 判断，并补 `first == 0 && baseline == 0` 守卫。

**发现三（一次自我误判）：用冲激探测高通滤波组件是错的。**
第一轮实测「VDC 输出全是 0」，我判为「VDC 没生效」。实际是
**VDC 是高通滤波器**（AKG K2xx 曲线在 DC 处增益为 0），冲激是纯 DC，
一进去就被滤光。用正弦验证 1 kHz 处 peak 比 **1.17**，
宽带噪声验证 peak 比在 **1.060 ~ 1.328** 间变化 —— 产品完全正常，
错的是测试方法。

据此把 `probe_first_nonzero` 的激励从**单位冲激**换成**宽带噪声**
（确定性 LCG，保证可复现；首块静音让内部状态收敛）。
高通/低通类组件从此测得准。

**L-05（mono 分支）结论：环境不支持，非代码缺陷。**

（扫描结果：85 个全是 VST3/CLAP）。系统已安装的 VST3 中无 mono 变体。
`m_inChannels == 1` 分支仍是防御性实现，本机无法实测覆盖。

#### 13.4.23 C4：EQ 预设感知采样率 / 声道 / 链位（2026-10-11）

原计划只写了「C3 已按 Nyquist 钳位，缓解了最常见失真」，并未说明
C3 到底缓解了什么。查下来发现 **C3 的钳位方式本身就有缺陷**，
而且预设侧还有第二处缺陷。

**缺陷一：逐点钳位把网格压成退化坐标轴。**

`eqFreqs7/10/15/31` 是**硬编码常量**（顶端到 20000 Hz），与采样率无关。
`_pushEqCurve` 用 `math.min(f, nyquist)` 逐点钳位 —— 这不是「截断」，
而是让**多条频带塌缩到同一个频率**：

| 采样率 | Nyquist | `eqFreqs31` 钳位结果 |
|---|---|---|
| 48 kHz | 24 kHz | 31 点全保留 |
| 32 kHz | 16 kHz | 12500/16000/20000 → 全部变 16000 |
| **24 kHz** | **12 kHz** | **6300 以上共 9 条带塌缩到 12000** |

引擎拿到这条含重复频点的坐标轴后，`build_eq_axis` 排序后并列，
vendor 的 makima 在等距零点上求差分 —— 插值结果毫无意义。
这正是计划里「预设跨采样率失真」的真实机制。

**修复**：`eqGridFor(count, sampleRate)` 按频率**裁掉整条频带**
（`f < nyq * 0.995`），网格始终严格升序无重复。
留 0.5% 余量的理由：中心频率正好等于 Nyquist 的滤波器，
有一半响应在 Nyquist 之上，必然混叠 —— 那条带不可用，不是可用边界。

**缺陷二：预设只存增益、不读频率。**

`snapshot` 明明写了 `'frequencies': m.eqFrequencies`，`apply` 却完全不读，
只按 `bandsCount` 重建网格再**按下标**灌 `gains`。
预设存于 48k/31 段、载回到 24k/15 段时，第 i 个增益会贴到完全不同的频点上，
曲线形状被彻底打乱 —— 这是独立于缺陷一的第二重失真。

**修复**：新增 `AppModel.applyEqCurve(freqs, gains)`，按**频率**重映射
（每个目标频点取预设中最接近者的增益）。`apply` 在有 `frequencies`
时走新路径，老预设（无频率信息）仍按下标还原，保持向后兼容。

**采样率变更**同样需要重建：新增 `setSampleRate()`，
内部调 `_rebuildEqGridForSampleRate()`。注意**初始化顺序**——
Dart 的字段初始化器先于构造函数体，所以 `eqFrequencies` 的初值只能用
硬编码 48000，真正按 `config.sampleRate` 的重建放在构造函数体里
`ConfigManager.load()` 之后。这一点不看初始化顺序很容易漏。

**关于声道与链位：经核查当前无需改动。**

- **声道**：引擎侧 EQ 走 `jdsp->tmpBuffer[0]` / `[1]`（左右各一条），
  多声道场景经 `mx_downmix` 下成立体声后处理，与声道数无关。
  EQ 曲线本身不随声道数变化。
- **链位**：`chainOrder` 已在预设里存取。EQ 的**曲线**不随链位变化，
  链位影响的是各级的先后次序，而非 EQ 的频响。

这两项若将来 EQ 引入真正的多声道分支（如每声道独立曲线），
再回来补。现在加元数据只会是无人使用的死字段。

**测试**（新增 2 个文件，10 条断言）：

- `eq_grid_samplerate_test.dart`（4 条）：网格无重复升序、钳位后无重复、
  无越界频点、只裁高频不移位。
- `eq_preset_curve_test.dart`（6 条）：网格一致时无损、跨段数/跨采样率
  低频段逐点对齐、无交集时退化为常量而非崩溃、等比网格严格升序。

> 测试断言本身也修正过一次：我最初断言 32 kHz 下应保留 16000 Hz，
> 结果失败。复查后发现**裁掉是对的** —— 16000 正好等于 Nyquist，
> 中心频率在此处必然混叠。错的是我的断言，不是实现。
> 与 §13.4.21 那次「用冲激测高通」同源：**先确认物理前提，再写断言**。

2. **5 GB 暴涨只在重度操作下出现**（反复开关音效、切页面、粉噪），
   且**非单调泄漏**——有回落能力（4941→854），是"暴涨→部分回落→再暴涨"模式。
3. 暴涨量级 3-4 GB，远超正常音频缓冲（IR FFT 16 KB / WASAPI 几 MB /
   IR 全载 ~46 MB），指向某次操作触发的大块临时分配或 GPU 驱动系统内存映射。
4. tone-only 下观察到周期性 ~900 MB 尖峰（间隔约 20 s），每次回落；
   疑似 Flutter GC 或 AmbientSpectrum GPU surface 周期性分配。
5. GPU 占用 68-71%（核显 3D 引擎），对音频应用偏高，疑与 AmbientSpectrum 有关。
6. 用户报告：粉噪打开时主页卡顿明显；快速切左栏页面有一定缓慢。
   可能是 pump 阻塞 UI 或内存压力导致 GC 停顿。

**待定位**：逐个开关音效 + 切页面，隔离 5 GB 暴涨的具体触发操作。

**附带发现（IR spectrum 第二频带归零）**：
引擎 `compute_ir_spectrum`（`auradsp_engine.cpp:559`）第 607 行
`if (hi <= lo) → 0.0f`。第二频带 kBandEdges[1]=25Hz→[2]=31Hz，
bin_hz=48000/4096=11.72Hz，lo=(int)(25/11.72)=2, hi=(int)(31/11.72)=2，
hi<=lo → 归零。修法：`hi = max(hi, lo+1)` 保底 1 bin。
实时可视化器（line 908）同套 band edges 但 viz_fft_size 可配，
不一定复现。需重编译引擎 DLL。

##### 13.4.27.1 取证工具自身导致 APP 崩溃（已定位并修正）

第四轮（带点击追踪）测试中 APP 崩溃，事件日志：
`flutter_windows.dll`，`0xC0000005` + `0xC000041D`，偏移 `0xFA13`。

**符号化**（Flutter 缓存里有 `flutter_windows.dll.pdb`，与 bundle DLL
md5 完全一致 `4beb7f06bef02c01`，用 dbghelp 解析故障线程栈）：
```
CRASH  flutter::FlutterPlatformNodeDelegateWindows::HitTestSync+0xD1
       ui::AXTree::GetFromId / RelativeToTreeBoundsInternal
       flutter::AccessibilityBridge::GetFlutterPlatformNodeDelegateFromID
       flutter::AccessibilityBridgeWindows::GetChildOfAXFragmentRoot
       ui::AXPlatformNodeWin::accHitTest        ← UIA 命中测试入口
```

**根因：是取证工具，不是 APP。** 本轮给 `mem_baseline.py` 加的点击追踪用
UI Automation 的 `ControlFromPoint` 读控件名，每点一次就触发 `accHitTest`
→ Flutter Windows 无障碍桥 `HitTestSync` 崩溃。**已彻底移除 UIA**，改为点击时
保存光标周围截图切片（纯 GDI，不触碰目标进程）。音频路径全程健康
（debug log `viz#100` 到崩溃前 2 秒仍 rc=0），佐证崩溃在 UI 无障碍层。

**副产品（真实缺陷）**：`FlutterPlatformNodeDelegateWindows::HitTestSync`
崩溃是 Flutter Windows 无障碍桥的真实缺陷——屏幕阅读器等 UIA 客户端会频繁
命中测试，同样会触发。对本项目日常使用无影响，但值得记录/上报。

**结论不受影响**：早期三轮「5 GB 暴涨」的测试在加 UIA 之前，纯 mem_baseline
采样，数据有效。本轮点击追踪数据因工具崩溃作废。

##### 13.4.27.2 根因定位：渲染层 GPU/内存 churn（2026-10-11）

修好工具后重跑（第四次，安全版）：**无崩溃**，180s 完整采样。
场景：重启 → 只切左侧菜单 + 反复开关 440Hz（不动音效）。
结果：Private 544→655（漂移 **+111 MB**），峰 **2001 MB**；
每次点击/切页出现 **800–1400 MB 尖峰**，随后部分回落（锯齿）。
切片证实 y≈780 处是首页音源芯片行（light 主题，选中态橄榄绿）。

**根因（渲染层）**：
1. `chrome.dart:288` `_AmbientPainter`——每页都有的氛围频谱。每帧（30fps）
   绘制 **72 根柱子，每根 `MaskFilter.blur(BlurStyle.normal, 7)`**
   = **2160 次高斯模糊 draw/秒**。Windows/ANGLE/D3D11 下每次模糊都倾向
   分配离屏渲染目标，是 GPU 68–71% 与内存尖峰的主因。
   `super(repaint: spectrum)` 使它在播放时持续重绘。
2. `chrome.dart:83 _reveal`——页切换入场动画对每个子卡片用 `Opacity(<1)`
   （强制 saveLayer/离屏 layer），4 张卡片同帧 = 4 个大离屏面。
3. 其他 `MaskFilter.blur`：`effects_page.dart:1775/1839/1860`（10/20/6）、
   `interactive_eq.dart:785`（5）、`plugins_page.dart:865/888`——按页触发，
   非每帧常驻，次要。

**待修（未动代码）**：
- AmbientSpectrum：去掉每柱 `MaskFilter.blur`，改「低分辨率离屏图 + 放大」
  （双线性放大 = 免费模糊），或直接靠现有 LinearGradient alpha 衰减；
  并考虑把重绘节流到 ~15fps。
- PageScaffold `_reveal`：降低/合并 Opacity 层。
- 修后重测对比 GPU 占用与内存漂移。

##### 13.4.27.3 AmbientSpectrum 修复与实测（2026-10-11）

**改动**（`chrome.dart` `_AmbientPainter`）：72 根柱子不再每根 `MaskFilter.blur`
（2160 次模糊/秒 → 0），改为画进一张约 1/10 分辨率的离屏 `ui.Image`（~140×90），
再 `FilterQuality.medium` 放大到全屏（放大自带双线性平滑 = 廉价光晕）；离屏图
重渲染节流到 ~15fps；`dispose` 释放图；异步渲染带 `_disposed` 守卫。

**实测对比**（同场景：切左侧菜单 + 反复开关 440Hz，不动音效）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| Private 漂移 | +111 MB | **-129 MB** |
| 后半程均值 | 850 MB | **540 MB** |
| 末值 | 655 MB | **448 MB** |
| 峰值 | 2001 MB | 1557 MB |

**结论**：泄漏消除（漂移转负）、稳态降约 30%。

**未解决**：
- 每次交互仍有 ~1000–1500 MB 瞬时尖峰（可回落，非泄漏）。
- **GPU 仍 ~70%**——去掉模糊后 GPU 无变化，说明 GPU 成本不在模糊，而在
  **30fps 全窗口可视化重绘本身**（频谱画布 + 电平表 + 全页 ambient 贴图 +
  引擎每 33ms 推数据触发整树重建）。核显上属固有成本。
- 下一步候选：①降 viz 帧率（30→20/15，最有效）；②加 Dart 堆日志区分
  Dart 堆 vs GPU 驱动 WDDM 分配；③重测重度场景（反复开关音效）确认早期
  5 GB 暴涨是否受控。

**视觉**：氛围光晕较原来略柔（放大平滑 vs 高斯模糊），待用户目视确认。

##### 13.4.27.4 vizFps 降帧 + 重度场景验证（2026-10-11）

**改动**（`config.dart`）：`defaultVizFps` 30 → **20**；config 版本 v2→v3，
`load()` 迁移旧配置自动降到新默认并落盘；用户 config 已验证迁移为
`version:3 / vizFps:20`。
