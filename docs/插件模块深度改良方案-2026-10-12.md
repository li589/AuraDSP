# 插件模块深度改良方案 — 2026-10-12

> 复审对象：M1 插件宿主（VST3 / CLAP）自 UI 到引擎的全链路。
> 触发：用户实测反馈 6 项缺陷 + 架构复审发现 4 项接口卫生问题。
> 关联：[`插件宿主重构与状态总览-2026-10-11.md`](插件宿主重构与状态总览-2026-10-11.md)、
> [`adr/ADR-004-plugin-multi-slot-and-stage-topology.md`](adr/ADR-004-plugin-multi-slot-and-stage-topology.md)、
> [`APP-插件与信号图扩展规划.md`](APP-插件与信号图扩展规划.md)

---

## 0. TL;DR

| 类别 | 结论 |
|---|---|
| **最严重根因** | 插件 GUI 有**线程亲缘性**，而当前 ABI 把 GUI 调用暴露为**同步接口、由任意线程执行**（实际是音频 isolate）。这是"打开卡死"与"卸载崩溃"的共同源头 |
| **最易修但影响最大** | 元数据存在**两套提取实现**（扫描路 vs 加载路），二者结论互相矛盾——"厂商读不出来 / 名字对不上 / 分类全是 AudioEffect"全部源于此 |
| **最明确的缺陷** | 32 位插件在 `resolveBundleBinary` 里被**静默丢弃**（不是标记不兼容，是根本扫不出来） |
| **修复策略** | 引入专职宿主 GUI 线程 + GUI ABI 异步化 + 元数据单一真相源；**彻底删除**编辑器线程与 detach 路径 |

## 2. 问题清单与根因

### 2.1 A 类：元数据不一致（对应用户问题 1、4）

| 编号 | 问题 | 根因 | 位置 |
|---|---|---|---|
| A1 | 扫描与加载两套实现，结论矛盾 | `queryMetadata()`（描述符静态读取）与 `IPluginInstance::load()`（实例化后查询）各自实现了一遍字段提取 | `auradsp_plugin_host.cpp:2379` / `:843` / `:1635` |
| A2 | 加载后 vendor 丢失 | 加载路径的 VST3 vendor 提取依赖实例化后的 `getVendorString()`，部分插件（FabFilter）在该时机返回空；**没有回退到扫描期已拿到的描述符数据** | 同上 |
| A3 | 扫描期 category 恒为 `AudioEffect` | 描述符路径没提取真实分类（VST3 `classInfo.subCategories`、CLAP `features`），填了默认值 | `queryMetadata` |
| A4 | 扫描期 version 恒为 `1.0` | 同上，未读 VST3 `version` / CLAP `version` | 同上 |
| A5 | **UI 显示"自报名"而非用户选择的条目** | `chain_page.dart:459`、`_ActivePluginHero` 直接用 `active.name`（加载后元数据），与列表选中项（扫描元数据）**不是同一份数据** | `chain_page.dart:459`、`plugins_page.dart:936` |

**关键认识**：A1~A4 是**数据层**缺陷，A5 是**展示层**缺陷；但两者叠加才造成用户感知到的"文案全乱"。
即使修好 A1~A4（两路一致了），仍应修 A5——因为**用户选择的实体**必须与**显示的名称**可对应。

### 2.2 B 类：32 位插件（对应用户问题 2）

| 编号 | 问题 | 根因 |
|---|---|---|
| B1 | 32 位 VST3 完全扫不出来 | `resolveBundleBinary` 硬编码只找 `Contents/x86_64-win`；找到就返回，找不到直接 `return ""`，`Contents/x86-win` 从未进入判断 |
| B2 | 无架构判定 | `is64Bit` 硬编码 `true`；从未读取 PE 头 `IMAGE_FILE_MACHINE`（`0x014c` = i386，`0x8664` = amd64） |
| B3 | 无"不兼容"表达 | 即使标记了 `isCompatible=false`，UI 也没有对应视觉与操作拦截 |

**技术约束（必须在方案里说清）**：本引擎是 **x64 进程**，**无法加载 32 位 DLL**。
这不是"实现没做"，而是 Windows 的进程架构隔离——除非引入独立的桥进程，
而 [ADR-004](adr/ADR-004-plugin-multi-slot-and-stage-topology.md) 已明确 v1 **不引入桥进程**。
因此 B 类的正确目标是：
> **「能被发现 + 明确告知不兼容 + 不消失、不崩溃」**，而不是「能加载」。
> 顺带一提：本机已有 76 个 64 位插件，32 位插件的实际价值有限，
> 但"静默消失"是**用户无法自行诊断的错误**，必须消除。

### 2.3 C 类：GUI 与生命周期（对应用户问题 5、6）

| 编号 | 问题 | 根因 |
|---|---|---|
| C1 | **GUI 调用线程身份不可控** | `auradsp_plugin_slot_show_editor` 等是**同步 ABI**，由调用者线程直接执行；在 App 中调用者是**音频 isolate 线程**。CLAP/JUCE 要求 GUI 调用发生在它认可的 main thread，否则 `MessageManagerLock` 死锁（已证实会卡住 VST3 的 `view->attached`，D6） |
| C2 | **detach 造成 UAF → 崩溃**（N2 的高度嫌疑） | `closeEditor` 等待 3s 超时后 `m_editorThread.detach()`，但该线程仍会访问 `this`（写 `m_editorHwnd` / `m_editorOpen`）；随后 `s.instance.reset()` 销毁对象 → 后台线程写已释放内存 |
| C3 | `m_editorHwnd` 数据竞争 | 声明为非原子 `HWND`（`auradsp_plugin_host.cpp:1610`、`:2282`），却被编辑器线程与调用线程同时读写 |
| C4 | **GUI 阻塞会冻住音频 isolate** | isolate 同步等待 C++ 返回。任何 GUI 阻塞（哪怕几百 ms）都会让音频泵停摆、UI 等不到回执——这就是"打开就卡死"的机制 |
| C5 | 每开一次编辑器就新建线程 | 无复用的宿主 GUI 线程；频繁开关会堆积线程与 HWND |

### 2.4 D 类：品牌与展示（对应用户问题 3、4）

| 编号 | 问题 | 现状 |
|---|---|---|
| D-1 | 无插件 logo | `_ActivePluginHero`（`plugins_page.dart:705`）只有渐变 badge + Material 图标；`_PluginSlotChainCard` 只有数字槽位徽章 |
| D-2 | 命名策略未定义 | 一处用 bundle 名、一处用自报名、窗口标题又用 `[AuraDSP] + 自报名`，三处不统一 |
| D-3 | 用户反馈"CLAP 组件上显示 Element FX，无需显示" | 即 D7/A5：显示的是插件内部名，与所选文件不符 |

**关于 logo 的可行性边界（必须先说清，避免过度承诺）**：
- **VST3**：无标准 logo 接口。可在 bundle 的 `Contents/Resources/` 找快照图；`IPlugView::getSnapshot` 能截插件界面但**需要先创建实例与视图**，代价高且不稳定。
- **CLAP**：无 logo 概念。
- **可靠且零依赖的做法**：**默认品牌 logo + 厂商首字母 monogram + 格式角标**三合一。
  确定性、离线可用、对所有插件一致，且与现有暗色工作站风格协调。
  可选增强：扫描时顺手探测 `Contents/Resources/snapshot*.png`，命中则替换 monogram。

### 2.5 E 类：接口卫生（架构复审发现）

| 编号 | 问题 | 位置 | 处置 |
|---|---|---|---|
| E1 | `show_editor` FFI 多一个死参数 | `auradsp_ffi.dart:341` vs `auradsp_engine.cpp:2292` | **接通它**（让 Dart 能定窗口标题）或**删掉它**。二选一，不留中间态 |
| E2 | `engine.h` 注释漂移 `slot: 0..1` | `auradsp_engine.h:167` | 改为 0..3（`kMaxPluginSlots = 4`） |
| E3 | 处理链阶段标签硬编码英文 | `chain_page.dart:363/367/371/375/379` | 补 l10n 键（zh/en/ja 三语） |
| E4 | `slot_get_bypass` 已实现导出但 Dart 未绑定 | `auradsp_engine.h:172` / `.def` | 绑定，避免每次读旁路都走 JSON |

## 3. 架构根因（一句话）

> `auradsp_engine.h` 的设计目标写着「UI 不感知引擎所在进程与形态」，
> 但**插件 GUI 天然带有线程亲缘性**——它必须在插件认可的 main thread 上操作。
> 把 GUI 调用做成**同步 ABI、让任意线程执行**，等于把这个约束泄漏给了调用方，
> 而调用方（音频 isolate）恰好是最不该承担它的线程。

现有"编辑器线程 + 调用线程分工"的设计，隐含假设「调用线程是 main thread」。
这个假设在 `test_plugin_direct`（C++ main 线程）成立，**在 App（isolate 线程）不成立**——
这解释了为什么测试全绿而实机出问题。

## 4. 改良方案

### 4.1 专题一：宿主 GUI 线程（根治 C 类）

**引入进程内唯一的 `PluginGuiThread`**：

- 单例，随引擎创建，**拥有自己的 Win32 消息泵**，生命周期与引擎一致（而非每次开编辑器新建）。
- 实现 `clap_host_thread_check::is_main_thread()` → 该线程返回 `true`，其它线程 `false`；
  同时为 VST3 提供稳定的宿主线程语义。
- **所有插件 GUI 操作串行化在此线程执行**：`gui->create / set_parent / show / hide / destroy`、
  `IPlugView::attached / removed / release`、窗口创建与销毁。
- **删除 per-editor 编辑器线程**（`m_editorThread`）与 `detach` 路径 → 直接消除 C2（UAF）与 C5（线程堆积）。
- `m_editorHwnd` 改为 `std::atomic<HWND>` → 消除 C3。

**效果**：GUI 调用线程身份从"取决于谁调用"变为"恒为宿主 GUI 线程"，`MessageManagerLock` 死锁的条件被结构性移除。

### 4.2 专题二：GUI ABI 异步化（根治 C4）

GUI 相关 ABI 改为**投递即返回**：

```
int auradsp_plugin_slot_show_editor(h, slot, const char* title)   /* 2 → 3 参，接通 E1 */
    ├─ 校验 slot / hasActive
    ├─ 向 PluginGuiThread 投递 GUI 任务
    └─ 立即返回 0（已受理）；结果经既有 evt 机制回执
```

- 调用方（isolate）**永不被 GUI 阻塞** → 音频泵不停摆 → "打开就卡死"消失。
- 回执复用已有通路：`pluginSlotEditorResult`（`audio_isolate.dart` 已存在），
  扩展 `action: show|close` + `rc` + `isOpen`，UI 据此更新状态。
- 需定义**超时语义**：GUI 任务超时仅记录并回执失败，**不 detach、不置悬空指针**。

> 这是本方案唯一涉及 ABI 语义变化的改动，但**不改函数签名个数以外的既有调用点**；
> 旧签名保留（2 参版本）转发到新实现，保持向后兼容。

### 4.3 专题三：元数据单一真相源（根治 A 类）

**原则：一套提取实现，两条路径共用。**

1. 抽取 `PluginMetadata` 填充逻辑为单一函数，**优先使用静态描述符**（CLAP `clap_plugin_descriptor_t`、
   VST3 `IPluginFactory` / `classInfo`），实例化后的查询仅作**补全**，且**不覆盖已有非空值**。
2. 补齐真实字段：
   - VST3：`classInfo.subCategories` → category；`version`；`vendor`（描述符优先）
   - CLAP：`features` → category；`version`；`vendor`
3. **加载后元数据不得回退**：加载路径拿到空的字段，一律回填扫描期缓存的值
   （按 `path + id` 索引）——直接修掉 D2/A2。
4. 增加**回归测试**：同一插件扫描值与加载值必须逐字段一致（当前会 FAIL，正好作为修复的验收信号）。

### 4.4 专题四：架构识别与不兼容表达（根治 B 类）

1. `resolveBundleBinary` 支持**多架构探测**：依次尝试 `x86_64-win` → `x86-win`，并记录命中的架构。
2. 增加 **PE 头解析**读取 `IMAGE_FILE_MACHINE`，判定 `is64Bit`（不再硬编码）。
3. 32 位插件**正常进入列表**，但 `isCompatible = false` + `errorMessage`（如"需要 64 位版本"）。
4. UI 表达：列表项灰显 + 角标"32 位不兼容"；点击挂载时给出明确提示而非静默失败。
5. 文档同步：在 `auradsp_engine.h` 注释与 `APP-插件与信号图扩展规划.md` 写明
   「x64 进程无法加载 32 位插件；桥进程是 ADR-005 议题」。

### 4.5 专题五：品牌与展示（根治 D 类）

1. **统一定名规则**（唯一真相）：显示名 = **扫描期名称**（即用户在选择列表里看到的名字），
   加载后的自报名作为副标题。窗口标题 = `<显示名> — AuraDSP`。
   → 用户选 `KV-Element-FX.clap`，那里就显示 `KV-Element-FX`。
2. **logo 三合一**：
   - 基底：AuraDSP 默认品牌图标（矢量，随主题着色）
   - 叠加：厂商首字母 monogram（有 vendor 时）
   - 角标：格式徽章（VST3 蓝 / CLAP 紫，沿用现有渐变）
   - 可选增强：扫描时探测 `Contents/Resources/snapshot*.png`，命中则以缩略图替换基底
3. 空 vendor 不再显示空白或"未知厂商"，而是降级为 monogram（避免"读不出来"的观感）。

### 4.6 专题六：接口卫生（根治 E 类）

- E1：`show_editor` 接通 `title`（配合 4.2 的新签名），窗口标题由 Dart 决定，删除 C++ 侧硬编码前缀。
- E2：修正 `engine.h` 注释为 `slot: 0..3`。
- E3：`chain_page` 五处阶段标签补 l10n（`chainStagePreDsp` 等 5 键 × 3 语言）。
- E4：补 `auradsp_plugin_slot_get_bypass` 的 Dart 绑定，UI 改走该符号。

## 5. 实施计划

| 批次 | 内容 | 依赖 | 验收信号 |
|---|---|---|---|
| **B1 数据层** | 专题三（元数据单一真相源）+ 专题六 E2/E4 | 无 | 新增回归测试：扫描值 == 加载值（逐字段）；`FabFilter` vendor 不再为空；category/version 真实 |

| **B3 GUI 层** | 专题一（宿主 GUI 线程）+ 专题二（ABI 异步化） | B1 | `detach` 从代码中消失；worker 线程调用不再触发 VST3 3s 超时；App 内打开编辑器不冻音频 |
| **B4 表现层** | 专题五（命名 + logo）+ 专题六 E3 | B1、B3 | 三语阶段标签；槽位卡显示用户选择的名称；logo 三合一渲染 |

**排序理由**：B1/B2 是纯数据层、风险最低、能立刻改善用户感知；B3 是根治项但动 ABI 语义，
放在数据层稳定之后；B5 是**诚实性要求**——没复现的问题不许标"已修复"。

## 6. 验收标准

1. **元数据一致性**：对全部 76 个已扫描插件，扫描值与加载后值**逐字段相等**（name/vendor/category/version）。
2. **32 位**：任何含 `Contents/x86-win` 的 bundle 都出现在列表中，`isCompatible=false`，
   UI 灰显并可解释原因；**不允许静默消失**。
3. **GUI 稳定性**：
   - 代码中不再存在 `detach()` 调用；
   - 从任意线程（含 isolate）调用 GUI ABI **均立即返回**，不阻塞调用线程；
   - CLAP 与 VST3 的 open → 交互 → close → unload 全程无卡死、无崩溃。
4. **展示**：中文/日文界面下处理链阶段标签本地化；槽位卡与激活卡显示的名称与用户选择项一致。
5. **回归门禁**：`flutter analyze` 0 issue；`runner.py --smoke` 全绿；
   `test_plugin_direct.exe` 退出码 0（三插件）。
6. **可复现性**：N1/N2 若无复现步骤，对应条目保持"待复现"状态，不得标记已修复。

## 7. 风险与回滚

| 风险 | 评估 | 缓解 |
|---|---|---|
| GUI ABI 异步化改变调用语义，UI 需适配 | 中 | 旧 2 参签名保留转发；UI 已具备 `evt` 回执机制，改造成本可控 |
| 宿主 GUI 线程成为新的单点 | 中 | 线程与引擎同生命周期；GUI 任务队列加超时与丢弃策略 |
| 32 位插件进入列表后用户误以为可用 | 低 | `isCompatible=false` + 灰显 + 挂载拦截提示 |
| 元数据统一后与旧 `plugin_cache.json` 不兼容 | 低 | 缓存加 schema 版本号，版本不符自动重扫 |
| 删除编辑器线程影响已通过的 `test_plugin_direct` | 中 | B3 完成后必须重跑该测试；若有回归，保留线程模型作为回退路径 |

**回滚条件**：B3 若导致 `test_plugin_direct` 或 App 音频链路回归且 24h 内无法定位，
则回退到"编辑器线程 + 同步 ABI"，仅保留 B1/B2/B4 的成果（它们相互独立）。
