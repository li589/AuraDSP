## 1. 复现证据（本轮实测，含 1 项自纠错）

> 全部证据来自引擎 DLL 直调（`core/desktop/windows/out/Release/auradsp_engine.dll`），
> 探针脚本在 `.tmp/`（gitignore，不入库）。参数：48000 Hz / 1024，slot 0。

### E-1 ｜ VST3 编辑器 **100%** 打不开（3/3）— 结论被改写

| 插件 | load | createView | `isPlatformTypeSupported(HWND)` | `attached` | `showEditor` | unload | 进程退出码 |
|---|---|---|---|---|---|---|---|
| **Auto-Tune EFX+** | rc=1 | ok | `0` | **阻塞 >3s，从未返回** | **0**（6.04s，超时+detach） | **崩溃** | **`0xC0000374` 堆损坏** |
| ConvologyXT_64 | rc=1 | ok | `0` | 阻塞 | 0（6.16s） | rc=1（0.04s） | 0 |
| KV-Element-FX.vst3 | rc=1 | ok | `0` | 阻塞 | 0（6.02s） | rc=1（0.03s） | 0 |

**改写点**：`rev1` 把它描述为"Auto-Tune 的个别问题"。实测是**所有 VST3 插件都打不开** ——
这不是插件兼容性差异，而是宿主路径缺陷。

**关键判别**：日志只有三行，**没有** `view->attached returned non-ok`，**也没有**异常捕获行。
参照本项目既有纪律（按"哪一行由谁打印"判定责任），说明是**阻塞**，不是插件拒绝。

**一个读日志的坑（已记入经验）**：`isPlatformTypeSupported(HWND)` 打印 `0`，看着像"不支持"，
但本仓库 SDK 头 `core/desktop/vendor-src/plugin-api/steinberg/vst3/base/TUID.h:71` 明确
`kResultTrue = kResultOk`，即 **`0` 表示支持**。按 `!= kResultTrue` 判断时恰好正确放行 ——
所以这一行**不是**问题所在。是否"读成拒绝"只影响日志可读性。

### E-2 ｜ 卸载崩溃已复现，N2 结案

`Auto-Tune EFX+`：被包装器捕获的退出码 = `3221226356` = **`0xC0000374` STATUS_HEAP_CORRUPTION**，总耗时 8.05s。

日志的时间顺序把死点钉死了：

```
[DBG Slot] unloadLocked[0] quiesced (spins=0), calling closeEditor
[DBG Slot] unloadLocked[0] deactivate
[DBG Slot] unloadLocked[0] unload          ← 死在这里，之后再无 reset / complete，也无 DONE-OK
```

对照正常卸载（ConvologyXT / KV-Element.vst3）会继续打印 `reset (dtor)` → `complete` → `unload rc=1`。

**竞态属性（重要）**：三个插件走的是**完全相同的代码路径**，却只有 1/3 崩溃。
这解释了用户"后来又试了一次，卸载时发生一次闪退"—— **偶发**。

**机制**：`showEditor` 超时 → `m_editorThread.detach()` → 该线程**仍停留在 `view->attached()` 内部**，
手上握着 `view` 与插件对象；宿主随即 `closeEditor` → `deactivate` → `unload` 去释放
controller/component。线程稍后返回时触碰已释放内存 / 二次释放 → 堆损坏。
**`detach` 不是"放弃等待"，而是"放弃所有权但保留引用"。**

### E-3 ｜ CLAP 白框根因 = 父子窗口跨线程（**含自纠错**）

**先纠错**：第一次测量时我把 `GetWindowThreadProcessId` 的 **out 参数（进程 ID）** 当成了线程 ID，
于是得出"子窗口与父窗口同线程、白框另有原因"的结论并一度写进了记录。**该结论作废。**
该 API 的**返回值**才是线程 ID；改正后重测：

| 窗口 | 类名 | 创建线程 |
|---|---|---|
| 宿主父窗口 | `AuraDSP_Plugin_Host_Window` | **21876**（编辑器线程） |
| 插件编辑器子窗口 | `JUCE_1a12bd5cd83` | **4548**（调用线程） ← **跨线程** |

- 消息泵只在编辑器线程（21876）上跑，而它只泵**父窗口**的消息；
- 插件的子窗口属于**调用线程**（4548）——在 App 里这个线程就是**音频 isolate**，
  它从不泵 Windows 消息；
- → 子窗口永远收不到 `WM_PAINT` → **白框**；拖动父窗口进入模态循环时子窗口仍不重绘 → **"很快无响应"**；
- **窗口本身完全正常**：1230×730、`client` 同尺寸、`visible=True`。
  → 所以既不是尺寸问题、也不是可见性问题，**是"谁来重绘"的问题**。

**对应代码**（`auradsp_plugin_host.cpp`）：CLAP 路径把职责拆给了两个线程 ——
`gui->create`（`:1119`）、`gui->set_parent`（`:1289`）、`gui->show`（`:1299`）都在**调用线程**，
而父 HWND 却由**编辑器线程**创建（`:1159`）。VST3 路径（`:2106` 建窗、`:2126` attached）则是同一线程 ——
所以 VST3 没有跨线程问题，它的问题是 `attached` 直接阻塞（E-1）。
**两条路径各错一半，指向同一个病根：宿主没有"唯一的 GUI 线程"概念。**

### E-4 ｜ CLAP 元数据字段错位（本轮新发现）

`auradsp_plugin_get_all` 实测：

| format | name | vendor | category | version |
|---|---|---|---|---|
| **CLAP** | `Element FX` | `Kushview` | **`KV-Element-FX`** | `1.0.0` |
| VST3 | `KV-Element-FX` | `Kushview` | `AudioEffect` | `1.0.0` |

- CLAP 路径把 **descriptor 的 `description`**（自由文本，恰为 bundle 名）写进了 **`category`** 字段
  （实测 `KV-Element-FX.clap` 的 `description = b'KV-Element-FX'`、`features = ['audio-effect']`；
  成因是旧代码把 description 当分类用，不是 id——行为后果相同，但字段名以实测为准）；
- `name` 取的是**插件自报名**（`Element FX`），真正的 bundle 名 `KV-Element-FX` **只存在于 `path` 里**；
- 因此"用户选了 `KV-Element-FX.clap`，界面却显示 `Element FX`"**在数据层就已经错了**，
  不只是 `chain_page.dart:459` 取了哪个字段的展示层问题；
- **本机 CLAP 插件只有 2 个**（都是 Kushview Element）→ 整条 CLAP 通路实际上只被**一个厂商**验证过。
  这也解释了为什么 CLAP 侧的诸多缺陷（E-3、E-4）从未被测出来。

### E-5 ｜ 列表数据源是一份陈旧缓存（用户第 3 点的端到端根因）

`%APPDATA%\AuraDSP\plugins\plugin_cache.json` 实测：

| 项 | 实测值 |
|---|---|
| mtime | **2026-10-10 17:14**（两天前） |
| 条目数 | 76 |

→ `_parsePluginsJson` → 列表渲染。同一条信息因此有了**两个来源**：

| 位置 | 数据源 | 用户看到 |

同一份缓存与扫描器连 `name` 都对不上（见 E-4）。**schema 已经漂移但无人察觉。**

## 3. 根因（一句话）

> 插件 GUI **天然线程亲缘**：它要求「创建父窗口、创建自己的子窗口、收消息、重绘」全在**同一个线程**上，
> 而那个线程必须**在泵消息**。当前宿主**没有"宿主 GUI 线程"这个概念** ——
> 它按"谁调用 ABI"决定执行线程（实机上是音频 isolate），又额外开一个编辑器线程去建父窗口，
> 于是：**父窗口归 A、子窗口归 B、泵只有 A** → 白框/无响应；
> VST3 更直接：在非 UI 线程调 `attached` → 阻塞 → 超时 → **`detach` 留活引用** → unload 释放 → 堆损坏。

`test_plugin_direct` 用 C++ main 线程调用，恰好"接近"了正确形态，所以测试全绿；实机用 isolate 线程，所以出事。

## 4. 改良方案

### 4.1 专题一：宿主 GUI 线程（根治 A1、A2、A5、A6）

引入进程内**唯一**的 `PluginGuiThread`：

- 单例，随引擎创建、随引擎销毁（**不再每次开编辑器新建**）；拥有自己的 Win32 消息泵。
- **独占三件事**，缺一不可：
  1. 创建/销毁宿主父窗口；
  2. 执行**全部**插件 GUI 调用 —— CLAP 的 `gui->create/get_size/set_parent/show/hide/destroy`、
     VST3 的 `createView/setFrame/attached/removed/release`；
  3. 泵消息。
- 实现 `clap_host_thread_check::is_main_thread()`：**仅该线程返回 `true`**，其余一律 `false`
  （现在 `auradsp_plugin_host.cpp:1454` 是 `t_clapThreadType != Audio`，等于"除音频线程外全是主线程"，语义虚设）。
- `m_editorHwnd` 改 `std::atomic<HWND>`（A5）。
- **删除 per-editor 线程**（`m_editorThread`）与全部 `detach` 路径（A3、A6）。

> **可自动断言的验收信号**：插件子窗口的**创建线程 ID** 必须等于父窗口的创建线程 ID，
> 且等于 `PluginGuiThread` 的 ID。E-3 的探针已能直接测这一条。

### 4.2 专题二：GUI ABI 异步化 + **彻底消除 `detach`**（根治 A3、A4）

GUI ABI 改为**投递即返回**：

```
int auradsp_plugin_slot_show_editor(h, slot, const char* title)   /* 2 → 3 参，顺带接通 E1 */
    ├─ 校验 slot / hasActive
    ├─ 向 PluginGuiThread 投递任务
    └─ 立即返回 0（已受理）；结果经既有 evt 通路回执
```

- 调用方（isolate）**永不被 GUI 阻塞** → 音频泵不停摆 → "打开就卡死"消失。
- 回执复用已有的 `pluginSlotEditorResult`（`audio_isolate.dart:976`），扩展 `action: show|close` + `rc` + `isOpen`。
- **超时语义必须改**：超时后**不 detach、不释放**。GUI 任务超时 = 记录 + 回执失败，
  并把该实例标记为 **quarantined（隔离）**：**放弃释放**，对象留到进程退出或引擎销毁时统一回收。
  > 原则：**"无法安全拆除时，就不拆除"。** 泄漏一个插件实例 ≪ 一次堆损坏崩溃。
  > 这是唯一能同时保住"不卡死"和"不崩溃"的做法。
- 旧 2 参签名保留并转发到新实现，保持向后兼容。

### 4.3 专题三：元数据单一真相源（根治 B1~B6）

1. 抽取**单一**的 `PluginMetadata` 填充函数，两条路径共用；
   **优先使用静态描述符**（CLAP `clap_plugin_descriptor_t`、VST3 `IPluginFactory`/`classInfo`），
   实例化后的查询仅作**补全**，且**不得覆盖已有非空值** → 修 B2。
2. **修正 CLAP 字段映射**（B3、B4）：
   - `category` ← `features`（如 `audio-effect`），**而不是 `id`**；
   - `name` ← 自报名，但**保留 bundle 名**（`path` 的叶子名去掉扩展名）作为
     `displayName` / `bundleName`，供 UI 使用 → 用户选 `KV-Element-FX.clap` 就显示 `KV-Element-FX`；
   - 顺手把 `id` 放进 `id` 字段（当前为空串）。
3. VST3 补真实 `category`（`classInfo.subCategories`）与 `version` → 修 B5。
4. **显示名唯一规则**：显示名 = 用户在选择列表里看到的名字（扫描期名），自报名作为副标题
   → 修 B6，并让 D4 的命名策略有据可依。
5. **回归测试**：扫描值与加载后值**逐字段相等**（当前必 FAIL，正是修复的验收信号）。

### 4.4 专题四：缓存治理（根治 C1~C3 —— 用户第 3 点）

1. **缓存加 schema 版本戳**：
   ```json
   { "schema": 2, "scannedAt": "2026-10-12T01:10:00+08:00", "plugins": [ ... ] }
   ```
   由裸 `list` 升为对象（**加载时兼容读取旧裸 list，但一律视为过期**）。
2. `loadCache()`：`schema` 缺失或版本不符 → **直接丢弃并触发一次自动重扫**
   （或至少把列表置为空 + 明确的"需重新扫描"空态），**绝不放行陈旧数据**。
3. **写缓存前做一次自检**：若 `vendor` 全为 `"Unknown"` 或空，视为无效快照，不落盘 / 标记
   `degraded`（避免把坏数据固化下来）。
4. `onPluginScanned` 落盘时写入新 schema；`is64Bit` 等新键随之补齐。
5. **加去重键**：`path + format` 作为唯一键，避免同一插件多格式条目互相覆盖。

> 修完这一条，用户第 3 点（列表显示 `Unknown`）**当场消失**，且不会再复发。

### 4.5 专题五：架构识别与不兼容表达（根治 D1~D3）

1. `resolveBundleBinary` 支持**多架构探测**：`x86_64-win` → `x86-win`，记录命中架构。
2. 增加 **PE 头解析**读 `IMAGE_FILE_MACHINE`（`0x014c` = i386，`0x8664` = amd64），
   `is64Bit` 不再硬编码。
3. 32 位插件**正常进入列表**，但 `isCompatible = false` + `errorMessage`（"需要 64 位版本"）。
4. UI：列表项灰显 + 角标"32 位不兼容"；挂载时明确提示，不做静默失败。
5. 文档同步：`auradsp_engine.h` 注释与 `APP-插件与信号图扩展规划.md` 写明
   「x64 进程无法加载 32 位插件；桥进程属 ADR-005 议题」。

### 4.6 专题六：表现层与接口卫生（D4、D5、E1~E4）

1. **logo 三合一**：AuraDSP 品牌底 + 厂商首字母 monogram + 格式角标（VST3 蓝 / CLAP 紫，沿用现有渐变）。
   确定性、离线、对所有插件一致。
   - 关于"提取真实图标"的边界，必须先说清：**VST3 无标准 logo 接口**
     （只能在 bundle 的 `Contents/Resources/` 找快照图；`IPlugView::getSnapshot` 需要先建实例+建视图，
     代价高、不稳定）；**CLAP 根本没有 logo 概念**。故默认方案就是三合一。
   - 可选增强：扫描时顺手探测 `Contents/Resources/snapshot*.png`，命中则以缩略图替换基底。
2. 空 `vendor` 不再显示空白/"未知厂商"，降级为 monogram（避免"读不出来"的观感）。
3. D5：`chain_page` 五处阶段标签补 l10n（`chainStagePreDsp` 等 5 键 × zh/en/ja）。

## 7. 风险与回滚

| 风险 | 评估 | 缓解 |
|---|---|---|
| GUI ABI 异步化改变调用语义，UI 需适配 | 中 | 旧 2 参签名保留转发；UI 已具备 `evt` 回执机制 |
| 宿主 GUI 线程成为新的单点 | 中 | 与引擎同生命周期；任务队列加超时；**超时走"隔离"而非释放** |
| **超时改为"隔离不释放"会泄漏实例** | 中（有意为之） | 泄漏量有界（每插件至多 1 个实例）；进程退出统一回收。**用可控泄漏换掉不可控崩溃** |
| 缓存升为对象结构，旧格式不兼容 | 低 | 加载时兼容读裸 list，但一律判为过期并触发重扫 |
| 删除编辑器线程影响已通过的 `test_plugin_direct` | 中 | B3 后必须重跑；若回归，保留线程模型作为回退路径 |
| 32 位插件进入列表后被误以为可用 | 低 | `isCompatible=false` + 灰显 + 挂载拦截提示 |

**回滚条件**：B3 若导致 `test_plugin_direct` 或 App 音频链路回归且 24h 内无法定位，
则回退到"编辑器线程 + 同步 ABI"，仅保留 B1/B2/B4 的成果（它们相互独立）。

## 8. 本方案未做的事

- **不引入桥进程**：32 位支持止步于"识别 + 告知"；真正的加载能力属 ADR-005 议题。
- **不重写插件页 UI 骨架**：仅补 logo、改命名来源、补 l10n。
- **不"修复"未复现的问题**：`rev2` 之后，`rev1` 中 N1/N2 已转为实测结论（E-3/E-2）；
  若后续还有无法复现的反馈，仍按"待复现"登记，不做"已修复"断言。
- **不承诺插件侧兼容性**：VST3 `attached` 阻塞可能有个别插件自身的成分，
  本方案只保证**宿主不再以错误线程调用它、且不因超时而留下活引用**。

## 11. B3 实施记录（2026-10-12，已完成）

### 11.1 根因链（拓扑探针实证）

1. **CLAP 白框**：`gui->set_parent` 在 caller 线程执行 → JUCE 子窗口归 caller
   （音频 isolate，无消息泵）所有 → WM_PAINT 无法分发 → 白框 + 拖动无响应。
2. **JUCE MessageManager 归属**：在 `entry->init`（或 VST3 `initialize`）首次触达
   并把 message thread 固定为**首触线程**；非 message thread 的 GUI 调用死等
   （实验证明 `gui->create` 在编辑器线程也挂死 → "只移 set_parent"方案被推翻）。
3. **VST3 attached 挂死**（Auto-Tune EFX+ 实测）：initialize 在 caller、
   `view->attached` 在临时编辑器线程（≠ initialize 线程）→ attached 死等
   （编辑器白框）；旧 showEditor 3s 超时后 detach 编辑器线程 → unload 的
   `terminate/release/FreeLibrary` 撞上仍卡在插件代码里的线程 → **0xC0000374
   堆损坏**（对正在执行 DLL 代码的线程 FreeLibrary 是未定义行为）。

### 11.2 修复架构：每实例 plugin main 线程（CLAP/VST3 同构）

长寿命专用线程（`clapMainLoop` / `vst3MainLoop`）承载：
- 插件对象创建与初始化（`entry->init` / `createInstance` / `initialize`），
  确立 JUCE MessageManager 归属；
- 全部 main-thread 任务（GUI create/attach/close、state、destroy）——任务经
  `WM_APP_*_TASK` 唤醒、在 GetMessage 循环间隙执行（packaged_task + 有界等待）；
- 编辑器容器窗口的消息泵（新窗口类 `AuraDSP_CLAP_Host_Window` /
  `AuraDSP_VST3_Host_Window`，WndProc 纯 DefWindowProc，**刻意不
  PostQuitMessage**——旧 `AuraDSP_Plugin_Host_Window` 的 WM_DESTROY 带
  PostQuitMessage，会杀掉泵线程）。

废弃路径（挂死隔离，而非 detach 后继续用）：
- 任何 `postTaskAndWait` 超时 → `m_threadAbandoned = true` → `unload()` 入口
  abandoned 守卫**最先执行**，跳过全部插件对象触碰与 FreeLibrary；
- manager 侧 `abandoned()` 检查 → `quarantineAbandonedInstance()` 收容。
  隔离区容器为**堆分配 + 从不 delete**——静态存储容器会在进程 exit() 触发
  析构并逐个销毁实例，同样撞上挂死线程（实测退出阶段堆损坏/挂死）。
  泄漏量级 = 挂死次数（罕见路径），换 use-after-free 的不可控崩溃。

## 14. C1 实施记录（2026-10-12，已完成）—— 多槽挂载同一插件

用户第 1 点：同插件多槽挂载（直接挂载 + Blue Cat 类间接嵌套）下，同时显示界面（冲突/死锁/
标题区分/预设/资源竞争/单插件崩溃）、卸载与开着界面卸载/换插件。

### 14.1 根因与方案

Windows `LoadLibrary` 对同路径返回同一模块（引用计数）。B3 的「每实例一条 plugin main
泵线程」在多槽同插件时：两条泵线程抢 JUCE MessageManager 归属（`entry->init` 首触固定
message thread）→ `MessageManagerLock` 互等死锁。方案：**按规范化二进制路径共享泵线程**
（`ModulePumpThread`），实例经 `shared_ptr` 引用计数持有，最后一实例卸载时线程才停。

### 14.2 架构要点

| 机制 | 设计 |
|---|---|
| `ModulePumpThread` | 长寿命消息泵线程；任务队列 + `postTaskAndWait`（packaged_task + 有界 future）自每实例迁入；registry `map<string, weak_ptr>` 按 canonical+小写二进制路径共享 |
| `PumpDeleter` | 引用计数归零触发 `stop()`（WM_QUIT + join 3s）；**成功才 delete，失败故意泄漏**（挂死线程仍引用 this，对齐 B3 隔离区哲学） |
| SEH 任务守卫 | `runTaskGuarded`（无 unwind 帧成员函数）捕获任务内插件硬件异常 → 置 `m_abandoned` 毒化队列 → 后续任务 future 永不兑现 → 各实例超时后自行隔离；**单插件 GUI 崩溃不再炸进程**；毒化泵不被 registry 复用 |
| `WM_APP_PUMP_TASK` | 统一替换 `WM_APP_CLAP_TASK`/`WM_APP_VST3_TASK`（泵与格式解耦） |
| `onEditorWmClose()` | 容器 WndProc 经 `GWLP_USERDATA` 把 WM_CLOSE 分发回实例（泵线程内直接收尾）；泵循环不再截获 WM_CLOSE——泵与实例解耦 |
| 编辑器登记 | `registerEditor/unregisterEditor`；泵异常退出时兜底 `DestroyWindow` 全部登记容器 |
| `abandoned` 守卫 | CLAP `unload()` 补齐 VST3 同款入口守卫（B3 时 CLAP 缺失） |
| 槽位号标题 | Dart：`plugEditorTitleNamed`（zh/en/ja）+ `plugin_manager.showEditor` 兜底 `[Slot n]`；同插件多槽的两个编辑器窗口可区分 |
| 资源竞争 | 同模块 DLL 引用计数天然由 `LoadLibrary/FreeLibrary` 管理；泵线程引用计数保证「最后一实例卸载才停线程」，且停线程**先于** `FreeLibrary`（DLL 代码无人执行时才卸载） |

### 14.3 实施中发现并修复的回归

1. **窗口类注册共享 `once_flag`**：参数化的 `EnsureEditorWindowClassRegistered` 内
   `static once_flag` 被两个类名共享 → 只有第一个注册成功 → 另一格式 `CreateWindowExW`
   必失败（实测：VST3 先跑时 CLAP 编辑器全挂 + close 任务挂死 + 实例被误隔离）。

## 15. C2 实施记录（2026-10-12，已完成）—— 扫描加速 + 异步不阻塞 + 扫描动画

对应 §1 用户需求第 2 条：**"扫描不要阻塞 UI，UI 上加一个简单的扫描动画（Android 系统的那种就行），
如果因为插件数量多或者读厂商、架构费时间就应该异步处理"**，并明确拒绝 FL Studio 式
"扫描时逐个验证/打开插件以确保全库随时可编辑"的做法——我们只在**加载前**确认插件可用，
扫描阶段不做任何 LoadLibrary（深扫是用户显式 opt-in 的例外）。

### 15.1 根因

| 现象 | 根因 | 证据 |
|---|---|---|
| 扫描期间 UI 冻结、转圈无意义 | Dart isolate 内 `case 'pluginScan'` 同步 `await` 一次性 FFI；一次调用 0.05~2s 内事件循环完全停摆 | 深扫 1.7s 期间无帧可绘 |
| 深扫特别慢 | 每个候选 `LoadLibrary` + 工厂枚举，单步 p50 8.7ms 但 max 1041.8ms（长尾集中在少数大厂 DLL） | `bench_scan_c2.py` 单步统计 |
| 重扫同样慢 | 无缓存；文件没变也要重读 PE 版本资源 / 重 LoadLibrary | 冷 57ms、热 57ms |
| 无法取消 / 无进度 | 一次性 API 只有"开始"和"结束"两个时刻 | 抽象缺失 |

### 15.2 架构：枚举与元数据解耦，扫描变成可步进的任务

引擎侧把原来的一次性 `scan()` 拆成三段，**枚举（纯目录遍历，零 PE / 零 LoadLibrary）与
元数据提取彻底分离**：

```
scanBegin(extraDirs, deep)  ->  enumerate() 得到候选列表，返回候选总数
scanStep(maxItems)          ->  只处理至多 maxItems 个候选，返回本步处理数
scanProgress()              ->  (processed, total)
scanEnd()                   ->  收尾 + 刷新元数据缓存，返回条目总数
scanAbort()                 ->  丢弃 job，已扫到的部分保留
```

关键设计点：

1. **渐进写入**：结果边扫边 append 进 `m_scannedPlugins`，因此扫描过程中调 `get_all` 就能拿到
   已扫到的部分——UI 可以"边扫边长"，而不是最后一刻才刷新整张列表。
2. **元数据缓存**：`fileStamp()` 取 `(文件大小, 修改时间秒)` 作指纹；缓存按二进制路径存
   **条目列表**，`m_scanCacheDeep` 记录该条目是否是深扫产出。命中条件要求
   **指纹一致且深度足够**（深扫结果可服务快扫，反之不可）。
3. **一次性 API 与分块 API 共用同一条管线**：`scanPlugins()` 改为
   `scanBegin → 排空 scanStep → scanEnd`，保证两者结果逐条一致、且都能命中缓存。
4. **ABI 新增 4 个符号**：`auradsp_plugin_scan_begin / _scan_step / _scan_progress / _scan_end`
   （`.def` / `engine.h` / `ffi.dart` 三处同步，现共 **42** 符号）。

### 15.3 Dart 侧：把同步阻塞改成可让出的分块循环

同步消息循环的 `case` 分支内不能 `await`（`await_in_wrong_context`），故抽出独立异步函数
`_scanChunked`，以 fire-and-forget 启动、结果以事件回报：

```
_scanChunked(): begin -> while(scanStep(batch) > 0) { scanProgress; send(pluginScanProgress);
                await Future<void>.delayed(Duration.zero)  // 关键：让出事件循环
              } -> scanEnd -> send(pluginScanned)
```

- 深扫 `batch=1`（单步可达 1s，必须一步一让出）；快扫 `batch=8`。
- 步间的 `await Future<void>.delayed(Duration.zero)` 是"不阻塞 UI"的实质保障：
  它把 isolate 的控制权交还给事件循环与音频泵。
- 异常路径同样回报 `pluginScanned`（count=0），避免 UI 永远停在"扫描中"。

UI：`AuraScanProgress`——Android/Material 风格水平进度条，双模式：

- `total > 0`：**确定性**，`TweenAnimationBuilder` 平滑填充到 `done/total`；
- `total <= 0`：**不确定**，`AnimationController.repeat` 驱动一段 35% 宽的渐变左右扫动。

配 `plugScanProgressCount`（已完成/总数/已发现）读数与 `plugScanPreparing` 文案；
深扫改为**显式勾选的 opt-in**，旁边 Info 图标 Tooltip 说明 `plugScanNoVerify`
（"扫描阶段不加载/验证插件，只在加载前确认可用"）。

### 15.4 实测（本机 76 个候选 / 79 个插件条目，2026-10-12）

| 路径 | 条目 | 耗时 |
|---|---|---|
| 一次性快扫（冷） | 76 | 57.0 ms |
| 一次性快扫（热/命中缓存） | 76 | **4.9 ms** |
| 分块深扫（每步 1 个，冷） | 79 | 1710.0 ms（76 步，单步 p50 8.7 / max 1041.8 ms） |
| 分块深扫（热/命中缓存） | 79 | **4.7 ms** |
| 分块快扫（热/复用深扫结果） | 79 | **5.1 ms** |

结论：**重扫从"秒级/百毫秒级"降到 ~5ms**；深扫仍为秒级但被切成 76 个小步，
每步之间 UI 可绘制，用户看到的是持续推进的进度条而非冻结。

### 15.5 实施中发现并修复的两个自引入回归

1. **多插件 bundle 被缓存折叠（79 → 76）**：缓存初版按 `path` 存单条 `PluginMetadata`，
   而一个二进制（.vst3 / CLAP bundle）可含多个插件类，深扫会产出 N 条同 path 的元数据。
   重扫命中缓存时 N 被折叠成 1，**凭空少 3 个插件**。修复：缓存值改为
   `std::vector<PluginMetadata>`，命中时整体回放；缓存重建改为 `push_back` 而非覆盖。
   → 已固化为回归断言：`bench_scan_c2.py` 强制 `deep_cold == deep_warm`。
2. **一次性 `scan()` 绕过缓存**：原 `scanPlugins()` 直调 `PluginScanner::scan`，
   不查缓存，于是"一次性 46ms / 分块 4ms"——快慢差异其实**不是实现不同，而是有没有命中缓存**。
   修复：一次性扫描改走同一条分块管线（见 15.2 第 3 点），热扫 57ms → 4.9ms。

## 16. C3 实施记录（2026-10-12，已完成）—— 挂载/卸载卡顿根治

对应 §1 用户需求第 3 条：**"偶尔挂载和卸载插件会卡一下，尤其大插件，需要看看异步和阻塞问题。"**

### 16.1 根因（两层，缺一不可）

| 层 | 现象 | 实测证据 |
|---|---|---|
| **Dart 侧（主导）** | `pluginSlotLoadWrap` / `pluginSlotUnloadWrap` 是**单个长同步 FFI**，在音频 isolate 的事件循环上执行；而音频泵（每 5ms 一轮推 WASAPI）与命令处理**在同一事件循环** | 挂载 p50 **77.6ms**、max **1144.1ms**（KV-Element-FX）→ 1.1s ≈ 跳过 220 轮泵 → buffer underrun → 可听爆音/停顿。卸载 p50 18.2ms、max **231.3ms**（RX 12 De-hum） |
| **引擎侧（放大）** | `loadPluginSlot` 把**整个加载**（LoadLibrary / 工厂枚举 / createInstance / activate）放在 `m_hostMutex` 下；`unloadPluginSlot` 同样把 deactivate/destroy/FreeLibrary 全放在锁下 | 锁虽不阻塞 RT 路径（`processSlot` 不持锁，靠 `inFlight`/`hasActive` 无锁握手），但会把所有其他控制命令一并卡住，且让"能否异步化"变成全有全无的问题 |

### 16.2 方案：重活双拆分 + 控制线程

**关键洞察**：锁不是瓶颈（RT 路径本就不持锁），瓶颈是**调用方线程被占住**。所以真正的修法是两步：

1. **重活移出 m_hostMutex 临界区** —— 把 load/unload 拆成"重活（锁外）+ 微秒级提交（锁内）"：
   - load：`prepareInstance`（解析 bundle → LoadLibrary → createInstance → activate，锁外）→ `commitInstanceLocked`（把指针挂进槽位，锁内）
   - unload：`detachInstanceLocked`（摘出槽位 + 等 RT 退出临界区，锁内、短）→ `destroyInstance`（deactivate / destroy / FreeLibrary，锁外）
2. **重活挪到引擎控制线程** —— 新增 `ControlTaskThread`（std::thread + deque + cv），调用方只做微秒级入队，然后轮询原子状态。

新增 3 个 ABI 符号（共 45）：

```
auradsp_plugin_slot_load_async(h, slot, path, id)   -> 1 已受理 / 0 被拒（该槽已有任务）
auradsp_plugin_slot_unload_async(h, slot)           -> 同上
auradsp_plugin_slot_task_state(h, slot)             -> 0 无任务 1 进行中 2 成功 3 失败
```

### 16.3 Dart 侧：不阻塞 UI 的实质保障

同步消息循环 case 内不能 `await`（`await_in_wrong_context`），故沿用 C2 的
"抽出独立 async 函数 + fire-and-forget + 事件回报"模式：

```
_submitAndWait(): 提交 → send(pluginSlotBusy) → for { task_state; if !=1 return;
              await Future<void>.delayed(5ms)   // 关键：让出事件循环
            } → 终态事件（busy=false）
```

- 轮询间隔 **5ms**，与泵节奏一致；上限 30000 轮（150s）防悬挂。
- **被拒时静默返回、不发终态事件** —— 那个在跑的任务自己会发，这里发会让调用方误判"失败"。
- 引擎回执 `pluginSlotBusy` 事件 → `PluginManager.onPluginSlotBusy` → 槽位卡按钮全部禁用
  + 忙态小转圈。`loadPlugin` / `unloadPlugin` 侧乐观置忙并拦截重复下发（双保险）。

### 16.4 实测（2026-10-12）

| 路径 | 同步基线 | 异步提交 | 异步总耗时 |
|---|---|---|---|
| BC PatchWork VST3 | 61.6 ms | **0.056 ms** | 47.0 ms |
| Auto-Tune EFX+ | 91.0 ms | **0.010 ms** | 41.5 ms |

提交耗时降 **约 1000 倍**；调用方线程立刻可用，音频泵在挂载期间照常推进。
总耗时并未减少（活没变少），但**从"卡住用户"变成"用户可继续操作"**——这正是用户描述的
"偶尔卡一下"要解决的目标。
