# AuraDSP 性能优化结案报告

- 日期：2026-11-06
- 平台：Windows x64，release（`flutter build windows --release --no-tree-shake-icons`）
- 测量窗口：1400 × 900（外层窗口，与用户实际使用同量级）；机器 32 逻辑核
- 配置：可视化样式 `bars`、歌词关闭、无插件；音频模式分 `sysapo`（非 VB，DSP STANDBY）与 `voicemeeter_api`（VB attach，8 路引擎全建）
- 结论一句话：**可视化页从"1.2 GB / 5% 总 CPU / 30–38% GPU"降到"372 MB / 38% 单核 / 18% GPU"；主页常驻从 322 MB 降到 274.6 MB；最小化从"照常跑动画"降到 330 MB / 2% 单核 / GPU 0。并且明确了哪些改动不能再往前走、为什么。**

> 读者须知：本报告不是"数字堆"。第 3 节解释每个数字从哪来，第 4 节解释每项改动为什么有效，第 5 节专门记录**试过但必须否决的方案及证据**。如果只想看最终结果，直接跳第 6 节；如果准备继续优化，请先读第 5 节和第 7 节，能省掉至少一次返工。

---

## 0. 摘要

1. **主因不是音频，是 UI 每帧重绘。** 播放态 163.8% 单核 CPU / 32% GPU 的可视化页，在"频谱全零"时依然满速跑；把动画停下来后立刻降到 334 MB / 1.1% / GPU 0。音频链路本身在 VB 下是稳定开销（8 路泵送），不是这轮的主要矛盾。
2. **四层归因成立且可复现：** 无门控的 Ticker → 每帧全屏重绘（含 HUD `BackdropFilter`）→ 每帧大量临时对象 → 全屏径向渐变氛围层。对应 P0-1/P0-2、P0-3、P1-1、P1-2 四组改动，每组都有单变量对照。
3. **被否决的方案有硬证据：** 整页动态层设 `willChange:false` 会把内存从 387 MB 拉到 824.8 MB；8 个引擎实例不能延迟预建（首块会直通 21–64 ms，且 RT 线程不能分配）；可视化协议里的每帧分配属于 RT→UI 传输语义，不能为省内存拆掉。

## 1. 初始现象与用户体感

优化前用户可感知的问题，按严重度排序：

| 现象 | 用户体感 | 对应测量 |
| --- | --- | --- |
| 可视化页播放时风扇转、机器热 | 看频谱时明显更费电、笔记本掉电快 | S4：163.8% 单核（≈5.1% 总 CPU）、GPU 3D 32% |
| 真实播放 + 可视化内存暴涨 | 开一会儿就"吃 1 GB 内存"，被任务管理器报警 | S7：RSS 1077 MB，峰值 1201 MB；S8 歌词开 1270/1503 MB |
| 窗口最小化后仍占 CPU/GPU | 最小化放后台依旧发热，不符合预期 | P0-4 前：最小化 CPU 36.9%、GPU 19.5%，fps 17 |
| 启动常驻偏高 | 冷启动后什么都不做就 300+ MB | S2 主页空闲 322 MB |
| 播放态无法 profile | 一进播放态 VM Service 崩溃，无法定位 | `0xC0000005`，`flutter_windows.dll+0x8b3dd0` |
| 歌词开启更糟 | 开歌词后内存再涨 ~190 MB | S5/S8 对照 |

用户原始描述的核心诉求是"**别在我不看的时候还在烧 CPU/GPU，别让可视化页吃掉 1 GB 内存**"，而不是"把音频延迟换内存"。本轮的取舍始终按这个优先级执行。

### 2.4 已知限制（影响结论可信度，后续者必须知道）

1. **播放态 profile 必崩**：`0xC0000005`，`flutter_windows.dll+0x8b3dd0`。Impeller/Skia 均复现；用 Flutter 3.47.9 / Dart 3.13.7 的**官方空模板**同样复现，属于引擎 VM Service 1 kHz CPU 采样缺陷，不是应用代码。规避方式：`--dart-flags=--profile_period=10000`（100 Hz）。播放态 heap/timeline 因此改用 release + 编译期计数插桩 + 系统计数器。
2. 计数器构建中 `pageBuilds` 字段未接线（恒 0），不作为证据。
3. RSS 含 GPU 共享内存映射；Windows 的"共享 GPU 内存"另列，两者不可相加当"用户可见内存"。
4. **"启动空载"有两个口径**：S1（219 MB）是窗口刚出现即测；最终回归（273.5 MB）是启动后 settle 14 s、首帧着色器/字体/氛围位图都就绪后的稳定值。后者才是可回归的稳态，不要拿 219 去对比 273。
5. 基线 S2 主页 322 MB 与最终 274.6 MB 的差，是 P1-2/P2-1 的真实收益（主页的氛围层与静态层同样受益），不是口径差。

## 3. 逐层归因结论

从"现象"到"代码位置"的完整链条：

### 3.1 第一层：Ticker 无活动门控（主因）

- 可视化页进入后 `AnimationController.repeat()` 无条件启动；频谱全零、静默、甚至窗口被遮挡/最小化时都不停。
- 结果：UI 线程以刷新率（~85 fps）空转，每次 build 都重绘全屏 `CustomPaint`。
- 证据：S3 未播放时 GPU 1.9%（有动画但数据平）、S4 强制播放 32%（数据全零仍然高）；冻结时间轴后 GPU 4.6%。
- 这一层决定了后面所有层被"每帧"放大。

### 3.2 第二层：每帧全屏光栅化 + HUD 模糊

- 可视化舞台本身是全屏层；HUD 叠在上面还有一个 `BackdropFilter`（blur），每帧要求全屏 `saveLayer` + 双 pass。
- 去模糊单变量：602 → 392 MB，shared 188 → 92 MB。**仅 HUD 模糊一项就是 ~210 MB 的波动源。**
- 结论：`BackdropFilter` 在"每帧变化的全屏底层"上等于每帧重建全屏离屏表面，必须去掉或改为静态岛区。

### 3.3 第三层：每帧对象分配（GC 压力与内存峰值）

静态审计列出的热路径分配（P1-1 前）：

- `viz` 流每帧 7 个 `toList()` + 一个 16 键 `Map`；
- painter/widget 每帧重建（`CustomPainter.shouldRepaint` 恒真路径）；
- bars 的 `Rect`/`RRect`/`Offset`，氛围层的 `Offset`/`Color`；
- 这些对象每帧产生、下一帧丢弃，直接把峰值推到 1201 MB（S7）。

P1-1 只做"安全复用"（`Paint`、`TextStyle`、`Path` 等可复用对象提出循环），**没有改数据协议**，RSS 1149 → 855、峰值 1311 → 931、CPU 101.9 → 54.8、GPU 27.4 → 23.7。

### 3.4 第四层：全屏径向渐变氛围层

- 氛围层每帧用 `RadialGradient` 铺满全屏，属于"每帧重新生成一张位图"。
- P1-2 把它预烘焙成 10 Hz 的 `ui.Image`（双缓冲 + 两代回收），实测 p12：387.4/394.4 MB、CPU 43.19、GPU 16.53、shared 134。
- 这层与帧率解耦：氛围视觉上不需要 85 Hz，10 Hz 已足够（且不影响频谱动态）。

### 3.5 第五层：可缓存/不可缓存的边界（P2-1）

- P1-1 给可视化 `CustomPaint` 加了 `willChange:true`（告诉 Flutter"别缓存我"），这是**对动态层正确**的选择。
- P2-1 把"氛围位图 + 网格基底"这类**静态层**单独放进 `RepaintBoundary` 并设 `willChange:false`（允许缓存），动态层继续 `true`。
- 结果 p21：355.78/384.16 MB、CPU 44.82；后续 `cached_120` 354.21 MB vs `nocache_120` 376.22 MB，稳定省 ~22 MB。
- **边界结论**：静态层可以缓存，动态层必须明确告诉引擎"我在变"。混在一起会同时得到两边的坏处（见 5.1）。

### 3.6 第六层：引擎侧（VB 8 实例 + PDC）

- VB 下每个总线一路独立 DSP 状态，8 路 `VmAudioCallback` 全量预建；单实例 vendor 结构原 28.3–29.6 MB。
- PDC（插件延迟补偿）延迟线改为**插件挂载时按需分配**（commit `3138e67`），单实例降到 18.4 MB；VB 播放峰值 664 → 554 MB。
- 这层不是 UI 主因，但它把 VB 的"固定地板"从 ~500 MB 降到 ~453 MB，并让 8 实例的边际成本可算。

## 4. 每项改动的原理与对照数字

按提交顺序。所有数字为 release、同机、同窗口、同配置。

### P0-1 静默/无数据时停时间轴（commit 前序，17:12 批次）

- 原理：可视化页在"无频谱事件 + 不可见"时 `AnimationController.stop()`；用视觉静默阈值判定（不是简单 0 值，避免毛刺导致频繁启停）。
- 对照：602 → 334 MB；CPU 163.8 → 1.1% core；GPU 32 → 0。
- 备注：这一项把"每帧放大"的乘数直接归零，是全部改动里收益最大的一步。

### P0-2 可视化调度降到 30 Hz

- 原理：动画仍需要，但视觉上 30 Hz 足够；把 Ticker 的驱动从"刷新率"改为 30 Hz 节拍，减少全屏重绘次数。
- 对照：602 → 532 MB；CPU 163.8 → 66.2% core；GPU 32 → 24.3；fps 85 → 33。
- 备注：P0-1 + P0-2 叠加后，播放态 CPU 从 163.8 降到 38% 量级（最终 38–52%）。

### P0-3 HUD 去模糊、改静态岛区

- 原理：HUD 从 `BackdropFilter` 全屏模糊改为不透明/半透明岛区，只在数据变化时更新。
- 对照：609 → 531 MB；shared 332 → 267 MB；GPU 31.9 → 29.0。
- 备注：与 2.3 的去模糊实验同向，但保留视觉层级。

### P0-4 最小化/不可见时停 UI 时间轴（`85e79b9`）

- 原理：`TickerMode` + 生命周期监听，最小化时停 UI 侧动画；补齐 `setVizSuspended` 的 UI 侧缺口（原生侧早已能停，UI 没接）。
- 对照：CPU 36.9 → 3.59% core；GPU 19.5 → 2.29；RSS 503 → 481；fps 17 → 2。
- 备注：这一项修正了"最小化还发热"的用户体感；最终回归最小化 329.8 MB / 1.93% / GPU 0（非 VB）。

### P1-1 painter 逐帧对象复用（`f60e835`）

- 原理：把 `Paint`/`TextStyle`/`Path` 等从每帧创建改为字段复用；不改 `viz` 数据协议，不改绘制语义。
- 对照：RSS 1149 → 855 MB；峰值 1311 → 931；CPU 101.9 → 54.8；GPU 27.4 → 23.7。
- 备注：同时给可视化 `CustomPaint` 设 `willChange:true`（动态层声明），为 P2-1 的"静态/动态分离"铺路。

### P1-2 氛围层预烘焙 10 Hz 位图（`4dbf884`）

- 原理：全屏径向渐变只在需要时重画，改为 10 Hz 生成 `ui.Image`，双缓冲避免撕裂，两代回收限制驻留。
- 对照：p12 387.4/394.4 MB、CPU 43.19、GPU 16.53、shared 134。
- 备注：把"随刷新率变化的成本"变成"固定 10 Hz 成本"，是这轮性价比最高的渲染改动之一。

### P2-1 静态层独立缓存（`8865efb`）

- 原理：氛围位图 + 网格基底单独 `RepaintBoundary`，`willChange:false`；动态层保留 `willChange:true`。
- 对照：p21 355.78/384.16 MB、CPU 44.82；`cached_120` 354.21 vs `nocache_120` 376.22；`post` 391.22/398.05。
- 备注：**省 22 MB 是"静态层缓存"的收益，不是"整页缓存"的收益**——后者会灾难性增内存，见 5.1。

### PDC 延迟线按需分配（`3138e67`）

- 原理：`plugin_chain_component.{h,cpp}` 增加 `ensureDelayLines`，在插件 load 时分配 PDC 延迟线；`plugin_abi.cpp` 两处 load 钩子调用；`delay_line.h` 加空指针守卫；补测试。
- 对照：单实例 28.3–29.6 → 18.4 MB；VB 播放峰值 664 → 554 MB；5 files +43/−9。
- **口径必须如实**：无插件会话不 `prepare`，探针仍是 18.395 MB；2.0 MB 的 stereo 节省只在插件态；8.4 MB 的 PDC 只在插件挂载时分配。**不能写成"所有会话省 10 MB"**。

## 5. 被否决的方案与否决理由（最重要的一节）

### 5.1 `willChange:false` 设到整页动态层 —— 负优化 +437 MB

- 尝试：把可视化页整个动态层（含全屏内容）设为 `willChange:false`，期望"让 Flutter 缓存整页，减少重绘"。
- 实测：`wc/proc_willchange.json`（120 s）RSS **824.8 MB**，对比同条件 `p12` 387.4 MB、`cached_120` 354.21 MB、`nocache_120` 376.22 MB。
- 原因：`willChange:false` 的语义是"我不会变，请缓存"，而全屏层每帧都在变。引擎会为每帧产生新的 picture/layer 并保留缓存快照，内存随帧数累积；同时因为层内容变化，缓存永远失效，CPU 也没省。
- 结论与落地：**只有静态层可以 `false`，动态层必须 `true`**。最终代码就是这个边界（P2-1）。
- 后来者注意：不要看到 `cached_120` 比 `nocache_120` 省 22 MB 就把 `false` 扩大到动态层，那会得到 824.8 MB。

### 5.2 8 个引擎实例延迟预建/按需创建/复用 —— 不允许作为默认路径

- 事实：VB 模式下 Potion/Banana/Standard/未知分别预建 8/5/2/8 路；每路是**独立总线 DSP 状态**（EQ、动态、混响、limiter 等），不能共享；单实例 18.4 MB（PDC 后）。
- 为什么不延迟：
  1. **groups 只有首回调后才可知**，延迟创建必然发生在音频回调内或紧随其后；在 RT 回调内 `new` 违反"音频线程零分配/零锁/零系统调用"的硬约束。
  2. 若在首回调前不建，首块音频会**直通**，实测 21–64 ms 的未处理音频，属于可听缺陷（尤其切换设备/首播）。
  3. 在控制线程延迟建再切流，会引入"首播前必须完成"的同步点；handle 创建实测 28.5–44.9 ms，放到用户路径就是把开销挪到可感知处。
- 量化：全量预建 8 路 ≈ 128.8 MB（8×18.4 中 7 路额外，A1 常驻）。延迟建最多省 128 MB，但代价是首播直通或 RT 违规。
- **允许的例外**：仅"低内存模式"可对**非 A1 总线**延迟建，且必须证明"首次播放前在控制线程建好、RT 内零分配"；默认不启用。这条留给后续低内存模式，不作为常规优化。

### 5.3 拆掉"必须保留的每帧分配"

- 清单：`viz` 流 7 个 `toList` + 16 键 `Map`；painter/widget 重建；bars 的 `Rect`/`RRect`/`Offset`；氛围层 `Offset`/`Color`。
- 为什么不能拆：
  - `toList`/`Map` 是 **RT→UI 的传输契约**：音频线程写环形缓冲，UI 侧拿到的是不可变快照；去掉拷贝就要在 UI 直接读可变环，会看到撕裂数据（读到半帧）或需要加锁，两者都违反实时安全。
  - painter/widget 重建是 Flutter 的 widget 契约，强行复用会绕过 `shouldRepaint` 语义，导致该重绘时不重绘。
  - `Rect`/`RRect`/`Offset` 是绘制 API 的参数对象，且被用作缓存键；复用对象池收益在 1 MB 量级，风险是脏状态串帧。
- 已做与未做：P1-1 只复用**无跨帧语义**的对象（`Paint`/`TextStyle`/`Path`），协议层一个没动。这条边界必须守住。

### 5.4 profile 1 kHz 采样 —— 不修，改口径

- 现象：播放态 1 kHz CPU sampling 必崩（`flutter_windows.dll+0x8b3dd0`）。
- 已证明：Flutter 3.47.9 / Dart 3.13.7 官方空模板同样复现，属于引擎 VM Service 采样器缺陷，不是应用代码。
- 决策：不改应用代码、不 patch 引擎；采集口径固定 100 Hz（`--dart-flags=--profile_period=10000`）。后来者若再次遇到，先确认版本与空模板。

### 5.5 其它被否决项（低收益/高风险）

| 方案 | 量级 | 否决理由 |
| --- | --- | --- |
| App handle 延迟建 | 18.4 MB | 插件扫描依赖 handle 存在，延迟建属中风险；为 18 MB 改初始化顺序不划算 |
| HRTF 表跨实例共享 | ≤1 MB | 需引用计数 + 生命周期；收益低于复杂度 |
| Reverb/mc_rev 状态共享 | 数 MB/实例 | 每路混响状态独立，共享会串音，违反总线独立性 |
| stereo 状态跨实例复用 | ~7.3 MB/实例 | 属每路独立 DSP 状态，复用破坏声道独立性 |
| 用 Skia 替代 Impeller | 内存 508–529 MB | 不解决 Ticker/重绘主因，GPU 36.1%，无收益 |
| 降低可视化刷新率到 15 Hz | 视感下降 | 30 Hz 已是视觉下限；再降频谱明显卡顿，收益递减 |

## 7. 当前架构下的剩余空间与已知天花板

### 7.1 固定基线构成（非 VB 主页 274.6 MB）

| 组成 | 约 MB | 能否压缩 |
| --- | --- | --- |
| Flutter 引擎 / ANGLE / D3D / ICU / 字体 / 表面 | ~236 | 不能（框架常驻） |
| 引擎 handle（A1 单实例） | 18.4 | 中风险（插件扫描依赖，见 5.5） |
| Dart 堆 | ~16 | 不能（运行时） |
| 宿主 / 插件宿主壳 | ~4 | 不能 |
| EQ/arbMag 表 | ~1.55 | 不能（算法数据） |
| inline 表 | ~0.63 | 不能 |
| VizRing | ~0.10 | 不能（传输缓冲） |
| scratch | ~0.34 | 不能（实时工作区） |

### 7.2 VB 固定基线构成（453–456 MB）

- 非 VB 274.6 + 7 × 18.4（额外总线）≈ 128.8 + VB bridge / vendor / 额外线程 ≈ 50 → 453.4（与实测 453.2–455.6 相符）。
- 这 128.8 MB 是"8 路总线必须独立"的代价，不可复用（5.2）。除非引入低内存模式（仅非 A1 延迟建，最多省 128 MB，但需证明首播前建好且 RT 零分配）。

### 7.3 本轮新发现的最大剩余空间：VB 主页 169% CPU / 37% GPU

- 现象：VB 主页空闲 CPU 169.05% core（≈5.3% 总）、GPU 36.91%，远高于非 VB 的 0.53% / 0%。
- 归因：**主页的实时频谱卡在 viz 事件驱动下持续重绘**（VB 下单核百分比被 8 路引擎泵送抬高，但 37% GPU 与 169% 中相当一部分是 UI 侧重绘）。最小化后 VB 降到 5.16% / GPU 0，证明这部分**可以被活动门控消除**（同样的 `TickerMode`/可见性门控思路，只是主页频谱卡还没接）。
- 量级：约 1.7 个核 + 37% GPU（VB 启动态）；非 VB 因 `DSP STANDBY` 无 viz 事件，主页只有 0.5%，所以这个问题只在 VB/真实设备下暴露。
- 本轮未做（避免收口阶段引入新行为）；这是**下一个最值得做的单一改动**，预计可把 VB 主页从 169% 降到接近最小化后的 5–10% 量级，同时不影响频谱（看不见时不画）。

### 7.4 已知天花板

1. **30 Hz 光栅地板**：可视化在 30 Hz 下仍有固定的 raster 成本（~11.5 ms/帧量级）；继续降帧率会牺牲视感，继续压 raster 需要改渲染管线（不在本轮范围）。
2. **8 引擎必须预建**：VB 的 128.8 MB 是结构性的，除非做低内存模式（非 A1 延迟建，需完整证明首播路径）。
3. **PDC 只在插件态生效**：无插件会话不会省这 8.4 MB；把 PDC 也预建反而增加常驻，已选择按需。
4. **Flutter 框架 ~236 MB 不可动**：这是 release 下的引擎地板，任何"再省 50 MB"的方案都要先解释这 236 MB 里哪部分不是框架。
5. **profile 只能在 100 Hz**：1 kHz 崩溃是引擎缺陷，不修；意味着采样精度有上限。
